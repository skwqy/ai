# 一、总览

## 1.1 一句话定位

> **这不是三个 API 的对比,而是三条技术路线对同一个问题的三次回答。** 那个问题是:服务器 90% 的时间在"等 IO",**等待的成本由谁承担?**
>
> - **范式一(线程池 + CompletableFuture + ThreadLocal)**:让 **OS 承担**——一个等待占死一个内核线程,用池控制数量,用回调链在不占线程的地方"接力"。
> - **范式二(Project Reactor)**:让 **程序员承担**——把"等待与继续"手工展开成状态机(操作符链),几十个 event loop 线程服务上万连接,可读性换吞吐。
> - **范式三(虚拟线程 + ScopedValue + StructuredTaskScope)**:让 **JVM 承担**——阻塞时把调用栈卸载到堆、让出载体线程,等待变得近乎免费,**同步写法重新成为高吞吐写法**。

## 1.2 设计哲学:同一问题的三种"状态保存"方案

并发编程的本质难题之一是**在等待期间,谁替你保存"接下来该做什么"**(状态)。三个范式给出了三种存储方案:

| | 状态存在哪 | 谁来恢复执行 | 恢复成本 | 对程序员的呈现 |
|---|---|---|---|---|
| 范式一:线程池 + CF | **回调链对象图**(`Completion` 链表,堆上) | 完成后回调线程接着跑 `tryFire` | 线程切换 + 调度排队 | 人肉把顺序逻辑拆成 lambda 链 |
| 范式二:Reactor | **操作符状态机**(每个操作符一个 `Subscriber`/`Subscription`) | 信号(onNext/onError)驱动 `drain` | 同上,但线路固定 | 用声明式操作符"接线", JVM 帮你拆 |
| 范式三:Loom | **栈本身**(`Continuation`,阻塞时快照到堆) | 调度器把栈重新挂载到载体线程 | 栈复制(微秒级,用户态) | 你什么都感觉不到,就当普通线程 |

一句话:**范式一和范式二把"栈"拆散了存,所以代码必须变形;范式三把"栈"原样保存,所以代码不用变形。** 这是理解一切差异的钥匙。

# 二、范式竞争六十年:每一轮都在回答同样三个问题

## 2.1 第一波(1963~1995):线程很贵,于是发明"便宜的线程"

【白话】计算机早期,并发 = 进程(昂贵)。1963 年 Conway 提出协程:在**用户态**保存/恢复执行位置,切换成本只是"记下 PC 和栈指针"。这个思想在 Simula 67、Modula-2、CLU 里开花,在 Erlang(1986,actor 模型)里变成工业级产品——**轻量进程,百万级并发,30 多年前的 BEAM 虚拟机就这么干**。

Java 出生时(1995)选择的就是这条路:**绿色线程**——JVM 自己在用户态调度所有 Java 线程,全部跑在一个 OS 线程上。这是今天虚拟线程的"前世"。

**为什么它死了?** 两个原因:① 当年用户态调度的实现无法利用多核(所有绿色线程挤在一个 OS 线程上);② 阻塞系统调用会挂起整个进程(内核不知道"逻辑线程"的存在)。多核服务器成为主流后,1:1 映射的内核线程(POSIX pthreads)在 2000 年的 JDK 1.3 上取代了绿色线程——**JVM 第一次把调度权交还 OS**。

## 2.2 第二波(1995~2010):内核线程王朝与它的第一个补丁——线程池

1:1 内核线程模型很好用:每个 Java 线程就是一条内核调度实体,阻塞 IO、锁、调度全部由内核处理,写代码就是"顺序思维"。但内核线程有三笔账:

- **内存**:每线程默认预留 1MB 栈(`-Xss`),几千个线程就是 GB 级;
- **切换**:内核态切换 1~10μs,上下文颠簸直接吃掉 CPU;
- **创建**:系统调用,毫秒级。

于是 **Java 5(2004)的 JSR-166 给出了王朝的第一块基石:线程池**。池的本质是**用"复用"摊销创建成本,用"池大小"限制线程总数**。`ThreadPoolExecutor.execute`(`java.base/java/util/concurrent/ThreadPoolExecutor.java:1339`)的三步决策(addWorker/入队/拒绝)从此成为 Java 服务端的标准起手式,这个模型沿用至今。

但池解决不了另一个问题:**等待仍在占线程**。一个 200ms 的下游调用,池线程就阻塞 200ms。池大小成了系统的并发上限——这也是后来"线程池打满"类故障的根源。

## 2.3 第三波(2009~2016):异步大爆炸——回调、Future 链与响应式流

Web 规模继续膨胀(C10K、移动端、微服务),"等待占线程"的账单越来越贵。行业给出两条补救路线:

**路线 A:不阻塞线程(事件循环 + 回调)。** 2009 年 Node.js 把"单线程事件循环 + 回调"变成时尚;Java 这边,Netty(基于 2002 年 Java 1.4 NIO)在通信层做了同样的事。代价是**回调地狱**:逻辑被拆散进嵌套 lambda,控制流(顺序/分支/循环/异常)全部手工重写。

JDK 的三次迭代试图驯服它:

1. `Future`(Java 5):有状态没手段,只能 `get()` 阻塞轮询;
2. `CompletableFuture`(Java 8,2014):可编排——`thenApply/thenCompose/thenCombine` 把回调拍平成链。**但它只是"把回调写得体面",内核没变:还是回调,还是不管理线程**(3.2 源码解析);
3. `Flow`(Java 9,2017):把 Reactive Streams 规范的 4 个接口收编进 JDK,只给契约不给实现(`SubmissionPublisher` 除外)——官方把"流"的问题域承认下来,实现交给 Reactor 这类库(深度解析见 [Flow.md](<Flow.md>))。

**路线 B:把"等待"变便宜(用户态调度)。** 2012 年 Go 1.0 让 goroutine(M:N 用户态调度,栈 2KB 起)从第一天起就是语言标配。C# 5.0(2012)选择另一条路:`async/await` 由**编译器**把异步方法改写成状态机,不占线程但代码保留顺序形态。Kotlin 协程(2018,1.0)把这条路线带上 JVM——注意它是**语言层**方案(需要 `suspend` 标记传染),JVM 本身不知道协程的存在。

两条路线在 JVM 上正面相遇:Project Loom 主导者 Ron Pressler(2018 年加入 Oracle)在论文和演讲中给出的判断是:**async/await 是一次"病毒式分裂"**——它把代码库切成异步/同步两半,生态两级化(C#/Kotlin 的 `suspend` 传染问题)。Loom 的目标是**在 JVM 层解决,让所有现有代码无感受益**。

**路线 A 的顶点:Reactive Streams 规范(2015-04-30)。** Netflix(RxJava)、Pivotal(Reactor)、Lightbend(Akka)、Red Hat、Kaazing 五家坐下来,把"异步流"的最小契约固化成 4 个接口:`Publisher/Subscriber/Subscription/Processor`——核心增量是**背压**(消费者用 `request(n)` 告诉生产者能吃多少)。2015 年 Reactor 2.0 对齐规范;2016-09 发布的 Reactor 3.0(`Flux`/`Mono`)随后成为 2017 年 Spring 5/WebFlux 的底座;同年 Java 9 把契约收编为 `java.util.concurrent.Flow`。**至此,范式二的产业链完成:规范(Flow)→ 实现(Reactor)→ 框架(WebFlux/R2DBC/rsocket)。**

## 2.4 第四波(2017~今):Loom 回归——把 1963 年的答案带回来

Project Loom(2017 立项,Ron Pressler 主导)的判断可以压缩成一句话:**"等待"不需要内核,把调用栈从内核线程上拆下来放进堆里。** 于是阻塞 = 栈快照存堆 + 让出载体线程;就绪 = 找个载体把栈挂回去。线程创建变成普通对象分配(字节级),阻塞变成用户态操作(纳秒~微秒级),**"一请求一线程"这种最易读的写法重新成为高吞吐写法**。

Loom 是个"三件套"工程,三块拼图各自演进(详见 5.4 的 JEP 全表):

1. **虚拟线程**(JEP 425/436/444,21 转正):便宜的线程;
2. **ScopedValue**(JEP 446/464/481/487/506,25 转正):为"百万线程 + 不可变上下文"重新设计的 ThreadLocal 继任者;
3. **StructuredTaskScope**(JEP 428/437/453/480/499/505/525/533,25 起第五预览至今):CSP 思想的落地——并发任务的寿命限定在语法块内,像局部变量一样有结构。

**这不是复古,是押韵**:绿色线程死于"不能用多核 + 阻塞系统调用挂起进程";虚拟线程由 JVM 调度器(ForkJoinPool work-stealing)天然吃满多核,且在 JVM 层拦截阻塞点(改写 NIO/锁/park 路径),当年杀死绿色线程的两个凶手都不在了。

## 2.5 本章小结:范式之争的三个判定问题

六十年的钟摆摆动,可以浓缩成三个问题。每轮范式竞争,胜负都由这三个问题的答案决定:

1. **状态存哪?** 内核线程(1:1)/ 回调链 / 操作符状态机 / continuation——决定了代码形态与心智负担;
2. **等待多贵?** 占内核线程 / 占池线程 / 不占线程 / 近乎免费——决定了并发伸缩性;
3. **生态改多少?** 全量改写(Reactor)/ 语言层标记传染(suspend)/ 零改写(虚拟线程)——决定了扩散速度。

带着这三个问题,下面三章逐个解剖三种范式。

# 三、范式一:线程池 + CompletableFuture + ThreadLocal(命令式异步)

## 3.1 白话定位与同题代码

【白话】这套范式的世界观:**线程是稀缺资源,要池化;并发编排用 CompletableFuture 的回调链表达;跨代码片段共享数据用 ThreadLocal**。它统治了 2004~2023 年的 Java 服务端,今天仍是存量代码的主力形态。

统一场景(**第六章三范式同题对比**):并行调用 3 个下游服务(耗时 100/150/200ms)→ 聚合结果 → 500ms 超时 → 全程携带 traceId → 任一失败快速失败。核心代码(完整可跑版本在 `D:\tmp\paradigm-demo\P1Threadpool.java`):

```java
static final ThreadLocal<String> TRACE_ID = new ThreadLocal<>();
static final ThreadPoolExecutor POOL = new ThreadPoolExecutor(
        2, 2, 0, TimeUnit.SECONDS, new LinkedBlockingQueue<>());   // 故意只给 2 个线程

static String call(String downstream, long costMs) {
    // 坑 1:这里读不到主线程 set 的 TRACE_ID(ThreadLocal 不跨线程)
    System.out.printf("  [%s] 调 %s, 线程内 ThreadLocal traceId=%s%n",
            Thread.currentThread().getName(), downstream, TRACE_ID.get());
    Thread.sleep(costMs);
    return downstream + ":OK";
}

// 编排:traceId 只能逐个 lambda 手抄;allOf 聚合;get(500ms) 超时
CompletableFuture<String> f1 = CompletableFuture.supplyAsync(() -> { TRACE_ID.set(traceId); return call("userSvc", 100); }, POOL);
CompletableFuture<String> f2 = CompletableFuture.supplyAsync(() -> { TRACE_ID.set(traceId); return call("orderSvc", 150); }, POOL);
CompletableFuture<String> f3 = CompletableFuture.supplyAsync(() -> { TRACE_ID.set(traceId); return call("stockSvc", 200); }, POOL);
CompletableFuture.allOf(f1, f2, f3).get(500, TimeUnit.MILLISECONDS);
```

【实测】(`P1Threadpool.java`,JDK 25.0.1)四个关键现象,完整输出见附录 A:

- **A** 主线程 `TRACE_ID.set("trace-001")` 后,池线程里读到 `null`(不跨线程);
- **B** 三个任务在 2 个池线程上排队,**聚合耗时 306ms 而非理论 200ms**——池大小成了并发上限;
- **C** `stockSvc` 20ms 就抛异常,但 `allOf().join()` 不会取消 `userSvc`,它**继续跑满 103ms**;捕获到的异常被包装:`CompletionException ← ExecutionException ← IllegalStateException`(剥两层才是原始异常);
- **D** 池线程复用:前一个任务 set 了 traceId 忘 `remove`,下一个任务**读到上一个任务的脏值**(串号)。

## 3.2 源码解析:池、回调链、ThreadLocalMap

### 3.2.1 ThreadPoolExecutor:池化即限流

【源码证据】`java.base/java/util/concurrent/ThreadPoolExecutor.java:1339` 的 `execute(Runnable)`:

```java
public void execute(Runnable command) {
    ...
    int c = ctl.get();
    if (workerCountOf(c) < corePoolSize) {
        if (addWorker(command, true))   // ① 线程数 < core:新建 Worker
            return;
        c = ctl.get();
    }
    if (isRunning(c) && workQueue.offer(command)) {  // ② 核心满:入队等待
        ...
    }
    if (!addWorker(command, false))  // ③ 队列满:扩到 max,再满则拒绝
        reject(command);
}
```

【白话】注意 ②:**核心线程满了先入队**,队列再满才扩容——这与直觉相反(很多"先扩容后排队"的面试答案是错的)。线程本体是内部类 `Worker`(`ThreadPoolExecutor.java:608`),它继承 AQS 兼任锁:工作循环 `runWorker`(`:1123`)里 `getTask()` 拿不到任务时 park,本质上**池线程的空闲=阻塞在队列上**。

推论:范式一里"并发度=池大小"是**硬约束**。上面实测 B 的 306ms 就是证据——2 个线程跑 3 个 200ms 内的 IO 任务,第三个必须排队。想提高并发?加线程——然后重付内存和切换成本的账。

### 3.2.2 CompletableFuture:回调链的"体面外衣"

【白话】CF 的本质是一张**手工维护的回调依赖图**。每个 CF 节点持有:结果槽、状态(完成/未完成)、以及一组**下游 Completion 节点**(栈式链表)。`thenApply` 不是"对值做转换",而是**往链上挂一个回调节点**;上游完成时(`postComplete`)逐个弹出触发。

【源码证据】`java.base/java/util/concurrent/CompletableFuture.java:467`:

```java
abstract static class Completion extends ForkJoinTask<Void>
        implements Runnable, AsynchronousCompletionTask {
    volatile Completion next;      // 回调链:栈式单链表(LIFO)
    ...
    abstract boolean tryFire(int mode);
}
```

`thenApplyAsync` 家族(`CompletableFuture.java:2203`)一律落到 `uniApplyStage(fn)`——若上游未完成,构造 `UniApply` 节点**挂到上游的栈上**;若已完成,立即在**当前线程或指定执行器**上执行。而 `join()`(`:2114`)在未完成时把**调用线程 park 进等待队列**。

【白话】这套机制带来四个连锁后果,每个都在实测中现了形:

1. **异常要手工接力**:回调链没有栈,异常不会自动传播——每个环节要么显式 `exceptionally/handle`,要么等 `join()` 时被包成 `CompletionException`(实测 C:剥两层才见原始异常)。源码上,异常在 `postComplete` → `tryFire` → `UniExceptionally` 等节点间显式流转,**没有 Java 异常的栈语义**。
2. **取消是假的**:`cancel(mayInterruptIfRunning)` 的 javadoc 自己承认 `mayInterruptIfRunning` **在此实现中没有效果**——CF 不知道执行线程是谁,无法中断它。所以实测 C 里 stockSvc 失败后 userSvc 照跑。
3. **执行线程不可预测**:同一个 `thenApply`,上游完成时可能跑在**上游线程**(调用方线程/池线程),未完成时跑在**触发完成的那条线程**——"这段代码跑在哪"成了玄学,monitor/ThreadLocal 全都失锚。
4. **编排语法与业务逻辑混杂**:`thenCombine/thenCompose/allOf` 的 lambda 链是"手写的控制流",嵌套两层就难读(社区俗称 "CF 天书"),重构时极易漏掉某个 `exceptionally`。

### 3.2.3 ThreadLocal:线程级的全局变量

【源码证据】`java.base/java/lang/ThreadLocal.java:371`:

```java
static class ThreadLocalMap {
    static class Entry extends WeakReference<ThreadLocal<?>> {   // :381
        Object value;   // 注意:弱引用的是 key(ThreadLocal 本身),value 是强引用!
        ...
    }
}
```

【白话】每个 `Thread` 对象里藏一张 `ThreadLocalMap`,以 ThreadLocal 实例(弱引用 key)为键。**value 是强引用**——key 被回收后 value 仍挂在 map 里(陈旧条目),靠后续 set/get 的探测清理兜底;池化线程永不死亡,陈旧条目(和被 value 引着的对象)就**长期驻留**,这就是"池化线程 + ThreadLocal = 内存泄漏/串号"双坑的来源(实测 D 的串号就是它)。

而它的设计前提——**线程身份稳定**——在池化场景下本来就不成立:线程被复用,"线程级全局变量"实际是"线程槽位的全局变量",上一位租客的数据会漏给下一位。范式三用 ScopedValue 把这个前提连根拔掉(5.3)。

## 3.3 结构性缺陷盘点(全部有实测证据)

| # | 缺陷 | 实测证据 | 根源 |
|---|---|---|---|
| 1 | **上下文断裂**:traceId 等上下文跨线程即失联 | 实测 A:池线程读到 `null` | ThreadLocal 绑定线程身份,回调链换线程 |
| 2 | **池大小=并发上限** | 实测 B:2 线程跑 3 任务,306ms | 等待占线程(3.2.1) |
| 3 | **失败不取消、异常被包装** | 实测 C:失败后白跑 103ms;`CompletionException` 包两层 | 回调链无栈语义,CF 无法中断执行线程(3.2.2) |
| 4 | **池复用串号/泄漏** | 实测 D:读到上一个任务的脏值 | ThreadLocalMap value 强引用 + 线程不死(3.2.3) |
| 5 | **执行线程不可预测** | (可复现)"thenApply 跑在哪条线程"取决于完成时序 | 完成时机决定 tryFire 的执行线程(3.2.2) |
| 6 | **超时只是"放弃等待"** | `get(500ms)` 抛 TimeoutException 后,下游调用仍在池里跑 | 同 #3:没有取消传播的通道 |

其中 #1 在工程上催生了整个"上下文传递"补丁产业(3.4),#2/#3 则是把无数团队推向 Reactor 的直接动因。

## 3.4 生态补丁:为了"传个 traceId"造了多少轮子

范式一的缺陷不是没人看见,而是大家用补丁把它糊住了——这本身就是范式生命周期的信号:

- **手动装饰执行器**:Spring 的 `ContextPropagatingTaskDecorator`(Boot 3.2+/Framework 6.1 起,配合虚拟线程开关)、阿里的 `TransmittableThreadLocal`(TTL)——用装饰器把"捕获-回放上下文"塞进 `Runnable` 前后。可用,但每一处池、每一个第三方库的内部池都要覆盖,**漏一处就断**。
- **Micrometer Context-Propagation 库**(`io.micrometer:context-propagation`):为 Reactor/CF/Bridge 统一注册 `ThreadLocalAccessor`,本质还是"快照+恢复"ThreadLocal。
- **InheritableThreadLocal**:只在"创建线程时"复制一次,池化线程不复用创建时机,基本失效(分析见 [虚拟线程 vs 线程.md](<虚拟线程 vs 线程.md>) 4.2)。

【白话】这些补丁的共同形状:**在没有"隐式作用域"的语言运行时里,手工模拟隐式作用域**。每个补丁都要求业务代码自觉配合(set 后 remove、用指定装饰器、注册 accessor)——配合是靠纪律,不是靠机制。范式三的 ScopedValue 把这件事变成**机制**(作用域结束自动失效、不可覆写、子线程随 fork 捕获)。

## 3.5 本章小结

- 范式一的三大件(池/CF/ThreadLocal)各自都曾是正确的答案,组合在一起却互相放大缺陷:**池放大 ThreadLocal 的坑,ThreadLocal 放大回调链的坑,回调链放大池的坑**。
- 它的两个"不可替代"遗产仍然成立:`ThreadPoolExecutor` 对 CPU 密集任务仍是标准工具;CF 作为**单个异步值的原语**(如 JDK 内部 API 返回 CF)无处不在。
- 亡的不是原语,是"**把 CF 回调链当编排范式写业务**"这种用法——虚拟线程时代,这一层被同步写法接管(7.1)。

# 四、范式二:Project Reactor(声明式响应式流)

## 4.1 白话定位与同题代码

【白话】Reactor 的世界观:**业务是一个"流过流水线的信号序列",而非"线程里的一段顺序代码"**。你组装一条操作符链(声明"要什么"),Reactor 在订阅时把它装配成 Subscriber 树(决定"怎么跑"),信号沿树流动(什么时候跑、跑在哪)。线程不再属于你的逻辑,而属于调度器——等待期间线程去服务别的流。

同一场景的 Reactor 版(完整可跑:`D:\tmp\paradigm-demo\P2Reactor.java`,reactor-core 3.8.7):

```java
static Mono<String> call(String downstream, long costMs) {
    // context 不是 ThreadLocal:订阅上下文沿流水线反向传播,切线程照样读得到
    return Mono.deferContextual(ctx ->
            Mono.fromCallable(() -> {
                        Thread.sleep(costMs);          // 模拟下游 IO
                        System.out.printf("  [%s] 调 %s, context.traceId=%s%n",
                                Thread.currentThread().getName(), downstream,
                                ctx.getOrDefault("traceId", "<无>"));
                        return downstream + ":OK";
                    })
                    .subscribeOn(Schedulers.boundedElastic()));
}

var result = Mono.zip(call("userSvc", 100),
                      call("orderSvc", 150),
                      call("stockSvc", 200))
        .contextWrite(Context.of("traceId", "trace-002"))   // 一次声明,全链可见
        .timeout(Duration.ofMillis(500))
        .block();
```

【实测】(`P2Reactor.java`)关键输出(全录见附录 A):

- **A** 三个下游在 `boundedElastic-1/2/3` 并行执行,**每个任务都读到 traceId**——一次 `contextWrite` 全链生效,没有"逐个 lambda 手抄",也没有 set 后忘 remove;
- **B** 任一下游 `Mono.error`,zip **立即失败**并把**原始异常**(未包装,`IllegalStateException (stockSvc down)`)直达订阅端——对比范式一实测 C 的两层包装;
- **C** `Flux.interval().limitRate(4).take(4)`:无限流按需生产——**背压**是范式一、三都没有的武器;
- **D** `publishOn(Schedulers.boundedElastic())` 显式把后续阶段搬到指定线程——"调度"是一等公民,但也是必须学会的心智。

## 4.2 Reactive Streams 契约:四个接口与背压

【白话】2015 年五家厂商定下的规范只有 4 个接口,全部收编在 `java.util.concurrent.Flow`(Java 9,JEP 266):

```java
Flow.Publisher<T>    { void subscribe(Flow.Subscriber<? super T> s); }
Flow.Subscriber<T>   { void onSubscribe(Subscription s); void onNext(T item);
                       void onError(Throwable t); void onComplete(); }
Flow.Subscription    { void request(long n); void cancel(); }   // ← 背压的钥匙
Flow.Processor<T,R>  extends Subscriber<T>, Publisher<R> { }
```

【白话】背压机制:订阅建立时上游只给 `Subscription`,**数据必须等下游 `request(n)` 才流动**——消费者的处理速度反压到生产端,缓冲不失控。`Flux`/`Mono` 的每个操作符都是这棵契约树上的一个节点:

【源码证据】`reactor-core/src/main/java/reactor/core/publisher/Flux.java:90,126`(3.8.8-SNAPSHOT):

```java
 * A Reactive Streams {@link Publisher} with rx operators that emits 0 to N elements, and then completes
 * (successfully or with an error).
public abstract class Flux<T> implements CorePublisher<T> {
```

`Mono.java:81` 同款:"emits at most one item"。`CorePublisher` 是 Reactor 对规范接口的内部扩展,为的是让 `Context`(4.3.3)能沿订阅链传递。

## 4.3 源码解析:组装即建树,订阅即执行,调度器定线程

### 4.3.1 操作符链 = Subscriber 树(组装期)

【白话】`Mono.zip(a,b,c).map(...).block()` 这行代码在**组装期**不产生任何信号,只是层层 new 出包装节点:`FluxZip → MonoMap → MonoBlock`。每个操作符是一个 `FluxXxx/MonoXxx` 类,实现 `subscribe(Subscriber)`:被订阅时 new 一个内部 `Subscriber` 接住下游,再把自己包装后向**上游**订阅——**订阅从下游向上游传播,数据从上游向下游流动**。

### 4.3.2 调度器 = 线程的"出租公司"(执行期)

【源码证据】切换执行位置的两个操作符,语义截然不同:

- `Flux.subscribeOn(Scheduler)`(`Flux.java:8939`):决定**订阅动作**发生在哪个线程——整条链的"地基";
- `Flux.publishOn(Scheduler)`(`Flux.java:7656`):决定**它之后的信号**在哪个线程——流水线中段的"换轨"。

`FluxSubscribeOn.java:32` 的类注释一语中的:"Subscribes to the source Publisher asynchronously through a scheduler";其内部(`:54`)通过 `scheduler.createWorker()` 拿一个 Worker,把真正的订阅任务 `schedule` 上去。`Schedulers.java:277` 的 `boundedElastic()` 是为"阻塞型任务"准备的弹性池(默认上限 10×CPU,队列 100k),`:295` 的 `parallel()` 是 CPU 密集专用(恰为 CPU 核数)。

【白话】于是"这段代码在哪跑"在 Reactor 里有**确定答案**,但要求你显式声明(范式一是"不可预测",范式三是"你不用管")。代价是每一个 map/flatMap 你都得想一遍调度——这就是学习曲线的实体。

### 4.3.3 Context:为"沿信号传播的上下文"发明的体系

【源码证据】`reactor-core/src/main/java/reactor/util/context/Context.java:39`:

```java
public interface Context extends ContextView {   // 只读视图/可写上下文分离
```

【白话】Reactor 的世界没有"当前线程"的概念(信号在哪个线程触发是调度器的事),ThreadLocal 失效,于是它自建了**订阅级上下文**:`contextWrite` 从下游向上游写入,`deferContextual` 在任意环节读取——**绑定的是订阅关系,不是线程**。这也解释了它最反直觉的规则:Context 只能"向上游传"(因为写入发生在订阅传播阶段),而 ThreadLocal 是"向下游传"。Spring Security Reactive、Micrometer Tracing 在 WebFlux 下全靠这套体系。

顺带一提,Reactor 自己也承认两种世界的裂缝:源码里专门有 `ConnectableFluxRestoringThreadLocals.java` 这样的类,在信号进入回调时**恢复 ThreadLocal**——为了跟"另一个世界"的库互操作,它在操作符里做 ThreadLocal 快照/恢复。范式之间的缝隙,连框架作者都得用胶水填。

## 4.4 Reactor 不可替代的能力

这三样是范式一/三**结构上给不出**的,也是 7.1 里"Reactor 退守流主业"的底气:

1. **无限流与背压**:消息队列消费、SSE、WebSocket 帧、gRPC 流——"上游多少个我不知道,下游能吃多少算多少"。虚拟线程可以把阻塞消费也做高并发,但**"下游速度反压生产端"这个控制论问题,只有 request(n) 机制原生解决**。JDK 对应物是 `Flow`(JDK 9 已收编接口)——所以严格说,这一条的"未来主人"是 Flow 契约,Reactor 是它最成熟的实现。
2. **声明式组合的流算子**:`buffer/window/merge/zipWith/retryWhen/backoff`——对"事件流"做变换的代数库。用命令式代码手写这些 = 手写并发状态机。
3. **取消的精确语义**:`Subscription.cancel()` 沿操作符树逐层上抛,每个环节清理资源(`doOnCancel/doFinally`)。对比 CF 的假取消(3.2.2)和 STS 的"整组取消"(5.1 实测 B),**流式的细粒度取消**仍是 Reactor 主场。

## 4.5 结构性代价(同样是实测与源码背书)

| # | 代价 | 说明 |
|---|---|---|
| 1 | **学习曲线最陡** | 操作符 200+,`publishOn/subscribeOn` 语义、"向上游订阅/向下游发信号"、Context 方向……心智模型自成体系 |
| 2 | **栈不可用** | 一切在信号处理器里,异常栈是操作符链,不是调用栈——调试要靠 `checkpoint()`/`onOperatorDebug()`/BlockHound 补 instrument |
| 3 | **生态隔离** | 全库 Reactive 化(R2DBC/WebFlux client)才能兑现收益;混一个 `block()`/JDBC 就"污染"事件循环。整个调用链被锁定在同一个范式里——正是 Ron Pressler 批评的"病毒式分裂" |
| 4 | **简单编排被过度收费** | 实测 A 的场景(3 个下游聚合)用 zip 写没有问题,但维持这条流水线需要团队理解整个模型;同样的业务在范式三里是三个 `scope.fork` |
| 5 | **测试与观测复杂** | `StepVerifier` 专用测试法;传统 profiler/线程 dump 对流内部状态无感 |

## 4.6 本章小结

- Reactor 的正确打开方式是**"流"**:把"事件序列 + 背压 + 声明式算子"作为问题域。在纯 CRUD 编排场景,它的表达力优势被学习曲线、调试成本和生态隔离三重税抵消。
- 它与 JDK 的关系已经理顺:**契约进 JDK(Flow),实现留在 Reactor**。这意味着范式二的"思想"已获官方永久承认——被淘汰的只会是"用 Reactor 写普通并发编排"这种用法。

# 五、范式三:虚拟线程 + ScopedValue + StructuredTaskScope(结构化并发)

## 5.1 白话定位与同题代码

【白话】范式三的世界观:**线程便宜到可以随便开;上下文绑定到"代码作用域"而不是"线程";并发的编排写进语法块,像局部变量一样有结构**。三件套分工:虚拟线程解决"等得起",ScopedValue 解决"传得对",StructuredTaskScope 解决"管得住"(失败即取消全组、超时即取消全组、父等子收尾)。

同一场景(JDK 25;完整可跑:`D:\tmp\paradigm-demo\P3Structured.java`,需 `--enable-preview`):

```java
static final ScopedValue<String> TRACE_ID = ScopedValue.newInstance();

static String call(String downstream, long costMs) {
    // 对比范式一:直接 ScopedValue.get()——绑定沿 fork 自动传播,无需 lambda 手抄
    System.out.printf("  [%s] 调 %s, traceId=%s, virtual=%b%n",
            Thread.currentThread().getName(), downstream, TRACE_ID.get(),
            Thread.currentThread().isVirtual());
    Thread.sleep(costMs);
    return downstream + ":OK";
}

ScopedValue.where(TRACE_ID, "trace-002").run(() -> {
    try (var scope = StructuredTaskScope.open(Joiner.<String>allSuccessfulOrThrow())) {
        var s1 = scope.fork(() -> call("userSvc", 100));
        var s2 = scope.fork(() -> call("orderSvc", 150));
        var s3 = scope.fork(() -> call("stockSvc", 200));
        Stream<String> ok = scope.join().map(StructuredTaskScope.Subtask::get);
        System.out.printf("  聚合结果: %s, 耗时 %dms%n", ok.toList(), ...);
    } catch (Throwable e) { /* 原始异常,不包装 */ }
});
```

【实测】(`P3Structured.java`,JDK 25.0.1 `--enable-preview`)三个决定性现象(全录见附录 A):

- **A** 三个子任务全部 `virtual=true`,`TRACE_ID.get()` 在子任务里直接读到 `trace-002`——**ScopedValue 绑定随 fork 自动传播**;
- **B** stockSvc 20ms 失败 → `userSvc` 在 **22ms 时收到 interrupt**(没有白跑 103ms)→ `join()` 抛出**原始异常**(`FailedException: IllegalStateException: stockSvc down`)→ 全程耗时 22ms;
- **C** `open(joiner, cfg -> cfg.withTimeout(80ms))`:超时 84ms 整组取消,抛 `TimeoutException`。

再对比第六章的同题横评:范式一实测同样的失败场景白跑 103ms + 异常包两层;**范式三把"取消传播"从"程序员的自觉"变成了"语法的保证"**——这就是结构化并发的全部意义。

## 5.2 虚拟线程调度器:一页最小回顾

机制细节(mount/unmount、pinning、状态机、实测数据)已在 [虚拟线程 vs 线程.md](<虚拟线程 vs 线程.md>) 一~三章讲透,这里只保留对"范式"理解必需的四条:

1. **调度器是 JVM 内的 FIFO ForkJoinPool**:`java.base/java/lang/VirtualThread.java:71` `private static final ForkJoinPool DEFAULT_SCHEDULER = createDefaultScheduler();`,默认并行度 = CPU 核数。阻塞时 `Continuation.yield`(`VirtualThread.java:449`)把栈卸到堆、释放载体线程;成功则调度器把载体派给下一个就绪的虚拟线程。
2. **线程创建 = 对象分配**:百万级并发可行(实测 20 万个 160ms 任务全部并发,见兄弟文档 3.3)。
3. **JDK 阻塞点已改造**:网络 IO/`sleep`/锁 park 等自动让出载体;JDK 24 起连 `synchronized` 也不再 pin(JEP 491)。残余 pin 场景(native 帧)见兄弟文档 3.4。
4. **"池大小限流"失去意义**:不再需要池来保护内存/切换成本,并发上限改由业务语义控制(如 `Semaphore` 保护下游)——这正是范式一"池"的心智破产点。

## 5.3 ScopedValue(JDK 25 转正,JEP 506):ThreadLocal 的官方继任者

【白话】ThreadLocal 的三大病根:可变(set 覆写造成"回写污染")、生命周期无界(忘了 remove 就漏)、绑定线程身份(池化即串号)。ScopedValue 的设计就是对着病根开药:**只读、作用域绑定、随栈传播**。

【源码证据】`java.base/java/lang/ScopedValue.java`(JDK 25,无 preview 标记,`grep PreviewFeature` = 0):

```java
public static <T> ScopedValue<T> newInstance() {          // :538,替代 new
    return new ScopedValue<>();
}

public static <T> Carrier where(ScopedValue<T> key, T value) {  // 绑定入口
    return new Carrier<>(new Snapshot(key, value, ...));
}
// Carrier 链式叠加:where(sv1, v1).where(sv2, v2)...,然后 run()/call()
```

绑定数据结构是一个**不可变链表**(Snapshot):

```java
    static final class Snapshot {                             // ScopedValue.java:253
        final Snapshot prev;                                  // :254,指向上一个绑定帧 → 栈形结构
        final Carrier bindings;
        final int bitmask;                                    // 位图加速多绑定的查找
    }
```

读取路径 `get()`(`:678`)从当前线程的 `scopedValueBindings`(`:799` 起,`Thread` 内部持有)沿 Snapshot 链查找——**绑定就"住在"调用栈里**:进入 `run()` 压入,`run()` 返回自动弹出。线程死了绑定自动消失;**不存在"忘了 remove"**。

三个关键语义对比:

| | ThreadLocal | ScopedValue |
|---|---|---|
| 可变性 | `set()` 任意覆写 | **不可变**:作用域内一个值,写即开新作用域 |
| 生命周期 | 手工 remove,忘了就漏 | 语法块结束自动失效 |
| 跨线程 | 不跨(InheritableThreadLocal 仅创建时复制一次) | **fork 时自动捕获**(配合 STS;`ScopedValue.java:144` 明确写入契约) |
| 池化风险 | 串号(实测 D)/泄漏 | 结构上不可能 |

【源码证据】跨线程传播的官方承诺,`ScopedValue.java:144`(类注释):

> *scoped value bindings are **captured** when creating a `StructuredTaskScope`*

【实测】P3 的 A 段:主线程 `where(TRACE_ID,"trace-002").run(...)`,`scope.fork()` 的三个子任务里 `TRACE_ID.get()` 全部读到——零胶水代码。

> 注意 ScopedValue 与 ThreadLocal 不是互换关系:`set`-style 的可变"每请求槽位"仍有合法性(如可变 session 状态);迁移决策表见 [虚拟线程 vs 线程.md](<虚拟线程 vs 线程.md>) 4.3。

## 5.4 StructuredTaskScope:API 变了四次,现在到底怎么写

【白话】结构化并发的思想(源自 CSP,普及推手是 Martin Thompson/Nathaniel Smith 的文章与 Swift/Kotlin 的实践):**并发的分支要在同一个语法块里汇合**——fork 出的子任务必须被 join,scope 关闭时一切子任务保证终结,失败/超时自动取消全组。父任务的 try 块就是子任务的"生死簿"。

### 5.4.1 JEP 演进全表(网上教程大量过时,以此为准)

| JDK | JEP | API 形态 |
|---|---|---|
| 19/20 | 428/437(孵化器) | `new StructuredTaskScope.ShutdownOnFailure()` + fork 返回 `Future` |
| 21~24 | 453/480/499/(24 无新 JEP) | 预览:`fork` 改返回 `Subtask`;仍是 `class StructuredTaskScope<T>` + 策略内部类(`ShutdownOnSuccess/ShutdownOnFailure`) |
| **25** | **505(第五预览)** | **重设计:`sealed interface StructuredTaskScope<T, R>` + 静态工厂 `open(Joiner)`**;策略类废除;`Joiner` 接口 `@since 25` |
| 26 | 525(第六预览) | 增加 `onTimeout` Joiner、`List` 返回等 |
| 27 | 533(第七预览) | `StructuredTaskScope<T, R, R_X extends Throwable>`,异常类型进泛型,`ExecutionException`/`CancelledByTimeoutException` 融入 |

【源码证据】三版 API 形态对照(本地源码):

```java
// JDK 21:java.base/java/util/concurrent/StructuredTaskScope.java:302
public class StructuredTaskScope<T> implements AutoCloseable {   // 策略类:ShutdownOnFailure()

// JDK 25:同路径(本文件其他位置)
public sealed interface StructuredTaskScope<T, R>                // :352
        extends AutoCloseable
        permits StructuredTaskScopeImpl {
    @PreviewFeature(feature = PreviewFeature.Feature.STRUCTURED_CONCURRENCY)
    @FunctionalInterface
    interface Joiner<T, R> {                                     // :506,@since 25
        static <T> Joiner<T, Stream<Subtask<T>>> allSuccessfulOrThrow() { return new Joiners.AllSuccessful<>(); }  // :593
        static <T> Joiner<T, T> anySuccessfulResultOrThrow() { ... }        // :609
        static <T> Joiner<T, Void> awaitAllSuccessfulOrThrow() { ... }      // :628
        static <T> Joiner<T, Void> awaitAll() { ... }                       // :660
        static <T> Joiner<T, Stream<Subtask<T>>> allUntil(Predicate<Subtask<? extends T>> isDone) { ... }  // :721
    }
    static <T> StructuredTaskScope<T, Void> open() { ... }                  // :914,默认策略=全成功或抛
    static <T, R> StructuredTaskScope<T, R> open(Joiner<? super T, ? extends R> joiner) { ... }  // :887
    static <T, R> StructuredTaskScope<T, R> open(Joiner<...> joiner, Function<Configuration, Configuration> config) { ... }  // :865(withName/withThreadFactory/withTimeout)
}

// JDK 27:三泛型 + 异常进签名
public sealed interface StructuredTaskScope<T, R, R_X extends Throwable>  // :374
    static <T> StructuredTaskScope<T, Void, ExecutionException> open()    // :1268
    static <T> Joiner<T, List<T>, ExecutionException> allSuccessfulOrThrow()   // :750
```

> **结论:写新代码,请直接用 25 的 `open()+Joiner` 形态**(27 兼容它);网上铺天盖地的 `ShutdownOnFailure` 示例是 21~24 的旧 API,25 里已废。

### 5.4.2 Joiner 语义速查(JDK 25)

| Joiner | 成功时 `join()` 返回 | 失败行为 | 适用 |
|---|---|---|---|
| `allSuccessfulOrThrow()` | `Stream<Subtask<T>>`(按 fork 顺序) | **任一失败 → 取消全组**,join 抛失败异常 | 同构子任务聚合 |
| `anySuccessfulResultOrThrow()` | 最先成功的那个结果 | 全部失败才抛 | 竞速(多副本/多供应商) |
| `awaitAllSuccessfulOrThrow()` | `null` | 任一失败 → 取消全组 | 异构子任务(各自 get) |
| `awaitAll()` | `null` | **不取消**,等全部跑完 | 扇入/副作用型(如 accept loop,JDK javadoc 官方示例) |
| `allUntil(predicate)` | 命中的 Subtask 流 | 自定义 | 自定义完成策略 |
| `open()` 默认 | `null` | 任一失败 → 取消全组 | 等价 `awaitAllSuccessfulOrThrow` |

【源码证据】`allSuccessfulOrThrow` 的取消语义(`StructuredTaskScope.java:593` javadoc):

> *The `Joiner` **cancels the scope** and causes `join` to throw if any subtask fails.*

【实测】P3 B 段:stockSvc 20ms 失败,100ms 的 userSvc **22ms 即被 interrupt**——"取消"不是注释,是发生在 2ms 内的线程中断。注意异常形态:`StructuredTaskScope$FailedException: java.lang.IllegalStateException: stockSvc down`——join 抛的是 FailedException(cause=原始异常),**比 CF 的两层包装浅一层,且类型确定**(27 起 FailedException 的角色由 `ExecutionException` 接管,见 5.4.1 表)。

## 5.5 当前短板(范式三的诚实清单)

1. **结构化并发仍是预览**(JEP 505→533,25/26/27 三连预览):API 还会微调(27 已把异常类型编进泛型),生产使用需 `--enable-preview`,等转正再大规模铺开是理性策略;
2. **CPU 密集不适用**:虚拟线程让出载体的前提是"在等 IO";纯计算场景平台线程/ForkJoinPool/并行流仍是正解(`Thread.java:102` 类注释原话:not intended for long running CPU intensive operations);
3. **背压问题域没有覆盖**:百万个虚拟线程一窝蜂打向下游,只会把下游打挂——限流仍要 `Semaphore` 等显式手段(兄弟文档 5.7);"消费速度反压生产端"的流问题,依旧是 Flow/Reactor 的主场;
4. **存量 ThreadLocal 生态待迁移**:Spring RequestContextHolder 等(清单见兄弟文档 4.5),迁移期内 ThreadLocal 在虚拟线程上仍可用,只是池化摊销逻辑不再成立;
5. **native 阻塞仍 pin**(JNI 调用内阻塞):JDK 24 解掉了 `synchronized` pin(JEP 491),native 帧内等待仍占载体。

## 5.6 本章小结

- 范式三 = **线程(虚拟)+ 上下文(ScopedValue)+ 编排(StructuredTaskScope)** 三件套,分别对应范式一的 Thread(池)、ThreadLocal、CF。
- 它把三件此前靠**纪律**维持的事,变成靠**机制**保证:上下文必达(fork 捕获)、子任务必亡(语法块)、失败必传播(scope 取消)。
- 短板集中在"预览未转正"与"流问题域缺失"——后者不是缺陷,是分工(7.1)。

## 6.2 逐项展开:三个最有含金量的差异

### 6.2.1 取消与失败传播(维度 5/6/7):纪律 vs 机制 vs 数学

- **范式一**:`allOf` 不取消同伴(实测:白跑 103ms),`cancel` 假取消,超时后下游照跑——**每个环节靠程序员自觉写 exceptionally/cancel 联动**,漏一处就是生产事故。
- **范式二**:error 信号沿操作符树直达,`zip` 一个失败整个失败,**取消沿 Subscription 树精确下传**——这是规范保证(Reactive Streams 契约),语义最强、粒度最细,但要先理解整棵树。
- **范式三**:语法块保证。scope 的生命周期 = try 块,失败 → cancel 全组 → `Thread.interrupt` 落到每个子任务(实测 22ms 生效)——**不学任何新东西就得到正确行为**,这正是"结构化"两个字的分量。

### 6.2.2 上下文传递(维度 4):三代技术的同台

```text
ThreadLocal(2004)     手抄 lambda(范式一实测)→ TTL/装饰器(补丁)→ 注册 ThreadLocalAccessor
Context(2015,Reactor) contextWrite 一次声明全链生效——但只活在"流的世界",出流即断
ScopedValue(2025,JDK) where(...).run(整段业务);fork 自动捕获——普通 Java 代码、无框架胶水
```

范式三胜出的本质:**上下文回到了"栈"上**。栈是唯一不需要框架接力就能贯穿所有代码的骨架。

### 6.2.3 心智负担(维度 8/9):代码即真相

三段等价业务代码并排看一遍,结论自明:范式一要追踪"哪个 lambda 在哪个线程什么时候跑";范式二要脑内展开操作符树;范式三**读代码 = 读业务**,出错时 `jstack` 看到的就是真实调用栈。这不是美学问题,是**维护成本曲线的斜率**问题。

# 七、谁是未来的主流范式

## 7.1 结论先行:三分格局,各有领地

> **虚拟线程 + ScopedValue + StructuredTaskScope 将成为服务器端业务的默认范式;Reactor 退守"流"的主业并持续统治它;CompletableFuture 退化为异步原语,不再承担"编排范式"的角色;而"线程池"回归其本来面目——CPU 密集任务的资源管理工具。**

一句话记住新秩序:**"并发问题"归 Loom,"流问题"归 Flow/Reactor,"计算问题"归池与并行流。** 未来的仓库里,90% 的并发编排是同步风格(虚拟线程),WebFlux/RSocket/流式 gRPC 的代码仍是 Reactor 风格,两者通过清晰边界协作。

## 7.2 证据链:为什么这样判断

**证据一:JDK 官方把三件套做成了"平台能力",而不是"又一个库"。**

- 虚拟线程转正(JDK 21)当天起,`Thread` 这个类**就是**虚拟线程——不是新 API,是替换内核。JDK 自身的阻塞点(网络、sleep、锁)全部改造完毕(JEP 491 连 synchronized 都不再 pin)。
- ScopedValue 转正(JDK 25),ThreadLocal 的官方继任者写进了 `java.lang`。
- 结构化并发 25/26/27 三连预览且 API 快速收敛(27 已把异常类型编入泛型签名)——**JDK 对它的打磨投入远超一般预览特性**,转正是时间问题。
- 反观"流",JDK 只收编了接口(Flow)就停手——官方的态度是:流是库的地盘,Loom 是平台的地盘。**平台层解决的事,库层会被架空;库层独有的问题域,平台不抢。**

**证据二:Spring 的动作就是风向标。**

- Boot 3.2 起 `spring.threads.virtual.enabled=true` 一键切换;Boot 4.x(兄弟文档 [虚拟线程 vs 线程.md](<虚拟线程 vs 线程.md>) 第五章基于 4.1.1 实测)里这一个开关背后是 Tomcat/Jetty/@Async/@Scheduled/上下文传播等**十处联动**——官方把虚拟线程当默认演进方向,连上下文传播的官方方案都转向了虚拟线程友好的路径。
- WebFlux 没有被砍,但其定位在 Spring 生态的叙事里已从"高并发的必需品"收缩为"流式/响应式场景的专业工具"。Spring 官方博客与 Framework 7 文档对普通 MVC 应用推荐虚拟线程,对流式应用保留 WebFlux。

**证据三:范式一的三宗罪在范式三身上全部消失,而 Reactor 的三宗罪只解决了一半。**

范式一的问题(上下文断裂/池限流/假取消)在范式三是**结构性消失**(机制保证);范式二的问题(学习曲线/生态隔离/调试)在范式三只解决了"普通编排"那部分,**流问题的表达力仍是 Reactor 独占**。所以替代发生的位置,恰好是范式二"用流算子写普通并发"的越界部分,而不是它的本行。

**证据四:用户态调度是行业收敛解,Java 只是最后到场。**

Go(2012)用 goroutine 证明了"用户态线程 + 同步写法"能把可读性与吞吐同时拿走;Kotlin 协程、Erlang、甚至 Rust 的 async 生态都在同一方向。Java 虚拟线程的独特优势在于**零 API 迁移**(就是 Thread)——这是所有同类方案里迁移成本最低的,也决定了它的扩散速度会最快。

## 7.3 反方观点:最强的反驳与回应

**反方一:"Reactor 的函数式组合与操作符代数是不可替代的表达力,同步代码写不出 `window/backoff/retryWhen`。"**
——成立,而且这正是 7.1 里 Reactor 保留领地的理由。但注意范围:**对"无限事件流"成立,对"有限并行编排"不成立**。业务的并发编排绝大多数是后者。

**反方二:"虚拟线程没有背压,百万线程会打死数据库。"**
——半对。虚拟线程不提供背压,但**也不需要用"线程池大小"这种副作用手段做限流**(那是范式一被迫发明的方法)。`Semaphore` 限并发、连接池限资源,语义更干净(见兄弟文档 5.7)。"消费速度反压生产速度"的流问题则本来就是 Flow 的领地——两个问题不该混为一谈。

**反方三:"结构化并发还预览着,三年内别想生产化;而 Reactor 已十年成熟。"**
——前半句事实正确(这也正是本文建议的节奏:虚拟线程+ScopedValue 现在生产可用,STS 等转正)。但"成熟即未来"不成立——范式一的 CF 也已十年成熟,它的编排地位照样在让渡。**预览状态影响的是采用节奏,不影响方向判断。**

**反方四:"百万线程的内存代价(每线程堆上栈)并不免费。"**
——对,免费的是"等待",不是"栈内存"。虚拟线程栈按需增长(几百字节~KB 级),百万级实测可行(兄弟文档 3.3:20 万并发仅数十 MB),比平台线程 1MB 预留低两个数量级。但"无界开线程"永远是反模式——虚拟线程把"线程太贵"的问题换成了"要自己管并发度"的问题(Semaphore),只是后者便宜得多。

## 7.4 历史类比:NIO 的剧本正在重演

2002 年 Java 1.4 给出 NIO(类似今天的"底层能力"),所有人都去手写 Selector——直到 Netty(2004)把 NIO 包装成可靠基座,**而普通 Web 应用最终根本没有直接用 NIO**:Tomcat/Servlet 容器在底下用了 NIO,业务代码保持着同步形态(`service(req,resp)`)。

今天的结构几乎同构:**Reactor 之于虚拟线程 ≈ Netty 之于 Servlet 容器**——它们不是竞争者,是分层:基础设施层(容器/通信)继续用事件驱动/流(Reactor/Netty 会活得很好),业务层回归同步写法(虚拟线程)。NIO 没有死,死的是"业务代码直接写 NIO";同理,**Reactor 不会死,正在死的是"业务代码直接写 Reactor 编排"**。

## 7.5 决策树与迁移路线

```text
你的问题域是……?
├─ 无限流/需要背压/SSE/gRPC 流/响应式全栈已有投资 ──▶ Reactor(范式二),别犹豫
├─ CPU 密集并行 ──▶ 平台线程池/ForkJoinPool/并行流(池的本职)
├─ 有限并行编排(微服务聚合/扇出扇入/批处理)──▶ 虚拟线程
│   ├─ JDK 21~24:Thread.ofVirtual + Executors.newVirtualThreadPerTaskExecutor
│   │   + CF 原语(join 可用,不建编排链)+ ThreadLocal 慎用
│   └─ JDK 25+:+ ScopedValue(上下文);STS 转 正 后 + StructuredTaskScope(编排)
└─ 存量 CF/Reactor 代码 ──▶ 不强行重写;新代码用新范式,边界处用 CF 兼容(虚拟线程下 CF.join 很便宜)
```

三条迁移铁律(与兄弟文档第六章反模式呼应):**别把 Reactor 的 block 塞进 event loop;别给虚拟线程做池化;别在新代码里再造 CF 编排链。**

## 7.6 结语

六十年来,并发范式之争每次换代,赢家的共性都是:**让上一代"靠纪律"维持的正确性,变成"靠机制"保证**——线程池之于手工管线程、Reactive Streams 契约之于裸回调、结构化并发之于手工 join/cancel,莫不如此。虚拟线程三件套把"同步写法"重新扶上主位,但这一次它没有牺牲任何吞吐,也没有杀死流——**它只是把"流"还给流,把"业务"还给业务**。
