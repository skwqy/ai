# 一、总览:25 年演进地图

## 1.1 一句话定位

> **Java 的日期时间 API 经历了三代:JDK 1.0 的 `Date`(一个会自己变的毫秒数)、JDK 1.1 的 `Calendar`/`SimpleDateFormat`(打补丁的字段袋),最终在 JDK 8 被 JSR 310 的 `java.time` 统一——不可变、线程安全、类型即文档;此后 9→27 十四个版本再做精装修,直到今天。**

一句话判断"该用谁":**新代码一律 `java.time`(`LocalDate`/`LocalTime`/`LocalDateTime` 三件套起步);`Date`/`Calendar`/`SimpleDateFormat` 只出现在老代码和遗留接口边界上,且边界处立即转换(见第十章)。**

## 1.2 设计哲学:读完全文只需记住的四条

`java.time` 的每一条工具函数都来自这四条设计决策,理解它们比背 API 更重要:

1. **不可变(Immutable)与线程安全**:所有核心类型都是 `final` 类、`final` 字段,"修改"一律返回新对象——`plusDays` 不会动原对象。对比:`Date` 的 `setMonth` 直接改自己,多线程下没任何保护;`SimpleDateFormat` 官方 javadoc 自认线程不安全(`SimpleDateFormat.java:432`)。
2. **领域驱动,类型即文档**:"只有日期"就是 `LocalDate`,"只有时间"就是 `LocalTime`,"本地日期时间(无时区)"就是 `LocalDateTime`,"时间线上的绝对时刻"就是 `Instant`,"带时区"就是 `ZonedDateTime`。旧 API 里这些概念全挤在一个 `Date`/`Calendar` 里,靠约定区分——这就是 bug 的温床。
3. **ISO-8601 默认**:默认日历系统是 ISO(`IsoChronology`),月份 1~12、星期一~星期日、`toString()` 直接是标准格式(`2026-10-05`),不用再记忆任何偏移量。
4. **工厂方法与流畅链式 API**:不用 `new`,用 `of/now/parse` 创建;用 `plus/minus/with` 链式推导。API 读起来像句子:`LocalDate.of(2026, 10, 5).plusMonths(1).with(TemporalAdjusters.lastDayOfMonth())`。

## 1.4 类型全景:两个维度拆开 java.time

`java.time` 有 20 多个类,但只需两个维度就能定位每一个:

**维度一:你想表达什么?**(日期 × 时间 × 时区)

| | 只有日期 | 只有时间 | 日期+时间 |
|---|---|---|---|
| **本地(不含时区)** | `LocalDate` | `LocalTime` | `LocalDateTime` |
| **带偏移(+08:00)** | — | `OffsetTime` | `OffsetDateTime` |
| **带时区(Asia/Shanghai)** | — | — | `ZonedDateTime` |
| **纯时刻(UTC 秒/纳秒)** | `Instant`(时间线上的点,日期时间只是它的投影) | | |

**维度二:给谁看?**(人类时间 vs 机器时间)

| | 人类时间(日历字段) | 机器时间(单个数) |
|---|---|---|
| **时间段(长度)** | `Period`(年月日,如"3 个月") | `Duration`(纳秒,如"90 分钟") |
| **时间点** | `LocalDate` 族 | `Instant` |
| **度量衡** | `ChronoUnit.YEARS/MONTHS/DAYS` | `ChronoUnit.NANOS..DAYS` |

辅助角色:`Year`/`YearMonth`/`MonthDay`(部分日期)、`Month`/`DayOfWeek`(枚举)、`ZoneId`/`ZoneOffset`(时区)、`Clock`/`InstantSource`(时钟)、`DateTimeFormatter`(格式化)、`TemporalAdjusters`/`TemporalQueries`(调整器/查询器工厂)、`java.time.chrono`(非 ISO 纪年:日本、佛历等)。

**一个必须刻在脑子里的区别**:`LocalDateTime` **不是**时间线上的一个点。"2026-10-05T14:30"在上海和纽约是两个不同时刻——它只是"墙上的钟"的读数。要变成时间线上的点,必须补上时区:`atZone(ZoneId)` → `ZonedDateTime`,或 `atOffset(ZoneOffset)` → `OffsetDateTime`。这也解释了为什么 `Instant`(而不是 `LocalDateTime`)才是与 `Date` 对应的"时刻"类型。

# 二、博物馆第一层:java.util.Date(JDK 1.0,1996)

> **一句话定位:`Date` 是"一个自 UTC 1970-01-01 起算的毫秒数",但 1996 年的设计让它身兼"时刻 + 日历 + 时区"三职,年份偏移 1900、月份从 0 数起、方法全部可变——它是 Java 集合框架之前、最早的"设计事故"级 API,其绝大多数方法在 JDK 1.1 就被废弃。**

## 2.1 白话:Date 到底是什么

`Date` 内部其实只有一个 `long`(`fastTime`,毫秒时间戳),这一点和 `Instant` 一脉相承。问题是它在毫秒数之外还提供了一整套**日历操作**:`getYear()`、`getMonth()`、`setHours()`……这些操作依赖"当前 JVM 默认时区"来解释这个毫秒数,于是同一个 `Date` 在上海和纽约"看起来"不一样;更糟的是每个方法还各自带一个坑(见 2.2)。

## 2.2 源码证据:三宗罪

【源码证据 1:字段与构造】`java.base/java/util/Date.java`

```java
public class Date                                             // Date.java:128
    implements java.io.Serializable, Cloneable, Comparable<Date>
{
    private transient long fastTime;                          // Date.java:135 —— 全部状态就这一个毫秒数(+惰性日历缓存 cdate)
    ...
    /**
     * @param   year    the year minus 1900.                  // Date.java:185 —— 罪状一:年份要减 1900
     * @param   month   the month between 0-11.                // Date.java:186 —— 罪状二:月份 0~11
     * @deprecated As of JDK version 1.1,                      // Date.java:189
     */
    @Deprecated                                               // Date.java:193
    public Date(int year, int month, int date) { ... }
```

【源码证据 2:可变 setter】`getYear`/`setYear`/`getMonth`/`setMonth`/`setHours` 等 22 个方法挂着 `@Deprecated`(如 `Date.java:648~870` 的成对 get/set):

```java
@Deprecated
public void setMonth(int month) { ... }                       // Date.java:703-704 —— 直接改自身,非线程安全
```

**罪状清单(附实测输出):**

| 罪状 | 证据 | JDK 27 实测 |
|------|------|-------------|
| 年份减 1900 | `Date.java:185` | 想表达 2026 年要写 `new Date(126, 9, 5)`,输出 `Mon Oct 05 00:00:00 CST 2026` |
| 月份 0~11 | `Date.java:186` | `10` 月要写 `9`;传 `2026, 9, 5` 实际存的是 3926 年,但 `getYear()` 又减回 1900 打出 2026——**双重偏移互相抵消,看起来"对"了,最坑** |
| 可变 | `Date.java:648~870` 的 setter 群 | 共享一个 `Date` 实例,谁都能 `setTime` 改掉它 |
| 时区语义混叠 | toString 按**默认时区**渲染 | 同一毫秒数,换台机器输出不同字符串 |
| 解析/格式化外包给 `SimpleDateFormat` | — | 又引入线程不安全(见 3.3) |

需要说句公道话:`Date` 作为"毫秒时刻"本身没毛病(这层职责后来传给了 `Instant`),错在它被迫兼任日历和时区。JDK 8 的拆分正是把这三职还给三个类型。

## 2.3 本章小结

- `Date` = 可变毫秒数 + 日历/时区混合职责;年份 -1900、月份 0~11 两处偏移写进了参数 javadoc(`Date.java:185-186`)。
- JDK 1.1 起 22 个方法陆续 `@Deprecated`;JDK 8 给它留了两个"新身份":`toInstant()`(变成时刻)和 `Date.from(Instant)`(从时刻构造)——这两个是新旧世界的桥(见 10.1)。
- 新代码出现 `new Date(...)` 即 code smell;只有"与遗留 API 边界"才需要它。

# 三、博物馆第二层:Calendar 与 SimpleDateFormat(JDK 1.1,1997)

> **一句话定位:`Calendar` 用"字段袋 + 工厂方法"接管了 `Date` 的日历职责,`SimpleDateFormat` 接管格式化——它们修好了"偏移量"却没修好"可变"和"线程不安全",还引入了宽容模式(lenient)这种静默改日期的机制;官方 javadoc 至今仍在推荐你换用 `java.time`。**

## 3.1 白话:一个"字段袋"式的补丁

`Calendar` 把日期拆成一堆 int 常量字段(`YEAR`、`MONTH`、`DAY_OF_MONTH`……),用 `get(field)`/`set(field, value)` 存取,并用 `getInstance()` 工厂按地区/日历系统返回子类(通常是 `GregorianCalendar`)。月份终于不用减 1900 了——但月份仍是 0~11(`Calendar.MONTH` 从 0 数起),而且**所有字段可变**。

## 3.2 源码证据:字段袋、工厂与宽容模式

【源码证据】`java.base/java/util/Calendar.java`

```java
public static Calendar getInstance() { ... }                  // Calendar.java:1623 —— 工厂,返回地区相关子类
public int get(int field) { ... }                             // Calendar.java:1852 —— 按字段取值
public final void set(int year, int month, int date) { ... }  // Calendar.java:1928 —— month 仍是 0~11
private boolean lenient = true;                               // Calendar.java:910 —— 宽容模式默认开着!
```

**宽容模式是 `Calendar` 最阴险的特性**(javadoc 明确讨论:`Calendar.java:110-122`):默认 `lenient = true` 时,`2026-02-30` 不报错,静默滚成 `2026-03-02`。实测对照:

```text
new GregorianCalendar(2026, Calendar.FEBRUARY, 30).getTime()
    → Mon Mar 02 00:00:00 CST 2026        // 静默滚日
LocalDate.of(2026, 2, 30)
    → DateTimeException: Invalid date 'FEBRUARY 30'   // java.time 直接拒绝
```

## 3.3 SimpleDateFormat:官方自认线程不安全

【源码证据】`java.base/java/text/SimpleDateFormat.java:428-437`

```java
 * <h3><a id="synchronization">Synchronization</a></h3>
 * <p>
 * Date formats are not synchronized.                          // :432
 * It is recommended to create separate format instances for each thread.
 * If multiple threads access a format concurrently, it must be synchronized
 * externally.
 * @apiNote Consider using {@link java.time.format.DateTimeFormatter} as an
 * immutable and thread-safe alternative.                      // :436-437 —— 官方亲自指路 java.time
```

一个静态 `SimpleDateFormat` 字段被并发使用时,内部共享的 `CalendarBuffer` 会互相踩踏:轻则日期串位,重则 `ArrayIndexOutOfBoundsException`/`NumberFormatException`。**这是面试与生产双高频事故**,而 `DateTimeFormatter` 是不可变类(`DateTimeFormatter.java:516`),随便共享。

## 3.4 第三方救火队:Joda-Time(2002~2014 的事实标准)

在官方修好之前的十几年,社区答案是 Stephen Colebourne 主导的 **Joda-Time**:不可变、领域类型、流畅 API——它验证了"正确的设计",也积累了一批"还能更好"的经验。2007 年 Colebourne 联合 Oracle 发起 **JSR 310**,值得注意的是 JSR 310 **没有直接拿 Joda 代码库改造,而是另起炉灶**(项目代号 **ThreeTen**,他在博客《What about JSR-310?》里解释了原因:回到日期时间的泥沼重新设计,洗掉 Joda 的历史包袱)。JSR 310 一度瞄准 Java 7,最终随 **JDK 8 的 JEP 150** 落地。这段"官方缺位 → 社区标准 → 吸收转正"的路径,与后来虚拟线程(Loom)的故事如出一辙。

## 3.5 本章小结

- `Calendar` 修好了偏移量,但留下:字段袋 API(`get(int)` 不类型安全)、月份仍 0 起算、默认宽容模式静默滚日(`Calendar.java:910`)、全字段可变。
- `SimpleDateFormat` 官方 javadoc 自认线程不安全(`SimpleDateFormat.java:432`),并亲自推荐 `DateTimeFormatter` 替代。
- Joda-Time/JSR 310 证明:正确 API 的形状早已被社区验证,JDK 8 只是"收编"。

# 四、定型:java.time(JSR 310 / JEP 150,JDK 8,2014)

> **一句话定位:`java.time` 用"不可变 + 领域类型 + ISO-8601 + 流畅 API"四件套,把 25 年的日期时间债务一次性清偿;它的接口骨架(Temporal 族)让"加减、调整、查询"在所有类型上行为一致——你学会一次,20 个类通用。**

## 4.1 设计五原则(源码可验证)

| 原则 | 源码证据 |
|------|----------|
| 不可变与线程安全 | `LocalDate` 三个 `private final transient` 字段(`LocalDate.java:199-207`);类 javadoc 明写 "immutable and thread-safe"(`LocalDate.java:139`) |
| 工厂方法创建 | `now()/of()/parse()/from()` 四族静态工厂;没有公共构造器 |
| 领域类型 | `LocalDate`(日期)/`LocalTime`(时间)/`LocalDateTime`(本地日期时间)各自独立 final 类 |
| ISO-8601 默认 | `toString()` 即 `2026-10-05`;`Month` 是枚举(JANUARY=1 起算,`Month.java:106`),`DayOfWeek` 枚举 MONDAY=1(`DayOfWeek.java:109`) |
| 严格模式拒绝非法值 | `LocalDate.of(2026, 2, 30)` 抛 `DateTimeException: Invalid date 'FEBRUARY 30'`(实测),没有宽容模式 |

## 4.2 类型体系全景(二维定位法复述)

1.4 节的表格在这里落成类清单,按"创建一个类型时你脑子里的问句"来记:

- **"今天几号?"** → `LocalDate`(本章第五章)
- **"现在几点?"** → `LocalTime`(第六章)
- **"现在的时间戳(墙上钟读数)?"** → `LocalDateTime`(第七章)
- **"这毫秒数是什么时刻?"** → `Instant`(时间线上的绝对点,`Instant.java:210`,字段 `seconds`+`nanos`,`Instant.java:257-262`)
- **"北京此刻的完整语境?"** → `ZonedDateTime`(`ZonedDateTime.java:167`,= `LocalDateTime` + `ZoneId` + 消歧规则)
- **"只带数字偏移即可?"** → `OffsetDateTime`/`OffsetTime`(偏移 `ZoneOffset` 是 `ZoneId` 的唯一子类之一,`ZoneId.java:180` 是 sealed,permits `ZoneOffset`/`ZoneRegion`)
- **"时长/日历间隔?"** → `Duration`(纳秒数) / `Period`(年月日,字段 `years/months/days`,`Period.java:160-168`)
- **"部分日期?"** → `Year`(`Year.java:136`)/`YearMonth`/`MonthDay`/`Month`/`DayOfWeek`

## 4.3 底层骨架:Temporal 接口族(学会一次,处处通用)

`java.time` 所有"可操作的时间对象"都实现 `Temporal`/`TemporalAccessor` 接口,围绕它们有五个配套抽象:

| 抽象 | 含义 | 内置实现 |
|------|------|----------|
| `TemporalField` | "哪个字段"(年?月?日?) | `ChronoField` 枚举 |
| `TemporalUnit` | "什么单位"(天?月?) | `ChronoUnit` 枚举(`ChronoUnit.java:83-189`,从 NANOS 到 FOREVER 十六级) |
| `TemporalAmount` | "一段时间量" | `Duration`、`Period` |
| `TemporalAdjuster` | "怎么调整"(下周一?月末?) | `TemporalAdjusters` 工厂(5.5 节) |
| `TemporalQuery` | "从对象里提取什么" | `TemporalQueries` 工厂 |

于是通用操作只有三个动词,任何类型都一样:

```java
t.plus(amountOrNumber, unit)   // 加
t.minus(amountOrNumber, unit)  // 减
t.with(adjusterOrField, value) // 调整(返回新对象,原对象永远不变)
```

这就是"类型爆炸但学习成本不高"的原因:**20 个类共享同一套动词**,差异只在各自支持的 field/unit 范围(`isSupported()` 查询,`LocalDate.java:552-586`)。

## 4.4 本章小结

- `java.time` = JSR 310(ThreeTen 新写)+ JEP 150(JDK 8 落地),Joda-Time 的精神续作。
- 四条设计原则:不可变、领域类型、ISO-8601、工厂 + 流畅 API;一个骨架:`Temporal` 族接口让所有类型共享 plus/minus/with 三个动词。
- 类型选择的两个维度:"表达什么(日期/时间/时区)"×"给谁看(人类/机器)"——1.4 的两张表就是决策树。

# 五、LocalDate 深度解析:只有年月日的日期

> **一句话定位:`LocalDate` 用三个字段(`int year` + `byte month` + `byte day`)表达"ISO 日历上的一天",内部换算成"纪元日"(epoch day,距 1970-01-01 的天数)参与计算;它的 70 余个公开方法与重载按"创建 → 读取 → 修改 → 调整 → 区间 → 格式化 → 转换"七个动作分组,每组都有 1~2 个高频主力。**

## 5.1 数据模型与源码坐标

【源码证据】`java.base/java/time/LocalDate.java`

```java

    public static final LocalDate MAX = LocalDate.of(Year.MAX_VALUE, 12, 31); // :172 —— +999999999-12-31
    public static final LocalDate EPOCH = LocalDate.of(1970, 1, 1);           // :178 —— JDK 9 新增

    private final transient byte month;                        // :203
    private final transient byte day;                          // :207
```

三个原始类型字段 + 静态常量缓存,不可变、天然线程安全。所有跨月/闰年计算最终都落到"纪元日"这个 long 上(`toEpochDay()`,`LocalDate.java:1954`;纪元起点常量 `DAYS_0000_TO_1970 = 719528` 天,`LocalDate.java:194`)。

## 5.2 创建:七种姿势

## 5.3 读取与判断:取值的"无坑"版本


## 5.4 修改:plus / minus / with(永远返回新对象)

```java
LocalDate b = a.plusDays(1);   // a 原封不动,b = 2026-10-06   (:1373)
a.plusWeeks(1)      // :1354    a.plusMonths(1)    // :1328    a.plusYears(1)  // :1300
a.minusDays(1)      // :1535    (minusYears/Months/Weeks/Days 对称,:1473-1535)
a.plus(Period.of(1, 2, 3))     // :1172 加"1年2个月零3天"
a.minus(3, ChronoUnit.DAYS)    // :1448 按单位减
a.withYear(2027)    // :1085    a.withMonth(1)     // :1104
a.withDayOfMonth(31)// :1124    a.withDayOfYear(1) // :1143
a.with(TemporalField, value)   // :1050 通用字段调整
```

**月末自动收缩规则(实测)**:加减月份时"日"超出目标月长度会被拉回月末,而不是滚到下个月:

```text
2026-01-31 .plusMonths(1)  → 2026-02-28    // 不是 2026-03-03(Calendar 宽容模式会滚)
2026-03-31 .minusMonths(1) → 2026-02-28
```

这与 `Calendar` 的静默滚日(3.2)形成鲜明对比:**`java.time` 的规则是可预期的"收缩",不是可预期的"滚动"**——两个 API 都不改日,只是规则不同,写代码时要知道自己依赖的是哪种。

| `lastInMonth(DayOfWeek)` | :310 | 最后一个周一 |

## 5.6 区间与遍历:until / datesUntil

```java
LocalDate start = LocalDate.of(2026, 10, 5);
LocalDate end   = LocalDate.of(2027, 3, 4);

start.until(end)                    // Period P4M27D —— "日历差":0年4个月27天 (:1705)
start.until(end, ChronoUnit.MONTHS) // 4 —— 按单位整除、截断 (:1644)
ChronoUnit.DAYS.between(start, end) // 150 —— 总天数(第八章 8.2)
start.datesUntil(end)               // Stream<LocalDate> 逐日流(:1733,JDK 9 新增)
start.datesUntil(end, Period.ofMonths(1))                    // (:1760,JDK 9 新增)
    // → 2026-10-05, 2026-11-05, 2026-12-05, 2027-01-05(步进 1 个月,月末规则与 plusMonths 一致)
```

三个"差"语义不同,选错就出 bug:**`until(end)` 是日历差**(年月日三元组),**`until(end, unit)` 是整除截断**,**`ChronoUnit.DAYS.between` 是精确总天数**(4 个月 27 天 ≠ 150 天的换算关系由具体日历决定)。`datesUntil` 返回的是惰性 `Stream`,配合 `filter/map` 可以一行写"未来一年里的所有周一":`start.datesUntil(start.plusYears(1)).filter(d -> d.getDayOfWeek() == DayOfWeek.MONDAY)`。


## 5.8 本章小结

- 数据模型:三个不可变字段(int year + byte month + byte day),一切计算落到纪元日 long。
- 七个动作的 API 地图:**创建**(`now/of/ofEpochDay/ofYearDay/ofInstant*/parse/from`)→ **读取**(`getYear.../get(field)`)→ **修改**(`plus/minus/with`,月末收缩)→ **调整**(`with(TemporalAdjusters.*)` 14 个预置)→ **区间**(`until`×2 语义不同 + `datesUntil` 流)→ **格式化**(`format/parse`)→ **组合换算**(`atTime/atStartOfDay/toEpochDay/toEpochSecond`)。
- 三个高频陷阱预告:月末收缩(5.4)、`until` 两义(5.6)、`atStartOfDay()` 与 `atStartOfDay(zone)` 差一个时区(5.7)。

# 六、LocalTime 深度解析:只有时分秒的时间

> **一句话定位:`LocalTime` 用四个字段(byte hour/minute/second + int nano)表达"一天内的时间读数",内部是"当日纳秒数"(0~86399999999999);它没有日期,所以 `plusHours(25)` 会回绕而不是进位到明天——想跨天,请和 `LocalDate` 组成 `LocalDateTime`。**

## 6.1 数据模型与四个常量

【源码证据】`java.base/java/time/LocalTime.java`

```java
public static final LocalTime MIN;       // :135 00:00 —— 与 MIDNIGHT 是同一个实例!
public static final LocalTime MAX;       // :140 23:59:59.999999999
public static final LocalTime MIDNIGHT;  // :144 00:00
public static final LocalTime NOON;      // :148 12:00
private final byte hour;    // :233
private final byte minute;  // :237
private final byte second;  // :241
private final int  nano;    // :245
```

静态块里预建了 24 个整点实例 `HOURS[0..23]`(`LocalTime.java:152-161`),`MIN`、`MIDNIGHT` 都是 `HOURS[0]` 的别名——整点时间不用重复建对象。

## 6.2 创建:与 LocalDate 对称,外加两个"秒数工厂"

| 工厂 | 行号 | 说明 |
|------|------|------|
| `LocalTime.now()` / `now(ZoneId)` / `now(Clock)` | :259/:275/:289 | 与 `LocalDate` 同构 |
| `LocalTime.of(14, 30)` | :307 | 时+分(重载到 :350 带秒、纳秒) |
| `LocalTime.ofInstant(Instant, ZoneId)` | :371 | JDK 9 新增 |
| `LocalTime.ofSecondOfDay(52215)` | :391 | 当日第 52215 秒 → 14:30:15 |
| `LocalTime.ofNanoOfDay(long)` | :409 | 当日纳秒数,机器视角 |
| `LocalTime.parse("14:30:15")` | :459 | ISO 格式(可只写时分) |
| `LocalTime.parse(text, formatter)` | :473 | 自定义格式 |
| `LocalTime.from(temporal)` | :438 | 从 `LocalDateTime` 等提取 |

## 6.3 读取与修改:truncatedTo 是隐藏主力

```java
LocalTime t = LocalTime.of(14, 30, 15, 123_456_789);   // 14:30:15.123456789
t.getHour()    // 14      (:722)   t.getMinute() // 30 (:731)
t.getSecond()  // 15      (:740)   t.getNano()   // 123456789 (:749)

t.truncatedTo(ChronoUnit.MINUTES)  // 14:30          (:982) —— 截断到整分,高频!
t.truncatedTo(ChronoUnit.HOURS)    // 14:00          (:982)
t.withHour(9).withMinute(0).withSecond(0).withNano(0)   // (:902-953) 逐字段改
t.plusHours(1).plusMinutes(30).plusSeconds(10).plusNanos(1)  // (:1105-1176)
t.minusHours(2)                    // (:1254 起,与 plus 对称)
t.plus(90, ChronoUnit.MINUTES)     // (:1077) 任意单位
```

**回绕规则(实测)**:`LocalTime.of(14, 30).plusHours(25)` → `15:30`。小时加减对 24 取模,**不会**产生"明天"——`LocalTime` 没有明天的概念。对比:`LocalDateTime.of(2026,10,5,14,30).plusHours(25)` → `2026-10-06T15:30`,进位交给日期部分。

`truncatedTo` 与 `withSecond(0).withNano(0)` 的区别:前者语义是"截断到给定单位"(传 `DAYS` 会抛异常,因为时间装不下一整天),后者是逐字段赋值;清零精度一律优先 `truncatedTo`。

## 6.4 转换与判断

```java
t.toSecondOfDay()   // 52215     (:1483) —— ofSecondOfDay 的逆运算,存库/传输常用
t.toNanoOfDay()     // (:1496)
t.toEpochSecond(LocalDate date, ZoneOffset offset)  // (:1519,JDK 9) —— 补上日期和偏移才能换算成时间线秒数
t.atDate(LocalDate.of(2026, 10, 5))  // → LocalDateTime (:1459) —— 与 LocalDate.atTime 互为逆操作
t.atOffset(ZoneOffset.ofHours(8))    // → OffsetTime    (:1472)
t.isBefore(other) / t.isAfter(other) // (:1576/:1564)
t.until(LocalTime.NOON, ChronoUnit.HOURS)  // -2 (:1417) —— 允许负值,方向感明确
```

## 6.5 本章小结

- 四字段(byte×3 + int)不可变模型,常量 `MIN==MIDNIGHT` 同一实例、`NOON` 表达正午。
- 创建与 `LocalDate` 完全对称,多两个机器视角工厂 `ofSecondOfDay/ofNanoOfDay`;`toSecondOfDay` 是对称的逆。
- 两大特性:**回绕**(加 25 小时 = 加 1 小时)与**截断**(`truncatedTo`,去精度首选);需要跨天语义时升级到 `LocalDateTime`。

# 七、LocalDateTime 深度解析:本地日期 + 本地时间

> **一句话定位:`LocalDateTime` 不是第三个独立系统,而是"一个 `LocalDate` + 一个 `LocalTime`"的组合体(两个 final 字段),它把前两章的全部工具函数原样继承过来,自己只多一件事——与时间线(时刻)的进出站口:`atZone/atOffset` 出站、`ofInstant/ofEpochSecond/toInstant` 进站。**

## 7.1 数据模型:组合而非继承

【源码证据】`java.base/java/time/LocalDateTime.java`

```java
public static final LocalDateTime MIN = LocalDateTime.of(LocalDate.MIN, LocalTime.MIN); // :147
public static final LocalDateTime MAX = LocalDateTime.of(LocalDate.MAX, LocalTime.MAX); // :154
private final LocalDate date;   // :165
private final LocalTime time;   // :169
```

没有第三个字段、没有新算法:`getYear()` 直接委托 `date.getYear()`,`plusHours()` 委托 `time` 后必要时进位到 `date`。这也是它 API 面积巨大的原因——**它透明地暴露了两个成员类型的所有能力**。

## 7.2 创建与拆分

```java
// 创建
LocalDateTime.now() / now(zone) / now(clock)          // :183/:199/:213
LocalDateTime.of(2026, 10, 5, 14, 30)                 // :314(int 月份重载至 :364)
LocalDateTime.of(2026, Month.OCTOBER, 5, 14, 30)      // :239(枚举月份重载)
LocalDateTime.of(LocalDate, LocalTime)                // :377 —— 组合
LocalDateTime.ofInstant(Instant, ZoneId)              // :397 —— JDK 8 起就有(注意:LocalDate/LocalTime 的同名方法是 JDK 9 才补)
LocalDateTime.ofEpochSecond(0, 0, ZoneOffset.UTC)     // :420 —— 秒 + 纳秒 + 偏移
LocalDateTime.parse("2026-10-05T14:30:00")            // :480(ISO,'T' 分隔)
LocalDateTime.parse(text, formatter)                  // :494

// 拆分:组合的逆操作
dt.toLocalDate()   // :735      dt.toLocalTime()  // :831
dt.getYear()/getMonthValue()/getDayOfMonth()/getDayOfWeek()   // :749-817,全部委托 date
dt.getHour()/getMinute()/getSecond()/getNano()                // :840-867,全部委托 time
```

## 7.3 修改:两个成员的全部工具函数在这里汇合

`LocalDateTime` 的 `plus/minus/with` 家族是两个成员的同名方法合集(:917-1530):日期侧 `plusYears/plusMonths/plusWeeks/plusDays`、`withYear/withMonth/withDayOfMonth/withDayOfYear`;时间侧 `plusHours/plusMinutes/plusSeconds/plusNanos`、`withHour/withMinute/withSecond/withNano`、`truncatedTo`(:1119)。月末收缩规则(5.4)原样生效:

```text
LocalDateTime.of(2026, 1, 31, 14, 30).plusMonths(1) → 2026-02-28T14:30
```

跨日期/时间边界的加减自动进位:`plusHours(25)` = `2026-10-06T15:30`。

## 7.4 通往时间线:出站与进站

`LocalDateTime` 自身"没有时区",所有时间线换算都必须先补一个"时区语境":

```java
LocalDateTime dt = LocalDateTime.of(2026, 10, 5, 14, 30);

// 出站(本地 → 时间线)
dt.atZone(ZoneId.of("Asia/Shanghai"))   // 2026-10-05T14:30+08:00[Asia/Shanghai]  (:1795) → ZonedDateTime
dt.atOffset(ZoneOffset.ofHours(8))      // 2026-10-05T14:30+08:00                  (:1761) → OffsetDateTime
dt.toInstant(ZoneOffset.ofHours(8))     // Instant —— 默认方法,接口 ChronoLocalDateTime.java:456
dt.toEpochSecond(ZoneOffset.ofHours(8)) // 1791181800 —— ChronoLocalDateTime.java:474

// 进站(时间线 → 本地)
LocalDateTime.ofInstant(instant, ZoneId.of("Asia/Shanghai"))  // :397
LocalDateTime.ofEpochSecond(epochSec, nano, ZoneOffset)       // :420
instant.atZone(zone).toLocalDateTime()                        // 链式等价写法
```

两个细节值得点名:① JDK 27 源码里 `toInstant`/`toEpochSecond` 定义在 `ChronoLocalDateTime` 接口的 default 方法上(`java.base/java/time/chrono/ChronoLocalDateTime.java:456,474`),`LocalDateTime` 继承使用——这解释了为什么它们不在 `LocalDateTime.java` 的方法索引里;② `atZone` 与 `atOffset` 的区别:时区(`ZoneId`)带夏令时规则和消歧策略,偏移(`ZoneOffset`)只是一个固定数字,存档/序列化推荐至少带偏移,面向用户展示才用完整时区(陷阱详见 10.2)。

## 7.5 本章小结

- `LocalDateTime` = `LocalDate` + `LocalTime` 的组合,API 是两者的并集,学习成本为零(前两章就是它的说明书)。
- 增量能力只有一项:**与时间线互转**——出站 `atZone/atOffset/toInstant/toEpochSecond`,进站 `ofInstant/ofEpochSecond`。
- 记住身份:`LocalDateTime` 是"墙上的钟",不是时刻;做时间戳存储/跨系统传输时,入站 `Instant` 或出站带偏移的类型(10.3 决策表)。

# 八、配套工具类:Duration/Period/ChronoUnit/DateTimeFormatter/Clock

> **一句话定位:三主角之外,真正决定"用得对不对"的是五个配角:`Duration`(机器时长)与 `Period`(日历时长)的分野、`ChronoUnit` 的统一度量衡、`DateTimeFormatter` 的线程安全格式化、`Clock`/`InstantSource` 的可注入时钟。**

## 8.1 Duration vs Period:一张决策表

| | `Duration` | `Period` |
|---|---|---|
| 语义 | 物理时长(纳秒计数) | 日历间隔(年月日三元组) |
| 字段 | `seconds` + `nanos`(参照 `Instant.java:257-262` 的同构设计) | `years` + `months` + `days`(`Period.java:160-168`) |
| 适用对象 | `Instant`、`LocalTime`、`LocalDateTime` 等有"时间感"的对象 | 基本只对 `LocalDate`/`LocalDateTime` 有意义 |
| 创建 | `ofDays/ofHours/ofMinutes/ofSeconds/ofMillis/ofNanos`(`Duration.java:213-313`)、`between(start, end)`(:519) | `of(1, 2, 3)`(:235)、`ofDays/ofMonths/ofYears`、`between(date1, date2)`(:388) |
| "1 天"等于 | 恒 24 小时(物理) | 看日历(跨夏令时那天是 23/25 小时) |

**两者在夏令时切换日的实测差异**(纽约 2026-11-01 凌晨结束夏令时,时钟回拨 1 小时):

```text
基准:2026-10-31T12:00-04:00[America/New_York]

plus(Period.ofDays(1))   → 2026-11-01T12:00-05:00   // 钟面还是 12:00,实际只过了 23 小时
plus(Duration.ofDays(1)) → 2026-11-01T11:00-05:00   // 实打实过了 24 小时,钟面变 11:00
```

规律:**给 `ZonedDateTime` 加"日历量"(天/月/年)用 `Period` 或 `plusDays/plusMonths`,加"物理量"(确切时长,如超时、重试间隔)用 `Duration`。** `ZonedDateTime.plus` 家族(`ZonedDateTime.java:1553` 起)对两者行为不同,这正是接口族把 `TemporalAmount` 拆成两个类的用意。

`Duration` 的实用成员:`isPositive()`(:626,JDK 18)、`dividedBy(Duration)`(:1057,JDK 9,整除取倍数)、`toSeconds()`(:1246,JDK 9)以及把时长按"天/时/分/秒/毫秒/纳秒"**分位**拆开的 `toDaysPart()/toHoursPart()/toMinutesPart()/toSecondsPart()/toMillisPart()/toNanosPart()`(:1316-1399,JDK 9)——`Duration.between(a,b)` 得到 PT3H30M 时,`toHoursPart()=3`、`toMinutesPart()=30`,而老的 `toMinutes()` 是总量 210。

## 8.2 ChronoUnit:统一的度量衡

`ChronoUnit`(`ChronoUnit.java:83-189`)从 `NANOS` 到 `FOREVER` 十六级枚举,每个常量都自带一个 `Duration`(如 `MONTHS = Duration.ofSeconds(31556952/12)`,即儒略年/12)。它的静态方法 `ChronoUnit.between(start, end)` 是跨类型通用的"取差":

```java
ChronoUnit.DAYS.between(start, end)       // LocalDate → 150(总天数)
ChronoUnit.HOURS.between(t1, t2)          // LocalTime
ChronoUnit.SECONDS.between(instant1, instant2)  // Instant
```

与 `until(unit)` 的关系:`a.until(b, unit)` 与 `ChronoUnit.between(a, b)` 等价,前者是实例方法风格、后者是静态工具风格,选一种团队统一即可。

## 8.3 DateTimeFormatter:线程安全的格式化

【源码证据】`java.base/java/time/format/DateTimeFormatter.java:516`(`public final class DateTimeFormatter`,全字段 final,不可变)——对比 `SimpleDateFormat.java:432` 的 "not synchronized"。

```java
// 自定义模式
DateTimeFormatter f = DateTimeFormatter.ofPattern("yyyy年MM月dd日 EEEE");  // :568,带 Locale 重载 :592
LocalDate.of(2026, 10, 5).format(f.withLocale(Locale.CHINA));  // "2026年10月05日 星期一"
LocalDate.parse("2026-10-05");          // 内置 ISO 解析,不用自己写 pattern

// 预定义 ISO 常量(推荐优先用,免于 pattern 争论)
DateTimeFormatter.ISO_LOCAL_DATE        // :797   → 2026-10-05
DateTimeFormatter.ISO_LOCAL_DATE_TIME   // :999   → 2026-10-05T14:30:00
DateTimeFormatter.ISO_OFFSET_DATE_TIME / ISO_ZONED_DATE_TIME / ISO_INSTANT ...

// 本地化格式(JDK 19 新增,LDML 模板)
DateTimeFormatter.ofLocalizedPattern("yMMMEd")   // :766
    .withLocale(Locale.US).format(LocalDate.of(2026, 10, 5))  // "Mon, Oct 5, 2026"

// 覆盖 locale/时区/纪元(JDK 10 新增)
f.localizedBy(Locale.JAPAN)             // :1575
```

**`yyyy` vs `uuuu`(解析端最经典坑)**:pattern 字母 `y` 是"纪元年(year-of-era)",`u` 是"推算年(proleptic year)"。解析器有三种模式(`ResolverStyle`):默认 `SMART`、严格 `STRICT`、宽松 `LENIENT`。`ofPattern` 默认 SMART 能应付大多数输入,但**一旦切到 STRICT,`yyyy` 会要求附带"纪元"字段而失败,改用 `uuuu` 即可**;需要防御"2 月 30 日"这类输入时用 STRICT + `uuuu`。记忆口诀:**格式化用啥都行,解析(严格)用 `uuuu`**。

## 8.4 Clock 与 InstantSource(JDK 17):让"现在"可注入

业务代码里 `LocalDate.now()` 散落各处,测试就没法固定"今天"。JDK 8 的答案是 `Clock`(`Clock.java`:systemUTC :159、systemDefaultZone :182、system(zone) :201、tickMillis :230(JDK 9)、tickSeconds :254、tickMinutes :277、tick(基准钟, 步长) :312、fixed(固定时刻) :347、offset(基准钟, 偏移) :373,抽象方法 `instant()` :446):

```java
Clock clock = Clock.fixed(instant, ZoneId.of("Asia/Shanghai"));   // 测试:时间冻结
LocalDate.now(clock)      // 所有 now(Clock) 重载都吃它
```

JDK 17 进一步抽出**只读**接口 `InstantSource`(`InstantSource.java:98`,`@since 17`):只要"时刻"不要时区语义的代码(比如生成 ID、打点)依赖 `InstantSource` 即可,`Clock` 实现它。依赖收窄 + 测试注入更轻,是接口隔离原则的一次教科书落地。

## 8.5 本章小结

- `Duration` 是物理时长、`Period` 是日历间隔,夏令时切换日两者差一小时(实测);`toXxxPart` 家族(JDK 9)解决"分位显示"。
- `ChronoUnit.between` 是跨类型通用的取差工具。
- `DateTimeFormatter` 不可变线程安全;预定义 ISO 常量优先;严格解析记 `uuuu`。
- 测试固定时间:`Clock.fixed` / JDK 17 `InstantSource` 注入。

# 九、演进余波:JDK 9 → 27 的 java.time 增量全景专题

> **一句话定位:JDK 8 之后的 `java.time` 没有伤筋动骨的变化,按"最后一次实质变化"的约定,本主题的全景专题落在 JDK 27(新增格式化模式 SPI);本节用一张时间线表收拢 9→27 的全部增量,再对四个关键版本展开。**

## 9.1 增量时间线总表(全部经 JDK 27 源码 `@since` 注解核对)

| 版本 | 新增 API(`@since` 依据) | 解决什么 |

## 9.2 四个关键版本展开

**JDK 9——补"用着别扭"的口子。** 最有代表性的是 `datesUntil`:JDK 8 想遍历日期区间只能手写 for 循环,JDK 9 之后是一行流。`toXxxPart` 家族同理:JDK 8 的 `Duration.toMinutes()` 给的是总量,显示"3 小时 30 分"得自己做减法,JDK 9 的分位方法直接给 30。这一版的主题词是**人体工学**。

**JDK 17——`InstantSource` 接口隔离。** `Clock` 承担了两个职责:取时刻(`instant()`)和提供时区语境(`getZone()`)。大量代码只要前者,JDK 17 把它抽成单方法接口,`Clock` 反向实现它。存量代码不受影响,新代码的依赖注入点建议直接写 `InstantSource`。

**JDK 26——饱和运算。** `Instant` 的可表示范围是 `±1000000000` 年,普通 `plus` 越界抛 `ArithmeticException`;对于"限流冷却、超时预算"这类"加个大数,封顶即可"的场景,`plusSaturating` 不抛异常而是钳到边界(实测:`Instant.MAX.plusSaturating(Duration.ofDays(1))` → `+1000000000-12-31T23:59:59.999999999Z`)。配套的 `Duration.MIN/MAX` 哨兵常量则让"无界/上限"有了标准表达(实测 `Duration.MAX` → `PT2562047788015215H30M7.999999999S`)。

**JDK 27——格式化模式开放为 SPI。** `DateTimeFormatterPatternProvider` 继承 `LocaleServiceProvider`,意味着 `ofLocalizedDateTime(FormatStyle)` 背后的"某 locale 用什么模式"可以由 JDK 之外的提供方定制(如跟随 CLDR 更新节奏或企业定制),这是 `java.time` 第一次把格式化决策权外部化。

## 9.3 本章小结

- 增量主线:**9(人体工学)→ 13(新纪元)→ 17(接口隔离)→ 26(饱和运算)→ 27(SPI 化)**,无破坏性变更,升级无感、好用度渐增。
- 升级唯一要警惕的是 JDK 9 的 JEP 252(CLDR 默认)带来的文案/格式静默变化。
- 与[JDK版本特性变化.md](JDK版本特性变化.md)的 2.5 节呼应:那里是 8 版全景的一页摘要,这里是 9→27 的完整余波。

# 十、实战:新旧互转、六大陷阱与选型决策

> **一句话定位:`java.time` 时代的日常痛点只剩三件事——和老 API 打交道的转换、几个反直觉的语义陷阱、以及"到底该用哪个类"的决策。本章一次讲完。**

## 10.1 新旧互转:边界上转换,边界内只留新 API

```java
// Date ↔ Instant ↔ java.time(实测往返无损)
Date legacy = new Date();
Instant instant = legacy.toInstant();                          // Date → Instant
LocalDateTime ldt = LocalDateTime.ofInstant(instant, ZoneId.systemDefault());
Date back = Date.from(ldt.atZone(ZoneId.systemDefault()).toInstant());
// back.equals(legacy) → true

// Calendar → java.time
Calendar cal = Calendar.getInstance();
ZonedDateTime zdt = cal.toInstant().atZone(cal.getTimeZone().toZoneId());

// java.time → Calendar(经 GregorianCalendar.from(ZonedDateTime))

// 老代码为何常写 toInstant().atZone(zone):Instant 无时区,必须补语境才有"本地日期时间"
```

记忆锚点:**`Instant` 是新旧世界的桥**(它接替了 `Date` 的"毫秒时刻"职责),一切转换都从它过一遍,不要找 `Date` 与 `LocalDateTime` 的"直达车"。

## 10.2 六大陷阱(全部有实测依据)

| # | 陷阱 | 实测表现 | 对策 |
|---|------|----------|------|
| 1 | 遗留 API 偏移量 | `new Date(2026, 9, 5)` 存的是 3926 年;`getYear()` 又减 1900 打出 2026,双重偏移互相抵消"看着对" | 见 2.2;`Calendar.MONTH` 同样 0 起算 |
| 2 | `Calendar` 宽容模式静默滚日 | `new GregorianCalendar(2026, FEBRUARY, 30)` → `Mar 02` | `java.time` 直接抛 `DateTimeException: Invalid date 'FEBRUARY 30'`;确需宽容语义自己显式写 |
| 3 | 月末加减的自动收缩 | `2026-01-31.plusMonths(1)` → `2026-02-28`(收缩,不滚动) | 知道规则即可;与 Calendar 行为不同,迁移测试别漏月末用例 |
| 4 | `Period` vs `Duration` 混用 | 夏令时切换日:`plus(Period 1 天)` 钟面不变(23h),`plus(Duration 1 天)` 过足 24h 钟面变 | 日历量用 Period,物理量用 Duration(8.1) |
| 5 | `LocalDateTime` 当时刻用 | 存库/传参丢时区,跨机器语义漂移 | 时间戳用 `Instant`;确要本地时间就显式 `atZone/atOffset` 后再序列化 |
| 6 | `SimpleDateFormat` 并发 / 解析 `yyyy` | 线程串位;STRICT 模式下 `yyyy` 缺纪元字段解析失败 | `DateTimeFormatter` + 严格解析用 `uuuu`(8.3) |

## 10.3 选型决策表

| 场景 | 用什么 |
|------|--------|
| 生日、账单日、日程的"那天" | `LocalDate` |
| 营业时间、闹钟、课表时刻 | `LocalTime` |
| 日志时间戳(本地视角)、表单里的日期时间 | `LocalDateTime` |
| 数据库时间戳、跨服务传输、过期时间 | `Instant`(配 `Duration` 算间隔) |
| 面向用户展示"北京时间几点" | `ZonedDateTime` / `OffsetDateTime` |
| 排班/月报按"月"推算 | `LocalDate` + `Period` + `TemporalAdjusters` |
| 超时、重试、限流冷却 | `Instant` + `Duration`(边界场景用 `plusSaturating`,JDK 26) |
| 注入测试 | `Clock` / `InstantSource`(JDK 17) |
| 与遗留 `Date`/`Calendar` 接口对接 | `toInstant()` / `Date.from()` 边界转换 |

## 10.4 本章小结

- 桥是 `Instant`:新旧的每一次握手都从它过。
- 六大陷阱一半来自旧 API(偏移、宽容模式、线程不安全),一半来自新 API 的反直觉语义(月末收缩、Period/Duration 分野、本地≠时刻)——前者靠迁移,后者靠记住规则。
- 一句话收束全文:**类型即文档——选对类型,一半的 bug 就不会发生。**
