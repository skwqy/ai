# 一、总纲:三条架构原则

1. **代码回归同步直写。** 不再为"线程贵"做任何设计妥协:不写回调链、不写 Reactor、不池化业务线程。`Controller → Service → Mapper` 一条直线读完,读代码=读业务。
2. **并发上限从"隐式池大小"改为"显式资源闸门"。** 虚拟线程时代没有"池满自动背压"这层保护了,必须显式设计**三层闸门**:连接层(Tomcat `max-connections`)→ 应用层(`Semaphore` 舱壁)→ 资源层(Hikari `maximumPoolSize`)。
3. **超时是第一道防线。** 池时代"排队缓冲"天然吃掉突发流量;现在请求全部立即执行、直接挤向下游——**每一个外呼(HTTP/JDBC/Redis/MQ)必须显式超时,闸门上的等待也要带超时与降级**(`tryAcquire(timeout)`,无界等待=全站一起变慢)。

# 四、分层设计与代码示例

## 4.1 Web 层:接受"每请求一线程",别再用池思维限流

Tomcat worker 池已退役——`TomcatVirtualThreadsWebServerFactoryCustomizer` 把协议执行器整个换成 `VirtualThreadExecutor`,每请求一个新虚拟线程(源码证据见兄弟文档 5.2)。**不要**试图配回线程池"保护自己"——要限的是下游资源(4.3),不是线程数。Jetty 的 `server.jetty.threads.max` 语义已变为"并发任务上限"(`VirtualThreadPool.maxTasks`)。

## 4.2 服务层编排:两条路线

**路线 A(主推):StructuredTaskScope,见六。** 需要项目接受 `--enable-preview`。

**路线 B(兜底):虚拟线程 executor 模式**——不想开 preview 时用,语义是手工版结构化并发:

```java
private static final ExecutorService VIRTUAL = Executors.newVirtualThreadPerTaskExecutor();

ProductDetail aggregate(long id, Duration timeout) throws Exception {
    try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
        var priceF  = exec.submit(() -> priceClient.get(id));
        var stockF  = exec.submit(() -> stockClient.get(id));
        var reviewF = exec.submit(() -> reviewClient.get(id));
        var all = exec.invokeAll(List.of(priceF, stockF, reviewF),
                                 timeout.toMillis(), TimeUnit.MILLISECONDS);  // 到点全组取消
        return new ProductDetail(all.get(0).get(), all.get(1).get(), all.get(2).get());
    }
}
```

要点:`try-with-resources` 包住 executor——**任何子任务异常/超时,close 时整组 interrupt**;没有 `allOf`、没有 `exceptionally`、没有 ExecutionException 剥壳。STS 转正后路线 A 取代它,调用方签名不变。

**两条路线共同的"不要"**:不要 `CompletableFuture.thenApply/thenCompose` 编排链、不要 `allOf+join` 手工异常接力。CF 只保留一个角色:**单值异步原语**(JDK/三方 API 返回 CF 时收下它,虚拟线程上 `join()` 很便宜)。

## 4.3 下游保护:舱壁 + 排队上限 + 降级(必做的架构件)

池时代 `pool.max-size=50` 隐式做了舱壁;现在必须显式建。**一句话定位:虚拟线程让"发起调用"无限便宜,舱壁负责把"调用方的并发"重新对齐到"资源的真实容量"。** `acquire()` 必须带超时(无界等待让所有请求一起变慢而不是快速失败):

```java
@Component
public class DbBulkhead {
    private final Semaphore permits = new Semaphore(50);   // = DB 能承受的并发,不是线程数!

    public <T> T call(Supplier<T> query, Duration maxWait) {
        boolean acquired = false;
        try {
            acquired = permits.tryAcquire(maxWait.toMillis(), TimeUnit.MILLISECONDS);
            if (!acquired) throw new OverloadException("db busy, fail fast");  // 排队也设上限
            return query.get();
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new CancellationException("cancelled while waiting for permit");
        } finally {
            if (acquired) permits.release();
        }
    }
}
```

### 4.3.1 主要用在什么地方

| 资源 | 舱壁放在哪 | permits 配多大 | 不做的后果 |
|---|---|---|---|
| **数据库(JDBC)** | Repository 切面或如上包装,*在 Hikari 之前* | = DB 容量,通常 20~50 | 10 万请求全 park 在 `getConnection()`,所有接口 P99 一起飙升(不是崩,是"慢性变慢",更难排查) |
| **下游微服务** | **每个下游一个独立舱壁**,包在 RestClient 外 | = 下游压测出的稳态吞吐 | 下游 A 一慢占住全部请求——池没了,A 的慢直接传染整个进程(堆内存、调度) |
| **第三方 API** | client 包装层 | = 对方配额折算的并发数 | 超配额被 429/封禁,重试风暴加剧 |
| **重查询与 OLTP 共库** | 报表/导出类方法单独一个**小舱壁**(如 5) | 宁小勿大 | 一条慢查询挤占全部连接,在线交易跟着遭殃 |
| **本地重资源**(Excel 生成/文件处理) | service 入口 | = 内存/CPU 可承受并发 | 并发 500 个大 Excel = OOM |
| **MQ 消费** | Kafka listener 的 `concurrency`(它本身就是消费侧舱壁) | = 下游写库能力 | 消费快过写入 → 打爆 DB |

**例外**:Redis(Lettuce)单连接多路复用,客户端并发 ≠ 连接数,一般不需要并发舱壁,保护点是命令超时与慢命令隔离。

> 为什么舱壁在虚拟线程上"便宜":`Semaphore.acquire/tryAcquire` 基于 `LockSupport`,虚拟线程等待时让出载体——**10 万个请求排队只占堆内存,不占 OS 线程**,这是池做不到的。Hikari `maximumPoolSize` 退化为最后一道物理闸(按 DB 容量 20~50 设,不再承担限流)。

### 4.3.2 业务示例:电商下单链路的三种舱壁策略(实测)

【白话】舱壁的精髓不在 Semaphore 本身,而在**降级策略按业务语义定制**:强依赖满了就拒单(快速失败),弱依赖满了就降级(保主流程),不同下游互不传染。以下 demo 完整可跑(`D:\tmp\paradigm-demo\P5BulkheadBusiness.java`,纯 JDK):

```java
/** 通用舱壁:permits=资源容量,maxWaitMs=排队预算,超限走 fallback(降级) */
static final class Bulkhead {
    private final String name;
    private final Semaphore permits;
    private final long maxWaitMs;

    Bulkhead(String name, int permits, long maxWaitMs) { /* 存字段 */ }

    <T> T call(String biz, Supplier<T> action, Supplier<T> fallback) {
        boolean acquired = false;
        try {
            acquired = permits.tryAcquire(maxWaitMs, TimeUnit.MILLISECONDS);
            if (!acquired) {                       // 排队预算耗尽 → 降级/拒单,而不是无限等
                log("[" + name + "] " + biz + ": 排队超时 → 走降级");
                return fallback.get();
            }
            return action.get();
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new IllegalStateException(e);
        } finally {
            if (acquired) permits.release();
        }
    }
}

static final Bulkhead INVENTORY = new Bulkhead("库存舱壁(2)", 2, 50);   // 强依赖
static final Bulkhead COUPON    = new Bulkhead("优惠券舱壁(1)", 1, 30); // 弱依赖

// 场景 1:强依赖(库存)满了 → 降级策略是"拒单"(action 抛异常穿透,fallback 直接拒)
INVENTORY.call("下单#3",
        () -> inventorySvc("SKU-3", 100),
        () -> { throw new IllegalStateException("稍后再试"); });   // 拒单,用户看到"稍后再试"

// 场景 2:弱依赖(优惠券)满了 → 降级策略是"无优惠继续下单"
COUPON.call("下单#2",
        () -> couponSvc("u1", 80),
        () -> "无优惠(降级)");                                     // 订单照建,损失一次营销
```

【实测】(JDK 25.0.1,三个场景一次跑完):

```text
== 场景 1. 3 个下单并发抢 2 个库存许可,第 3 个 50ms 超时 → 拒单 ==
  [库存舱壁(2)] 下单#3: 排队 50ms 拿不到许可 → 走降级
  结果: 库存已锁定:SKU-1
  结果: 库存已锁定:SKU-2
  结果: 拒单(稍后再试)
== 场景 2. 3 个下单并发抢 1 个优惠券许可,超时的降级为无优惠 ==
  [优惠券舱壁(1)] 下单#1: 排队 30ms 拿不到许可 → 走降级
  结果: 无优惠(降级)
  结果: 优惠-100元
  结果: 无优惠(降级)
== 场景 3. 库存舱壁占满(2×100ms)期间,详情接口不受影响 ==
  商品详情:SKU-9,耗时 21ms ← 舱壁把故障锁在库存舱里
```

三个场景对应三条设计规则:**① 强依赖(下单必须有库存)满了要快速拒单**——宁可少接单,不让全部请求慢性变慢;**② 弱依赖(优惠券只是增益)满了要业务降级**——主流程(下单)保住;**③ 每个下游独立舱壁**——库存打满时,商品详情接口照常 21ms 返回,故障被锁在自己的舱里(bulkhead 本义:船的隔水舱)。

### 4.3.3 三个部件各管一段、放在哪一层

- **舱壁(permits)**:决定"同时能进去几个"——对齐资源容量;**排队上限(tryAcquire timeout)**:决定"外面最多等多久"——延迟预算;**降级(fallback/OverloadException)**:排队也满时的出路——快速失败好过慢性死亡。三者缺一不可:只有限并发没有排队上限,下游一慢全站跟着慢;只有排队没有降级出口,雪崩只是推迟。
- **形态**:手写 `Semaphore` 包装(如上,收敛成一个 `Bulkhead` 组件),或 Resilience4j 的 `SemaphoreBulkhead`/Sentinel——Resilience4j 默认实现就是这个语义,虚拟线程在其 `tryAcquire` 上照常让出等待。**与断路器的关系**:舱壁管"放多少进去"(常态限流),断路器管"连续失败整个别放"(故障熔断)——舱壁在断路器内侧,叠加使用;虚拟线程会把断路器阈值**更快**触发,压测重新校准。
- **位置原则**:贴着**资源**放,不贴着业务放——"调 DB 的每个入口"都有一个闸,而不是某个 Controller 自己配一个。

### 4.3.4 permits 怎么定、什么时候不需要

- **permits 不是按虚拟线程数配**,是按"下游能承受的并发"配——数字来自压测(DB:连接数 × 每查询耗时的倒数;下游服务:稳态吞吐),**宁小勿大**;虚拟线程数永远不用规划,需要规划的只有这些闸门的值。`maxWait` 按用户体验预算定(如 200ms),超了宁可失败。
- **不需要的场景**:纯内存小操作;资源方自带配额(云服务返回 429 且有完善重试)。判断标准一条:**这个资源容量有没有上限、打满会不会把别的请求拖下水**——有,就给它一个舱壁。

## 4.4 上下文传递:框架桥 + 自研 ScopedValue 双轨

Boot 4.1 官方方案仍是 **Micrometer context-propagation 桥**(已核对 Framework 7.x 源码,尚无 ScopedValue 集成;STS 的 fork 也不走 `applicationTaskExecutor`,见六.5):

```java
// 轨道 1:与 Spring/MDC/Tracing 互通 —— 注册 ThreadLocalAccessor
public class TenantAccessor implements ThreadLocalAccessor<String> {
    private static final ThreadLocal<String> TENANT = new ThreadLocal<>();
    @Override public Object key() { return "tenantId"; }
    @Override public String getValue() { return TENANT.get(); }
    @Override public void setValue(String value) { TENANT.set(value); }
    @Override public void setValue() { TENANT.remove(); }    // 清理钩子
}
// 启动注册一次;之后 @Async/propagate-context 自动携带,MDC/trace 同一机制

// 轨道 2:纯自研代码(JDK 25+)—— ScopedValue,结构性防串号
public final class Tenant {
    private static final ScopedValue<String> TENANT = ScopedValue.newInstance();
    public static <R> R with(String tenantId, ScopedValue.CallableOp<R, ?> body) throws Throwable {
        return ScopedValue.where(TENANT, tenantId).call(body);   // 作用域结束自动失效
    }
    public static String current() { return TENANT.orElse("default"); }
}
```

设计红线:**新代码禁止裸 `ThreadLocal.set()`**(一次性虚拟线程让"复用摊销"消失,大对象 set 就是 OOM 工厂);跨框架边界走轨道 1,业务内部用轨道 2。

## 4.5 异步与定时任务:语义已经变了

- **`@Async`**:每次投递 = 一个新虚拟线程,无队列无池。用 `spring.task.execution.simple.concurrency-limit` 限流(3.1);`propagate-context: true` 让 MDC/tracing 自动跟随。
- **`@Scheduled`**:`SimpleAsyncTaskScheduler` **每次触发都开新线程——`fixedRate` 上一次没跑完,下一次照样开跑**(池时代会排队,现在会重叠):

```java
private final AtomicBoolean running = new AtomicBoolean(false);
@Scheduled(fixedDelay = 60_000)              // 优先 fixedDelay:上次完成后才计时,天然不重叠
public void nightlyReport() {
    if (!running.compareAndSet(false, true)) return;   // 防同实例重叠(多实例另加分布式锁)
    try { /* ... */ } finally { running.set(false); }
}
```

- **CPU 密集任务**(报表计算/压缩/加解密):显式隔离到平台线程池,绝不上虚拟线程——载体只有核数个,会饿死整个应用:

```java
@Bean ExecutorService cpuExecutor() {        // 唯一值得保留的平台线程池
    return Executors.newFixedThreadPool(Runtime.getRuntime().availableProcessors(),
            Thread.ofPlatform().name("cpu-", 0).factory());
}
```

## 4.6 响应式边界

只允许 Reactor 出现在两种地方:① 真流式(SSE 推送/RSocket/无限消息流——那是 Flow/Reactor 的主场);② 引用的库本身返回 `Mono/Flux`。规则:不在 event loop 上 `block()`;虚拟线程模块优先用 `RestClient`,别把两个世界搅在一起(Boot 打开开关后 `boundedElastic` 会跑在虚拟线程上,但 Netty event loop **不是**虚拟线程,语义见兄弟文档 5.6)。

## 4.7 声明式 HTTP 框架(OpenFeign / @HttpExchange):能用,六个注意点与选型

**立场先行:声明式接口风格本身就是推荐方案**——同步阻塞模型与虚拟线程天然契合(阻塞等响应时让出载体,代码零改造),且省掉样板代码。要"不建议"的只有两件具体的事:**OpenFeign 这个实现**(维护模式)和**几个被注解隐藏的配置决策**。

### 4.7.1 选型:新应用用 @HttpExchange,OpenFeign 已进维护模式

Spring Cloud 官方在 [spring-cloud-openfeign issue #968](https://github.com/spring-cloud/spring-cloud-openfeign/issues/968)(2024-01)确认 OpenFeign 进入**维护模式**,推荐新代码用 Spring 自家 **HTTP Interface Clients**。本地源码印证:`spring-cloud-openfeign 5.1.x` 仍随 Spring Cloud 发版、Boot 4.1 能用,但只修不加;Spring Framework 7 的接口客户端体系已成熟——`HttpServiceProxyFactory` + `RestClientAdapter`(`spring-web/.../client/support/RestClientAdapter.java:162` 的 `create(RestClient)`)。

### 4.7.2 注意点一(最重要):底层 client 决定一切,它的连接池就是免费的舱壁

| 底层 | 阻塞行为 | 连接池(= 舱壁) | 注意 |
|---|---|---|---|
| **feign 默认 `Client.Default`** | `HttpURLConnection`(`feign/core/.../Client.java:49,90`) | JDK 内部 keep-alive 缓存,**无配置点** | 只该用于 demo;配 `feign-hc5` 或弃用 |
| **JDK HttpClient** | 异步内核 + `send()` 阻塞门面(虚拟线程上 join **会让出**,不钉住) | **无池上限配置**,HTTP/1.1 每并发请求一连接 | 高并发把下游当无限池用,必须外层舱壁兜底 |
| **Apache HttpClient 5**(推荐) | 阻塞 socket,虚拟线程正确让出 | 默认 `maxConnTotal=25 / maxConnPerRoute=5` | **每路由池 = 每下游天然舱壁**,按下游容量调大 |
| **OKHttp** | 同上 | Dispatcher 对同步调用**不限流** | 别误以为有 Dispatcher 限制 |

Boot 4.1 的选择开关是 `spring.http.clients.imperative.factory`(`ImperativeHttpClientsProperties.java:54-79`,枚举 `SIMPLE/JDK/HTTP_COMPONENTS/JETTY/REACTOR`)——默认按 classpath 自动探测,显式声明 `http-components` 最稳。

### 4.7.3 注意点二:超时必须显式配(各框架默认值互不相同)

呼应 4.3 的"超时是第一道防线":

- **OpenFeign**:默认 connect 10s / read 60s——60s 读超时在舱壁模型下等于"一个下游挂了占住许可 60 秒",必须压到业务预算内;
- **RestClient / @HttpExchange**:默认**无超时**——用 Boot 4.1 的 `spring.http.clients.imperative.connect-timeout / read-timeout`(`HttpClientSettingsProperties.java:44,49`,Duration)全局设置。

```yaml
spring:
  http:
    clients:
      imperative:
        factory: http-components        # 池即舱壁
        connect-timeout: 2s
        read-timeout: 3s                # 下游预算,不是容器预算
```

### 4.7.4 注意点三:舱壁的整合位置

两级:**第一级**用底层连接池(hc5 `maxConnPerRoute` 按每个下游容量设,经 `RestClientCustomizer` 或 `ClientHttpRequestFactoryBuilder.httpComponents(...)` 定制);**第二级**才是 4.3 的 `Bulkhead`(tryAcquire 带排队预算 + 按业务的降级语义)——连接池只能"排队",给不出"库存满拒单、优惠券满降级"这种业务化降级。JDK HttpClient 无池上限时第一级缺失,外层舱壁从"建议"变"必须"。

### 4.7.5 注意点四~六:上下文/返回类型/重试

- **上下文无断裂**:同步模型下 interceptor 都在**调用线程**执行,MDC/SecurityContext/trace 直接可读——不存在 Reactor 的 Context 断裂(这正是虚拟线程架构偏爱同步声明式的理由)。反过来的坑:接口方法**别声明返回 `CompletableFuture`/响应式类型**——请求被搬去别的线程,上下文又断了,且虚拟线程栈里毫无必要。
- **重试要配额、要幂等**:OpenFeign 默认 `Retryer.NEVER_RETRY`(安全);引入 Spring Retry/Resilience4j Retry 时,重试 = 下游流量放大 N 倍,而虚拟线程"发起重试"零成本——**重试必须与舱壁叠加**(重试也消耗许可);读超时重试只对幂等操作(GET)安全,下单类接口用幂等键。

### 4.7.6 完整装配示例

```java
@HttpExchange("/inventory")
public interface InventoryClient {
    @GetExchange("/{sku}")
    Inventory get(@PathVariable String sku);
}

@Configuration
public class InventoryClientConfig {
    @Bean
    InventoryClient inventoryClient(RestClient.Builder builder) {   // Boot 已按 4.7.3 的 yml 装好底层与超时
        RestClient rc = builder.baseUrl("http://inventory-service").build();
        return HttpServiceProxyFactory
                .builderFor(RestClientAdapter.create(rc))           // RestClientAdapter.java:162
                .build()
                .createClient(InventoryClient.class);
    }

// Service 里:同步调用 + 外层舱壁(强依赖)
public void placeOrder(Order o) {
    var inv = inventoryBulkhead.call("lock-stock",
            () -> inventoryClient.get(o.sku()),

}
```

### 4.7.7 HTTP 调用的方案推荐光谱(决策表)

| 场景 | 推荐方案 | 理由 |
|---|---|---|
| **对外/跨语言 REST,接口较多** | **@HttpExchange + RestClient**(本文默认) | 声明式可读性 + 官方路线 + 同步模型契合虚拟线程 |
| **只调一两个接口** | 裸 `RestClient`(不建接口) | 声明式接口是为"多接口复用"服务的,一两处直接调更简单 |
| **内部服务间高频 RPC(同团队、强类型)** | gRPC(HTTP/2 多路复用、池化流控内建)或保持 @HttpExchange | 性能敏感才引入 gRPC;其复杂度(protobuf/生态)要用吞吐 justification |
| **允许异步解耦的场景** | **消息(MQ)优先于同步 HTTP** | 把同步调用链变短,比优化任何 HTTP 客户端都有效;下单链路里"通知/积分/统计"类下游改事件 |
| **存量 OpenFeign** | 照常工作,不强行重写 | 新代码不再新增 @FeignClient 即可,按 4.7.2/4.7.3 核对底层与超时 |
| **需要熔断/多版本路由等治理** | @HttpExchange + Resilience4j(或继续 Sentinel) | 治理能力在客户端外的舱壁/断路器层,不绑定框架选择 |

> 一句话:声明式框架省掉的是样板代码,省不掉的是"底层 client 选型 + 全局超时 + 每下游舱壁"三件架构决策——前两件 Boot 4.1 已全局化(`spring.http.clients.*`),第三件仍是显式设计。

池时代教会我们写、而**现在不该再写**的东西:

- ❌ 自定义 `ThreadPoolExecutor`/`TaskExecutor` Bean(业务线程不用池)

# 六、StructuredTaskScope 实战(现在就用的架构方案)

## 6.1 决策与纪律

不等转正、现在用 STS 是合理决策——虚拟线程已是生产底座,而"扇出/超时/取消"这三件事在 executor 模式里是手工拼的,STS 给了有语义契约的原语。**唯一纪律**:JDK 25/26/27 期间 API 还会变(27 已把 `Joiner` 泛型改为 `<T,R,R_X extends Throwable>`、`FailedException` 角色由 `ExecutionException` 接管),所以把 STS **收敛到一个基础设施模块的少数 helper 方法**里,业务代码不直接 import `StructuredTaskScope`——预览期每次 JDK 升级,改动面锁定一个文件。

## 6.2 StructuredOps 骨架(全项目唯一的 STS 进口)

```java
/** concurrency 模块:业务只见语义,不见预览 API */
public final class StructuredOps {

    /** 异构聚合(同构列表):全部成功才返回,任一失败整组取消并抛原始失败原因 */
    public static <T> List<T> gatherAll(List<Callable<T>> tasks) throws InterruptedException {
        try (var scope = StructuredTaskScope.open(Joiner.<T>allSuccessfulOrThrow())) {
            var subs = tasks.stream().map(scope::fork).toList();
            return scope.join().map(StructuredTaskScope.Subtask::get).toList();
        } catch (StructuredTaskScope.FailedException e) {
            throw asRuntime(e.getCause());            // 剥到原始异常,业务 @ExceptionHandler 无感
        } catch (TimeoutException e) {
            throw new AggregationTimeoutException(e); // 自有异常类型,隔离 JDK 未来的改名
        } catch (Throwable e) {                       // join() 声明 throws Throwable——预览期摩擦点
            throw asRuntime(e);
        }
    }

    /** 竞速:任一成功即返回,其余被 close 取消 */
    public static <T> T anySuccess(List<Callable<T>> tasks) throws InterruptedException {
        try (var scope = StructuredTaskScope.open(Joiner.<T>anySuccessfulResultOrThrow())) {
            tasks.forEach(scope::fork);
            return scope.join();
        } catch (Throwable e) {                       // "全部失败"的异常形态预览期可能调整,兜底吸收
            throw asRuntime(e);
        }
    }

    /** 扇出收集:失败收集成结果而非取消全组(批处理/报表);balkhead 函数负责限流 */
    public static <T, R> GatherResult<T, R> gatherEach(List<Callable<T>> tasks,
            Function<T, R> onSuccess, Function<Throwable, R> onFailure) throws InterruptedException {
        try (var scope = StructuredTaskScope.open(Joiner.<T>awaitAll())) {   // awaitAll:不互斥取消
            List<StructuredTaskScope.Subtask<T>> subs = tasks.stream().map(scope::fork).toList();
            scope.join();                             // Void:只等全部终结
            List<R> ok = new ArrayList<>(), fail = new ArrayList<>();
            for (var t : subs) {
                (t.state() == StructuredTaskScope.Subtask.State.SUCCESS ? ok : fail)
                        .add(t.state() == StructuredTaskScope.Subtask.State.SUCCESS
                                ? onSuccess.apply(t.get()) : onFailure.apply(t.exception()));
            }
            return new GatherResult<>(ok, fail);
        } catch (Throwable e) { throw asRuntime(e); }
    }

    private static RuntimeException asRuntime(Throwable t) {
        return (t instanceof RuntimeException r) ? r : new IllegalStateException(t);
    }
}
```

> **fork 一律经过 helper 的第二个理由**见 6.5 的 MDC 桥——`fork(withMdc(() -> ...))`,上下文恢复在 helper 统一做。

## 6.3 五个实测模式(P4StsPatterns.java,JDK 25.0.1 --enable-preview 实跑)

### 模式 1:页面异构聚合(最常用)

```java
try (var scope = StructuredTaskScope.open(Joiner.<Object>awaitAllSuccessfulOrThrow())) {
    Subtask<Price>  p = scope.fork(() -> priceClient.get(id));   // 100ms
    Subtask<Stock>  s = scope.fork(() -> stockClient.get(id));   // 150ms
    Subtask<Review> r = scope.fork(() -> reviewClient.get(id));  // 200ms
    scope.join();                                    // 全成功才继续;任一失败→整组取消+抛失败原因
    return new ProductPage(p.get(), s.get(), r.get());   // join 之后 get() 才合法
}
```

【实测】耗时 ≈ 最慢的 200ms(255ms 含冷启动);任一子任务失败,其余毫秒级收到 interrupt,`join` 抛 `FailedException(cause=原始异常)`——对比 CF 版"白跑 103ms + 异常包两层"(P1Threadpool 实测)。

### 模式 2:批量扇出 + 舱壁 + 失败收集

```java
try (var scope = StructuredTaskScope.open(Joiner.<Fetch>awaitAll())) {
    List<Subtask<Fetch>> tasks = new ArrayList<>();
    for (long id : ids) tasks.add(scope.fork(() -> guardedFetch(id)));  // guardedFetch 内 Semaphore 舱壁
    scope.join();
    return tasks.stream().map(t -> t.state() == Subtask.State.SUCCESS ? ok(t) : failed(t)).toList();
}
```

【实测】20 任务、`Semaphore(2)` 舱壁、1 个下游异常 → **19 成功 + 1 失败,谁都没被取消**。

### 模式 3:超时是 scope 的属性,不是调用方的手段

```java
try (var scope = StructuredTaskScope.open(Joiner.<Fetch>awaitAll(),
        cfg -> cfg.withTimeout(Duration.ofMillis(120)))) {   // JDK 25 名字是 withTimeout(非 timeout)
    for (long id : ids) scope.fork(() -> guardedFetch(id));
    scope.join();
}
```

【实测】120ms 整组到点 → `TimeoutException` 耗时 128ms;运行中的子任务收到 interrupt(`[task-5] 被 scope 取消`),等舱壁的子任务被打断进 FAILED;close 等全部终结后才返回。

### 模式 4:竞速

```java
try (var scope = StructuredTaskScope.open(Joiner.<String>anySuccessfulResultOrThrow())) {
    scope.fork(() -> search("primary", q, 30));
    scope.fork(() -> search("backup", q, 120));
    return scope.join();     // 第一个成功即返回;输的在 close 时被取消
}
```

【实测】`[backup] 输了,被 scope 取消` → `primary:jdk25`。

### 模式 5:嵌套(fan-out of fan-out)

```java
try (var outer = StructuredTaskScope.open(Joiner.<Integer>allSuccessfulOrThrow())) {
    for (String region : regions) outer.fork(() -> regionReport(region, 4));   // 区域内再开 inner scope
    int total = outer.join().mapToInt(StructuredTaskScope.Subtask::get).sum();
}
```

【实测】3 区域 × 4 分片,总耗时 ≈ 单区域最慢链 120ms(51ms 冷启动后);取消沿嵌套链自上而下传导。

## 6.4 Joiner 速查(JDK 25,源码行号见《虚拟线程编程范式.md》5.4)

| Joiner | 成功时 `join()` 返回 | 失败行为 | 适用 |
|---|---|---|---|
| `allSuccessfulOrThrow()` | `Stream<Subtask<T>>`(按 fork 顺序) | 任一失败 → **取消全组**,抛失败原因 | 同构聚合 |
| `awaitAllSuccessfulOrThrow()` | `null` | 任一失败 → 取消全组 | 异构聚合(各自 `Subtask.get()`) |
| `anySuccessfulResultOrThrow()` | 最先成功的结果 | 全部失败才抛 | 竞速 |
| `awaitAll()` | `null` | **不取消**,等全部终结 | 批处理收集/扇入 |
| `allUntil(predicate)` | 命中的 Subtask 流 | 自定义 | 自定义完成策略 |
| `open()` 默认 | `null` | 任一失败 → 取消全组 | 等价 `awaitAllSuccessfulOrThrow` |

## 6.5 Spring 集成四个硬陷阱(全部实测/源码背书)

**1. ThreadLocal(MDC/SecurityContext)不随 fork 传播——最大的坑。** Boot 的 `propagate-context` 只装饰 `applicationTaskExecutor`,**管不到 STS 的 fork**。实测对比(P4 场景 4):ScopedValue 子任务直接读到 `trace-004`,MDC 读到 `null`:

```text
  [] A-桥了MDC: scoped=trace-004, mdc=trace-004, virtual=true
  [] B-没桥:    scoped=trace-004, mdc=null,    virtual=true
```

解法:fork 提交点捕获、执行点恢复(收进 `StructuredOps`,所有 fork 经过它):

```java
static <T> Callable<T> withMdc(Callable<T> task) {
    Map<String, String> ctx = MDC.getCopyOfContextMap();     // 或 ContextSnapshot.captureAll()
    return () -> { if (ctx != null) MDC.setContextMap(ctx);
                   try { return task.call(); } finally { MDC.clear(); } };
}
```

**2. 事务不跨 fork。** `@Transactional` 的连接绑定在 ThreadLocal 上:fork 子任务里走 Spring 代理可**各开各的新事务**,但**绝不加入父线程事务**。设计约束:scope 内子任务只做读/独立写;"多子任务协作写同一事务"在结构化并发下必须拆掉(改为聚合后单点写,或消息化)。

**3. API 摩擦要在 helper 里吸收。** `join()` 声明 `throws Throwable`、`fork` 只接受 `throws Exception` 的 Callable、失败异常是包装形态——三者在 `StructuredOps` 一次性处理(6.2 的 `asRuntime`),业务层只见 `RuntimeException` 语义。

**4. 异常映射。** `@ExceptionHandler(AggregationTimeoutException.class)` 返回 503/降级数据;`asRuntime` 保证业务异常原样穿透(`stockSvc down` 直接命中 `@ExceptionHandler(IllegalStateException.class)`,不用剥壳)。

## 6.6 预览期防变预案(25→26→27 已知变化点)

| API 点 | JDK 25(当前) | JDK 27 已变 | 防线 |
|---|---|---|---|
| 类形态 | `sealed interface StructuredTaskScope<T,R>` | `<T,R,R_X extends Throwable>`(异常进泛型) | 只在 `StructuredOps` 出现,改一处 |
| 失败异常 | `FailedException` | `ExecutionException` | helper 内 catch,业务无感 |
| 超时异常 | `TimeoutException` | `CancelledByTimeoutException` 参与语义 | 包成自有 `AggregationTimeoutException` |
| Joiner 工厂 | `allSuccessfulOrThrow()` 等 | 同名但泛型变 | 同上 |
| 预览状态 | JEP 505(第五预览) | JEP 533(第七预览) | `--release`/运行参数随版本抬升 |

升级动作固定三步:改 `--release`/运行参数 → 改 `StructuredOps` 内部 → 跑并发集成测试(把 6.3 五个场景固化成测试用例,就是 API 兼容性回归集)。

# 七、观测与验收(上线前必做)

1. 线程 dump 换 `jcmd <pid> Thread.dump_to_file -format=json`(`jstack` 看不到虚拟线程,运维脚本要升级);
2. JFR 常开 `jdk.VirtualThreadPinned`(压测期阈值调到 10ms)+ `jdk.VirtualThreadSubmitFailed`;
3. `/actuator/info` 的 `VirtualThreadsInfo`:**queued 持续高位 = 载体不够(CPU 密集混入或 pinning)**,mounted 高 = 真并发高——这是最重要的健康信号;
4. A/B 验证:同一压测脚本开/关 `spring.threads.virtual.enabled` 各跑一轮,重点看"等下游"类接口的 P99——虚拟线程的收益全部来自这里。

# 八、陷阱速查(全新开发也会踩)

| 陷阱 | 后果 | 防线 |
|---|---|---|
| 给虚拟线程做池化 | 收益归零 + ThreadLocal 垃圾回归 | 只用 per-task executor |
| CPU 密集混进虚拟线程 | 载体饿死,全站卡顿 | 4.5 的 `cpuExecutor` 隔离 |
| 闸门 `acquire()` 无超时 | 下游一慢全站雪崩式变慢 | `tryAcquire(timeout)` + 快速降级 |
| `fixedRate` 定时任务重叠 | 数据重复处理 | `fixedDelay` + 互斥守卫 + 分布式锁 |
| 裸 ThreadLocal 传大对象 | 请求峰值 × 对象大小 = OOM | ScopedValue / accessor 桥 |
| 在 event loop 里 `block()` | event loop 卡死 | 模块边界:虚拟线程模块不引 Reactor |
| 自定义 Executor Bean 使开关失效 | 虚拟线程根本没生效 | `mode=force` 或显式 per-task executor |
| fork 子任务里等父事务 | 事务永不提交(连接在父线程) | 6.5 陷阱 2:子任务独立事务 |
| `jstack` 排障 | 看不到虚拟线程,误判"没线程在跑" | `jcmd Thread.dump_to_file -format=json` |
