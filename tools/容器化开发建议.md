## 1.1 一句话定位

**容器化开发 = 把应用的"运行环境"（JDK、系统库、依赖的中间件、启动参数）从"装在我这台机器上、靠人肉记忆"变成"声明在 Dockerfile 和 compose.yaml 里、一条命令可复现"。**

## 1.3 该用容器还是直接在笔记本上跑？——本文的明确建议

**一句话结论：混合模式，但默认偏向容器——"要长期活着的东西"（要部署的应用、全部中间件）进容器；"你每天正在改的代码"留在宿主机，用 IDEA 直接跑。**

把它拆成两个"态"：

- **部署态**：凡是装上去就要一直运行的——MySQL/Redis/Kafka 这类中间件、你写完的服务要以"部署在本机长期运行"形态存在的——**一律容器**。本文 17 个动作主要服务的就是这个态。
- **开发态**：你自己正在开发的那个 Spring Boot 工程，日常直接在宿主机 IDEA 里启动调试；它依赖的中间件跑在容器里（4.2 节第一种拓扑，应用连 `localhost:3306`）。

### 为什么"部署态"选容器：针对这台笔记本的六个理由

1. **可复现、可迁移——笔记本是消耗品**。系统重装或换机时，容器化的全部家当 = 几个 compose.yaml + Dockerfile + 一份卷备份（动作 11），半小时原地满血；原生安装的 MySQL/Kafka/Nacos 每一个都要人肉重装重配，漏配一项就是隐蔽故障。
2. **隔离，不弄脏系统**。Windows 原生装一套 Kafka 意味着装依赖、改 PATH、注册 Windows 服务、留一堆注册表项；容器是 `docker compose down` 之后系统零残留。学习场景的试错（Redis 8 换回 7、Kafka 换 RocketMQ）从"卸载半天"变成"改一行 tag"。
3. **多版本并存**。想同时跑 MySQL 5.7 / 8.0 / 8.4 对照验证隔离级别（`D:\ai\db` 笔记的主题），原生安装几乎做不到；容器里就是三个不同 tag 的服务各占一个端口。
4. **生命周期统一、能自愈**。`restart: unless-stopped` 带来开机自启 + 崩溃自动拉起；升级 = 换镜像 tag 重建容器，回滚 = 换回旧 tag。原生部署的启停/升级/回滚没有统一入口，全靠记忆。
5. **与你的学习路线同构**。你在推进的 K8s（`D:\ai\k8s`）、OpenTelemetry（`D:\ai\cncf`）、负载均衡里的 Service/kube-proxy（`D:\ai\tools\负载均衡.md`），全部以容器为载体——本机容器化之后，"部署环境"和"学习环境"是同一个东西，笔记里的概念随手可验证。
6. **资源可控**。容器体系里每个应用的内存边界都能声明（`.wslconfig` 总闸 + `mem_limit` 分闸，1.6 节的预算才能落地）；原生进程各长各的，Windows 上没有统一的限额开关。

先拆一个常见顾虑——**"容器是不是比原生更耗资源"**：这个直觉来自 VM 时代。容器共享 WSL2 这一个内核，空载开销是每容器几 MB 的进程级开销，外加一台几百 MB 的轻量虚拟机；在 31.5 GB 的机器上，真正吃内存的是应用本身（JVM 堆、MySQL 缓冲池），容器化与否差别可以忽略——而"资源可控"反而是容器独有的收益。

### 为什么"开发态"不建议也塞进容器：三条反方向理由

1. **内循环效率差一个数量级**。Java 改一行代码的验证路径：宿主机是"IDEA 增量编译 → Run"（秒级）；容器是"打包 → docker build → 重建容器"（十秒到分钟级）。这个循环一天要做几十次。
2. **调试与工具链：一等公民 vs 二等公民**。IDEA 对本地进程的 debugger、hotswap、profiler 开箱即用；容器调试要走 jdwp 端口（动作 14 可行，但链路更长，profiling 更绕）。
3. **WSL2 文件事件的先天断层**。Windows 侧的文件改动事件不跨进 WSL2 虚拟机（9.2 坑 9），bind mount 下 devtools 热重载不可靠——这对 Java 开发体验的伤害是持续性的，不是偶发。

所以动作 14 的定位要说清楚：容器里的远程调试与 Testcontainers 服务于**外循环**（提交前的集成验证、按生产形态跑一遍），不替代日常**内循环**。

### 什么时候仍然直接在笔记本上跑

| 场景 | 选择 | 一句话原因 |
|---|---|---|
| 自己正在开发的项目，日常调试 | 宿主机 IDEA + JVM | 内循环最快（上面三条理由） |
| IDE、浏览器、桌面工具 | 宿主机 | 它们本来就是 Windows 应用 |
| 需要 Windows 桌面、GPU/硬件直通、驱动层的程序 | 宿主机 | 容器的隔离层在这里是阻碍而不是保护 |
| 偶尔跑一次的单文件 CLI 小工具 | 宿主机 | 为一条命令起容器不值（除非工具依赖很脏，那容器更干净） |
| **其余一切：中间件、要部署的服务、试玩新软件** | **容器** | 上面六条理由 |

**拿不准时的默认项：先容器。** 从"容器"退回"原生"很容易（照 compose 里的版本号装一遍即可）；从"原生"补成"容器"要凭记忆重建所有手工配置——先容器是更便宜的错误。

**如果你目前的应用实际部署在远程服务器上**（1.2 的场景 a）：这个结论不仅成立而且被强化——本机与远端用同一镜像、同一 compose 文件，本地验证完用 `docker context` 切到远端原样部署（8.3 节），"开发-部署同构"的完整闭环。

## 1.4 目标与原则

做完 17 个动作后，你的日常应该变成这样：

- `docker compose up -d` 一条命令拉起 MySQL + Redis + Kafka 全套依赖（目标 1）；
- 任何一个 Spring Boot 项目，复制同一份 Dockerfile 模板就能构建出规范镜像（目标 2）；
- 本地跑的容器和生产跑的容器是**同一个镜像**，"在我机器上是好的"不再是借口（目标 3）；
- 内存有上限、日志有轮转、磁盘有体检，笔记本不因容器而变卡（目标 4）。

贯穿全文的四条原则：

1. **镜像不可变**：配置通过环境变量注入，一个镜像从开发用到生产，不改镜像只改参数；
2. **数据在卷不在容器**：容器随时可删可重建，删容器不丢数据，`down -v` 才会丢；
3. **笔记本是迷你机房**：所有资源（内存/CPU/磁盘）都要有预算和上限，默认值往往超出笔记本承受力；
4. **先 compose 后 K8s**：compose 解决"拉起依赖"，K8s 解决"编排集群"；学习路线与 `D:\ai\k8s\k8s介绍.md` 衔接。

## 1.6 资源预算：笔记本不是服务器

表 1-2 这台机器（31.5 GB 内存）的建议预算：

| 消耗方 | 预算 | 控制手段 |
|---|---|---|
| Windows + IDEA + 浏览器等日常开发 | ~12 GB（实际占用） | 不归容器管，但决定容器上限 |
| **WSL2 虚拟机（所有容器共享）** | **≤ 8 GB** | `.wslconfig` 的 `memory=8GB`【动作 1】 |
| WSL2 swap | 4 GB | `.wslconfig` 的 `swap=4GB` |
| 剩余给系统的余量 | ~7 GB | 文件缓存、突发 |
| CPU | 8 / 16 线程 | `.wslconfig` 的 `processors=8` |
| 磁盘（镜像+卷+构建缓存） | 初期 20~40 GB，且**放 D 盘** | Docker Desktop 的 Disk image location【动作 2】 |

两个反直觉的点，先立规矩：

- **不配 `.wslconfig` 时，WSL2 默认可吃掉主机一半以上内存**，IDEA 卡顿的第一嫌疑就是它；
- **WSL2 的虚拟磁盘（vhdx）只增不减**——删了镜像磁盘文件也不会自动变小，治理手段见【动作 12】。

# 二、阶段 0：把运行时装起来（动作 1~4）

## 2.1 【动作 1】安装并配置 WSL2（P0，20 min）

**做什么**：安装 Windows 的 Linux 子系统第二版，并给它套上资源上限。

**为什么**：见 1.5 的说明——Docker 需要 Linux 内核特性，WSL2 就是 Windows 里那个"轻量 Linux 虚拟机"。**先配上限再装 Docker**，避免默认配置吃掉一半内存。【本机证据：虚拟化已启用（HypervisorPresent=True），本步骤不需要进 BIOS。】

**怎么做**（PowerShell 管理员）：

```powershell
# 只装 WSL 本体，不装发行版（Docker Desktop 自带所需发行版，不用 Ubuntu 也能工作）
wsl --install --no-distribution
# 重启电脑后：
wsl --update
wsl --version          # 确认 WSL 版本 ≥ 2.x
```

> 如果你还想顺手有个 Linux 环境学 Linux（`D:\ai\linux` 目录预留着），用 `wsl --install`（默认装 Ubuntu）替代上面第一条即可，不影响 Docker Desktop。

**配置资源上限**：在 `%UserProfile%\.wslconfig`（即 `C:\Users\Feng\.wslconfig`）新建文件：

```ini
[wsl2]
# WSL2 虚拟机最多吃多少内存——本机 31.5G，给 8G 足够跑整套学习栈（表 1-2）
memory=8GB
# 给几个逻辑核——本机 16 线程给一半，IDEA/浏览器不与容器抢核
processors=8
swap=4GB
# （可选）swap 也挪到 D 盘，省 C 盘
# swapFile=D:\\wsl\\swap.vhdx

[experimental]
# 空闲时逐步把内存还给 Windows——"vmmem 进程占用居高不下"的解药
autoMemoryReclaim=gradual
# vhdx 自动回收空洞，缓解虚拟磁盘只增不减
sparseVhd=true
```

改完执行 `wsl --shutdown` 再启动 Docker Desktop 生效。

**验收**：`wsl --version` 有输出；`wsl --status` 显示默认版本为 2。

**常见坑**：笔记本休眠唤醒后容器网络异常/命令无响应——WSL 时钟漂移或网络栈卡住，`wsl --shutdown` 后重开 Docker Desktop 即可（详见 9.2 坑 2）。

## 2.2 【动作 2】安装 Docker Desktop 并完成关键设置（P0，30 min）

**做什么**：安装 Docker Desktop（WSL2 后端），完成 4 项一次性的关键设置。

**怎么做**：

```powershell
winget install Docker.DockerDesktop
# 或从 https://www.docker.com/products/docker-desktop/ 下载安装包
```

安装后启动，完成设置（Settings）：

1. **General → Use WSL 2 based engine**：勾选（默认已勾）。这就是"用 WSL2 当 Docker 的 Linux 内核"。
2. **Resources → Advanced → Disk image location**：改到 **`D:\docker\data`**。镜像和卷的虚拟磁盘默认在 C 盘，D 盘还有 483 GB，直接搬家。【本机证据：C 盘 233 GB 可用，但镜像库是增长大户，一次搬家免后患。】
3. **Docker Engine**（JSON 配置，见下）加上**镜像加速**与**日志轮转**，两件事一次配完：

```json
{
  "builder": { "gc": { "enabled": true, "defaultKeepStorage": "20GB" } },
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" },
  "registry-mirrors": [
    "https://docker.m.daocloud.io",
    "https://docker.1ms.run"
  ]
}
```

   - `log-opts`：**不给所有容器日志设上限 = 每个容器都在无限写文件**。10MB×3 个文件轮转，学习环境够用（原理与补救见【动作 12】）。
   - `registry-mirrors`：加速器候选，见【动作 3】。
4. **General → Start Docker Desktop when you sign in**：**大部分时间不用的（本文按此假设，见 2.5 节），建议不勾**——平时开机零占用，用时手动打开（冷启动 30 秒~1 分钟）；只有"每天开机就要用"才勾上。

**许可说明**【官方文档证据：docker.com/legal】Docker Desktop 对个人、教育、非商业开源、以及 **员工 <250 人且年收入 <$10M 的企业** 免费；超出需订阅。公司规模触线时改用 Podman Desktop 或 WSL2 内手装 Docker Engine（表 1-1）。

**验收**：PowerShell 执行 `docker version` 能同时看到 Client 与 Server 两段；`wsl -l -v` 里出现 `docker-desktop` 发行版且 STATE 为 Running。

## 2.3 【动作 3】配置镜像加速并验证（P0，15 min）

**为什么**：Docker Hub 在国内直连基本拉不动，而公共加速器在 2024 年后经历了大面积关停，**"能用"是一个需要每周验证的动态事实**，不是一次配置。

**怎么做**（接动作 2 第 3 步的 JSON）：`registry-mirrors` 按优先级排列候选，Docker 会依次尝试。当前（2026-10）常见的候选包括 `docker.m.daocloud.io`、`docker.1ms.run` 等社区加速器——**拉取前先验证可用性**，失效就换：

```powershell
# 验证 mirror 是否真正生效：看 docker info 里的 Mirror 列表 + 实际拉一个小镜像计时
docker info --format '{{json .RegistryConfig.Mirrors}}'
docker pull hello-world
```

三条更稳的路线（按推荐排序）：

1. **阿里云容器镜像服务个人版**：开通后获得**专属加速地址**（每人一个，比公共池稳定），配置进 `registry-mirrors`；
2. **走代理**：本机有代理时，Docker Desktop → Settings → Resources → Proxies 配置，拉取走代理出网；
3. **公司/内网制品库**：有 Nexus/Harbor 就配它，这也是企业真实形态。

**验收**：`docker run --rm hello-world` 输出 Hello from Docker!。

## 2.5 空闲时最小化占用：写给"大部分时间不用"的你（P0，10 min）

**结论先行：既然大部分时间不跑这些程序，最优配置是——Docker Desktop 不开机自启，用时手动启动；用完 `docker compose stop`；长期不用托盘 Quit。四步下来空闲占用归零，数据一根毫毛都不少。**

**先认清三个状态的真实占用**：

| 状态 | 内存 | CPU | 何时处于此状态 |
|---|---|---|---|
| 未启动 | 0 | 0 | 没打开 Docker Desktop（关自启后，平时开机即此状态）；磁盘上只有程序 ~2~3 GB 和 vhdx 数据 |
| 启动、无容器（已挂起） | Windows 侧后端几百 MB；**vmmemWSL ≈ 0** | ≈0 | 开着但 5 分钟无容器运行——托盘图标出现叶子 🌿 |
| 启动、容器在跑 | VM 基线 1~2 GB + 各容器用量（被 `memory=8GB` 封顶） | ≈0（空闲） | Docker Desktop 打开且有容器 Up |

两个机制是这套配置的底气【官方文档证据：docs.docker.com/desktop，Resource Saver】：

- **Resource Saver（默认开启，Settings → Resources → Advanced）**：5 分钟（`AutoPauseTimeoutSeconds=300`）没有任何容器在跑，自动把 Linux VM 整个挂起、内存释放到接近 0；任何 `docker` 命令到达即自动唤醒（秒级）。它是"开着忘了关"的兜底。
- **WSL2 虚拟机的按需生灭**：`vmmemWSL` 只在有发行版运行时存在；Docker Desktop 退出时 `docker-desktop` 发行版停止，若没有其他发行版在跑，整个 VM 随之消失；`wsl --shutdown` 任何时候立即清零（若装了 Ubuntu 学习发行版会被一并关掉，无损）。

**你的模式下的四步配置**：

1. **关闭开机自启**：Settings → General → 不勾 "Start Docker Desktop when you sign in"（即动作 2 第 4 条）。平时开机 0 占用，要用时手动打开。
2. **确认 Resource Saver 开着**：进设置页确认开关即可（默认开启）。它保证"忘了关"的代价只是几百 MB 后端进程，而不是几个 GB。
3. **用完就 stop，而不是"不管它"**：

   ```bash
   cd /d/code/workspace/docker-stacks/study-stack
   docker compose stop   # 容器停止（保留容器与卷）；5 分钟后 Resource Saver 自动挂起 VM
   ```

   习惯规则一句话：**学习栈"用完 stop、要用 up -d"**——`up -d` 幂等，秒级恢复，数据在命名卷里不会丢（这正是动作 9 把数据放进卷的红利）。
4. **长期不用就归零**：托盘右键 Quit Docker Desktop（后端进程也退出，内存归 0）；想连 WSL 一起清就 `wsl --shutdown`（无损，下次打开 Docker Desktop 自动重建）。

**两个不会自动消失的东西**（"不用时"唯一还在悄悄变化的资源）：

- **磁盘**：vhdx 只增不减，空闲期不会自动瘦身——治理靠动作 12 的月度体检（`docker system df` → prune → 稀疏化）；
- **自启容器**：`restart: unless-stopped` 的容器会随 Docker Desktop 启动自动起来——"不使用"必须显式 `docker compose stop`（stop 过的容器不会被 restart 策略拉起，下次 `docker compose start` / `up -d` 即回）。

**一页速查：什么时候做哪个动作**：

| 时机 | 动作 | 结果 |
|---|---|---|
| 开机 | 什么都不做（自启已关） | 0 占用 |
| 要用栈 | 打开 Docker Desktop → `docker compose up -d` | 全套就绪，数据还在卷里 |
| 用完 | `docker compose stop` | 5 分钟后 VM 自动挂起，内存 ≈0 |
| 今天不再用了 | 托盘 Quit（可选加 `wsl --shutdown`） | 内存归 0 |
| 每月一次 | 动作 12 体检三连 | 磁盘不偷偷长大 |

> 与 9.2 坑 1/坑 2 的关系：vmmem 居高不下、休眠唤醒后网络异常，`wsl --shutdown` 都是第一解法——本节的"长期不用归零"顺带把这两个坑规避在前面。

## 本章小结

- 顺序不可乱：**先 WSL2 后 Docker Desktop**，先配 `.wslconfig` 上限再装 Docker；
- 四个一次性设置决定后续所有体验：内存/核数上限（`.wslconfig`）、数据盘迁 D、日志轮转（`log-opts`）、镜像加速（`registry-mirrors`）；
- 加速器是动态资源，验证命令 `docker pull hello-world` 随时复查；
- 目录规范十分钟，救的是三个月后的你；
- 空闲最小化四步（2.5 节，按"大部分时间不用"）：**关自启 → 确认 Resource Saver → 用完 `compose stop` → 长期不用 Quit / `wsl --shutdown`**；磁盘 vhdx 不会自动缩，靠动作 12 定期治理。

# 三、阶段 1：镜像构建规范（动作 5~8）

这一章做完：任何 Spring Boot 项目都能用同一套模板构建出"分层、瘦身后、可复现"的镜像。

## 3.1 【动作 5】基础镜像选型（P0，30 min）

**怎么选**（表 1-1 的展开）：

| 基础镜像 | 基座/大小 | 适合 | 注意 |
|---|---|---|---|
| `eclipse-temurin:25-jre` ★ | Ubuntu（glibc），~200-300MB 含依赖 | 日常首选 | 最稳，调试工具全 |
| `eclipse-temurin:25-jre-alpine` | Alpine（musl），更小 | 纯 Java、追求体积 | 含 JNI 本地库（Netty native、SQLite 等）要验证 musl 兼容 |
| `bellsoft/liberica-openjre-debian:25-cds` | Debian，带 CDS 支持 | 想吃满启动加速 | Spring Boot 官方 Dockerfile 文档用的就是它 |
| distroless 系列 | 无 shell | 生产安全极致 | 没 shell，进容器排障难，本地开发不推荐 |

三条规矩：

1. **用 JRE 不用 JDK** 做运行镜像（编译交给多阶段构建里的 builder 阶段）；JDK 25 是 2025-09 发布的 LTS，你的虚拟线程笔记相关的 JEP（含 JDK 24 的 JEP 491）都已包含；
2. **tag 锁大版本**（`25-jre`），既吃安全更新又避免大版本漂移；关键产物（要长期存档/上生产的）用 **digest 锁定**：`eclipse-temurin:25-jre@sha256:...`；
3. **永远不用 `:latest`**——它随时间指向不同内容，毁掉一切可复现性。

## 3.2 【动作 6】Spring Boot 多阶段 Dockerfile 模板（P0，1~2h，核心动作）

**为什么是"多阶段 + 分层"**：Spring Boot 的 fat jar 里，依赖 jar 占 90% 体积且极少变化，应用代码只占 10% 且天天变。把两者拆进不同的 Docker 层后：**改一行代码只重建最后一层**，构建缓存与镜像拉取都从"全量"变"增量"。【官方文档证据：docs.spring.io/spring-boot/reference/packaging/container-images/dockerfiles.html——Boot 3.3+ / 4.x 官方写法，以下模板已按其 2026-10 版本核对。】

**宿主机打包 + 容器分层的模板**（`Dockerfile` 放项目根，Maven 项目；Gradle 把 `target/*.jar` 换成 `build/libs/*.jar`）：

```dockerfile
# ---- 阶段一：解压分层（官方 Boot 3.3+/4.x 写法）----
FROM eclipse-temurin:25-jre AS builder
WORKDIR /builder
ARG JAR_FILE=target/*.jar
COPY ${JAR_FILE} application.jar
# Boot 自带 tools 模式：把 fat jar 解成 dependencies / spring-boot-loader /
# snapshot-dependencies / application 四个目录，供下面按层 COPY
RUN java -Djarmode=tools -jar application.jar extract --layers --destination extracted

# ---- 阶段二：运行镜像 ----
FROM eclipse-temurin:25-jre
RUN useradd --system --create-home app
USER app                              # 非 root 运行（安全基线，见动作 15）
WORKDIR /application
# 四个 COPY 各成一层：依赖层最稳定放最前，代码层最后——顺序即缓存策略
COPY --from=builder /builder/extracted/dependencies/ ./
COPY --from=builder /builder/extracted/spring-boot-loader/ ./
COPY --from=builder /builder/extracted/snapshot-dependencies/ ./
COPY --from=builder /builder/extracted/application/ ./
ENV TZ=Asia/Shanghai \
    JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75.0 -XX:+ExitOnOutOfMemoryError -Dfile.encoding=UTF-8"
# exec 形式（JSON 数组）：SIGTERM 直达 java 进程，优雅停机的前提（见动作 13）
ENTRYPOINT ["java", "-jar", "application.jar"]
```

> **版本注意**：这是 Boot **3.3+ / 4.x** 的 `jarmode=tools` 写法（`extract --layers --destination extracted`，产出上面四个目录）。Boot **≤3.2** 用旧的 `java -Djarmode=layertools -jar app.jar extract`，产出目录名相同但命令不同——以你项目 Boot 版本为准。
>
> **syntax 指令说明**：官方示例首行还有 `# syntax=docker/dockerfile:1`，它会强制 BuildKit 每次构建联网拉取 frontend 镜像，国内网络常在此超时；本模板未用其高级语法，已省略（实测配合本地基础镜像可完全离线构建）。

**构建、运行、验收**：

```bash
mvn -q package -DskipTests                 # 宿主机打包（builder 阶段只做解压）
docker build -t demo:dev .
docker run --rm -p 127.0.0.1:8080:8080 demo:dev
curl http://localhost:8080/actuator/health  # 或任意路由
```

**变体 A——"连构建都在容器里"**（不污染本机 Maven 仓库，CI 可原样复用；依赖 BuildKit 缓存挂载，`dependency:go-offline` 的缓存层在 pom 不变时直接命中）：

```dockerfile
# syntax=docker/dockerfile:1
FROM maven:3.9-eclipse-temurin-25 AS build
WORKDIR /src
COPY pom.xml .
RUN --mount=type=cache,target=/root/.m2 mvn -B -q dependency:go-offline
COPY src ./src
RUN --mount=type=cache,target=/root/.m2 mvn -B -q package -DskipTests
# 之后接上面模板的 builder/runtime 阶段（COPY --from=build /src/target/*.jar application.jar）
```

**`.dockerignore`**（放项目根，与 Dockerfile 同级）：

```
.git
.gitignore
.idea/
*.iml
HELP.md
logs/
target/classes/
target/test-classes/
target/maven-status/
.env
```

> `.env` 必须在列——它只属于 compose 运行时，绝不进镜像（动作 15）。

## 3.3 【动作 7】标签与版本策略（P1，15 min）

规矩只有三条，建议直接写进项目 README：

1. **tag = 语义版本 + git 短 sha**：`demo:1.0.0`、`demo:1.0.0-a1b2c3d`，一条命令生成：
   ```bash
   docker build -t demo:$(git rev-parse --short HEAD) .
   ```
2. **本地开发用 `:dev`**，进仓库/上环境的用带版本 tag；`:latest` 禁用（3.1 规矩 3）；
3. **要备份或跨机分发的镜像推到远端仓库**（阿里云 ACR 个人版免费，或 Docker Hub 个人仓库），`docker push` 前先 `docker login`。

## 3.4 【动作 8】体积与漏洞自检工具化（P1，30 min）

两个工具加进流程，各一行命令：

```bash
# 体积分析：逐层看"谁占了空间"，对照 3.2 的分层检查是否生效
docker run --rm -it --mount=type=bind,src=/var/run/docker.sock,dst=/var/run/docker.sock \
  wagoodman/dive:latest demo:dev

# 漏洞扫描：trivy 扫镜像里的 CVE
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock \
  aquasec/trivy:latest image demo:dev
```

验收标准：分层模板生效的标志是——**改一行 Java 代码重新 build，日志里只有 `application` 那层在重建**；体积参考：`temurin:25-jre` 基座 + 分层 Boot 应用，成品 **250~350MB** 属正常，超过 500MB 查是不是把 JDK 打进去了。

## 本章小结

- 分层是收益最大的一步：**依赖与代码分层后，增量构建/增量拉取**，官方模板（`jarmode=tools`）照抄即可；

- dive 看"空间去哪了"，trivy 看"漏洞在哪"，都一行命令。

## 4.1 【动作 9】沉淀"study-stack"中间件栈（P0，1~2h）

**做什么**：在 `D:\code\workspace\docker-stacks\study-stack\`（动作 4 的目录）落地下面这套栈——选 MySQL/Redis/Kafka 是因为它们正好对应你 `D:\ai\db`、`D:\ai\redis`、`D:\ai\mq` 的笔记主题，容器环境即实验环境。

**`compose.yaml`**（完整可用，逐段说明见注释）：

```yaml
name: study-stack

services:
  mysql:
    image: mysql:8.4                 # 8.4 是 LTS；9.x 为创新版，学习用 LTS
    container_name: mysql
    restart: unless-stopped          # 跟随 Docker Desktop 启动自动拉起
    ports:
      - "127.0.0.1:3306:3306"        # 只绑回环：局域网访问不到（安全基线）
    environment:
      MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD}
      TZ: Asia/Shanghai
    volumes:
      - mysql-data:/var/lib/mysql    # 数据进命名卷：删容器不丢数据（原则 2）
      - ./mysql/init:/docker-entrypoint-initdb.d:ro   # 首启自动执行建库脚本
    mem_limit: 1g                    # 单服务内存上限，防止吃光 WSL2 的 8G
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "127.0.0.1", "-uroot", "-p${MYSQL_ROOT_PASSWORD}"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 30s              # 初始化期不计失败次数

  redis:
    image: redis:8.2-alpine
    container_name: redis
    restart: unless-stopped
    ports:
      - "127.0.0.1:6379:6379"
    command: ["redis-server", "--appendonly", "yes", "--requirepass", "${REDIS_PASSWORD}"]
    volumes:
      - redis-data:/data
    healthcheck:
      test: ["CMD", "redis-cli", "-a", "${REDIS_PASSWORD}", "ping"]
      interval: 10s
      timeout: 3s
      retries: 5

  kafka:
    image: apache/kafka:4.0.0        # Apache 官方镜像；4.x 只走 KRaft，单容器=broker+controller
    container_name: kafka
    restart: unless-stopped
    ports:
      - "127.0.0.1:9092:9092"
      - "127.0.0.1:29092:29092"
    environment:
      KAFKA_NODE_ID: 1
      # ⚠️ 官方镜像默认 log.dirs=/tmp/kafka-logs（易失）——必须显式指向挂载卷，否则容器重建即丢数据
      KAFKA_LOG_DIRS: /var/lib/kafka/data
      KAFKA_PROCESS_ROLES: broker,controller
      KAFKA_CONTROLLER_QUORUM_VOTERS: 1@kafka:9093
      # 双 listener：PLAINTEXT=宿主机应用直连 localhost:9092；DOCKER=容器里的应用 host.docker.internal:29092
      KAFKA_LISTENERS: PLAINTEXT://0.0.0.0:9092,DOCKER://0.0.0.0:29092,CONTROLLER://0.0.0.0:9093
      KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://localhost:9092,DOCKER://host.docker.internal:29092
      KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: CONTROLLER:PLAINTEXT,PLAINTEXT:PLAINTEXT,DOCKER:PLAINTEXT
      KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: 1
      KAFKA_TRANSACTION_STATE_LOG_MIN_ISR: 1
      KAFKA_GROUP_INITIAL_REBALANCE_DELAY_MS: 0
    volumes:
      - kafka-data:/var/lib/kafka/data
    healthcheck:
      test: ["CMD-SHELL", "/opt/kafka/bin/kafka-broker-api-versions.sh --bootstrap-server localhost:9092 >/dev/null 2>&1"]
      interval: 15s
      timeout: 10s
      retries: 5
      start_period: 30s

volumes:
  mysql-data:
  redis-data:
  kafka-data:
```

**`.env`**（与 compose.yaml 同目录，**不进 git**）：

```ini
MYSQL_ROOT_PASSWORD=改成你自己的
REDIS_PASSWORD=改成你自己的
```

**`.env.example`**（同名去密码版，**进 git**，别人克隆后照抄改名）。

几个设计点，为什么这么写：

- **`healthcheck` + `start_period`**：MySQL/Kafka 首次启动要几十秒初始化，没有健康检查时"容器 Started"≠"服务可用"；
- **`mem_limit`**：这是"迷你机房"原则的落实——WSL2 总共 8G，逐个服务封顶才不会互相挤兑；
- **端口全绑 `127.0.0.1`**：`-p "3306:3306"` 会把端口暴露给局域网（Windows 防火墙可能放行），带前缀只允许本机访问；
- **镜像 tag 以拉取时官方仓库为准**：`mysql:8.4`、`redis:8.2-alpine`、`apache/kafka:4.0.0` 是 2026-10 的锚点，执行时若有新 LTS 可平移；RocketMQ（`apache/rocketmq`，需要 namesrv + broker 两个服务）、Nacos、MinIO 等按同样模式往栈里加。


## 4.2 【动作 10】打通"应用连容器"的三种拓扑（P0，30 min）

应用和中间件谁在哪，决定了连接串写什么——三种拓扑一张表：

| 应用跑在哪 | 中间件地址写什么 | 原理 |
|---|---|---|
| 宿主机（IDEA 里启动） | `localhost:3306` 等 | compose 已把端口映射到 Windows 回环 |
| 容器（不在同一 compose） | `host.docker.internal:3306` | Docker 提供的特殊域名，指向宿主机/其他容器映射端口 |
| 容器（同一 compose 栈内） | `mysql:3306`（**服务名**） | compose 自动建网络，服务名即 DNS |

Spring Boot 开发期配置（应用跑宿主机，对应第一行）：

```yaml
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/study?serverTimezone=Asia/Shanghai
    username: root
    password: ${MYSQL_ROOT_PASSWORD}     # 密码同样走环境变量，不硬编码
  data:
    redis:
      host: localhost
      port: 6379
      password: ${REDIS_PASSWORD}
```

**把应用也交 compose 管时的联动写法**（配合 3.2 的应用镜像）：

```yaml
services:
  my-app:
    image: demo:dev
    depends_on:
      mysql:
        condition: service_healthy   # 等健康检查通过才启动应用——
      redis:                         # 只写 depends_on: [mysql] 是"容器启动"≠"服务可用"
        condition: service_healthy
    ports:
      - "127.0.0.1:8080:8080"
```

> 开发期推荐**应用跑宿主机 + 中间件在容器**：改代码重启最快，调试器直连；等应用自己也要容器化验证时（阶段 1 模板）再用后两种拓扑。Kafka 的 advertised listener 按"宿主机直连"写的，若栈内容器要连 Kafka，需另加内部 listener（见 `D:\ai\mq` Kafka 笔记的 listener 机制部分）。

## 本章小结

- compose 文件是**资产**不是脚本：健康检查、内存上限、回环端口、命名卷四件套齐了才算沉淀完成；
- `down` 保数据、`down -v` 删数据——这条肌肉记忆请现在就建立；
- 连接地址三选一看"应用在哪跑"：宿主机→localhost，跨栈容器→host.docker.internal，同栈→服务名；
- 等健康检查（`condition: service_healthy`）而不是等容器存在。

## 5.1 【动作 11】数据卷规范与备份/还原（P1，1h）

**卷的两类用法**（动作 9 已在用）：

| 方式 | 写法 | 用途 |
|---|---|---|
| 命名卷 | `mysql-data:/var/lib/mysql` | **数据库数据**——由 Docker 管理，删容器不删卷 |
| 绑定挂载 | `./mysql/init:/docker-entrypoint-initdb.d:ro` | **配置/初始化脚本**——用宿主机文件，只读挂载 |

**红线**：任何"容器运行中往容器可写层里写的数据"（比如 `docker exec` 进去手改的文件、没挂卷就写的库文件）在 `docker rm` 时**全部丢失**。判断标准一句话：**重建容器后还应该存在的东西，必须在卷里。**

**备份脚本**（存 `D:\code\workspace\docker-stacks\backup.sh`，Git Bash 执行；两种方式各有用途）：

```bash
#!/usr/bin/env bash
set -euo pipefail
STAMP=$(date +%Y%m%d_%H%M%S)
DEST=/d/code/backup                 # 动作 4 定的备份目录
mkdir -p "$DEST"

# 方式一：物理备份——直接打包数据卷，快、全量，适合学习环境随手备
docker run --rm -v study-stack_mysql-data:/src:ro -v "$DEST":/bak alpine \
  tar czf "/bak/mysql-data_${STAMP}.tgz" -C /src .

# 方式二：逻辑备份——mysqldump 导出，一致性更好、跨版本还原更稳
docker exec mysql sh -c 'exec mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" --all-databases' \
  | gzip > "$DEST/mysql_dump_${STAMP}.sql.gz"

echo "备份完成 -> $DEST"
```

**还原**（物理还原前先 `docker compose stop mysql`）：

```bash
# 物理还原：倒灌进同名卷
docker run --rm -i -v study-stack_mysql-data:/dst alpine \
  sh -c 'cd /dst && tar xzf -' < /d/code/backup/mysql-data_XXXXXXXX_XXXXXX.tgz

# 逻辑还原：
gunzip -c /d/code/backup/mysql_dump_XXXXXXXX_XXXXXX.sql.gz | \
  docker exec -i mysql sh -c 'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD"'
```

**执行频率**：学习环境手动每周一次足够；要定期化就用 Windows 任务计划程序挂 `backup.sh`（不必引 cron 体系）。

## 5.2 【动作 12】日志轮转、磁盘体检与 vhdx 收缩（P1，30min）

**日志**：轮转上限已在动作 2 的 `log-opts` 全局配好（10MB×3）。它只对**之后新建**的容器生效，老容器重建一下即可。验证：`docker inspect mysql --format '{{.HostConfig.LogConfig.Config}}'`。没有这条配置的后果：一个调试日志刷屏的应用一晚上能写满几个 GB。

**磁盘体检**（每月顺手一跑）：

```bash
docker system df              # 镜像/容器/卷/构建缓存各占多少（加 -v 看明细）
docker system prune           # 清理：停止的容器、悬空镜像、无用网络（不带卷！）
docker system prune -a        # 更狠：连没被容器引用的镜像一起清（下次构建要重拉）
docker builder prune          # 构建缓存单独清（df 里常见的大头）
```

**vhdx 只增不减的收缩**：删了镜像/卷后，Docker 里的空间释放了，但 Windows 侧 `D:\docker\data\docker_data.vhdx` 文件不会自动变小。处理链：①先 `docker system prune -a --volumes`（确认没有要保的数据！）→ ②`wsl --shutdown` → ③启用了 `sparseVhd`（动作 1）的系统大多会自动回收；仍偏大则管理员 PowerShell 执行：

```powershell
wsl --manage docker-desktop --set-sparse true   # 新版 WSL：把 docker-desktop 磁盘设为稀疏
# 或传统方案：Optimize-VHD -Path D:\docker\data\docker_data.vhdx -Mode Full（需 Hyper-V 模块，Win11 专业版可启用）
```

## 本章小结

- 数据分两类存放：**状态进命名卷、配置走绑定挂载**；重建容器后还要在的东西一律进卷；
- 备份两把刀：物理（打卷，快）与逻辑（mysqldump，稳），脚本化后各留一份；
- 日志上限是全局一次性配置（`log-opts`），漏配的代价是磁盘被日志吃穿；
- 磁盘治理节奏：`docker system df` 体检 → prune 清理 → vhdx 稀疏化/收缩。

# 六、阶段 4：Java 应用在容器里的正确姿势（动作 13~14）

这一章做完：JVM 与容器资源"互知互敬"，停机优雅，调试顺手，测试用真容器。

## 6.1 【动作 13】JVM 容器参数基线（P1，1h）

**容器感知（Container Awareness）**：JDK 10 起 JVM 默认识别 cgroup 限额（`UseContainerSupport` 默认开启），`Runtime.availableProcessors()` 和默认堆大小都按容器配额来，而不是按宿主机的 16 核 31.5G——这就是为什么容器里不配参数时 JVM"看起来变小了"。**不要用固定 `-Xmx`**，改用百分比，同一镜像就能在 1G 和 8G 限额的环境里复用：

```
-XX:MaxRAMPercentage=75.0        # 堆上限 = 容器内存限额 × 75%
-XX:+ExitOnOutOfMemoryError      # OOM 立即退出，交给 restart 策略重拉，别让僵尸堆活着
```

**配比公式**（决定 compose 里 `mem_limit` 给多少）：**容器限额 ≈ 期望堆 / 0.75 + 300~500MB**。堆之外还有元空间、直接内存（Netty）、线程栈、JIT 代码缓存——这部分不归堆管但归容器限额管，漏算的下场就是 **exit 137（OOMKilled）**：内核因超限直接杀进程。看到 137 先查 `docker inspect --format '{{.State.OOMKilled}}'`，再回头调公式两端。

**优雅停机链路**（四环缺一不可，前两环在 3.2 模板里已就位）：

1. Dockerfile 用 **exec 形式 ENTRYPOINT**（`["java", ...]`）——shell 形式会让 java 变成 shell 的子进程，收不到 SIGTERM；
2. `docker stop` 默认给 **10 秒**优雅期，compose 里显式放宽：`stop_grace_period: 30s`；
3. 应用侧接住 SIGTERM：Boot 配 `server.shutdown: graceful` + `spring.lifecycle.timeout-per-shutdown-phase: 20s`；
4. 到期 SIGKILL 兜底。

**虚拟线程注意点**（衔接 `D:\ai\jdk\虚拟线程*.md`）：JDK 25 容器里开 `spring.threads.virtual.enabled=true`（Boot 3.2+）即可；历史上"synchronized 块 pin 载体线程"的限制已被 **JDK 24 的 JEP 491** 解决，你笔记里若记录了旧版 pinning 规避手法（换 ReentrantLock 等），在 25 上大部分可以还原为普通写法；另外容器 CPU 配额会被 JVM 感知，虚拟线程的调度并行度跟 `availableProcessors()` 走。

## 6.2 【动作 14】开发体验：IDEA 集成、远程调试、Testcontainers（P1，1h）

**IDEA 集成**：Settings → Build Tools → Docker 识别 Docker Desktop 后，Services 面板可视化管理容器/镜像/ compose 栈——起停、日志、exec 都不用离开 IDE。Dockerfile 有语法补全，compose.yaml 同理。

**远程调试容器里的应用**：在 3.2 模板的 `JAVA_TOOL_OPTIONS` 上追加（或 compose 里用环境变量覆盖）：

```
-agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005
```

compose 暴露 `127.0.0.1:5005:5005`，IDEA → Run → Edit Configurations → Remote JVM Debug 指向 `localhost:5005`，断点照打。

**Testcontainers：测试直接用真容器**（衔接你 Spring 测试与 db 笔记——比 H2 内存库真实得多，Windows + Docker Desktop 下开箱即用）：

```java
@SpringBootTest
@Testcontainers
class OrderRepositoryTest {

    @Container                              // 测试启动时拉起、结束时销毁
    @ServiceConnection                      // Boot 3.1+：连接串自动注入，零配置
    static MySQLContainer<?> mysql = new MySQLContainer<>("mysql:8.4");

    @Test
    void insertAndQuery() { /* 用真 MySQL 跑的集成测试 */ }
}
```

依赖：`org.springframework.boot:spring-boot-testcontainers` + `org.testcontainers:mysql` + `junit-jupiter`。

**本章小结**

- 容器感知让 JVM 自动按限额自适应：**只给百分比（MaxRAMPercentage），不给绝对值（-Xmx）**；
- 内存公式与 exit 137 是一对因果：限额 = 堆/0.75 + 堆外余量；
- 优雅停机四环：exec ENTRYPOINT → stop_grace_period → graceful shutdown → SIGKILL 兜底；
- 调试就是暴露 5005 + Remote JVM Debug；集成测试交给 Testcontainers + @ServiceConnection。

# 七、阶段 5：安全基线（动作 15）

这一章做完：镜像扫过漏洞、容器以最小权限跑、密钥不落在任何会进 git 的地方。学习环境不追求零风险，但这四条是"顺手就该做对"的。

## 7.1 【动作 15】四条基线（P1，1h）

1. **镜像层**：`trivy` 扫描进构建后置步骤（命令见动作 8）；基础镜像每月重拉重建一次（`docker build --pull`），让 CVE 修复随基座更新进来；Docker Desktop 自带的 Docker Scout 可作补充视图。
2. **进程权限**：模板已带 `USER app`（非 root）；更严的场景加 `read_only: true` + `tmpfs: [/tmp]`（根文件系统只读，写路径显式声明）；`--privileged` 与 `cap_add: SYS_ADMIN` 属于"知道自己在干什么才用"。
3. **网络面**：所有端口映射带 `127.0.0.1:` 前缀（动作 9 已做）；**永不**勾选 Docker Desktop 的 "Expose daemon on tcp://localhost:2375"——等于把 root 等价权限暴露给本机任意进程；要远程管理用 `docker context`（8.3 节），走 SSH 加密。
4. **密钥管理**：`.env` 进 `.gitignore`、`.env.example` 进 git（动作 4/9 已搭好骨架）；密码不出现在 Dockerfile（镜像层可被 `docker history` 翻出来）、不出现在 README、不出现在聊天记录；一个栈一套密码，别复用。

## 本章小结

- 习惯四件套：**扫镜像、非 root、绑回环、密钥走 .env**；
- 镜像层是"可被翻出来的"，`docker history` 能看到每一层干了什么——秘密永远别进镜像；
- 2375 端口是 Windows 上最常见的"自伤型"配置，记成禁手。

## 8.1 【动作 16】kind 单机 K8s 实验环境（P2，1~2h）

**选型**（本地跑 K8s 的四种方式）：

| 方案 | 特点 | 适合 |
|---|---|---|
| **kind** ★ | K8s 官方 CI 同款，每个节点=一个容器，秒级建删 | 学 K8s 本体、验证 YAML |
| k3d | k3s 套壳，更轻，自带 Traefik | 资源敏感、想要开箱 ingress |
| Docker Desktop 内置 K8s | 一键开关，零配置 | 只想快速有个 API Server |
| minikube | 驱动多样（docker/hyperv…），功能全但偏重 | 需要 addons 生态时 |

**为什么推荐 kind**：它吃你现有的 Docker Desktop，节点即容器，配合你 `D:\ai\k8s\k8s介绍.md` 与 `iptables.md` 的学习——坏了一分钟重建一个集群，比"怕弄坏"的共享环境学习效率高得多。

```yaml
# kind-config.yaml —— 1 控制面 + 1 工作节点，NodePort 暴露到宿主机
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: lab
nodes:
  - role: control-plane
    extraPortMappings:
      - containerPort: 30080
        hostPort: 30080
  - role: worker
```

```bash
winget install Kubernetes.kind    # 或从 kind.sigs.k8s.io 安装
kind create cluster --config kind-config.yaml
kubectl get nodes                 # 双节点 Ready
kubectl apply -f <你的实验清单>    # 从 k8s 笔记里挑 Service/Deployment 实验开始
kind delete cluster --name lab    # 坏了就删，重建只要一分钟
```

注意：kind 集群与 compose 栈共享 WSL2 的 8G 预算——跑集群当天建议 `docker compose stop` 中间件栈腾内存。

## 8.2 【动作 17】可观测栈（P2，1~2h）

**指标三件套**（新栈 `docker-stacks/monitor/compose.yaml`；镜像 tag 执行时按官方仓库锁定当前稳定版）：

- **cAdvisor**：采集所有容器的 CPU/内存/网络指标（挂 docker.sock 只读）；
- **Prometheus**：拉取与存储，`scrape_configs` 加 `targets: ['cadvisor:8080']`；
- **Grafana**：可视化，导入社区容器监控面板（ID 14282 系列即可用）。

**链路追踪**（衔接 `D:\ai\cncf\OpenTelemetry.md`、`opentelemetry-javaagent.md`）：Java 应用挂上你笔记里研究过的 javaagent，OTLP 数据先发宿主机：

## 8.3 不装新东西的进阶：远程 context（混合模式）

对应 1.2 的场景 (a)——容器实际在远程服务器上。本机装好 Docker CLI 后（Docker Desktop 自带），**一条命令把远程 Docker 变成本地的一个"上下文"**，`docker`/`docker compose` 全部命令无缝切换目标：

```bash
docker context create prod --docker "ssh://user@你的服务器IP"
docker context use prod        # 之后所有 docker 命令都打在远程机上
docker context ls
docker context use default     # 切回本地
```

本地（default）与远程（prod）两套环境并存：本地写码验证，远程部署观察，同一个镜像 tag 两边通用。

- 可观测从"指标三件套 + 一个 agent"起步，复用你已有的 OTel 笔记；
- `docker context` 零成本打通"本地开发 + 远程部署"，这在服务器上已有容器时是性价比最高的一步。

## 9.2 常见坑 Top 12

| # | 现象 | 根因 | 解法 |
|---|---|---|---|
| 1 | `vmmem` 进程内存居高不下，IDEA 变卡 | WSL2 吃了内存不主动还 | `.wslconfig` 配 `autoMemoryReclaim=gradual` + `memory=8GB`（动作 1）；`wsl --shutdown` 立即释放 |
| 2 | 休眠唤醒后容器网络不通/命令卡死 | WSL 时钟漂移、网络栈卡住 | `wsl --shutdown` 后重开 Docker Desktop |
| 3 | C 盘空间莫名缩水 | docker vhdx 默认在 C 盘且只增不减 | Disk image location 迁 D（动作 2）+ sparseVhd/收缩（动作 12） |
| 4 | `docker pull` 超时 | 加速器失效（常态事件） | 换 mirror 候选 / 走代理 / 阿里云专属地址（动作 3） |
| 5 | 容器秒退，`exit 137` | 内存超限被内核 OOMKilled | `docker inspect --format '{{.State.OOMKilled}}'` 确认；调 `mem_limit` 与 MaxRAMPercentage 配比（动作 13 公式） |
| 6 | 容器时间差 8 小时 | 默认 UTC | compose 里 `TZ: Asia/Shanghai`；alpine 基座另装 tzdata |
| 7 | 容器里的应用连不上"localhost 的中间件" | 容器里的 localhost 是它自己 | 用 `host.docker.internal`（4.2 拓扑表第二行） |
| 8 | `depends_on` 了还是"连不上库" | 只等了"容器启动"没等"服务就绪" | healthcheck + `condition: service_healthy`（动作 9/10） |
| 9 | bind mount 下 devtools 热重载不触发 | Windows 文件事件不跨进 WSL2 VM | IDE 编译触发重启，或 `docker compose watch` 同步；接受"重启容器"作为兜底 |
| 10 | 挂进容器的 .sh 报 `\r: command not found` | Windows CRLF 行尾 | `.gitattributes` 加 `*.sh text eol=lf`；已存在的文件重新转存 |
| 11 | `docker compose down -v` 之后数据没了 | `-v` 连命名卷一起删 | 恢复自备份（动作 11）；日常只 `down`，`-v` 只用于刻意重置 |
| 12 | 开 VPN 后 WSL2 里 DNS 解析失败 | VPN 接管 DNS 与 WSL 默认 NAT 冲突 | `.wslconfig` 加 `networkingMode=mirrored`，或 WSL 内 `/etc/wsl.conf` 关闭自动 resolv.conf |

```bash
docker image ls / docker rmi <img>
```
