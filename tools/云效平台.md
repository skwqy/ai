# 一、总览：云效的定位、设计理念与能力全景

## 1.1 一句话定位

**云效（Yunxiao）是阿里云推出的企业级一站式 DevOps / BizDevOps 平台**：覆盖"需求 → 开发 → 测试 → 发布 → 运维"软件研发全生命周期，以 SaaS（公共云）为主、专有云/混合云可选，并叠加 AI 能力（AI 代码评审、MCP Server、通义灵码联动），目标是帮助企业实现"研发敏捷 + 组织敏捷"（官方称之为"双敏"组织）。

它解决的不是某一个单点问题，而是**研发工具链的割裂问题**：需求在一个工具、代码在另一个、CI 在 Jenkins、制品在 Nexus、度量靠人肉 Excel——账号不通、数据不通、流程断点。云效把这条链路装进一个组织账号里，让需求、代码、构建、制品、部署、度量天然串成一条数据链。

规模参考：官方口径"十万企业、百万开发者"，承载阿里巴巴"百万级代码库、数万工程师协作"，历经多次双十一大促验证；IDC 评测中云效产品能力排名第一（官网援引）。

## 1.2 设计理念：读全文前先记住六句话

1. **一站式、开箱即用**。免搭建、免运维，注册组织即用；项目协作、代码、CI、制品、测试、度量一套账号打通，不用自己拼 Jenkins + GitLab + Nexus + Jira。
2. **BizDevOps：业务与研发一体**。Projex 把需求管理（业务侧）和迭代执行（研发侧）放进同一平台，主打"精益需求协作 + 敏捷交付"，而不只是程序员的工具。
3. **云原生优先**。流水线对接 ACK/ACR/SAE/ECS/OSS，AppStack 以应用为中心管理 K8s 交付，官方把"云原生时代新 DevOps 平台"作为自我定位。
4. **AI 原生**。AI 不是外挂而是内嵌：Codeup 内置 AI 代码评审，平台提供 MCP Server 让通义灵码、Cursor、Claude 等 AI 助手直接操作云效（查工作项、读代码、提 MR、跑流水线）。
5. **源自阿里巴巴自研实践**。内部研发协同平台（Aone 体系）多年打磨后对外商业化，多副本高可用、大促级稳定性是它的底色。
6. **SaaS 为主、私有化可选**。公共云多地域开服（含上海站），政企客户可走专有云（Apsara Stack/飞天企业版）/混合云形态，支持 VPC 内访问，满足信创与等保诉求。

## 1.4 模块协同：一条需求到发布的完整链路

云效各模块不是简单并列，而是围绕"一条需求的旅程"环环相扣：

```
产品/业务                    研发                          质量与运维
────────                   ────────                      ──────────
Projex 创建需求 ──► 关联代码分支（Codeup）──► Flow 流水线构建 ──► Packages 存制品
     ▲                        │                    │                 │
     │                        │ 智能评审+代码检测      │ 单测/扫描/安全扫描 │
     │                        ▼                    ▼                 ▼
     └── 缺陷回流 ◄──── 合并请求 MR ────────── 测试管理 Testhub    AppStack/Flow 部署
            （Testhub 发现缺陷一键回流 Projex）                 （K8s/主机/蓝绿/金丝雀）
                                     │
                                     ▼
                          效能洞察 Insight 全程采集（需求吞吐/交付周期/质量）
                                     │
                  AI 层贯穿全程：AI 评审 / MCP 让 AI 助手操作以上任一环节
```

关键协同点：

- **需求 ↔ 代码**：Codeup 分支/提交可一键关联 Projex 的工作项；变更（MR）可关联需求，状态自动更新（AppStack 变更管理也复用此机制）。
- **代码 ↔ 流水线**：Codeup 提交可自动触发 Flow 流水线，流水线构建产物直接推入 Packages，元数据一路传递。
- **测试 ↔ 项目**：Testhub 测试发现的缺陷一键提交进 Projex 迭代，形成"需求 → 用例 → 缺陷 → 修复 → 验证"闭环。
- **度量 ↔ 全链路**：Insight 不需要单独埋点，直接消费 Projex/Codeup/Flow/Testhub 的过程数据出报表。

## 1.6 发展沿革（简要）

- 云效源于阿里巴巴内部自研的研发协同平台体系（Aone 一脉），先在阿里内部支撑"百万级代码库、数万工程师、双十一大促"的 extreme 场景，后对外商业化。

# 二、项目协作 Projex：研发管理的"驾驶舱"

## 2.1 模块定位

Projex 是云效的新一代企业级研发协作平台，承载 BizDevOps 理念中的"业务侧"：让产品经理、开发、测试在同一个平台上管理需求、规划迭代、跟踪缺陷。定位类似 Jira + TAPD，但内嵌了阿里巴巴敏捷研发实践，且与云效工程链路（Codeup/Flow/Testhub）天然打通。

## 2.2 核心能力

### 2.2.1 项目模板与研发场景

支持多种项目模板，覆盖三种典型研发模式：

- **Scrum 敏捷项目**：迭代制，需求 → 迭代 → 站会看板 → 燃尽图，适合快速变化的产品团队。
- **看板项目**：持续流动式管理，适合运维、客服、运营类持续需求流。
- **瀑布/经典项目**：阶段制管理，适合流程规范要求强的传统项目。

官方强调其集成了敏捷研发项目管理的最佳实践（如每日站会的看板用法、迭代回顾报表等均有配套功能与指南）。

### 2.2.2 工作项体系

以"工作项"为统一抽象：**需求、任务、缺陷**等多种类型，支持：

- 多层级分类组织（如缺陷分类最多支持 9 个层级）；
- 自定义工作项类型、字段与流转状态，适配企业自己的流程规范；
- 工作项之间建立关联（需求拆任务、缺陷挂需求）。

### 2.2.3 迭代管理与看板

- 迭代规划：把需求/任务拖入迭代，指派负责人与排期；
- 迭代看板：拖拽流转状态，每日站会直接投屏；
- 迭代概览：进度、**缺陷趋势图**、"存量缺陷按成员排名"等指标卡，站会与迭代回顾直接用。

### 2.2.4 统计与报告

提供项目/迭代/成员多维度统计报表（需求吞吐、缺陷分布、进度偏差等），管理者视角看交付节奏；个人统计在基础版可用，企业级效能分析归入高级版（见第八章 Insight 与第十二章）。

### 2.2.5 与工程链路的串联

- Codeup 的分支、提交、合并请求可关联工作项，代码动态回流到需求视图；
- Testhub 的测试计划关联需求，缺陷一键回流迭代；
- AppStack 的变更单关联需求，状态自动更新；
- 与钉钉深度集成：工作项动态、任务提醒、审批可触达钉钉，组织架构同步。

## 2.3 本章小结

Projex 解决"研发管理无平台"的问题：以工作项为原子、以迭代为节拍、以看板和报表为界面，把业务需求到研发执行的协作搬上同一平台。它的差异化不在功能多，而在**与代码、测试、交付、度量链路的原生打通**——需求不再只是 Excel 里的一行字，而是能一路追踪到代码、制品和线上版本的数据实体。

# 三、代码管理 Codeup：代码资产的保险柜

## 3.1 模块定位

Codeup 是云效的企业级代码托管平台（基于 Git），定位是"安全、稳定、高效的代码托管和研发管理"。官方称其源自阿里自研技术、支撑阿里百万级代码库与数万工程师协作，强调把企业代码资产当作最高价值资产来保护。

## 3.2 核心能力

### 3.2.1 代码托管

- 稳定 Git 托管，**多副本高可用架构**；
- 一键导入第三方 **Git/SVN 仓库**，提交历史完整保留（存量迁移友好）；
- 配套 WebIDE：浏览器内直接读码、改码，配合评审使用；
- 分支与提交规范管理：保护分支、强制评审等分支策略可配置。

### 3.2.2 代码评审

- 灵活定制评审规范（谁评审、多少通过、是否强制）；
- **冲突智能检测**，降低合并冲突成本；
- **AI 智能评审**（详见第十章）：AI 代码评审助手、合并请求标题/描述自动生成、评审对话。

### 3.2.3 代码检测（开箱即用四类扫描）

| 检测类型 | 防什么 |
|---|---|
| 敏感信息检测 | 密码、AK/SK、密钥误提交 |
| 代码规约检测 | 编码规范（阿里 Java 规约体系一脉相承） |
| 编码安全检测 | 常见安全漏洞模式 |
| 三方依赖漏洞检测 | 引入的开源组件已知漏洞（SCA 思路） |

### 3.2.4 权限与协作

- **企业 → 项目 → 代码库 → 人员四级精细化权限**；
- 一键串联 Projex 的需求/任务/缺陷（代码动作可关联工作项）；
- 可视化效能统计：提交贡献、合并动态报表；
- 与 Packages、Testhub、Flow 同账号打通，Codeup 内置 CI 入口（本质是调用 Flow 流水线）。

## 3.3 代码资产安全（差异化卖点）

- **删库保护**：防止恶意或误操作的大规模删除；
- **外包管控**：外包人员访问代码的受限模式（只给该看的、留痕可审计）；
- 风险运营体系：**事前监测、事中通知、事后审计**；
- IP 白名单访问控制、定时备份、代码加密存储；
- 支持站点仅 VPC 内部访问（企业代码不暴露公网）；
- 平台侧：阿里云高防、等保 2.0 三级、ISO 27001/ISO 9001。

## 3.4 本章小结

Codeup = GitLab 的托管能力 + 安全加固 + 阿里实践。三个记忆点：**多副本高可用**（稳定性）、**开箱即用的四类代码检测**（安全性）、**删库保护与外包管控**（企业级管控）。对从自建 GitLab 迁移的团队，SVN/Git 一键导入 + 历史保留是迁移动作里最实际的关怀。

# 四、流水线 Flow：CI/CD 引擎

## 4.1 模块定位

Flow 是云效的企业级自动化研发交付流水线，官方表述为"持续集成、持续验证、持续发布"三段能力，对应 CI/CD 中的构建 → 测试/扫描 → 部署发布全流程。对标 Jenkins/GitLab CI，但是 SaaS 托管：构建机由阿里云托管，免搭建免运维。

## 4.2 核心能力

### 4.2.1 流水线源（从哪里开始）

- 支持云效 Codeup 仓库作为流水线源（同账号无缝）；
- 支持第三方代码源（GitHub、GitLab、Gitee 等主流平台）接入触发。

### 4.2.2 持续集成（构建）

- 主流语言与技术栈开箱支持：**Java、Node.js、Python** 等（Java 生态最全，含 Maven/Gradle 构建上传）；
- **镜像构建**：Docker 镜像构建并推送 ACR（阿里云容器镜像服务）；
- 构建环境托管：公共构建集群开箱即用；**VPC 构建集群**（新版能力）支持在企业 VPC 内执行构建；
- 自定义构建镜像：带自己的工具链环境跑构建。

### 4.2.3 持续验证

- 内置**代码扫描、安全扫描**节点；
- 集成各类**自动化测试**（单元测试报告与质量门禁思路）；
- 测试不过、扫描不过可卡住流水线，禁止往下走。

### 4.2.4 持续发布（部署）

- **主机部署**：主机组管理 + 部署脚本，面向阿里云 ECS 及自有主机（IDC）；
- **Kubernetes 部署**：对接 ACK/自建 K8s 多账号多集群，配合 ACR 镜像做容器 CD；
- **SAE 部署**：Serverless 应用引擎场景（免运维 K8s 的落地方式）；
- **发布策略**：蓝绿、分批、金丝雀（灰度）发布，支持**快速回滚**；
- 与 ECS、ACK、ACR、OSS、SAE 等阿里云产品原生集成（服务连接/授权打通）。

### 4.2.5 流程编排与管控

- **可视化编排**：拖拽式编辑流水线，任务可串行、可并行，自定义研发发布流程；
- **人工卡点/审批**：关键阶段（如上线生产）插入人工审批；
- 触发方式：代码提交触发、手动触发、定时触发等；
- 消息触达体系：构建/部署结果通知到钉钉等渠道。

### 4.2.6 企业级管理

- **企业流水线模板**：把标准流程沉淀为模板，新应用一键套用；
- **流水线批量管理**：多流水线统一治理（批量启停、模板升级思路）；
- 精细化权限管控：谁可编辑、谁可执行、谁可审批分级设置。

## 4.3 规格配额（与计费挂钩，详见第十二章）

- 基础版：流水线最大并发 **3**，运行时长 **3000 核分/月**；
- 高级版：构建并发**弹性伸缩**、时长不限；
- 可叠加资源包扩容（如 10000 分钟/月包）。

## 4.4 本章小结

Flow 是云效的"发动机"：源（Codeup/第三方 Git）→ 构建（Java/Node/Python、镜像）→ 验证（扫描/测试门禁）→ 发布（主机/K8s/SAE、蓝绿/分批/金丝雀/回滚），全程可视化编排、可插人工审批。相比 Jenkins，它卖的是**免运维 + 与阿里云资源原生打通 + 企业模板治理**；相比 GitHub Actions，它对国内网络、国内云资源（ACK/SAE/ECS）和钉钉协同更友好。

# 五、制品仓库 Packages：研发资产的物流中枢

## 5.1 模块定位

Packages 是 SaaS 化的企业私有制品仓库（对标 Nexus/Artifactory/Verdaccio），托管二方/三方依赖与构建产物，口号"造企业级私有制品库，全面保障制品安全"，强调便捷打通 CI/CD。

## 5.2 核心能力

- **仓库类型**：通用制品仓库 + **Maven / Npm / PyPI / NuGet** 私有仓库（Java 后端团队的 Maven 私服是最高频用法）；
- **仓库代理与依赖加速**：可代理公共仓库、连接阿里云公共镜像仓库，显著提升依赖下载速度（国内网络下的实际刚需）；
- **CI/CD 元数据串联**：与 Flow 流水线全面打通，通过元数据把"哪条流水线、哪个提交、产出了哪个制品"一路记录，制品可追溯；
- **权限与安全**：组织级精细化仓库权限（上传/下载分离）、IP 白名单访问控制；
- 免搭建免运维，注册即享 10 GiB 免费存储。

## 5.3 本章小结

Packages 解决两个朴素问题：**依赖下载慢**（代理公共仓库 + 阿里云内网加速）和**二方包治理**（私有仓库 + 权限 + 元数据追溯）。对 Java 团队，它替代的就是内网 Nexus；差异化在于与 Flow/Codeup 的元数据级打通——制品不是孤立的文件，而是带着"谁构建的、来自哪次提交"的追溯链。

# 六、测试管理 Testhub：测试人员的武器库

## 6.1 模块定位

Testhub 是云效的测试用例与测试过程管理平台，解决"用例写 Excel、共享靠邮件、进度靠口头"的传统测试协作问题，官方称其为测试人员的专属"武器库"。

## 6.2 核心能力

- **测试用例库**：分组创建/编辑/**批量导入**，统一规范编写（用例等级、维护人），层级分类组织，**用例可复用**沉淀为团队资产；
- **测试计划**：为迭代规划用例，把测试任务分配给开发/测试人员，进度可视化；
- **需求驱动测试设计**：测试计划关联 Projex 需求，从需求阶段即设计测试（"需求 → 测试 → 反馈"一体化）；
- **缺陷管理联动**：执行测试发现缺陷**一键提交**并纳入 Projex 迭代，随时看测试进度、预防延期；
- **可视化质量报告**：工时与缺陷统计，按迭代版本回溯质量表现；
- 沉浸式执行界面：按计划逐条执行用例并记录结果。

## 6.3 本章小结

Testhub 补上 DevOps 链路里最容易缺失的一环——**测试过程数字化**。它的价值公式：用例库（资产复用）+ 测试计划（进度透明）+ 需求关联（覆盖可视）+ 缺陷联动（闭环回流）。单独用是"更好用的用例表格"，与 Projex/Codeup 一起用才是完整质量闭环。

# 七、应用交付 AppStack：以应用为中心的交付平台

## 7.1 模块定位

AppStack 是云效的**云原生应用交付平台**（起步于公测），与 Flow 的区别是：Flow 以"流水线"为中心（一次构建发布动作），AppStack 以"应用"为中心（应用全生命周期的环境、编排、部署、版本管理）。价值主张三个词：**高效**（开发者自运维）、**安全**（研发运维策略集中管控）、**规范**（标准化交付流程）。

## 7.2 核心能力

- **应用管理**：**应用模板**统一定义代码库、流水线、环境编排，一键从模板创建应用；人员权限随模板批量配置；
- **研发流程管理**：自定义开发/测试/生产阶段的构建部署流程，支持**人工卡点与阶段准入规则**；
- **变更管理**：落地分支开发模式——多个 feature 分支自动合并到 release 分支集成测试；**变更关联需求**，状态自动更新；
- **环境管理**：基于应用**编排**（K8s 原生编排及 **OAM 开放应用模型**，支持 YAML/Helm Chart 导出）一键拉起环境；**变量组**实现多环境差异化管理（同应用不同配置）；环境全生命周期：创建、运维、锁定、销毁；
- **部署运维**：**滚动升级、分批部署**，过程可观察可干预，**一键暂停/回滚**；一键扩缩容；容器日志、登录、重建等排障辅助；
- **版本管理**：版本追溯、对比、回滚，强调"回滚完整无遗漏"（不是只回滚镜像，而是整套编排与配置）。

## 7.3 支持的部署形态

- Kubernetes（ACK、自建集群），编排格式支持 YAML / Helm Chart，支持 **OAM** 模型；
- 主机环境部署；
- **多云**：阿里云之外的其他云厂商、自建机房均可纳管（跨云部署）。

## 7.4 本章小结

AppStack 的心智模型：**应用是长期资产，环境是应用的一个实例**。它把"某个应用在测试环境长什么样、怎么部署、现在跑哪个版本、如何回滚"变成平台上可管理的对象，特别适合**应用数量多、环境多套（日常/预发/生产）、部署频繁**的团队。官方宣传"十分钟从提交到部署"。简单场景只用 Flow 也够；多环境治理诉求上来后 AppStack 是升级路径。

# 八、效能洞察 Insight：研发效能的仪表盘

## 8.1 模块定位

Insight 是云效的交付过程观测与研发效能度量分析平台（高级版能力为主），回答管理层的三个问题：**交付快不快（流动效率）、资源用得好不好（资源效率）、质量稳不稳（质量保障）**。

## 8.2 核心能力

- **交付过程度量**：从计划、执行、风险等 **6 个方面**度量过程，跟进计划与执行、及时暴露偏差；
- **团队资源可视化**：人力分配、工作负荷、产出效率，辅助调配人力；
- **效能度量分析**：基于专业效能模型客观评价团队，改进可量化；
- **权威度量解读**：为指标/报表提供系统解读与场景化度量方案设计建议（避免"度量变 KPI"的经典坑，官方明确强调）；
- **报表能力**：**50+ 度量图表**覆盖软件交付全生命周期，报表可扩展、可自定义；
- **场景模板**：**8 大场景化专家实践模板**（含跨项目、交付效能分析等），零配置开箱即用。

## 8.3 本章小结

Insight 的差异化不是图表多，而是**自带度量方法论**：8 个场景模板 + 指标解读，直接回答"该看什么指标、指标异常说明什么"。基础版仅有个人/项目内统计；企业级效能分析、跨项目模板属于高级版专属——这也是高级版 618 元/人/年最核心的价值点之一。

# 九、知识库 Thoughts 与云端开发 DevStudio

## 9.1 知识库 Thoughts

企业级研发知识管理应用，定位"一站式研发文档协作与安全私库"：

- **多人实时协作编辑**，研发知识沉淀为企业核心资产；

## 9.2 云端开发 DevStudio

面向云原生场景的 **WebIDE**：浏览器打开即获得接近本地 IDE 的开发体验。

- 预置多种主流技术栈开发环境；
- 在线编辑、调试、运行、部署云端代码；
- 代码智能补全等智能编码能力。

> 说明：DevStudio 在云效官网产品家族列表中可见，但公开帮助文档相对较少，功能开放节奏以官网为准；它定位上与 GitHub Codespaces 类似，与 Codeup/Flow 打通可形成"云端开发 → 评审 → CI/CD"的闭环。

## 9.3 本章小结

Thoughts 解决"知识散落在个人脑子和聊天记录里"，DevStudio 解决"本地环境配置重、开发环境不一致"。两者都是锦上添花的模块：Thoughts 适合所有团队，DevStudio 更适合云原生新项目与外包/远程协作场景。

# 十、AI 能力体系：从 DevOps 到 AI 原生研发

## 10.1 AI 代码评审（Codeup 内置）

- **AI 代码评审助手**：合并请求自动触发 AI 评审，给出评审意见，显著缩短 Code Review 时间；
- **自定义评审规则**：企业可定义 AI 评审关注的规则（团队规范落地到 AI）；
- **合并请求标题/描述自动生成**：按 diff 自动撰写 MR 标题与描述；
- **智能对话**：评审过程中可与 AI 对话追问。

## 10.2 云效 MCP Server（开放给所有 AI 助手的操作面）

云效把整个平台 API 封装成 MCP（Model Context Protocol）服务并开源（`aliyun/alibabacloud-devops-mcp-server`），共 **194 个工具、8 大类**：

| 类别 | 覆盖能力 |
|---|---|
| 组织管理 | 组织、部门、角色、成员信息 |
| 项目协作 | 项目、工作项、字段、评论、工时 |
| 代码管理 | 仓库、分支、合并请求、文件树 |
| 流水线 | 流水线、任务、资源、标签、部署 |
| 制品仓库 | 仓库、制品列表 |
| 应用交付 | 部署单、应用、变量组 |
| 测试管理 | 用例、用例目录、测试计划、测试结果 |

接入后，AI 助手可用自然语言"查工作项、读代码、提合并请求、跑流水线"，以你的身份（PAT/OAuth 授权）执行。

**接入方式**（两种）：

```jsonc
// 方式一：远程托管（推荐，免安装；支持 OAuth 的客户端如 Claude Code/Qoder 可免 Token）
{
  "mcpServers": {
    "yunxiao": {
      "url": "https://openapi-rdc.aliyuncs.com/ai/mcp",
      "headers": { "Authorization": "Bearer <你的访问令牌>" }
    }
  }
}

// 方式二：本地 stdio（需 Node.js ≥ 20）
{
  "mcpServers": {
    "yunxiao": {
      "command": "npx",
      "args": ["-y", "alibabacloud-devops-mcp-server"],
      "env": { "YUNXIAO_ACCESS_TOKEN": "<你的访问令牌>" }
    }
  }
}
```

支持按 `toolsets` 参数只启用部分工具集；专有云/Region 站换专属域名即可。

## 10.3 与通义灵码的联动（全流程自动化）

通义灵码（阿里云智能编码助手）2025 年起进入智能体模式（自主决策、环境感知、工具使用），与云效 MCP 组合形成官方宣传的完整自动化链：

**需求/任务（Projex）→ AI 生成代码 → 推送 Codeup → 触发 Flow 流水线 → 创建合并请求（AI 评审）**

即从"拿到一个工作项"到"提完 MR 等人审"，AI 可以端到端完成；人只做确认与把关。

## 10.4 本章小结

云效 AI 体系分三层：**单点 AI**（代码评审、MR 描述生成）→ **平台 AI 化操作面**（MCP Server 让任意 AI 客户端操作云效）→ **端到端 AI 研发流**（通义灵码智能体 + MCP 全链路自动化）。思路很清晰：不绑定单一 AI 客户端，而是把平台能力 MCP 化——用 Cursor、Claude Code、通义灵码都能接。

# 十一、平台底座：组织权限、集成开放与安全合规

## 11.1 组织与权限

- 以**组织**为顶层容器（企业注册即建组织），成员、部门管理；
- **四级精细化权限**：企业 → 项目 → 代码库 → 人员（Codeup 为例，各模块类似）；
- 离职员工权限自动回收（Testhub 页面明确提及）；
- 外包管控模式：外包成员受限访问 + 行为留痕。

## 11.2 集成与开放

- **身份源与单点登录**：钉钉（深度集成：组织架构同步、消息通知、审批触达）、飞书、Okta；
- **消息触达**：流水线结果、工作项动态等推送钉钉等渠道；
- **OpenAPI**：平台能力开放 API，支持个人访问令牌（PAT）调用；
- **Webhook/触发器**：代码提交、定时、手动等触发研发动作；
- **MCP Server**（见第十章）与**开源仓库**（alibabacloud-devops-mcp-server）；
- 官方方案级集成：云效 + Kubernetes、云效 + ECS、云效 + 钉钉。

## 11.3 安全与合规

- **认证**：公安部等保 2.0 三级、ISO 27001 信息安全、ISO 9001 质量管理；
- **网络**：站点与代码仓库可配置仅 VPC 内访问；IP 白名单；
- **数据**：定时备份、代码加密存储、阿里云高防；
- **审计**：风险"事前监测、事中通知、事后审计"体系；产品安全白皮书公开。

## 11.4 部署形态

| 形态 | 说明 | 适合 |
|---|---|---|
| 公共云 SaaS | 多地域开服（含上海站），注册即用 | 绝大多数团队 |
| 专有云 | 随 Apsara Stack/飞天企业版部署，与公共云同根同源 | 政企、金融、大型集团 |
| 混合云 | 公共云 + 专有云组合 | 有过渡诉求的集团 |
| VPC 内访问 | 公共云站点限定 VPC 网络内可达 | 对暴露面敏感的企业 |

国产化属性：官方明确宣传"国产化平台，满足信创评估标准及信息安全监管"。

## 11.5 本章小结

底座决定了云效"能不能进企业"：钉钉/飞书/Okta 身份打通解决账号问题，四级权限 + 权限自动回收解决治理问题，等保/ISO + VPC + 加密 + 审计解决合规问题，三种部署形态解决"数据放哪"的问题。对政企客户，这一章的清单往往比功能清单更先被评审。

## 12.3 本章小结

# 十三、适用场景与选型建议

## 13.1 什么团队适合云效

| 团队画像 | 契合点 |
|---|---|
| 初创/小团队（预算敏感） | 基础版 0 元不限人数，Projex + Codeup + Flow 免费闭环 |
| 使用钉钉协作的国内企业 | 身份源/消息/审批钉钉原生打通 |
| Java 技术栈 + 阿里云基础设施 | Maven 私服、Java 构建链、ACK/SAE/ECS 部署全是原生路径 |
| 政企/金融（合规驱动） | 专有云/混合云、等保三级、信创口径、审计体系 |
| 想引入 AI 研发的团队 | AI 评审 + MCP Server + 通义灵码，一套组合拳 |

## 13.2 与自建工具链/其他平台的对比

| 维度 | 云效 | 自建（GitLab+Jenkins+Nexus+Jira） | GitHub Copilot 系 |
|---|---|---|---|
| 上手成本 | 低（注册即用） | 高（搭建、升级、备份全自理） | 低 |
| 链路打通度 | 全家桶原生打通，元数据贯穿 | 靠插件/脚本粘合 | GitHub 生态内打通 |
| 国内网络/合规 | 友好（信创、等保、VPC、专有云） | 取决于自建部署 | 公共云在境外，合规需评估 |
| 定制自由度 | 中（OpenAPI/MCP，但核心闭源） | 高（全开源可改） | 中 |
| 深度绑定风险 | 绑定阿里云生态（ACK/ACR/钉钉联动最佳） | 无 | 绑定 GitHub/Azure 生态 |
| 成本模型 | 免费起步 + 按人订阅 + 按量资源 | 人力运维成本为主 | 按席位订阅 |

一句话：**云效的强项是"国内企业 + 阿里云/钉钉生态 + 全链路一站式 + 合规"，弱项是平台本身闭源、深度定制不如自建**。

> 深入阅读：自建 GitLab+Jenkins 路线的架构、规格、运维账单与两条路线的正面对比、选型决策，见同目录《云效与自建GitLab+Jenkins对比.md》。

## 13.3 给 Java 团队的落地建议（Spring Boot 项目全流程）

一个 Spring Boot 微服务项目用云效跑通全链路的最短路径：

1. **Projex** 建 Scrum 项目，录入需求并拆迭代（或先用看板模板轻量管理）；
2. **Codeup** 建 Maven 代码仓（或从 GitLab/SVN 导入），配置分支保护 + 强制评审，开启敏感信息/规约/依赖漏洞检测；
3. **Packages** 建 Maven 私有仓库 + 代理公共仓库，`settings.xml` 指向私服，依赖下载提速；
4. **Flow** 套"Java 构建 → 镜像构建推送 ACR → 部署 ACK"流水线模板：提交代码自动触发，单测 + 扫描做门禁，生产部署前加人工审批，发布策略用分批/金丝雀；
5. **Testhub** 建用例库，每个迭代出测试计划，缺陷回流 Projex；
6. 两个迭代后打开 **Insight**，先用官方场景模板看交付周期与质量趋势，再决定要不要自定义指标；
7. AI 加持：在 IDE 装通义灵码并接入云效 MCP（第 10.2 节配置），让 AI 直接读工作项、提 MR；Codeup 开启 AI 代码评审。

分阶段建议：先跑通 **Codeup + Flow + Packages** 这条工程主线（价值最直接），管理线（Projex/Testhub）和度量线（Insight）随团队规模叠加。

## 13.4 本章小结

选型判断口诀：**小团队直接用（免费），用钉钉的优先选，上阿里云的最顺滑，政企私有化有解（专属版），重度定制/多云中立团队先试后评**。
