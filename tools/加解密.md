# 一、总览：加解密的定位、设计哲学与算法全景

## 1.1 一句话定位

**加密（Encryption）是用一把"密钥"把明文变成只有持密钥者才能读回的密文的数学变换——它只负责一件事：保密性（Confidentiality）。**

初学者最常见的误区是以为"加密了就安全了"。安全有三根柱子（安全界的行话叫 CIA），加密只是其中一根：

| 威胁 | 对策 | 靠什么工具实现 | 与加密的关系 |
|---|---|---|---|
| **窃听**（保密性） | 加密 | 对称加密（AES/ChaCha20/SM4）、非对称加密（RSA/ECC） | **本文主角** |
| **篡改**（完整性） | 校验 | MAC（HMAC）、AEAD 认证标签、数字签名 | 加密的"搭档"，AEAD 把两者焊在一起 |
| **冒充**（身份认证） | 认证 | 数字签名、证书、口令验证 | 非对称加密的孪生应用，见 4.5/4.6 |

三根柱子都立起来，才叫安全通信；只立加密一根，就像把贵重物品锁进箱子却不管是谁在递箱子——TLS（见姊妹篇 TLS.md）的全部复杂性，本质上就是把这三根柱子在一条不可信的网络上依次立起来的工程。

另一个要提前建立的认知是**加密不负责完整性**这句话对传统的"纯加密"模式（ECB/CBC/CTR）成立——它们只把明文搅乱，攻击者改了密文你未必看得出来；只有 AEAD（如 AES-GCM，3.5.4 节）才把"加密 + 防篡改"一次做完。这是本文反复强调、也是工程上翻车最多的一条。

## 1.2 设计哲学：读密码学前先记住四句话

1. **算法公开，密钥是唯一的秘密（Kerckhoffs 原则）**。一个密码系统只应该依赖密钥的保密性，而**必须假设攻击者完全掌握算法**——现实中的加密算法（AES、RSA）的每一行数学都是公开的，全球最聪明的人公开攻击它们几十年，这正是它们可信的原因。反过来说：自己发明的算法、"混淆过的算法"一律不可信；一个系统如果"算法泄露就完蛋"，它从一开始就不安全。
2. **对称管数据，非对称管密钥**。对称加密快得可以加密 GB 级数据流，但密钥必须先"当面交给你"才能用；非对称加密不需要事先共享秘密，但慢了几个数量级、且只能加密短数据。所以现实世界的标准答案是**混合加密**：用非对称加密安全地传递一把对称会话密钥，再用对称加密搬运全部数据——TLS、HTTPS、PGP、U 盘加密，无一例外（第五章展开）。
3. **安全性取决于最弱的一环，而最弱的一环往往不是算法**。AES-256 理论上坚不可摧，但密钥写死在代码里、用 `new Random()` 生成、ECB 模式加密图片、GCM 的 IV 用了两次——任何一条都能让"军用级算法"形同虚设。本文第七章专讲这些真实误用。
4. **算法在跟攻击者的算力赛跑**。DES 的 56 位密钥在 1977 年够用，1998 年被一台 25 万美元的机器一天穷举；RSA-1024 撑到了 2013 年前后被列入退役名单；量子计算机一旦实用化，RSA/ECC 的数学地基（大数分解、离散对数）将被 Shor 算法直接击穿。所以密码学永远在"退役旧算法、部署新算法"：DES→3DES→AES，RSA→ECC→ML-KEM（后量子，已进 JDK 24，见 7.5 节）。**选算法时永远选"当前主线"，而不是"我熟悉的那个"。**

## 1.3 加密算法体系全景

把"加解密"这个词拆开，它其实是一棵树，本文的主角标 ★：

```
密码学原语（按功能分）
│
├─ 加密（可逆，靠密钥）────────────────── ★ 本文主线
│   ├─ 对称加密：加解密用同一把密钥 ──────── ★ 第三章
│   │   ├─ 分组密码（一次处理一个块）：AES / SM4 / 3DES(已退役) / DES(已破)
│   │   │    └─ 必须叠加"分组模式"：ECB / CBC / CTR / GCM / XTS …
│   │   └─ 流密码（逐字节密钥流）：ChaCha20 / RC4(已破) / ZUC(祖冲之,4G)
│   │
│   └─ 非对称加密：公钥加密、私钥解密 ────── ★ 第四章
│       ├─ 基于大数分解：RSA
│       ├─ 基于离散对数：ECC（ECIES 加密、ECDH 协商）、DH、ElGamal
│       └─ 后量子（基于格）：ML-KEM（FIPS 203）、DHKEM/HPKE（RFC 9180）
│
├─ 哈希（不可逆，无密钥）：SHA-2 / SHA-3 / SM3 ── 配角：完整性指纹、KDF 的原料
├─ 消息认证码（对称密钥 + 哈希）：HMAC / GMAC ── 配角：防篡改
├─ 数字签名（非对称）：RSA-PSS / ECDSA / Ed25519 / SM2 ── 配角：防伪造 + 防抵赖
├─ 密钥协商（非对称）：(EC)DHE ── 配角：不加密数据，只"商量"出对称密钥
└─ 密钥派生（KDF）：PBKDF2 / HKDF / Argon2 ── 配角：把口令/秘密变成合格的密钥
```

读这张树的要点：

1. **"加密"只是密码学的一支**。哈希、MAC、签名、KDF 常被初学者叫成"加密"，本文 2.4 节专门澄清；它们在 5.4 节与加密拼成完整方案。
2. **对称加密不能直接用**——分组密码必须先选"分组模式"。说"AES 加密"是不完整的，必须说"AES-GCM"或"AES-CBC + HMAC"，模式选错比算法选错更常见（3.5 节）。
3. **非对称加密在今天几乎不直接加密业务数据**——它加密的是"对称密钥"（数字信封，4.6 节）或生成"签名"。"RSA 能加密多长的数据"这个问题本身就是陷阱（答案：2048 位密钥最多约 245 字节，且必须带填充）。

## 1.5 算法演进时间线：DES → AES；RSA → ECC → PQC

密码学的每次换代，都是"攻击者算力/数学进步"逼出来的：

| 年代 | 对称加密 | 非对称加密 | 换代原因 |
|---|---|---|---|
| 1977 | DES（56 位密钥，IBM/Lucifer） | RSA 诞生（1977，Diffie-Hellman 1976 先行） | RSA 是史上第一个非对称加密；DES 是第一个商用国标 |
| 1990s | 3DES（168 位，本质 DES×3） | ElGamal、ECC 提出（1985 Koblitz/Miller） | DES 密钥太短已可穷举；ECC 用更短密钥达到同强度 |
| 1998 | — | — | EFF"Deep Crack"机器 56 小时穷举 DES，判死刑 |
| 2001 | **AES（Rijndael）胜出，FIPS 197** | — | 全球公开竞赛选出，NIST 主导 |
| 2008 | ChaCha20（2013 定型；Poly1305 组成 AEAD，RFC 8439） | — | 无 AES 硬件加速的移动/CPU 场景需要软件也快 |
| 2013–今 | AES-GCM 成为主流（TLS 1.3 只收 AEAD） | RSA 2048/3072 与 ECC P-256 并行；RSA-1024 退役；Curve25519 流行 | 位数不够、填充预言等实现层攻击 |
| 2016–今 | 国密 SM4（GB/T 32907-2016，分组） | 国密 SM2（GB/T 32918，曲线） | 国内合规要求（金融、政务） |
| 2024–今 | AES 依旧稳如泰山 | **ML-KEM（FIPS 203，2024-08 定稿）**——后量子 KEM | 量子计算威胁 RSA/ECC 的数学地基 |

**JDK 27 的现状**（SunJCE 的自我介绍，`com/sun/crypto/provider/SunJCE.java:90-91`）：

```java
private static final String info = "SunJCE Provider " +
"(implements RSA, DES, Triple DES, AES, Blowfish, ARCFOUR, RC2, PBE, "
+ "Diffie-Hellman, HMAC, ChaCha20, DHKEM, ML-KEM, and HKDF)";
```

一行 INFO 串就是一个时代的快照：老三样（DES/3DES/Blowfish/ARCFOUR=RC4）还在，是给遗留系统留的过渡期；主力是 AES 与 ChaCha20；**ML-KEM、DHKEM（HPKE 的 KEM 层）、HKDF 已经就位**——SunJCE 已注册 `HPKE` Cipher 服务（`SunJCE.java:374`）与三级 ML-KEM KEM 服务（`SunJCE.java:765-768`，512/768/1024 三档安全强度）。也就是说，后量子密码在 JDK 里已不是论文，是可以直接 `getInstance` 的现役 API。

# 二、密码学地基：五组必须先分清的概念

## 2.1 加密的职责边界：它只管保密

把加密想象成一个黑盒：输入明文 + 密钥，输出密文；反向输入密文 + 同一把（对称）密钥，还你明文。这个黑盒**保证**的是：不知道密钥的攻击者读不出内容。它**不保证**：

- 攻击者不能改密文（完整性——传统模式下甚至能定向改动：CBC 模式下翻转密文的前一块，可预测地翻转明文的后一块，见 3.5.2）；
- 对方就是你以为的那个人（身份认证——公钥是公开的，谁都能拿你的公钥发消息，除非配合签名/证书）；
- 消息没有重放（攻击者把你昨天的合法密文原样再发一遍，加密层毫无察觉——需要序号/时间戳/nonce 防护）。

这就是 1.1 节那张 CIA 表存在的理由。本文后面讲到 AEAD（3.5.4）和签名（4.5）时，会看到这三件事是怎么补齐的。

## 2.2 Kerckhoffs 原则：算法公开，密钥是唯一的秘密

19 世纪密码学家 Auguste Kerckhoffs 提出的原则至今仍是整个行业的宪法：**一个密码系统即便除密钥外的所有细节（算法、实现、参数）全部公开，也必须保持安全。**

这条原则解释了密码学的一个反直觉事实：**公开 = 可信**。AES 经历了三轮全球公开竞赛征集与数年公开分析（FIPS 197, 2001），NIST 后量子竞赛同样全球征集了 8 年（2016–2024）才定稿 ML-KEM。正因为全世界都拿它当靶子打而不倒，它才敢被写进你手机里的每一条通信。

工程上的推论：

1. **永远不要自己发明加密算法**，也不要"改造"标准算法（"我把 S 盒换一下更安全"是典型危险信号）。
2. **不要依赖算法保密**——前端 JS 里藏着一段"混淆的加密逻辑"就以为数据安全了，抓个包就能抄走。
3. **密钥管理是全部安全的重心**（第七章 7.4 节）：密钥怎么生成、存哪、怎么轮换、怎么销毁。

## 2.3 随机数：密码学的地基材料

密码学到处需要随机数：对称会话密钥、GCM 的 IV/nonce、RSA 的两个大素数 p 和 q、填充字节、ECDSA 签名的随机数 k。**每一处"可预测的随机"都是致命漏洞**：

- 密钥可预测 → 整个系统等于没有加密；
- GCM IV 可预测或重复 → 见 7.2 节，加密和认证同时崩塌；
- 2010 年索尼 PS3 的 ECDSA 签名用了固定随机数 k，攻击者直接从两个签名**算出了私钥**。

Java 里要分清两个 Random：

| | `java.util.Random` | `java.security.SecureRandom` |
|---|---|---|
| 随机性来源 | 线性同余/固定种子的确定性算法 | 操作系统熵源（`/dev/urandom`、Windows CryptGenRandom）或 DRBG |
| 可预测性 | **给我 48 位内部状态就能推算全部后续输出** | 密码学安全（计算上不可预测） |
| 适用 | 游戏、测试、抽样 | **一切密码学用途** |

JDK 的类文档自己就把话说死了（`java/security/SecureRandom.java:41-58`）：

> This class provides a cryptographically strong random number generator (RNG). A cryptographically strong random number minimally complies with the statistical random-number generator tests specified in FIPS 140-2, *Cryptographic Module Validation Program*, section 4.9.1. … JDK implementations of SecureRandom also implement `SecureRandomParameters`-compliant Deterministic Random Bit Generator (**DRBG**), which means they use a deterministic algorithm to produce a pseudorandom bit stream from a seed.

工程规则只有一条：**凡是给密码学用的随机数，一律 `new SecureRandom()` 或 `SecureRandom.getInstance("DRBG", ...)`**（后者可指定安全强度与算法族，`SecureRandom.java:70`），并且不要自己种固定 seed——`setSeed(42)` 等于把随机性亲手交出去。

## 2.4 编码 ≠ 哈希 ≠ 加密：初学者最大的混淆

这三兄弟长得都像"把一段东西变成另一段乱码"，但本质完全不同。用一张表钉死：

| | 编码（Base64） | 哈希（SHA-256） | 加密（AES/RSA） |
|---|---|---|---|
| 目的 | **表示格式转换**（二进制↔文本） | **指纹/摘要**（验证完整性、存口令） | **保密**（只有持钥者能读） |
| 可逆性 | 可逆 | **不可逆**（数学上多对一） | 可逆，但**必须有密钥** |
| 有没有密钥 | 没有 | 没有 | **有，这是唯一的秘密** |
| 能不能"解密" | 能（`Base64.decode`） | 不能（只能重新哈希比对） | 有钥能，无钥不能 |
| 输出长度 | 随输入长度变化 | 固定（SHA-256 恒 32 字节） | 随输入（对称）/固定块长（RSA） |
| 典型误用 | "我用 Base64 加密了密码" —— 等于明文 | "对密码做 MD5 再加盐" —— 要用 bcrypt/Argon2 这类**慢哈希**，普通哈希太快利于暴力破解 | "用 ECB 模式"（3.5.1） |

三个工程判据：

1. 看到输出是 `ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789+/` 字符集的，先想到 Base64 而不是加密。
2. "存口令"永远不是加密问题：加密可逆，意味着服务器能还原明文口令，本身就违反口令存储原则。正确做法是慢哈希 + 盐（bcrypt/scrypt/Argon2/PBKDF2）。
3. "要不要解密回来看"决定工具：要还原 → 加密；只要验证"是不是它" → 哈希/MAC。

## 2.5 威胁模型：假设攻击者能做什么

谈"安全"必须先谈"防谁"。密码学的标准假设是攻击者拥有：

- **完整信道窃听能力**：能记录你所有的密文（Kerckhoffs 原则的自然延伸）；
- **主动篡改能力**：能改、删、重排、重放你的密文，甚至把别人的密文塞进对话；
- **有限算力**：2^128 次运算量级不可达（128 位安全强度的含义，见 8.2 附录等价表）；
- **拿不到你的密钥**：密钥的保密靠系统边界（内存、KMS、HSM）而不是靠加密算法本身。

在此之上，安全性有严格的递进定义（了解名字即可）：**IND-CPA**（选择明文攻击下不可区分——攻击者可以随便选明文看你加密，仍然分不出密文对应哪个明文）是现代加密的最低门槛；**IND-CCA**（再加选择密文攻击——连"你帮我解密任意密文"的查询都允许）是 AEAD 与"填充必须常数时间比较"要防的层面。两个定义落到工程上的直观要求：

- **加密必须是概率性的**：同样明文两次加密必须得到不同密文，否则攻击者手里有了"字典"。这就是为什么分组模式必须有随机 IV/nonce（3.5），为什么 RSA 必须有随机填充（4.3.2）——两者都在给加密注入随机性。
- **解密失败的报错不能区分失败原因**：先解后验还是先验后解，会在第七章"填充预言"里看到血泪史。

## 本章小结

- 加密只负责**保密性**；完整性靠 MAC/AEAD，身份靠签名/证书，防重放靠 nonce/序号——加密是必要条件，不是充分条件。
- **Kerckhoffs 原则**是行业宪法：算法公开、密钥唯一秘密。自己发明算法是红线。
- 一切密码学随机数只用 `SecureRandom`；`Random` 的输出是可推算的。
- 编码（Base64）无密钥可逆、哈希不可逆、加密有钥可逆——"存口令用慢哈希、传数据用加密"。
- 现代加密的最低标准是概率性的 IND-CPA：**同样明文两次加密，密文必须不同**——这个随机性由 IV/nonce/填充提供，后文两章的主角。

# 三、对称加密：同一把钥匙，加密又解密

## 3.1 模块定位：JDK 里的对称加密住在哪里

Java 的对称加密在 JCA（Java Cryptography Architecture，第六章展开）体系里由三样东西拼成：

- **门面**：`javax.crypto.Cipher`——应用代码唯一需要面对的类，`getInstance("AES/GCM/NoPadding")` 拿到实例；
- **实现**：`com.sun.crypto.provider` 包（Provider 名叫 **SunJCE**），AES、ChaCha20、模式、填充都在这里；
- **钥匙**：`javax.crypto.SecretKey` / `javax.crypto.spec.SecretKeySpec`——对称密钥就是一段字节。

SunJCE 注册表里对称相关的部分（`com/sun/crypto/provider/SunJCE.java:186-187`）：

```java
psA("Cipher", "AES",
    "com.sun.crypto.provider.AESCipher$General", attrs);
```

一句话总结对称加密的工程形态：**`Cipher` 是操作台，模式/填充是操作台上的旋钮，AES 是发动机，密钥是油门。** 本章从发动机讲到旋钮。

## 3.2 原理：异或与"搅乱"的堆叠

对称加密的白话本质：**把明文和密钥"搅"在一起，搅到看不出原样；解密就是用同一把钥匙"反着搅"回来。** 它的数学地基简单得出奇——**异或（XOR，记作 ⊕）**：

```
密文 = 明文 ⊕ 密钥流
明文 = 密文 ⊕ 密钥流        ← 异或两次，等于什么都没做
```

证明：`a ⊕ k ⊕ k = a ⊕ 0 = a`（任何数异或自身为零，任何数异或零不变）。

1 位异或太容易猜（穷举 0/1 就够），所以现代对称加密做两件事把"一段密钥"膨胀成"海量且难预测的密钥流"，并让每一位密文依赖密钥的每一位：

- **扩散（diffusion）**：明文的 1 位变化要影响整块密文（雪崩效应）；
- **混淆（confusion）**：密钥与密文的关系尽量复杂，统计分析无从下手。

按"怎么产生密钥流"，对称加密分成两大家族——**流密码**与**分组密码**。

## 3.3 流密码与分组密码：两种"搅法"

### 3.3.1 流密码：造一条永不重复的密钥流

流密码的思路：用密钥（+ IV/nonce）驱动一个"密钥流生成器"，源源不断吐出伪随机字节流，与明文逐字节异或。它是一次一密（theoretically unbreakable 的 XOR 方案，但要求密钥流真随机且绝不复用）的实用化——**用确定性算法从短密钥生成"看起来真随机"的长密钥流**。

JDK 27 的 ChaCha20 实现（`com/sun/crypto/provider/ChaCha20Cipher.java:51-66`）暴露了它的全部家底：

```java
abstract class ChaCha20Cipher extends CipherSpi {
    // Mode constants
    private static final int MODE_NONE = 0;
    private static final int MODE_AEAD = 1;

    // Constants used in setting up the initial state
    private static final int STATE_CONST_0 = 0x61707865;
    private static final int STATE_CONST_1 = 0x3320646e;
    private static final int STATE_CONST_2 = 0x79622d32;
    private static final int STATE_CONST_3 = 0x6b206574;

    // The keystream block size in bytes and as integers
    private static final int KS_BLK_SIZE = 64;
```

四个常量是 "expand 32-byte k"（0x61707865 ≙ "apxe"，按小端读出来正是这四个词）——ChaCha20 的初始状态 = 常量字 + **256 位密钥** + 块计数器 + **96 位 nonce**，对 64 字节的状态矩阵做 20 轮"列混淆+行混淆"（名字里的 20），输出 64 字节密钥流块。密钥流每 64 字节一块，计数器递增直到喂满整条消息。

流密码的死穴是**密钥流不能重复使用**：同一个密钥+IV 加密两条消息，等于 `C1 ⊕ C2 = P1 ⊕ P2`——两条明文的异或直接暴露（两段英文异或后用统计法可轻松分离，历史上一锅端过大量协议）。RC4（JDK 里的 `ARCFOURCipher`）就死于此以及密钥流前缀偏置，2015 年被 RFC 7465 从 TLS 禁用。ChaCha20 的对策是 nonce 空间极大（96 位，随机碰撞概率可忽略）+ 每个块的状态独立计算。

**流密码适合**：软件实现（无 AES 硬件指令的设备，如早期手机）、TLS 1.3 的备选套件 `TLS_CHACHA20_POLY1305_SHA256`（姊妹篇 TLS.md 12.1）。

### 3.3.2 分组密码：一次搅 16 字节

分组密码把明文切成固定长度的**块**（AES 为 128 位 = 16 字节），每块独立地经过一个"带密钥的可逆置换"。AES（FIPS 197）是唯一在役的世界主流，国密 SM4（GB/T 32907-2016）结构与思想同源（32 轮轮函数 + 反序变换），3DES/DES 只为兼容存量而存在（NIST SP 800-131A 已禁止 3DES 用于新协议加密）。

AES 的密钥长度与轮数在 JDK 里一目了然（`com/sun/crypto/provider/AES_Crypt.java:50-52` 与 `:905-921`）：

```java
private static final int AES_128_ROUNDS = 10;
private static final int AES_192_ROUNDS = 12;
private static final int AES_256_ROUNDS = 14;
...
if (key.length == AESConstants.AES_KEYSIZES[0]) {      // {16, 24, 32} 字节
    rounds = AES_128_ROUNDS;
} else if (key.length == AESConstants.AES_KEYSIZES[1]) {
    rounds = AES_192_ROUNDS;
} else if (key.length == AESConstants.AES_KEYSIZES[2]) {
    rounds = AES_256_ROUNDS;
}
```

（密钥长度常量在 `AESConstants.java:45`：`int[] AES_KEYSIZES = { 16, 24, 32 };`）

## 3.4 AES 内部：一个字节如何在 10 轮后面目全非

AES 对每个 16 字节块做四步操作（先看白话，公式细节查 FIPS 197）：

| 步骤 | 做什么 | 白话 |
|---|---|---|
| **SubBytes** | 每字节查固定 S 盒替换 | 逐字节非线性打乱——唯一的非线性步骤，混淆的主力 |
| **ShiftRows** | 状态矩阵逐行循环左移 | 让一列的字节散到不同列——扩散 |
| **MixColumns** | 每列做 GF(2^8) 上的矩阵乘 | 一列内 4 字节互相影响——扩散 |
| **AddRoundKey** | 与本轮轮密钥异或 | 唯一用到密钥的步骤——把"钥匙"插进去 |

先由密钥扩展算法从 16 字节主密钥生成 (轮数+1) 把 16 字节轮密钥，然后：

```
轮密钥异或（初始轮）
→ [SubBytes → ShiftRows → MixColumns → AddRoundKey] × (N-1) 轮   ← 最后一轮无 MixColumns
```

安全性的直觉：**S 盒提供非线性**（没有它，整个 AES 退化成大号异或，可解线性方程组直接破解——数学上称之为"可被代数攻击秒杀"），**ShiftRows/MixColumns 提供扩散**（数轮之后，1 位明文或 1 位密钥的变化影响全部 128 位——雪崩），**AddRoundKey 提供可逆的密钥依赖**。攻击者想在知道 P 与 C 的情况下反推 K，必须穿过 10 轮"搅面"，至今最佳攻击（Biclique）也只能把 AES-128 的穷举空间从 2^128 缩到 2^126.1——工程上等于没破。

工程上还有一条必知：**AES 是全世界被硬件加速得最狠的算法**。x86 的 AES-NI、ARM 的 crypto 扩展把 AES-128-GCM 加速到每秒数 GB 量级。JDK 源码里随处可见的注解就是挂钩（`com/sun/crypto/provider/AES_Crypt.java:1039`）：

```java
@IntrinsicCandidate
private int implECBEncrypt(byte [] in, int inOff, int len, byte[] out, int outOff) {
```

`@IntrinsicCandidate` 表示 JIT 会把这段 Java 汇编成一条 `AESENC` CPU 指令。同样注解也标在 CBC（`CipherBlockChaining.java:170`）、GCM（`GaloisCounterMode.java:604-630`，"AES and GHASH operations are combined in the intrinsic implementation"）上。**这也是"为什么主流选 AES 而不是更花哨的算法"的工程答案：有硬件的地方 AES 最快，没硬件的地方 ChaCha20 顶上。**

## 3.5 分组模式：ECB / CBC / CTR / GCM——模式错了，AES 再强也白搭

分组密码一次只能加密一个 16 字节块，而现实数据远不止一块。**分组模式决定"很多块怎么串起来"**，同时决定"IV 从哪来、能不能并行、要不要填充、有没有完整性"。同一个 AES，套不同模式，安全性天差地别——这是初学者翻车率最高的一节，请逐个读。

### 3.5.1 ECB：教科书模式，工程毒药

ECB（Electronic CodeBook，电码本）就是"逐块独立加密"。JDK 实现（`com/sun/crypto/provider/ElectronicCodeBook.java:100-108`）朴素到令人心慌：

```java
@IntrinsicCandidate
private int implECBEncrypt(byte [] in, int inOff, int len, byte[] out, int outOff) {
    for (int i = len; i >= blockSize; i -= blockSize) {
        embeddedCipher.encryptBlock(in, inOff, out, outOff);
        inOff += blockSize;
        outOff += blockSize;
    }
    return len;
}
```

没有任何"串"的动作：**相同明文块 → 相同密文块**，密钥完全遮不住这种规律。经典演示是 ECB 加密一张图片（著名的"ECB 企鹅"）：轮廓原样浮现，因为大片同色像素加密后仍然是大片同色密文。更严重的工程后果：

- 泄露数据模式（哪个字段等于哪个字段、哪条记录重复出现，全写在密文里）；
- 攻击者可以**重排/复制/删除整块密文**而不被发觉（比如把"转账金额: 00100"的密文块换成"99900"那块）——连完整性都谈不上。

JDK 的 `Cipher.getInstance("AES")` 默认就是 `AES/ECB/PKCS5Padding`——**默认值是坑，永远写全三段式 transformation**（第六章 6.5 坑清单第一条）。ECB 唯一合法的用途是加密"恰好一个块"的数据（例如密钥本身，且一般也用 AES-KW 密钥封装算法更好）。

### 3.5.2 CBC：链式异或，上一块的密文当下一块的"盐"

CBC（Cipher Block Chaining）的解法：每块明文先与**前一块密文**异或再加密，第一块与 IV 异或。JDK 实现（`com/sun/crypto/provider/CipherBlockChaining.java:170-185`）正是这条链：

```java
@IntrinsicCandidate
private int implEncrypt(byte[] plain, int plainOffset, int plainLen,
                        byte[] cipher, int cipherOffset)
{
    int endIndex = plainOffset + plainLen;

    for (; plainOffset < endIndex;
         plainOffset += blockSize, cipherOffset += blockSize) {
        for (int i = 0; i < blockSize; i++) {
            k[i] = (byte)(plain[i + plainOffset] ^ r[i]);     // 明文 ⊕ 上一块密文(r)
        }
        embeddedCipher.encryptBlock(k, 0, cipher, cipherOffset);
        System.arraycopy(cipher, cipherOffset, r, 0, blockSize); // 密文回填，链到下一块
    }
    return plainLen;
}
```

于是哪怕两块明文完全相同，因为异或的"盐"不同，密文也不同——ECB 的模式泄露被消除。IV 的三条使用规则由此而来：

1. **必须不可预测（推荐随机）**：IV 可预测时，攻击者可对首块做定向猜测验证（BEAST 攻击的原理）；推荐每次加密用 `SecureRandom` 生成新 IV；
2. **IV 不是秘密**：IV 明文随密文传输（解密要用），保密的是密钥；
3. **同一密钥下 IV 不得重复**：重复意味着两条消息首块的"盐"相同——泄露关系信息。

JDK 的贴心与陷阱：**加密时不传 IV，JDK 自动生成随机 IV**（`com/sun/crypto/provider/CipherCore.java:473-474`）：

```java
ivBytes = new byte[blockSize];
random.nextBytes(ivBytes);
```

但它不会自动告诉你——你必须用 `cipher.getParameters()` 取出 IV 并与密文一起存/传，否则没人解得开（6.2 代码示例有正确姿势）。

CBC 的残余问题：加密必须串行（块与块有依赖）；无自带完整性（篡改一块密文会污染一块明文，且 CBC 下翻转前一块密文的某位 = 翻转后一块明文的对应位，攻击者可控改动）→ 必须配 HMAC 或干脆升级 GCM；PKCS#5/7 填充引入了"填充预言"攻击面（7.3 节）。TLS 1.3 因此直接删掉了 CBC（TLS.md 3.2 节）。

### 3.5.3 CTR：把分组密码变成流密码

CTR（Counter）模式：加密的不是明文本身，而是"计数器"——密钥加密 counter 得到 16 字节密钥流块，与明文异或；counter 每块递增。JDK 实现（`com/sun/crypto/provider/CounterMode.java:47-48,87`）核心就是那个计数器：

```java
final class CounterMode extends FeedbackCipher {
    // current counter value
    final byte[] counter;
    ...
    // init 时把 IV 装进计数器
    System.arraycopy(iv, 0, counter, 0, blockSize);
```

优点一箩筐：无填充（密文与明文等长）、加密解密都是"加密 counter"（可完全并行、可随机访问任意偏移——磁盘/视频流友好）、实现简单。缺点与流密码同源：**key+nonce 对绝不能重复**——同一 (key, nonce) 下的密钥流完全一致，重用即 `C1 ⊕ C2 = P1 ⊕ P2`。CTR 也无完整性，需配 HMAC（组合即"Encrypt-then-MAC"，GCM 之前的传统主力，如 AES-CTR + HMAC-SHA256）。

### 3.5.4 GCM：加密与认证一次完成（AEAD，当前主流）

GCM（Galois/Counter Mode）= **CTR 模式加密 + GHASH 认证**，一个模式把保密性和完整性同时交付——这类"二合一"叫 **AEAD**（Authenticated Encryption with Associated Data）。AEAD 是 TLS 1.3 的强制项（TLS.md 3.3："1.3 的记录加密 AEAD-only"），也是本文对"该用什么模式"的默认答案。

JDK 实现的关键骨架（`com/sun/crypto/provider/GaloisCounterMode.java:61,62,121-127`）：

```java
abstract class GaloisCounterMode extends CipherSpi {
    private static final int DEFAULT_IV_LEN = 12;        // IV 推荐 96 位
    int tagLenBytes = DEFAULT_TAG_LEN;                    // 认证标签默认 128 位
    ...
    int tagLen = spec.getTLen();
    if (tagLen < 96 || tagLen > 128 || ((tagLen & 0x07) != 0)) {
        throw new InvalidAlgorithmParameterException(
            "Unsupported TLen value; must be one of " + "{128, 120, 112, 104, 96}");
    }
```

四个必懂部件：

1. **IV/nonce（96 位）**：GCM 只允许 12 字节 IV 时走最快的专用路径——`getJ0`（`GaloisCounterMode.java:541-562`）里 `if (iv.length == 12)` 直接把 IV 末位置 1 当起始计数器，其他长度要额外跑一遍 GHASH（能用 12 字节就别用别的长度）；
2. **加密：CTR 引擎**（`GCTR`）——同 3.5.3，nonce 重用 = 密钥流重用；
3. **认证：GHASH**（`GaloisCounterMode.java:547`）——在 GF(2^128) 上对"密文块 + AAD + 长度块"做乘法累加，最后加密成 **tag（认证标签）**，默认 128 位，随密文一起传输；解密端重算 tag，`AEADBadTagException` = 数据被篡改（或密钥/IV 不对）；
4. **AAD（附加认证数据）**：不加密但要保护的数据（如记录头、主键列名）——`updateAAD()` 喂入，改一个比特 tag 就对不上。

**为什么 GCM 是主流**：单遍计算（快）、自带完整性、AAD 机制贴合协议设计、有广泛硬件加速（AES-NI + PCLMULQDQ 把 GHASH 也算了）。

**为什么 GCM 翻车也最惨**：nonce 重用是"灾难中的灾难"——不仅 `P1 ⊕ P2` 泄露，**认证子密钥 H 直接被算出**，攻击者从此可以在该密钥下伪造任意密文通过验证（7.2 节展开）。JDK 在 Cipher 类文档里专门立了规矩（`javax/crypto/Cipher.java:113-114`）：

> A successful reset depends on the mode ({@code ENCRYPT_MODE} or {@code DECRYPT_MODE}) and the algorithm. AEAD algorithms may not reset, in order to prevent [key and IV reuse].

——AEAD 模式下 Cipher 对象用完一次就换新的，防止实例复用导致 IV 复用。

### 3.5.5 模式对比表（选型速查）

| 模式 | 保密 | 完整性 | IV/nonce 要求 | 并行 | 填充 | 结论 |
|---|---|---|---|---|---|---|
| ECB | ✗ 泄露模式 | ✗ | 无需 | 可 | 要 | **禁用**（唯一例外：单块） |
| CBC | ✓ | ✗（配 HMAC） | 随机、不复用 | 解密可 | 要（预言风险） | 存量兼容；新代码不选 |
| CTR | ✓ | ✗（配 HMAC） | 不复用（可计数器构造） | 完全 | 不要 | 配 HMAC 时可用 |
| **GCM** | ✓ | ✓（自带） | **96 位、同 key 下绝不复用** | 完全 | 不要 | **默认选择** |
| XTS | ✓ | 块级有限 | tweak（扇区号） | 完全 | 要 | 磁盘加密专用 |
| ChaCha20-Poly1305 | ✓ | ✓ | 96 位不复用 | 完全 | 不要 | 无 AES 硬件时的 AEAD 替代 |

## 3.6 交互流程：双方如何用对称加密通信

对称加密的交互流程短得可爱，难点全在"钥匙怎么到对方手里"：

```
前提：A、B 已经共享同一把 256 位密钥 K（怎么共享的？见第 3.6.2 ——这是全章最深的坑）

A（发送方）                                          B（接收方）
│ ① 生成随机 IV（12 字节，GCM）                        │
│ ② cipher.init(ENCRYPT_MODE, key, ivSpec)           │
│ ③ updateAAD(附加认证数据)（可选）                     │
│ ④ ciphertext = doFinal(plaintext)                  │
│                                                    │
│ ──── 发送 [IV ‖ ciphertext ‖ tag] ────────────────▶ │
│      （IV 与 tag 都是明文可见的，不泄密）              │
│                                                    │ ⑤ init(DECRYPT_MODE, key, 同一个 IV)
│                                                    │ ⑥ updateAAD(同样的 AAD)
│                                                    │ ⑦ plaintext = doFinal(ciphertext ‖ tag)
│                                                    │    tag 不符 → AEADBadTagException（被篡改）
```

读图要点：

1. **IV 每次随机新生成，明文传输**——保密靠密钥，IV 只是"这次加密的随机标签"；
2. **tag 紧跟密文**，解密端一次 `doFinal` 同时完成解密与认证；
3. **AAD 两端必须逐字节一致**（A 传了 B 不传 = tag 验证失败）；
4. 失败信息要谨慎：`AEADBadTagException` 说明"密文/密钥/tag 不匹配"，但对外报错不要区分具体原因（防侧信道，见 2.5）。

### 3.6.2 密钥分发问题：对称加密的"先有鸡还是先有蛋"

双方要用对称加密，前提是**已经共享了密钥**——可共享密钥本身就是要保密的内容：

- **n 个人两两加密通话，需要 n(n-1)/2 把密钥**：1000 人系统要 499,500 把，每把还要安全分发、存储、轮换——纯对称方案在开放网络里不可运维；
- **直接传密钥 = 白加密**：密钥走明文信道，攻击者窃听即得；
- 古典答案是"线下交换"（见面递 U 盘、信使），只适合两人世界，不适合互联网。

这个死结在 1976 年 Diffie-Hellman 密钥协商与 1977 年 RSA 诞生前无解——**非对称加密的存在理由，本质上就是替对称加密分发密钥**。这就引出第四章。

## 3.7 优缺点与适用场景

**优点**：

1. **极快**：AES-NI 硬件下 GB/s 量级，比 RSA 快 3~5 个数量级；
2. **密文不膨胀**：CTR/GCM 模式密文与明文等长（GCM 多 16 字节 tag）；
3. **算法统一、无长度限制**：任意长度数据一把梭；
4. 简单可靠：一个 `Cipher` 实例一条密钥，心智负担低。

**缺点**：

1. **密钥分发难题**（3.6.2）——对称加密的阿喀琉斯之踵；
2. **密钥数量爆炸**：n 对 n 通信需要 O(n²) 把密钥；
3. **无法做数字签名/不可否认**：密钥双方都有，无法向第三方证明"这条消息是谁写的"；
4. **模式/IV 用错即崩**：算法安全 ≠ 方案安全，ECB、IV 复用都在等着你（第七章）。

**适用场景**：一切"密钥已经/可以安全建立"的数据加密——TLS 建立信道后的全部应用数据、磁盘/分区加密、数据库字段加密、备份加密、消息队列信道的批量数据、文件加密（zip/Office 的 AES 加密）。**一句话：数据加密永远选对称，非对称只负责把对称密钥安全送到。**

## 本章小结

- 对称加密 = 同一把密钥加解密，数学地基是 XOR + 扩散混淆；两大家族：**流密码**（ChaCha20，造密钥流逐字节异或）与**分组密码**（AES，一次搅 16 字节）。
- AES 靠 S 盒非线性 + 行列扩散 + 轮密钥异或堆 10/12/14 轮（`AES_Crypt.java:50-52`）；有 AES-NI 硬件加速（`@IntrinsicCandidate`）。
- **分组模式是安全性的第一分水岭**：ECB 禁用；CBC 串行且须配 HMAC；CTR 无填充可并行但 nonce 绝不复用；**GCM（AEAD）加密+认证一次完成，是默认答案**——96 位 IV、同密钥下绝不重用、tag 默认 128 位、AAD 两端一致。
- 交互流程五件套：随机 IV → 加密 → 发 `[IV‖密文‖tag]` → 同 IV 解密 → tag 验证。
- 密钥分发是对称加密的死结（n 人 O(n²) 把密钥），这正是非对称加密诞生的理由——下一章。

# 四、非对称加密：公钥上锁，私钥开锁

## 4.1 原理：单向陷门函数

1976 年 Diffie 与 Hellman 发表《密码学的新方向》，1977 年 Rivest、Shamir、Adleman 落地第一个实现（RSA）。在那之前，全人类默认"加密双方必须共享密钥"——他们证明了不需要。白话比喻：**信箱**——投递口（公钥）在大街上谁都能塞信，只有钥匙孔（私钥）的主人能打开信箱取信。

数学根基是**单向陷门函数**：

- **单向**：正向计算容易（公钥加密、验签），反向极难（没有私钥解密、伪造）；
- **陷门**：知道某个秘密（私钥）时，反向变得容易。

两个经典陷门函数支撑着整个非对称世界：

| 陷门函数 | 正向容易 | 反向困难 | 代表算法 |
|---|---|---|---|
| 大数分解 | 两个大素数相乘，一瞬 | 把 2048 位合数分解回两个素数，按现有算力不可行 | RSA |
| 离散对数（模乘/椭圆曲线群） | 底数自乘（点自加）已知次数，快 | 已知 a^x mod n 求 x（或已知 aG、bG 求各自信钥），不可行 | DH/ECDH/ECDSA/ElGamal |

"公钥与私钥数学相关、却无法从公钥推出私钥"的直觉：公钥是 `n = p × q`（或公点 `d × G` 里的 `d × G`），私钥是 p、q（或 d）——**乘起来容易拆开难**，这就是全部魔法。

JDK 侧的模块分布：RSA 实现在 `sun.security.rsa`（Provider 名 **SunRsaSign**）与 SunJCE 各司其职（SunJCE 注册 `Cipher/RSA`，`SunJCE.java:156-157`）；椭圆曲线在 **SunEC**（`sun/security/ec` 包，如 `ECDHKeyAgreement.java:63`）；后量子 **ML-KEM** 在 SunJCE（`SunJCE.java:765-776`）。

## 4.2 RSA：大数分解上的陷门

### 4.2.1 数学原理与一次手算

RSA 的钥匙生成四步：

1. 选两个大素数 **p、q**（各约 1024 位，保密，销毁时用）；
2. **n = p × q**（公开，就是"模数"，位数即密钥长度：2048 位 RSA 的 n 是 2048 位）；
3. 欧拉函数 **φ(n) = (p−1)(q−1)**（中间量，保密）；
4. 选公钥指数 **e**（常用 65537 = 0x10001，与 φ(n) 互素），算出私钥指数 **d**，满足 **e × d ≡ 1 (mod φ(n))**。

加解密就是模幂：**加密 `c = m^e mod n`**（用公钥 (n, e)），**解密 `m = c^d mod n`**（用私钥 (n, d)）。正确性由欧拉定理保证：`m^(ed) = m^(1 + kφ(n)) ≡ m (mod n)`。

用一组教科书小数字手算一遍（真实密钥 2048 位，此处 p/q 仅两位演示）：

```
p = 61, q = 53
n = 61 × 53 = 3233                    ← 公开
φ = 60 × 52 = 3120                    ← 保密
e = 17, d = 2753                      ← ed = 46601 = 3120 × 14 + 941？
                                      验证：17 × 2753 = 46801 = 3120 × 15 + 1 ✓
加密 m = 65：c = 65^17 mod 3233 = 2790
解密 c = 2790：m = 2790^2753 mod 3233 = 65 ✓
```

安全性全押在"**从 n = 3233 反推 p、q 容易，从 2048 位的 n 反推 p、q 不可行**"上。按 NIST SP 800-57 的等价表（附录 8.2）：RSA-3072 ≈ AES-128 的 128 位安全强度，RSA-2048 ≈ 112 位——够用到 2030 年前后，新系统建议直接 3072 或转 ECC。

### 4.2.2 填充为什么是必须的：裸 RSA 的三宗罪

初学者最爱问："那我是不是可以 `c = m^e mod n` 直接加密文件？"——不行，裸 RSA（raw RSA）有三宗致命伤，每宗的解药都是"填充"（padding）：

1. **确定性**：同一明文每次加密结果相同，IND-CPA 直接不及格（2.5 节）——攻击者建"明文-密文字典"即可对照猜测（"这个密文是不是'是'"？拿"是"加密一下就知道了）；
2. **小明文/小指数攻击**：m 很小且 e=65537 时，`m^e` 在模 n 之前就是一个小数——直接开 e 次方根还原明文，根本轮不到离散对数；
3. **可塑（malleability）**：`c' = c × 2^e mod n` 解密出来是 `2m mod n`——攻击者可以合法密文为基础批量构造出新密文，解出可预测的新明文。

**PKCS#1 v1.5 填充**（RFC 8017 的历史方案）的加密块结构：

```
EM = 0x00 ‖ 0x02 ‖ PS(至少 8 字节非零随机数) ‖ 0x00 ‖ M(明文)
      起始    类型2    ↓ 引入随机性，同一明文两次加密结果不同      ↑ 防小指数攻击
```

随机填充字节 PS 由 `SecureRandom` 生成且逐字节非零——JDK 实现（`sun/security/rsa/RSAPadding.java:300-314`）：

```java
// generate non-zero padding bytes
// use a buffer to reduce calls to SecureRandom
while (psSize > 0) {
    // extra bytes to avoid zero bytes,
    // number of zero bytes <= 4 in 98% cases
    byte[] r = new byte[psSize + 4];
    random.nextBytes(r);
    for (int i = 0; i < r.length && psSize > 0; i++) {
        if (r[i] != 0) {
            padded[k++] = r[i];
            psSize--;
        }
    }
}
```

**OAEP 填充**（Optimal Asymmetric Encryption Padding，RFC 8017）是现代标准：用 MGF1 掩码函数把明文与随机种子搅在一起，可证明在随机预言机模型下抗选择密文攻击（IND-CCA），直接封死 Bleichenbacher 填充预言攻击（7.3 节）。JDK 同时实现了两种（`RSAPadding.java:88-90`）：

```java
public static final int PAD_NONE           = 3;   // 裸 RSA，仅内部/实验用
public static final int PAD_OAEP_MGF1 = 4;        // OAEP（现代标准）
// 另有 PKCS#1 v1.5（type 1/2），兼容存量
```

OAEP 有密钥长度下限——JDK 在密钥太短时直接拒绝（`RSAPadding.java:192`）：`"Key is too short for encryption using OAEPPadding"`（SHA-1 版 OAEP 至少 1280 位密钥，SHA-256 版至少 1920 位，因为填充结构本身要占掉若干个"一个哈希输出长度"的份）。

**RSA 的可加密长度**由此注定：明文 M 的长度上限 = 模数字节数 − 填充开销。RSA-2048（256 字节）+ OAEP(SHA-256) ≈ **最多 190 字节**；PKCS#1 v1.5 ≈ 245 字节。**RSA 天生不是用来加密业务数据的**——JDK 源码注释把话说得极其直白（`com/sun/crypto/provider/RSACipher.java:63`）：

```java
* Bulk encryption using RSA does not make sense and is not standardized.
```

它只加密"钥匙"（会话密钥、KEM 封装），这正是 4.6 节数字信封的数学前提。

### 4.2.3 实现层的两件护甲：CRT 与盲化

私钥运算 `c^d mod n` 里 d 接近 n，直接算是千位级大数幂。JDK 的优化与防护（`sun/security/rsa/RSACore.java:45-46`）：

> RSA operations (with and without CRT for private key ops). Private CRT ops also support blinding to thwart timing attacks.

- **CRT（中国剩余定理）**：把 `mod n` 的幂拆成 `mod p` 与 `mod q` 两次小数幂再合并，私钥运算快约 4 倍；
- **盲化（blinding）**：运算前先把密文乘上一个随机数 r^e、算完再除掉，让"密文的位模式"与"耗时"解耦——防计时侧信道（攻击者测你解密耗时差反推私钥位）。盲化参数还有缓存（`RSACore.java:61-67` 的 `blindingCache`）。

## 4.3 ECC：椭圆曲线上的陷门

RSA 的密钥长得慢（2048 位起步），ECC（椭圆曲线密码）用更短的钥匙换同等的锁——**256 位 ECC ≈ 3072 位 RSA ≈ 128 位安全强度**（SP 800-57，附录 8.2）。因为它的数学难题更难：**椭圆曲线离散对数**。

白话：把椭圆曲线上的点 G（基点，公开）反复"自加"——`P = d × G`（d 次点加，d 是私钥，P 是公钥）。正向已知 d 算 P 飞快；反向已知 P、G 求 d，目前没有亚指数级好算法（RSA 的大数分解有通用数域筛法，ECC 的破解难度指数级），所以密钥能短。

工程上 ECC 的两大用途：

1. **ECDH 密钥协商**（4.5 节）——TLS 1.3 的主力；
2. **ECDSA/Ed25519 签名**——JWT 的 ES256、SSH 的新式密钥、证书链里的 P-256 证书。

对"加密"而言，ECC 走 **ECIES**（椭圆曲线集成加密方案）：临时生成一对曲线密钥 → 用 ECDH 对方公钥算出共享秘密 → KDF 派生对称密钥 → 对称加密数据 + MAC。它本质上就是把 4.6 节的数字信封做成了标准封装，Java 标准库不直接提供 ECIES（用 BouncyCastle 可得），但提供了所有原料（ECDH + KDF + AES-GCM）。

JDK 对 ECDH 公钥的安全性检查可以直接读到 NIST 规范名（`sun/security/ec/ECDHKeyAgreement.java:149-175`）：

```java
// Validate public key
validate(privateKeyOps, (ECPublicKey) key);
...
// Verify that x and y are integers in the interval [0, p - 1].
private static void validateCoordinate(BigInteger c, BigInteger mod) ...
// Check whether a public key is valid, following the ECC
// Full Public-key Validation Routine (See section 5.6.2.3.3,
// NIST SP 800-56A Revision 3).
private static void validate(ECOperations ops, ECPublicKey key) ...
```

——不校验对端公钥的 ECDH 是著名的"无效曲线攻击"入口，JDK 按 SP 800-56A 的 Full Public-key Validation 做了校验，这是标准库的价值之一。

## 4.4 密钥协商 Diffie-Hellman：公开对话里长出秘密

严格说，DH/ECDH **不是加密**——它不加密任何数据，只解决一件事：**两个从未见过面的人，在公开信道上各说各的"公开数字"，最后各自算出同一个只有他俩知道的密钥。** 它是非对称密码学的另一半（甚至更常用），也是"对称密钥怎么分发"的标准答案之一。

经典 DH 的数学魔术（p 为大素数，g 为生成元，均公开）：

```
A：选秘密 a，广播 A_pub = g^a mod p
B：选秘密 b，广播 B_pub = g^b mod p

A 侧计算：B_pub^a mod p = (g^b)^a = g^(ab) mod p
B 侧计算：A_pub^b mod p = (g^a)^b = g^(ab) mod p      ← 同一个数！

窃听者手里只有 g、g^a、g^b，求 g^(ab) 需要解离散对数——难。
```

ECDH 是同一思想的曲线版：A 广播 `aG`，B 广播 `bG`，双方各自算 `a·(bG) = b·(aG) = abG`，再经 KDF（如 HKDF）派生出对称密钥。JDK 同时提供两套：JCE 的经典 DH（`com/sun/crypto/provider/DHKeyAgreement.java:48,180`）与 SunEC 的 ECDH（`sun/security/ec/ECDHKeyAgreement.java:63,132`，`engineDoPhase` 收进对方公钥、`generateSecret` 出共享秘密）。

DH 的两个"但是"：

1. **裸 DH 没有身份认证**：中间人可以跟 A 装扮成 B、跟 B 装扮成 A，两头各协商一个密钥——这就是 MITM。解药是给 DH 消息加**数字签名**（TLS 的 ServerKeyExchange/CertificateVerify 干的就是这事，TLS.md 第四章）；
2. **要前向安全就用临时密钥**：每次协商用一次性的 a、b（即 (EC)DHE，E=Ephemeral），私钥日后泄露也解不了过去的会话——TLS 1.3 把 DHE 定为强制（TLS.md 2.3 节）。

## 4.5 交互流程一：非对称加密的标准姿势——数字信封

把 4.2 的结论串起来：RSA 只能加密约 190 字节、还慢得要死，但它不需要事先共享秘密。把这两点与对称加密的优缺点对拼，答案自动浮现——**数字信封（Digital Envelope）/混合加密**：RSA 只加密一把随机对称密钥，AES 干全部重活。

```
B（接收方，提前一次性完成）                          A（发送方，每次发送时）
│ ① KeyPairGenerator 生成密钥对                      │
│    私钥 sk 自己藏好（KMS/keystore）                 │
│    公钥 pk 公开发布（证书锚定身份，TLS.md 第六章）     │
│ ◀────────────── pk 拿去随便用 ─────────────────────│
│                                                    │ ② 生成随机会话密钥 K（32 字节）
│                                                    │ ③ 用 pk 做 RSA-OAEP 加密 K
│                                                    │    EK = RSA_OAEP_pk(K)   ← 只有 sk 能解
│                                                    │ ④ 用 K 做 AES-256-GCM 加密数据
│                                                    │    C, tag = AES_GCM_K(data, iv)
│                                                    │
│                                                    │ ── 发送 [EK ‖ iv ‖ C ‖ tag] ──▶
│                                                    │
│ ⑤ sk 解开信封：K = RSA_OAEP_sk^-1(EK)              │
│ ⑥ K 解开数据：data = AES_GCM_K^-1(C, iv)，验 tag   │
```

读图要点：

1. **保密性与"没有事先共享秘密"两个目标同时达成**：中间人能看到 EK、iv、C、tag 全部字节，没有 sk 就打不开信封，没有 K 就读不了数据；
2. **一把会话密钥只用一次**（甚至一条消息一把），泄露损失面极小；轮换无感；
3. **信封里的 K 长度固定 32 字节**，RSA 的"只能加密短数据"恰好匹配；
4. 性能账：RSA 加密 32 字节 ~微秒级，AES 加密 GB 级数据 ~毫秒级——**整套方案贵在 RSA 那一次**，之后全是 AES 的天下。

## 4.6 交互流程二：ECDH 协商 + KDF（TLS 在用的路）

数字信封适合"A 发给 B"的单向加密；双向会话（如 TLS）更爱 ECDH——双方地位对等、每条连接新密钥、天然前向安全：

```
A                                                 B
│ 私钥 a，公钥 aG                                  │ 私钥 b，公钥 bG
│                                                 │
│ ──────────────── aG ──────────────────────────▶ │
│ ◀──────────────── bG ────────────────────────── │    （两个公钥公开可见）
│                                                 │
│ 共享秘密 s = a·(bG)                              │ 共享秘密 s = b·(aG)
│        = ab·G  ────────── 两侧相同 ──────────     │        = ab·G
│                                                 │
│ 密钥 = HKDF(s, transcript 上下文)                │ 密钥 = HKDF(s, transcript 上下文)
│ → 两侧得到同一把对称密钥 → 进入 AES-GCM 数据传输     │
```

比数字信封多两个细节，也都是 TLS 已经验证过的工程惯例：

1. **KDF 不省略**：ECDH 的共享秘密 s 是曲线点的 x 坐标，不是均匀的密钥——必须过 HKDF（RFC 5869）并绑定握手上下文（transcript）才成为合格密钥；
2. **认证不可省**：图里没有签名，就是 4.4 说的裸 DH——中间人可在 aG/bG 处调包。TLS 1.3 用证书 + `CertificateVerify` 签名把"这把 bG 确实是服务端的"钉死（TLS.md 第四章、第五章）。

## 4.7 优缺点与适用场景

**优点**：

1. **不需要事先共享秘密**——开放网络里两个陌生系统能直接建立保密通信，这是它与对称加密的本质分野；
2. **密钥管理从 O(n²) 降到 O(n)**：n 个用户每人保管 1 对密钥、公布 1 把公钥即可；
3. **签名/不可否认**：私钥签的只有私钥持有者签得出来，第三方可验证——合同、JWT、代码签名、证书链全靠它；
4. 配合临时密钥（DHE）实现前向安全。

**缺点**：

1. **慢**：RSA-2048 私钥运算 ~毫秒级，比 AES-GCM（硬件加速 GB/s）慢 3~5 个数量级；
2. **只能加密短数据**：RSA-2048 + OAEP 约 190 字节上限（4.2.2）；ECC 走 ECIES 也是"加密密钥而非数据"；
3. **密文大幅膨胀**：RSA 密文长度 = 模数长度（2048 位密钥 → 256 字节密文，哪怕只加密 1 字节）；
4. **密钥长度长、生成慢**：RSA 素数搜索秒级起步；3072 位起才能对标 AES-128；
5. **公钥的真实性是新的问题**：公钥随便发布，"这把公钥真是 B 的吗"靠证书/PKI 解决（TLS.md 第六章）；
6. **数学地基面临量子威胁**：Shor 算法在通用量子计算机上多项式时间破解 RSA/ECC（7.5 节）。

**适用场景**：

- **密钥交换/数字信封**：TLS 握手、JWT(JWE)、加密邮件(PGP)、API 网关向客户端分发数据密钥；
- **数字签名**：RSA-PSS/ECDSA/Ed25519——证书、JWT(JWS RS256/ES256)、代码签名、区块链交易；
- **密钥封装 KEM**：ML-KEM（后量子，JDK 24+ 内置）、HPKE（RFC 9180，SunJCE 已注册 `SunJCE.java:374`）——封装是"加密一把密钥"的现代化表述，API 层面连"明文"这个概念都省了（`javax.crypto.KEM`，JDK 21 JEP 452 引入）。

## 本章小结

- 非对称加密的地基是**单向陷门函数**：大数分解（RSA）与离散对数（DH/ECC）。公私钥数学相关但不可互推——"乘起来容易拆开难"。
- **RSA 原文**：`c = m^e mod n`、`m = c^d mod n`；安全全押大数分解；裸 RSA 三宗罪（确定性、小指数、可塑）由**填充**解决——新代码一律 **OAEP**（`RSAPadding.java:88-90`），且上限约 190 字节（RSA-2048）：**"Bulk encryption using RSA does not make sense"（RSACipher.java:63）**。
- **ECC 用短密钥换同强度**（256 位 ≈ RSA-3072）；ECDH 公钥必须按 SP 800-56A 校验（`ECDHKeyAgreement.java:169`）。
- **DH 协商**让公开信道长出共享秘密，但裸 DH 不防中间人——必须配签名，用临时密钥才前向安全。
- **两种标准交互流程**：数字信封（RSA 传会话密钥 + AES 传数据）与 ECDH+KDF（双方交换公钥各自派生）——TLS 是两者的集大成者。
- 非对称不与对称竞争，而是**给对称密钥开路**——下一章把两者拼成现实世界的标准答案。

# 五、对称 vs 非对称：对比、混合加密与场景选型

## 5.1 全维度对比表

| 维度 | 对称加密（AES-GCM/ChaCha20） | 非对称加密（RSA-OAEP/ECC/ML-KEM） |
|---|---|---|
| 密钥形态 | **1 把共享密钥**（32 字节） | **公钥 + 私钥对**（公钥可公开） |
| 加解密速度 | GB/s（AES-NI 硬件） | RSA-2048 私钥运算 ~ms 级，慢 3~5 个数量级 |
| 单次可加密数据量 | 无限制 | RSA-2048+OAEP ≈ 190 字节；ECIES/KEM 只封装密钥 |
| 密文长度 | ≈ 明文（GCM +16 字节 tag） | = 模数长度（2048 位密钥 → 256 字节密文） |
| 密钥分发 | **先有鸡后有蛋**，需线下/非对称手段 | 公钥随便发，天然解决分发 |
| n 方通信密钥数 | O(n²)（n=1000 → 49.95 万把） | O(n)（每人 1 对） |
| 签名/不可否认 | 不能 | 能（私钥唯一性 + 公钥可验证） |
| 前向安全 | 无（密钥泄露 = 历史全灭） | (EC)DHE 临时密钥可达成 |
| 典型角色 | **数据加密主力** | **密钥传输/协商 + 身份认证** |
| 量子抗性 | AES-256 尚可（Grover 只是减半强度） | RSA/ECC 被 Shor 击穿；ML-KEM 应战 |
| 代表算法 | AES-256-GCM、ChaCha20-Poly1305、SM4-GCM | RSA-3072、P-256/25519、ML-KEM-768、SM2 |

一句话记忆：**对称加密快但不能传钥匙，非对称能传钥匙但慢——所以钥匙用非对称传，数据用对称加密。**

## 5.2 现实世界的答案：混合加密无处不在

数字信封（4.5）与 ECDH+KDF（4.6）不是两个孤立技巧，它们是同一思想（混合加密）的两种实现，而 TLS 把两种都用了：

- **TLS_RSA_ 套件（已退役）**：数字信封路线——客户端用服务器 RSA 公钥加密 premaster secret（TLS.md 4.4 节讲它的命运：无前向安全，被 1.3 移除）；
- **TLS 1.3（现行）**：ECDH 路线——`(EC)DHE` 协商 + 签名认证 + AEAD 数据加密，前向安全强制（TLS.md 1.3 的 5 个套件全部是"AEAD"套件）。

除此之外，你每天都在享用混合加密：HTTPS 网页、SSH 会话、iMessage/Signal 端到端加密、U 盘的 BitLocker（公钥保护恢复密钥）、企业邮件 S/MIME、云对象存储的 SSE-KMS（KMS 用信封加密分发数据密钥——AWS 文档管这叫 Envelope Encryption，与 4.5 的图完全同构）。

## 5.3 场景选型手册

| 场景 | 推荐方案 | 为什么 | 注意 |
|---|---|---|---|
| 进程间/微服务间加密通信 | 直接上 TLS（mTLS 双向认证） | 别手搓密码学，TLS 全部踩过的坑（第七章）都有标准答案 | 禁 TLS_RSA_ 套件、开 1.3 |
| 数据库敏感字段（手机号/身份证） | **AES-256-GCM**，密钥放 KMS/密钥服务 | 等长、可查（加密列无法 like——需要确定性变体时评估 AES-SIV） | AAD 绑定表名+主键防换列挪用；密文用 Base64 存 |
| 磁盘/文件加密 | AES-XTS（磁盘）/ AES-GCM（文件） | XTS 按扇区 tweak，随机访问不串味 | XTS 不做完整性——那是另一层职责 |
| 备份/归档加密 | AES-256-GCM + 信封加密的密钥管理 | 数据量大 → 对称；密钥托管 → 非对称/KMS | 密钥丢了备份等于作废，恢复方案先行 |
| JWT / 接口令牌 | 签名 JWS(ES256/RS256)；需保密时 JWE(A256GCM 或 RSA-OAEP+ECDH-ES) | 签名防篡改即可时别用加密（加密带来密钥管理成本） | JWT 默认只是"编码+签名"，payload 可读 |
| 配置文件里的第三方密码 | KMS/凭据管理器优先；退而求其次 AES-GCM + 环境变量密钥 | 硬编码密钥 = 没加密（7.4） | 轮换预案 |
| 前端把密码传给后端 | **HTTPS 即可**；口令落库用 bcrypt/Argon2 | 传输保密 TLS 已解决；前端"加密"的密钥就嵌在 JS 里，防不了中间人 | 若防"浏览器历史/日志泄明文"，可用 SRP/OHTTP 等专用方案 |
| 端到端加密聊天 | 双棘轮 + X25519 + AES-GCM（Signal 协议族） | 前向安全 + 事后泄露保护，密钥每条消息轮换 | 超出本文范围，思路仍是本文三件套 |
| 国内合规（金融/政务） | SM4-GCM/CBC + SM2 + SM3 | 国标要求；BC（BouncyCastle）提供实现 | SM2 签名/加密均国标曲线 sm2p256v1 |
| IoT/低算力设备 | ChaCha20-Poly1305（无 AES 硬件时） | 软件实现也快、常量时间实现简单 | 96 位 nonce 由计数器构造最稳 |

选型三问（按顺序问自己）：

1. **密钥从哪来？** 能提前共享 → 纯对称；不能 → 先上非对称（信封/协商）；
2. **要防篡改吗？** 要 → AEAD 或"加密 + MAC"，纯 ECB/CBC/CTR 不合格；
3. **密钥放哪、怎么轮换？** 答不上来就先解决密钥管理（7.4），再谈算法。

## 5.4 完整的安全方案拼图：加密只是四分之一

把全文工具箱拼进一次真实通信（对齐 TLS.md 1.1 的 CIA 表）：

```
┌─────────────────────────── 一次安全通信 ───────────────────────────┐
│                                                                   │
│  身份认证   证书链/签名 ────────── "对方是谁"（防冒充）               │
```

## 5.5 实战全景：一次 TLS 1.3 握手里的混合加密（逐帧解析）

本节把第三、四章的零件放进真实协议，回答一个问题：**"对称管数据、非对称管密钥"在一次真实的 TLS 连接里，到底发生在哪一毫秒？** 本节始终是**密码学视角**——只关心每一步用了哪件工具、秘密在哪一刻诞生、窃听者看得到什么；**协议视角**（消息格式、扩展、状态机、HelloRetryRequest、0-RTT）请读 TLS.md 第五章，两文互为对方的"放大镜"。

下面逐帧拆解。每一帧回答三件事：用了哪件工具、为什么、窃听者此刻手里有什么。

**第 0 帧 · 握手前：秘密还不存在。** 会话密钥不在客户端、不在服务端、也不在路上一张纸上等着被偷——TLS 1.3 里它最终是被"算"出来的，不是被"传"过去的。双方手里只有静态资产：服务端一张证书（身份凭证 + 签名公钥），客户端一组预置的 CA 信任锚。

**第 1 帧 · ClientHello（明文）——非对称登场，用途一：协商。** 客户端用 `SecureRandom` 生成一次性 X25519 密钥对，把公钥 aG 放进 `key_share` 扩展，连同"我会的菜"（AEAD 套件、签名算法清单）和 SNI 一起明文发出。aG 公开不泄密：共享秘密 ab·G 必须同时知道某个临时私钥（a 或 b）才能算出，窃听者两样都没有（4.4 节的离散对数难题）。明文的原因很朴素：此刻双方没有任何共享秘密，想加密也没有钥匙。

**第 2 帧 · ServerHello + 共享秘密诞生——"密钥从未旅行"。** 服务端同样生成一次性 b/bG，回送 bG 并点菜。这一帧落地的瞬间，两侧各自计算 `s = a·(bG)` 与 `s = b·(aG)`，由点乘交换性得到同一个 ab·G（4.6 节）。请注意这里与数字信封（4.5 节）的本质差别：**没有任何会话密钥在网络上传输**。真正"把会话密钥用服务端公钥加密寄过去"的是 TLS 1.2 的 RSA 密钥交换（数字信封路线，TLS.md 4.4）——它因"服务器私钥一泄，历史抓包全部可解"（无前向安全）被 1.3 移除。1.3 用**协商**替代**传输**：密钥在两端同时长出来，线上飞过的只有 aG、bG 两把公开钥匙。

**第 3 帧 · HKDF 换挡——非对称交棒给对称。** s 是曲线点的 x 坐标，不是均匀密钥（4.6 节要点 1），且混合加密需要的不止一把钥匙（握手加密、应用加密、读写方向各不同）。双方跑同一条 HKDF 链（TLS.md 5.2 的密钥调度图）：Extract 把 s 压缩成均匀伪随机串，再以 **transcript**（两条 Hello 的哈希，把"菜单"也绑进去，防中间人篡改算法协商）为上下文 Expand 出握手密钥。这一步是整场握手的**换挡点**：非对称的活到此干完，之后每一个字节都出自对称算法。

**第 4 帧 · 加密的握手后半段——非对称登场，用途二：认证。** 从 EncryptedExtensions 开始全部密文——1.3 的"加密尽早"把证书、签名都藏了起来（1.2 时代证书是明文的，你的访问目标其实写在证书的 SNI 里）。{Certificate} 递上证书链；{CertificateVerify} 用**证书对应的私钥**对 transcript 签名，向客户端证明"我确实持有这张证书的私钥"——而且签名盖在 transcript 上，前面每一帧（含 aG/bG 与菜单）都被锁进签名，中间人改动任何一个字节都会让验签失败（2.2 节 transcript 绑定思想）。这里有一个关键解耦：**签名密钥（长期、静态）≠ 协商密钥（一次性、临时）**。服务器私钥明天泄露，过去会话依然安全——过去会话的对称密钥来自早已销毁的临时 a/b，与长期私钥毫无数学关联。这就是前向安全（PFS）的协议化落地（TLS.md 2.3）。

**第 5 帧 · {Finished} 与三连验证——把"协商出来的秘密"盖章。** 服务端 Finished 是对整个 transcript 的 HMAC：握手期间任何一帧被篡改，这里必然对不上账（TLS 安全性的"总闸"）。客户端三连验证——①证书链锚到本地信任的 CA（防冒充）；②CertificateVerify 验签（防伪冒 + 证明私钥持有者在线）；③Finished 校验（防篡改）——三道全过，握手密钥才算"可信的"。随后客户端回自己的 {Finished}，服务端同样校验（对称密钥两把，双向各自认证）。

**第 6 帧 · 再派生应用密钥——正式进入对称世界。** 双方沿同一条 HKDF 链继续 Expand，得到应用流量密钥：读、写方向各一把对称密钥 + 各自的 IV（读写分离，一把泄漏不殃及另一方向）。此后记录层每个字节都是 AES-256-GCM，nonce 由"静态 IV ⊕ 单调序号"构造（TLS.md 3.3）——同密钥下序号绝不重复，正是 7.2 节 GCM nonce 纪律的协议化。

**第 7 帧 · 应用数据——对称加密的天下。** 请求、响应、视频流、API JSON……全部 AES-256-GCM，GB/s 吞吐靠 AES-NI（3.4 节）。整个连接里非对称运算只有寥寥几次（两侧各生成一对临时密钥并做一次点乘、服务端签名一次、客户端验签一次），其余每个字节都是硬件加速的对称加密——这就是"混合"的性能账本：**贵的活只干一次，便宜的活干一辈子。**

**收尾 · NewSessionTicket。** 连接建立后服务端发会话票据，下次连接客户端可凭 PSK（上次会话派生的对称秘密）免协商直接进加密区。注意 1.3 连"恢复"都贯彻混合思想：纯 PSK 恢复没有前向安全，协议要求 PSK 必须再叠一次 (EC)DHE（`psk_dhe_ke` 模式，TLS.md 12.3）——对称秘密与新鲜的非对称协商层层叠加。

本节的零件与 TLS 的接线关系，一张表对齐（协议细节全部指向 TLS.md 对应章节）：

| 本文零件 | 在 TLS 1.3 里的位置 | 协议细节在 TLS.md |
|---|---|---|
| 3.6.2 密钥分发难题 | 整个握手存在的理由 | 第一章 |
| 2.3 SecureRandom | 每条连接的一次性密钥对 a/b | 5.1 |
| 4.4 ECDH 协商 | key_share 交换 aG/bG | 5.1 |
| 4.6 ECDH + KDF | HKDF 密钥调度链 | 5.2 |
| 4.5 数字信封（传输路线） | TLS 1.2 RSA 密钥交换（已退役） | 4.4 |
| 身份认证（2.1/4.5） | 证书链 + CertificateVerify 签名 | 4.3 / 5.1 |
| 3.5.4 AEAD | 握手后半段 + 全部应用数据的加密 | 3.2 / 3.3 |

把整节压成一句话：**TLS 1.3 握手里，非对称只干了三件一次性的活——两侧协商出共享秘密、服务端签名证明身份、客户端验签确认身份；会话密钥从头到尾没有在线上传输，而是被两侧各自"算"出来；其余每一毫秒、每一个字节都是对称加密的世界。**"对称管数据、非对称管密钥"在这张时间线上不是比喻，是逐帧可见的分工。

## 本章小结

- 对比一句话：**对称快但钥匙难传（O(n²)），非对称传钥匙自由但慢且只能短数据**。
- **混合加密/数字信封是所有现实系统的标准答案**：非对称传密钥、对称传数据；TLS 1.3 = ECDHE（协商）+ 签名（认证）+ AEAD（数据）。
- 5.5 节的逐帧拆解给出了最硬核的记忆锚点：**会话密钥从未在线上传输，而是被两侧各自"算"出来**；非对称只干一次性的协商与认证，其余字节全是对称加密。
- 场景选型按"密钥从哪来 → 要不要完整性 → 密钥怎么管"三问走；数据库字段、磁盘、备份用 AES-GCM/XTS，口令存储用慢哈希，传输用 TLS。
- 加密只是安全方案的四分之一：认证、协商、KDF、AEAD 四层拼齐才算"安全通信"。

# 六、工程落地：JDK JCA 与 Spring Security

## 6.1 JCA 体系：Engine 门面 + Provider 注册表

Java 密码学架构（JCA/JCE）的设计哲学与 JDBC 一模一样：**标准接口（Engine）+ 可插拔实现（Provider）**。

```
应用代码
   │  Cipher.getInstance("AES/GCM/NoPadding")
   ▼
Engine 门面（javax.crypto / java.security）
   │  Cipher 加解密   KeyGenerator 对称密钥生成   KeyPairGenerator 密钥对生成
   │  KeyAgreement 协商   KDF/KEM 派生/封装（JDK 21/25+）   SecureRandom 随机数
   ▼
Provider 注册表（Security.getProviders()，按优先级查找）
   ├─ SunJCE        ← AES/ChaCha20/模式/填充/DH/HKDF/ML-KEM（com.sun.crypto.provider）
   ├─ SunRsaSign    ← RSA 密钥对与签名（sun.security.rsa）
   ├─ SunEC         ← ECC（sun.security.ec）
   ├─ SunPKCS11     ← 硬件安全模块 HSM 桥接
   └─ BouncyCastle  ← 第三方补充（国密 SM2/SM4、ECIES 等）
```

要点三条：

1. **三段式 transformation 决定行为**：`算法/模式/填充`。JDK 类文档给出的推荐写法与内置映射（`javax/crypto/Cipher.java:79,125,132-133`）：

   ```
   Cipher c = Cipher.getInstance("AES/CBC/PKCS5Padding");   // 文档示例
   // 支持列表（JDK 默认 Provider）：
   //   AES/CBC/PKCS5Padding (128)
   //   AES/GCM/NoPadding (128)
   //   RSA/ECB/OAEPWithSHA-1AndMGF1Padding (1024, 2048)
   //   RSA/ECB/OAEPWithSHA-256AndMGF1Padding (1024, 2048)
   ```

   注意 RSA 里的 "ECB" 只是格式占位（RSA 不是分组密码，没有块模式），6.5 节有这个占位引发的 MGF1 坑。

2. **四个操作模式**（`javax/crypto/Cipher.java:164-179`）：

   ```java
   public static final int ENCRYPT_MODE = 1;
   public static final int DECRYPT_MODE = 2;
   public static final int WRAP_MODE = 3;     // 用公钥/密钥"包"另一把密钥
   public static final int UNWRAP_MODE = 4;   // 数字信封的官方 API
   ```

   `WRAP_MODE/UNWRAP_MODE` 就是 4.5 节数字信封的标准化封装——`wrap()` 一把 AES 会话密钥、对端 `unwrap()` 解开，比"把密钥当明文加密"更安全（密钥对象有类型与用途元数据，还能配合硬件密钥）。

3. **Cipher 实例不是线程安全的，且 AEAD 模式禁止复用**（`Cipher.java:113-114`："AEAD algorithms may not reset, in order to prevent [key/IV reuse]"）——每次加密 new 一个。

## 6.2 对称加密实战：AES-256-GCM 完整示例

以下代码可直接运行（JDK 17+），覆盖"生成密钥 → 加密（随机 IV + AAD）→ 打包传输格式 → 解密验证"全流程，即 3.6 节交互流程的代码化：

```java
import javax.crypto.Cipher;
import javax.crypto.KeyGenerator;
import javax.crypto.SecretKey;
import javax.crypto.AEADBadTagException;
import javax.crypto.spec.GCMParameterSpec;
import java.security.SecureRandom;
import java.util.Arrays;

public class AesGcmDemo {

    private static final SecureRandom RANDOM = new SecureRandom();
    private static final int IV_LEN = 12;    // GCM 标准 IV：96 位
    private static final int TAG_BITS = 128; // 认证标签：128 位

    /** 生成 256 位 AES 密钥（密钥生命周期起点，见 7.4） */
    static SecretKey newKey() throws Exception {
        KeyGenerator kg = KeyGenerator.getInstance("AES");
        kg.init(256);
        return kg.generateKey();
    }

    /**
     * 加密。返回传输格式：iv(12) || ciphertext || tag(16)
     * 同一密钥下，本方法每次调用的 IV 都是新的——GCM 的硬性要求。
     */
    static byte[] encrypt(SecretKey key, byte[] plaintext, byte[] aad) throws Exception {
        byte[] iv = new byte[IV_LEN];
        RANDOM.nextBytes(iv);                                  // ① 随机 IV，绝不复用

        Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding"); // ② 模式写全
        cipher.init(Cipher.ENCRYPT_MODE, key, new GCMParameterSpec(TAG_BITS, iv));
        if (aad != null) cipher.updateAAD(aad);                // ③ 附加认证数据
        byte[] ct = cipher.doFinal(plaintext);                 // ④ ct 末尾自带 16 字节 tag

        byte[] out = new byte[iv.length + ct.length];
        System.arraycopy(iv, 0, out, 0, iv.length);
        System.arraycopy(ct, 0, out, iv.length, ct.length);
        return out;
    }

    /** 解密。AAD 必须与加密端逐字节一致，否则抛 AEADBadTagException */
    static byte[] decrypt(SecretKey key, byte[] sealed, byte[] aad) throws Exception {
        byte[] iv = Arrays.copyOfRange(sealed, 0, IV_LEN);
        byte[] ct = Arrays.copyOfRange(sealed, IV_LEN, sealed.length);

        Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
        cipher.init(Cipher.DECRYPT_MODE, key, new GCMParameterSpec(TAG_BITS, iv));
        if (aad != null) cipher.updateAAD(aad);
        return cipher.doFinal(ct);      // 密文被改 → AEADBadTagException
    }

    public static void main(String[] args) throws Exception {
        SecretKey key = newKey();
        byte[] aad = "orders:column=id".getBytes();   // 绑定"这段密文属于谁"
        byte[] sealed = encrypt(key, "机密数据".getBytes(), aad);
        System.out.println(new String(decrypt(key, sealed, aad)));   // 解密回明文

        // 验证防篡改：翻转密文 1 位
        sealed[sealed.length - 1] ^= 1;
        try {
            decrypt(key, sealed, aad);
        } catch (AEADBadTagException e) {
            System.out.println("检测到篡改 ✓");
        }
    }
}
```

两个工程细节：

- 若不传 IV（`init(ENCRYPT_MODE, key)`），JDK 会生成随机 IV，但**必须**用 `cipher.getParameters()` 取出（`GCMParameterSpec`）随密文保存——忘取 = 这段密文永久解不开（CBC 同理，见 `CipherCore.java:473-474`）；显式生成再传入（如上）更可控；
- AAD 的典型用法：加密数据库某列时把"表名+主键"作 AAD，密文被搬到另一行/另一表时 tag 校验失败——**密文与数据位置绑定**。

## 6.3 非对称实战：RSA-OAEP（含必踩的 MGF1 坑）与 ECDH

### 6.3.1 密钥对与信封加密

```java
import javax.crypto.Cipher;
import java.security.*;
import javax.crypto.spec.OAEPParameterSpec;
import javax.crypto.spec.PSource;
import javax.crypto.spec.MGF1ParameterSpec;

// ① 生成密钥对：3072 位对标 AES-128 的 128 位安全强度（附录 8.2）
KeyPairGenerator kpg = KeyPairGenerator.getInstance("RSA");
kpg.initialize(3072);
KeyPair kp = kpg.generateKeyPair();     // 私钥入 KMS/KeyStore，公钥可分发

// ② 用公钥封装一把 AES 会话密钥（数字信封，4.5 节）
SecretKey sessionKey = AesGcmDemo.newKey();

// 显式 OAEPParameterSpec —— 见下文"MGF1 坑"，不要省略这一步
OAEPParameterSpec spec = new OAEPParameterSpec(
        "SHA-256", "MGF1", MGF1ParameterSpec.SHA256, PSource.PSpecified.DEFAULT);

Cipher cipher = Cipher.getInstance("RSA/ECB/OAEPWithSHA-256AndMGF1Padding");
cipher.init(Cipher.ENCRYPT_MODE, kp.getPublic(), spec);
byte[] sealedKey = cipher.doFinal(sessionKey.getEncoded());   // 384 字节密文

// ③ 接收方用私钥解出会话密钥（或直接用 UNWRAP_MODE）
Cipher unwrapper = Cipher.getInstance("RSA/ECB/OAEPWithSHA-256AndMGF1Padding");
unwrapper.init(Cipher.UNWRAP_MODE, kp.getPrivate(), spec);
SecretKey restored = (SecretKey) unwrapper.unwrap(
        sealedKey, "AES", Cipher.SECRET_KEY);
```

**MGF1 坑（源码实证）**：若省略显式 `OAEPParameterSpec`，SunJCE 会按 transformation 字符串把主哈希设为 SHA-256，但 **MGF1 的哈希固定回落到 SHA-1**（`com/sun/crypto/provider/RSACipher.java:316-317`）：

```java
spec = new OAEPParameterSpec(oaepHashAlgorithm, "MGF1",
    MGF1ParameterSpec.SHA1, PSource.PSpecified.DEFAULT);
```

这段密文与 OpenSSL/Go/Node 等按 RFC 8017 主哈希派生 MGF1 的实现**互操作时解不开**。结论：**跨语言场景永远显式传 `OAEPParameterSpec`，两端四元组（主哈希/MGF/MGF 哈希/PSource）逐一钉死。**

### 6.3.2 ECDH 协商 + HKDF 派生

```java
import javax.crypto.KeyAgreement;
import javax.crypto.KDF;
import java.security.*;
import javax.crypto.spec.HKDFParameterSpec;

// 双方各自生成一次性 X25519 密钥对（JDK 11+），4.6 节流程的代码化
KeyPair kpA = KeyPairGenerator.getInstance("X25519").generateKeyPair();
KeyPair kpB = KeyPairGenerator.getInstance("X25519").generateKeyPair();

// A 侧：用自己的私钥 + 对方公钥，算出共享秘密
KeyAgreement ka = KeyAgreement.getInstance("X25519");
ka.init(kpA.getPrivate());
ka.doPhase(kpB.getPublic(), true);
byte[] sharedSecret = ka.generateSecret();    // B 侧对称操作，得到同一秘密

// 共享秘密不是均匀密钥 —— 必须过 KDF（HKDF）再当 AES 密钥（4.6 节要点 1）
KDF kdf = KDF.getInstance("HKDF-SHA256");     // KDF API：JDK 25 起
SecretKey aesKey = kdf.deriveKey("AES",
        HKDFParameterSpec.ofExtract()
                         .addIKM(sharedSecret)
                         .addSalt("handshake-context".getBytes())
                         .thenExpand("session-key".getBytes(), 32));
```

（KDF 用法直接取自 JDK 类文档的标准示例，`javax/crypto/KDF.java:57-66`；ECDH 公钥由 JDK 按 NIST SP 800-56A 校验，`ECDHKeyAgreement.java:169`。JDK 21 起另有 `javax.crypto.KEM` 用于 ML-KEM/HPKE 封装。）

## 6.4 Spring Security crypto：站在 JCA 之上的一层封装

Spring 没有重造密码学，它做的是**把"选模式、管 IV、派生密钥"这些容易错的事固化到 API 里**（`D:\code\3rd\spring-security\crypto\src\main\java\org\springframework\security\crypto\encrypt\`）：

```java
// 文本加密：password + salt → PBKDF2 派生真正的 AES 密钥（用户口令不宜直接当密钥）
TextEncryptor encryptor = Encryptors.delux(password, salt);   // AES-GCM
String sealed = encryptor.encrypt("敏感配置");

// 字节加密：直接给 AES-256-GCM
BytesEncryptor gcm = Encryptors.stronger(password, salt);     // GCM 模式（较老版本为 CBC）
byte[] sealed2 = gcm.encrypt(data);
```

实现证据：`Encryptors.java:50-51` 把 `password(...)` 也指到 `AesBytesEncryptor(..., CipherAlgorithm.GCM)`；`AesGcmBytesEncryptor.java:109/122` 内部就是标准 `new GCMParameterSpec(TAG_LENGTH_BITS, iv)`——它替你做对的事：GCM（而非默认 ECB/CBC）、随机 IV 每次生成、盐防彩虹表、口令经 PBKDF2 派生。**选型启示：业务代码要么用这类高阶封装，要么照 6.2 手写并全部走 6.5 清单——不要半吊子组合。**

## 6.5 坑清单（每一条都对应过真实事故）

| # | 坑 | 正确姿势 | 依据 |
|---|---|---|---|
| 1 | `Cipher.getInstance("AES")` 裸写 | 永远写全三段式；首选 `AES/GCM/NoPadding` | 裸 "AES" 默认 ECB（3.5.1） |
| 2 | `new Random()` 生成密钥/IV | 一律 `SecureRandom`（DRBG） | `SecureRandom.java:41-58` |
| 3 | RSA 字符串式 OAEP 跨语言解不开 | 显式 `OAEPParameterSpec`（MGF1 哈希钉 SHA-256） | `RSACipher.java:316-317` |
| 4 | GCM IV/nonce 复用 | 同密钥下 IV 绝不复用；Cipher 一次性 | `Cipher.java:113-114`、7.2 |
| 5 | RSA 直接加密业务数据/大文件 | 信封加密：RSA 只封会话密钥 | `RSACipher.java:63`、4.2.2 |
| 6 | 加密后不存 IV，密文变"死文" | IV 随密文一起存/传（或取 `getParameters()`） | `CipherCore.java:473-474` |
| 7 | 密钥硬编码/写日志/进 Git | KMS、环境变量、KeyStore；byte[] 用完 `Arrays.fill(0)` 清零 | 7.4 |
| 8 | 自己拼"加密+校验"顺序（先 MAC 后加密等） | 用 AEAD；组合方案只认 Encrypt-then-MAC | 3.5.4、5.4 |
| 9 | 口令加密存储 | 慢哈希 bcrypt/Argon2/PBKDF2，加密可逆就不该用 | 2.4 |
| 10 | 确定性加密可被字典攻击仍上线 | 评估是否真需要确定性（等值查询）；是则用 AES-SIV/固定域加密 | 2.5、5.3 |

## 本章小结

- JCA = Engine 门面 + Provider 注册表；三段式 transformation 定行为；`WRAP/UNWRAP` 模式是数字信封的官方 API；AEAD 模式 Cipher 一次性。
- AES-GCM 五步：随机 12 字节 IV → `GCMParameterSpec(128, iv)` → AAD → `doFinal` → 发 `[iv‖ct‖tag]`；解密端 AAD 逐字节一致。
- RSA 三件事：3072 位起步、显式 `OAEPParameterSpec`（MGF1 坑 `RSACipher.java:316-317`）、只封会话密钥；ECDH 用 X25519 + HKDF（JDK 25 的 KDF API）。
- Spring Security crypto 的价值是把"模式/IV/派生"做对固化；手写则逐条对照 6.5 清单。

# 七、安全专题：真实误用与教训

## 7.1 ECB 的企鹅：模式泄露的具象化

把一张企鹅图片用 AES-ECB 加密后再看，企鹅还在——因为大片相同颜色的像素块加密后仍是大片相同密文块（`ElectronicCodeBook.java:100-108` 逐块独立加密，块间零交流）。 Wikipedia 用"ECB 企鹅"来纪念这个教训。推广到业务数据：状态位、重复 ID、金额档位……一切模式都写在密文里。**ECB 不是"加密了没加密好"，而是"加密了个寂寞"。**

## 7.2 GCM nonce 重用：灾难中的灾难

回顾 3.5.4，GCM = CTR 加密 + GHASH 认证。同一 (key, IV) 用两次，两条腿同时骨折：

1. **保密性塌**：密钥流相同，`C1 ⊕ C2 = P1 ⊕ P2`——两段明文的异或直接可见（可再结合格式知识分离）；
2. **完整性塌得更彻底**：GHASH 的认证子密钥 H 可以从重用的 IV 中**直接算出**，此后攻击者在该密钥下**伪造任意密文**且 tag 校验通过——AEAD 的"防篡改"承诺整体作废。

JDK 的防线在 API 层（`Cipher.java:113-114`，AEAD 模式 Cipher 对象禁止复用）与规范层（96 位 IV 随机碰撞概率 2^-48 起才需要担心——消息量到"亿条同密钥"量级时应改用**确定性构造的 IV**：`密钥专属前缀 ‖ 计数器`，NIST SP 800-38D §8）。工程纪律一句话：**AES-GCM 的 (key, IV) 是一次性票券，检票即作废。**

## 7.3 填充预言：一条报错信息引发的二十年攻防

攻击面来自 2.5 节那句话：**解密失败的报错不能区分失败原因**。

- **Bleichenbacher 攻击（1998）**：RSA PKCS#1 v1.5 解密时，若服务器对"填充格式错误"与"填充对了但业务出错"返回不同响应/耗时，攻击者就能把密文当"预言机"逐字节剥离填充、最终解出明文。SSL/TLS 为此打补丁打了近 20 年（2017 年的 ROBOT 攻击还在收割老设备）；
- **CBC Padding Oracle（Vaudenay, 2002）**：CBC 解密要先验填充再验 MAC，若"填充错"与"MAC 错"报错不同，攻击者可逐字节改造密文试探——经典案例是 ASP.NET 的 padding oracle（CVE-2010-3332）；
- **Lucky13（2013）**：填充错与 MAC 错的**时间差**也能当预言机——连报错内容一致都不够，耗时也得一致。

工程层面到处是应对的痕迹：JDK 的 RSA 解填充是显式的**常数时间实现**（`sun/security/rsa/RSAPadding.java:320-323`）：

（`bp` 变量全程位运算累计"坏填充"标记，`RSAPadding.java:336`，最后一次性决定返回值。）TLS 1.3 干脆用 AEAD 把填充概念从解密路径里删除。**给自己的服务的启示：解密失败对外统一返回"解密失败"，内部再记日志；能用 AEAD 就别手搓"加密+填充"。**

## 7.4 密钥管理：算法之外的全部战争

Kerckhoffs 原则（2.2）把安全全部押在密钥上，于是密钥的生老病死成了独立学科：

| 阶段 | 要点 | 工程手段 |
|---|---|---|
| 生成 | 密码学安全随机、足够长度 | `SecureRandom`/DRBG；`KeyGenerator.init(256)` |
| 存储 | **不进代码、不进 Git、不进日志** | KMS（云厂商）、HSM、KeyStore（JKS/PKCS12）、环境变量 + 启动注入 |
| 分发 | 信封加密（4.5）：主密钥在 KMS，数据密钥加密下发 | `WRAP/UNWRAP`（6.1） |
| 轮换 | 密钥版本化，旧密钥只解不加密 | KMS 密钥版本；信封加密天然支持（换数据密钥即可） |
| 销毁 | byte[] 用完清零；String 不可清零所以密钥别用 String | `Arrays.fill(keyBytes, (byte)0)` |
| 备份/恢复 | 丢了密钥 = 数据蒸发；恢复路径先于加密上线 | 密钥托管、多副本、恢复密钥离线保存 |

前向安全（PFS）是密钥管理的"时间维度"答案：**每次会话用临时 (EC)DHE 密钥，长期私钥只做签名**——长期私钥明天泄露，昨天的流量历史依然安全（TLS 1.3 强制，TLS.md 2.3）。

## 7.5 后量子：Shor 来了，ML-KEM 已就位

- **威胁**：Shor 算法在足够大的通用量子计算机上可以**多项式时间**分解大数与解离散对数——RSA、DH、ECC 的数学地基同时蒸发；对称加密只受 Grover 算法影响（等效密钥长度减半），AES-256 依然够用。**这就是为什么密钥交换是最急迫的迁移点。**
- **"现在收割，以后解密"（harvest now, decrypt later）**：攻击者今天记录你的密文，等量子计算机成熟再解——保密期超过 10 年的数据现在就该考虑后量子。
- **现状**：NIST 2024-08 定稿 FIPS 203（ML-KEM，基于格的 KEM）；**JDK 24 通过 JEP 496 内置 ML-KEM**，SunJCE 注册了 ML-KEM-512/768/1024 三档（`SunJCE.java:765-768`）以及 HPKE（RFC 9180，`SunJCE.java:374,761`）。迁移的主流姿势是**混合密钥交换**（X25519 + ML-KEM-768 各算一半，合起来派生密钥）——任一算法被破仍有另一条防线。

```java
// 后量子密钥封装在 JDK 里已是普通 API（KEM，JDK 21 起）
KEM kem = KEM.getInstance("ML-KEM-768");
KEM.Encapsulator enc = kem.newEncapsulator(recipientPublicKey);
KEM.Encapsulated sealed = enc.encapsulate();      // sealed.encapsulation() 发给对方
SecretKey sharedKey = sealed.key();               // 对方用私钥 decapsulate 得同一把
```

## 本章小结

- ECB 的企鹅与 GCM 的 nonce 重用，一个泄露模式、一个连加密带认证全塌——**模式与随机性纪律优先于算法强度**。
- 填充预言教会行业一件事：**报错与耗时都是信息**；JDK 用常数时间解填充（`RSAPadding.java:321`），新代码用 AEAD 绕开整个攻击面。
- 密钥的生成/存储/分发/轮换/销毁是算法之外的全部战争；KMS + 信封加密 + 前向安全是三件现代标配。
- 后量子已从论文变成 JDK API（ML-KEM/HPKE 内置）；保密期长的数据现在就该启用混合密钥交换。

## 8.2 安全强度等价表（NIST SP 800-57）

| 对称密钥 | RSA 模数 | ECC 曲线 | 说明 |
|---|---|---|---|
| 80 位 | RSA-1024 | P-192 | **已淘汰**，仅存量 |
| 112 位 | RSA-2048 | P-224 | 2030 年前够用的底线 |
| 128 位 | RSA-3072 | P-256 / X25519 | **新系统默认档** |
| 192 位 | RSA-7680 | P-384 | 高安全场景 |
| 256 位 | RSA-15360 | P-521 | 长期机密；对称侧选 AES-256 |

读法：密钥翻倍 ≠ 强度翻倍；**换算法家族（RSA→ECC）可以用指数级更短的密钥拿到同强度**，这正是 4.3 节 ECC 的卖点。

## 8.3 动手实验（按性价比排序）

1. **亲眼看见 ECB 泄露**（10 分钟）：用 6.2 代码把 `AES/GCM/NoPadding` 换成 `AES/ECB/PKCS5Padding` 加密一张 BMP 图片的字节，输出成文件再打开——企鹅浮现；再换回 GCM 对比。
2. **GCM 防篡改体验**（5 分钟）：跑 6.2 的 main，翻转密文任意 1 位，观察 `AEADBadTagException`；再翻转 IV 一位试试——tag 一样拦住。
3. **nonce 重用现场**（10 分钟）：写个循环用同一 (key, IV) 加密两段明文，把两个密文异或——你会看到明文的异或直接可读（英文场景甚至人眼可分）。
4. **RSA 信封走一遍**（15 分钟）：6.3.1 代码，用 `keytool`/openssl 生成密钥对互操作；再故意去掉显式 `OAEPParameterSpec`，与 `openssl pkeyutl -decrypt` 对解——体验 MGF1 坑。
5. **手算 RSA 小例子**（5 分钟）：4.2.1 的 p=61、q=53 那组数，用 Python/Java BigInteger 验证 `65^17 mod 3233 = 2790` 与反算——陷门函数第一次真正过手。
6. **量一次性能差距**（10 分钟）：循环加密 1 MB 数据分别用 AES-GCM 与 RSA-OAEP 分块——数量级差异（3~5 个数量级）会替你记住"为什么混合加密"。
