# 微服务开发语言选型：云原生与虚拟机

> **面向场景**：团队以微服务为主，开发范围覆盖网关、业务服务、治理与中间件，技术底座是 Spring 体系（对照 [Spring All Projects](../spring/Spring%20All%20Projects.md) 的项目清单）。同一套系统有时部署在 Kubernetes 上，有时部署在虚拟机上。
>
> **本文要回答的两件事**：
>
> 1. 云原生和虚拟机各自适合什么工作负载；
> 2. 网关、业务服务、注册配置、消息、安全、可观测、批处理、平台控制器这些组件，分别适合用什么语言开发。
>
> **核心结论（先读这一段即可做评审）**：部署形态决定的是运行合同（弹性、发布、隔离、运维入口），组件层次决定的是语言。业界已经稳定的分工是——**业务与集成用 Java（Spring）**，**流量数据面用 C++/Rust 的成熟实现（Envoy、Nginx、Linkerd2-proxy）**，**平台控制面、Operator、网格控制面用 Go**。虚拟机方案把语言收敛到 Java，用 SDK 集成；云原生方案允许业务继续用 Java，平台能力走探针、Service、Ingress、OpenTelemetry 这些进程外契约。JDK 21 之后的虚拟线程，已经拿掉了「IO 密集的业务服务必须改写成 Go」的主要理由。
>
> **时间锚点**：2026-10。运行基线按当前团队语境取 Spring Boot 4.x / JDK 21~25。文中案例均为各项目公开的实现语言与公开架构，不引用无法核对的内部指标。
>
> **姊妹文档**：能力重叠与「哪些治理下沉到 Kubernetes」见 [Spring Cloud vs k8s](../spring/Spring%20Cloud%20vs%20k8s.md)；组件职责见 [Spring All Projects](../spring/Spring%20All%20Projects.md)。

# 一、总览：先分清「跑在哪」和「用什么写」

## 1.1 一句话定位

**语言选型是按组件层次做的工程分工，部署选型是按工作负载做的运行合同；两者正交，只在交付物形态（镜像还是 fat jar、SDK 还是 Sidecar）上互相修正。**

把「上云原生」理解成「业务改写成 Go」，或把「还在虚拟机」理解成「只能用 Java」，都会选错。Netflix 的主体业务长期跑在 JVM 上，同时运行在 AWS 的容器平台 Titus 里；蚂蚁的 SOFA 业务是 Java，网格数据面 MOSN 是 Go；阿里的 Dubbo、Nacos、Sentinel、Seata、RocketMQ 是 Java，入口网关 Higress 是 Go 控制面加 Envoy（C++）数据面。这些系统都是微服务，也都同时存在容器与传统主机两种落地方式。

## 1.2 选型原则

做决定之前先记住六条，后面的表格都是这六条的展开。

1. **语言跟组件的热点走，不跟部署口号走。** 热点在领域模型和事务里，用 Java。热点在每包转发、每连接状态机里，用 C++/Rust。热点在对 Kubernetes API 的声明式调谐里，用 Go。
2. **调用方的语言决定共享库的语言。** 业务全是 Spring 时，内部 Starter、治理 SDK、数据访问封装就用 Java。要求业务引入一套 Go SDK，等于要求每个服务多一个进程模型。云原生里若不想绑定语言，就把能力做成 Sidecar 或集群插件，而不是再做一个多语言 SDK。
3. **中间件优先采用，自研限于业务语义。** 注册中心、消息 Broker、缓存引擎、入口数据面，业界都有默认实现。团队要写的是：路由里的租户规则、鉴权里的业务权限、消息的消费语义、事务的边界。自研一个「类 Nginx」或「类 Kafka」不在本文的推荐集合里。
4. **一种部署形态里，生产语言不超过两种。** 虚拟机方案收敛为 Java。云原生方案是 Java（业务）+ Go（自有控制器/运维工具）。Rust/C++ 只出现在「采用 Envoy/Nginx/Linkerd-proxy」，不出现在业务仓库里。第三种生产语言要单独评审。
5. **虚拟线程改变了业务层的并发理由，没有改变数据面的理由。** JDK 21 起的虚拟线程让「一个请求一个线程」的内存成本下降一个数量级，Spring Boot 3.2+ / 4.x 已能直接使用。IO 密集型 CRUD、网关过滤器、RPC 调用不再构成改写 Go 的充分条件。GC 尾延迟、每实例几十 MB 内存、无运行时的静态二进制，仍然是 Go/Rust 的理由，只是这些理由落在数据面和密度敏感的平台组件上。
6. **部署形态按工作负载拆，不按系统拆。** 一个系统里可以同时存在：无状态业务在 Kubernetes、Oracle 在虚拟机或物理机、入口数据面在独立节点池。第二章按负载给出边界，而不是要求整套系统一次选边。

## 1.3 组件分层全景

下面的分层对齐 Spring 项目清单，并补上清单之外、微服务落地必须有的平台组件。语言列是「若由本团队开发这一层」的默认选择；「采用」表示这一层不应从零开发。

```
┌────────────────────────── 入口与流量数据面 ──────────────────────────┐
│  集群入口 / 边缘代理          采用 Envoy(C++)、Nginx(C)、HAProxy(C)   │
│  业务网关（鉴权、租户路由）    Java：Spring Cloud Gateway              │
│  网格数据面                   采用 Envoy(C++) 或评估 MOSN(Go)          │
├────────────────────────── 业务与应用框架 ────────────────────────────┤
│  面向页面的 BFF               Java；前端独立发布且无事务时用 TypeScript │
│  业务微服务                   Java / Kotlin：Spring Boot + Framework  │
│  安全（登录、资源服务器）      Java：Spring Security、Authorization Server │
│  数据访问、事务边界            Java：Spring Data、本地事务；Seata 仅在有跨库诉求时 │
│  批处理、企业集成              Java：Spring Batch、Spring Integration  │
│  业务侧 AI 编排                Java：Spring AI；训练与笔记本用 Python   │
├────────────────────────── 治理与集成（库，不是新进程）────────────────┤
│  客户端负载均衡、声明式 HTTP   Java：Spring Cloud LoadBalancer、OpenFeign / HTTP Interface │
│  熔断限流（业务语义）          Java：Resilience4j、Sentinel            │
│  消息客户端                    Java：Spring for Apache Kafka / AMQP / Pulsar │
│  RPC                           Java：Spring gRPC、Dubbo；跨语言契约用 Protobuf │
│  指标与追踪埋点                Java：Micrometer、Micrometer Tracing、OTel API │
├────────────────────────── 独立中间件进程（优先采用）──────────────────┤
│  注册与配置   Nacos(Java) / etcd(Go) / Kubernetes API                 │
│  消息 Broker  Kafka(Scala/Java)、RocketMQ(Java)、Pulsar(Java)        │
│  缓存         Redis / Valkey(C)                                       │
│  配置灰度     Apollo(Java)、Nacos(Java)                               │
│  观测后端     Prometheus(Go)、OTel Collector(Go)、Jaeger(Go)          │
├────────────────────────── 平台控制面（云原生才需要自研时）────────────┤
│  Operator、CRD 控制器、网格控制面、集群插件    Go                       │
│  集群 CNI、eBPF 数据路径                  采用 Cilium(Go + eBPF)       │
└──────────────────────────────────────────────────────────────────────┘
```

请求从外到内经过：集群入口 → 业务网关 → 面向页面的 BFF → 业务微服务。BFF 负责「这一屏要什么」，领域服务负责「业务是否成立」，分工见 4.3。

Spring All Projects 的八类（应用核心、数据访问、云原生与分布式、安全、Web 与 API、消息与集成、会话与架构、可观测）几乎全部落在上图的第二、三层，默认语言是 Java。真正拉开语言差距的是第一层和第五层，这两层在 Spring 清单里要么没有，要么只是客户端。

## 1.4 部署形态如何修正语言结论

```
                         工作负载特征
                              │
              ┌───────────────┴───────────────┐
              ▼                               ▼
        虚拟机 / systemd                  Kubernetes
        Ansible / 安装包                  镜像 + 探针 + HPA
              │                               │
              │ 集成靠同语言 SDK               │ 集成靠进程外契约
              ▼                               ▼
        语言收敛为 Java                  业务仍是 Java
        fat jar + JDK 镜像               平台组件用 Go
              │                          数据面采用 C++/Rust
              └────────────┬─────────────────┘
                           ▼
                    交付物不同，领域代码相同
              （同一套 Spring Boot 工程，两种运行合同）
```

修正只发生在三处：

| 修正点 | 虚拟机 | 云原生 |
|---|---|---|
| 服务发现、配置、四层负载均衡 | 应用内 SDK（Nacos、Spring Cloud） | 集群 Service、ConfigMap、kube-proxy；业务代码不再写注册逻辑 |
| 入口 | 独立网关进程，业务网关可用 Spring Cloud Gateway | 集群入口用 Ingress / Gateway API（Envoy 系），业务网关仍可保留 |
| 自研运维控制器 | 很少需要，用脚本和配置管理 | Operator 用 Go，不用 Java 去对接 controller-runtime 生态 |

业务仓库的语言在两种形态下保持 Java。变化的是依赖清单：云原生上删掉 Eureka/Nacos 客户端这类与平台重复的治理，虚拟机上保留它们。这一点与 [Spring Cloud vs k8s](../spring/Spring%20Cloud%20vs%20k8s.md) 的分层结论一致。

## 1.5 关键问题 → 选型结论

| 要决定的问题 | 结论 | 详见 |
|---|---|---|
| 无状态业务、要滚动发布和按流量伸缩 | 云原生；语言保持 Java | 二、四.2 |
| Oracle、按核授权的商业中间件、超大本地盘 | 虚拟机或物理机；语言与机器无关，客户端仍是 Java | 二.3 |
| 服务只有个位数、没有平台组 | 虚拟机或单集群托管 Kubernetes 都可以；不要为语言单独立项 | 二.4 |
| 业务 CRUD、领域复杂、要本地事务 | Java（Spring Boot） | 四.2 |
| 入口要抗高连接数、规则相对规整 | 采用 Envoy / Nginx / Higress，自研语言不是 Java | 四.4 |
| 网关里塞满鉴权、租户、协议转换 | Java，Spring Cloud Gateway | 四.4 |
| 一屏要拼多个领域服务，或多种端的数据形状不同 | 为该端增加 BFF；领域 API 保持稳定 | 四.3 |
| 要写 Kubernetes Operator 或网格控制面 | Go | 四.11 |
| 要自研消息 Broker、缓存引擎、注册中心内核 | 不自研；采用 Kafka/RocketMQ、Redis、Nacos 或 etcd | 四.6、四.7 |
| IO 并发高，想因此把业务改成 Go | 先用虚拟线程；改语言要另有内存或尾延迟证据 | 三.1、五 |
| 模型训练、离线数据脚本 | Python；线上编排仍回到 Java 服务 | 四.10 |
| 前端团队要独立发布的 BFF | TypeScript（NestJS 一类）；带事务的领域逻辑留在 Java | 四.3 |

## 1.6 业界演进：语言分工是怎么稳定下来的

| 阶段 | 大概时间 | 运行形态 | 语言格局 | 对今天的意义 |
|---|---|---|---|---|
| 应用服务器 | 2004–2013 | 虚拟机 + WAR + 外置 Tomcat/WebLogic | 企业系统几乎只有 Java | Spring 取代 EJB，语言没有选择 |
| fat jar 微服务 | 2014–2018 | 虚拟机或 IaaS，Spring Boot 可执行包；Netflix OSS（Eureka、Zuul、Hystrix、Ribbon） | 业务和治理 SDK 都是 Java；Docker、Kubernetes、etcd、Prometheus 用 Go 写平台 | 「微服务 = Spring Cloud 全家桶」形成于这一阶段，绑定的是虚拟机式 SDK 集成 |
| 编排成为默认运行时 | 2017–2021 | Kubernetes 进入企业；服务网格出现 | 控制面 Go（Istio、Traefik、Argo），数据面 C++（Envoy）与稍后的 Rust（Linkerd2-proxy） | 平台语言和业务语言分开。阿里系中间件仍是 Java，蚂蚁用 Go 写 MOSN 做数据面 |
| 云原生业务语言分化 | 2018–2023 | 互联网新系统直接上 Kubernetes | 字节 CloudWeGo（Kitex、Hertz）用 Go；企业存量与金融继续 Java。Uber 从 Python/Node 把关键路径迁到 Go 和 Java | 新公司可以全盘 Go；已有 Spring 资产的团队迁移业务语言的收益远小于平台下沉 |
| 运行时补齐 | 2022–2026 | 两种部署长期并存 | JDK 17 基线、JDK 21 虚拟线程、Spring Boot 3 的 GraalVM 原生镜像、Boot 4 / Framework 7 继续这条线。Cloudflare 用 Rust 写 Pingora 替换边缘 Nginx。Discord 把尾延迟敏感的读状态服务从 Go 改到 Rust | 业务层「为并发离开 Java」的理由变弱；数据面「为尾延迟离开 GC 语言」的理由还在 |

2026 年的稳定格局可以压成一句：**企业微服务的业务仓库以 Java 为主，云原生平台仓库以 Go 为主，包转发路径以 C++/Rust 为主。** 三份代码很少在同一个仓库里。

# 二、部署形态：云原生与虚拟机各自适合什么

## 2.1 本章定位

本章只决定进程跑在哪、由谁拉起、失败了谁负责重启。它不决定语言。语言在第四章按组件给出，第五章说明部署形态会怎样小幅修正。

这里的「云原生」指容器 + Kubernetes 的运行合同：镜像为交付物，探针表达健康，副本可水平伸缩，发布是滚动或金丝雀，配置来自 ConfigMap/Secret 或外部配置系统，日志和指标走标准输出与 OpenTelemetry。托管 Kubernetes、自建 Kubernetes、云厂商 Serverless 容器都算这一类。

「虚拟机」指以 Linux 虚拟机（或少量物理机）为边界的运行合同：systemd 或等价进程管理拉起 fat jar，发布靠替换包和重启，伸缩靠加减机器，配置靠配置中心或机器上的文件，网络分区靠安全组和传统负载均衡。IaaS 云主机属于这一类，关键是没有 Kubernetes 控制循环。

## 2.2 两种合同分别买到什么

| 能力 | 云原生合同买到的 | 虚拟机合同买到的 |
|---|---|---|
| 发布 | 滚动、按流量比例金丝雀、声明式回滚 | 发布步骤少，窗口清晰，单机失败域好解释 |
| 伸缩 | HPA/VPA、按副本装箱，适合流量昼夜差大的无状态服务 | 垂直扩容直接，超大堆和本地盘好规划 |
| 失败恢复 | 节点故障时重新调度；探针摘除流量 | 进程级重启；机器级故障要靠负载均衡和备用机 |
| 密度 | 多服务共享节点，小服务更划算 | 一机少进程时简单；服务一多，机器利用率靠人肉 |
| 依赖治理 | Service、Ingress、网关 API、可选的网格 | SDK 注册中心、独立网关、传统四层负载均衡 |
| 隔离与合规 | 命名空间、配额、网络策略、Pod 安全标准 | 机器边界天然清晰，等保和专机审计路径短 |
| 状态与授权软件 | 本地盘、授权按核、超大页内存都要额外设计（独立节点池、本地 PV） | Oracle、按 socket/核授权的商业中间件、固定盘符的安装程序，路径成熟 |
| 团队成本 | 需要能维护集群、网络插件、证书、升级的平台能力 | 需要能写清楚 systemd、JVM 参数、机器基线的运维能力 |

两种合同都做得到「把 Java 进程跑起来」。差别在于：副本数、发布频率、服务个数上来之后，哪一份合同的边际成本更低。

## 2.3 场景决策矩阵

满足左列特征时，优先采用右列形态。一条负载只归一个主形态；同一系统的不同负载可以不同。

| 负载特征 | 更合适的形态 | 原因 |
|---|---|---|
| 无状态 HTTP/RPC，副本 ≥ 2，每周多次发布 | 云原生 | 滚动发布和副本调度是编排器的本职 |
| 流量有明显峰谷（大促、日间/夜间差一个数量级以上） | 云原生 | 弹性来自副本数，而不是提前买满峰值机器 |
| 服务数量持续增加，环境要 dev/staging/prod 同构 | 云原生 | 环境是声明式清单，不是另一套装机脚本 |
| 需要按请求特征做金丝雀（头、权重、租户） | 云原生 | Gateway API / 网格的流量策略比「再部署一套虚拟机」便宜 |
| 多语言进程要统一健康检查、日志、指标 | 云原生 | 探针、标准输出、OTel 是语言无关的合同 |
| Oracle 及同类按核/socket 授权、强依赖本地盘的数据库 | 虚拟机或物理机 | 授权计量、大页、NUMA、存储多路径在固定机器上更可控 |
| 安装模型是「解压 + 图形或 shell 安装程序」的商业中间件，厂商支持矩阵只覆盖主机 | 虚拟机 | 把支持边界外的容器化当成项目风险 |
| 单进程堆很大（数十 GB）、长期运行、副本数就是 1 或 2 | 虚拟机 | 垂直伸缩和 GC 参数按机器调；容器内存记账和 OOMKill 成为额外事故源 |
| 服务个位数、月级发布、没有平台组 | 虚拟机 | 集群本身的升级、证书、CNI、etcd 备份会超过业务收益 |
| 等保或行业审计要求故障域等于一台可点名的机器 | 虚拟机 | 机器边界比「这个 Pod 可能被调度到哪台节点」好写进审计说明 |
| 有状态消息或协调集群，磁盘吞吐和尾延迟是 SLO | 虚拟机，或云原生上的独立节点池 + 本地盘 | Kafka、etcd 可以上 Kubernetes（Strimzi、bitnami 一类），前提是磁盘和调度按有状态服务设计，而不是和业务副本混部 |
| 短任务、按事件拉起、空闲应为零 | 云原生（Job，或真正需要缩到零时再用 Knative 一类） | 虚拟机上空闲进程的固定成本更高 |
| 边缘机房只有一两台机器、运维靠登录 | 虚拟机 | 单机 Kubernetes 能装，但故障时多一层控制面 |

三个容易判错的边界：

- **「公司在用云」不等于这份负载该上 Kubernetes。** 云主机上的 systemd 就是虚拟机方案。很多 Oracle 和核心批处理长期停在这一层是合理的。
- **「已经有 Kubernetes」不等于所有进程都进业务节点池。** 数据库、入口代理、有状态消息应使用独立节点池或集群外机器，避免和业务副本抢 CPU、互相驱逐。
- **个位数微服务不必为了形态正确而自建集群。** 若组织已经有被维护的托管集群，无状态服务直接进去。若集群还要本团队从零搭建，先把无状态服务做成可容器化的 fat jar，跑在虚拟机上，等平台能力到位再迁。迁移的是运行合同，不是重写。

## 2.4 对本团队的组合方式

团队的业务是 Spring 微服务，数据侧有 Oracle 这类传统数据库，治理能力在 Spring Cloud 与 Kubernetes 之间取舍。组合方式按负载切开：

| 负载 | 形态 | 语言含义 |
|---|---|---|
| 业务微服务、业务网关、批处理作业 | 有平台时用云原生；平台未就绪时用虚拟机。同一份 Boot 工程 | Java |
| 注册、配置、熔断 | 虚拟机：Nacos + Sentinel/Resilience4j。云原生：发现交给 Service，熔断留在业务进程内，配置可用 ConfigMap 或继续用 Nacos | 客户端是 Java；不新写注册中心 |
| 集群入口 | 云原生用 Ingress 或 Gateway API 的 Envoy 实现；虚拟机用 Nginx/HAProxy 或同一套 Envoy | 采用，不自研数据面 |
| Oracle、需要稳定本地盘的 Broker | 虚拟机或独立节点池 | 业务通过 Java 驱动访问 |
| 自己写的 Operator、发布控制器 | 仅云原生需要 | Go |

服务数量还少（例如三五个）时，云原生的收益主要是发布和同构，不是语言。这个规模下维持一套 Nacos 往往比引入网格便宜；等服务数和发布频率上来，再把发现和入口下沉到集群。下沉顺序已在 Spring Cloud 与 Kubernetes 的对比文档里写过，这里不重复。

## 2.5 业界案例

案例说明「形态和语言是分开选的」，不说明每家都该照搬。

| 组织 | 部署形态 | 语言分工 | 可借鉴的点 |
|---|---|---|---|
| Netflix | AWS 上的容器平台 Titus，早期是云主机 | 播放与中台主体是 JVM；Zuul 1/2 是 Java（Zuul 2 基于 Netty）；Eureka、Hystrix、Ribbon 也是 Java。平台组件另有 Go | 微服务治理可以全在 JVM 内完成，同时运行在容器平台上。他们后来把一部分能力让给了平台，语言没有因此改成 Go |
| 阿里巴巴 | 大规模容器平台与传统部署并存 | Dubbo、Nacos、Sentinel、Seata、RocketMQ 是 Java；Higress 控制面是 Go，数据面是 Envoy | 业务中间件用 Java 吃透 Spring/Netty 生态；入口数据面改用 Envoy，而不是把 Spring Cloud Gateway 放到公网边缘硬抗 |
| 蚂蚁集团 | 金融级混合部署 | SOFA 业务栈 Java；Sidecar MOSN 用 Go | 网格数据面可以是 Go（MOSN 的模块化、可嵌入），但业务服务不因此改写 |
| 字节跳动 | 业务默认云原生 | RPC 框架 Kitex、HTTP 框架 Hertz 是 Go；CloudWeGo 的 Volo 用 Rust 做另一条 RPC 路线 | 这是「新系统从第一天就用 Go」的路径，适合没有 Spring 存量的团队。已有 Boot 资产时，迁移成本要单独算，不能只引用他们的框架名单 |
| Uber | 云上容器与编排 | 早期 Python、Node 撑不住关键路径后，服务端落到 Go 和 Java；Cadence 工作流引擎是 Go；Jaeger 起源于这里，收集器是 Go | 离开的是动态语言的关键路径，落到的是 Go **和** Java，不是单一语言 |
| Google | Borg / Kubernetes | Kubernetes、etcd 系控制组件是 Go；Envoy 的广泛使用把数据面留在 C++；gRPC 的核心实现是 C++，Java/Go 是一等公民的桩代码 | 平台用 Go，数据面用 C++，业务桩代码多语言。这是云原生语言分工的源头 |
| Cloudflare | 全球边缘节点 | 长期用 Nginx/OpenResty（C + Lua）；Pingora 用 Rust 重写边缘代理，用来控制尾延迟和连接规模 | 边缘数据面从 C 走到 Rust，是因为 GC 和 Nginx 的扩展模型都碰到了产品约束。业务 API 团队不应套用这个结论 |
| Discord | 云主机与容器混合 | 实时通道大量使用 Elixir；读状态服务因 Go GC 造成延迟毛刺，改写为 Rust | 只有尾延迟本身就是产品指标时，才值得为摆脱 GC 换 Rust |
| 典型银行与运营商 | 核心区虚拟机，渠道区逐步 Kubernetes | 渠道和中台 Java；核心库 Oracle 在虚拟机或小型机；网关数据面 Nginx/F5 | 与本团队最接近的参照：无状态 Java 服务可迁移，数据库和授权软件留在原形态 |

## 本章小结

- 云原生适合无状态、副本化、发布频繁、流量峰谷明显、服务数量还在涨的负载。
- 虚拟机适合数据库与按核授权软件、超大堆、个位数服务且没有平台组、以及审计边界必须是一台机器的负载。
- 一个系统按负载分形态。业务用 Java 写一次，两种合同都能跑。
- 形态切换时替换的是发现、入口和发布方式，不是业务语言。

# 三、候选语言能扛什么

只保留微服务主路径上真正会碰到的六种。Erlang（RabbitMQ）、Scala（Kafka 内核、Spark）是「采用该中间件时会遇到的实现语言」，不作为新组件的候选。C# 只在已经有 .NET 资产时成立，本团队不引入。

## 3.1 Java 与 Kotlin

**定位**：业务、业务网关、治理 SDK、数据访问、安全、批处理的默认语言。Kotlin 是同一平台上的方言：字节码、依赖、镜像、JVM 参数与 Java 相同，Spring 对 Kotlin 协程有一等支持。团队没有 Kotlin 存量时，新服务继续用 Java，避免两种方言并存。

**适合扛的负载**：

- 领域模型复杂、事务边界多、要和 Oracle/MySQL、Kafka、Redis 做成熟集成；
- 需要 Spring 的安全、数据、消息、观测一整套，而不是单点框架；
- 服务寿命以年计，人可以轮换，文档和 IDE 比「二进制小」更重要；
- IO 并发高，但单请求里有阻塞式 JDBC。虚拟线程把这类阻塞调用的线程成本降下来，JDBC 驱动保持阻塞模型即可，不必为了并发改成响应式。

**成本**：

- 常规 JVM 的常驻内存高于 Go，空载进程常见数百 MB 量级。副本很多、单副本 QPS 很低时，密度吃亏。
- 冷启动是秒级。长驻服务无感；缩到零的函数不适合用常规 JVM，原生镜像又受反射和 JDBC 驱动限制。本团队的服务是长驻微服务，这条成本可以忽略。
- 响应式（WebFlux）能提高网关和纯 IO 聚合的资源效率，也会提高排障成本。业务服务默认虚拟线程 + Spring MVC；只有业务网关这种「几乎不碰 JDBC、连接数是第一约束」的进程用 WebFlux。

**业界位置**：Spring 自身、Netflix 主体、阿里中间件家族、美团/京东的交易与中台、Keycloak、Elasticsearch、SkyWalking 后端、Flink、Cassandra、ZooKeeper。金融和运营商的渠道系统绝大多数仍是这条线。

## 3.2 Go

**定位**：云原生控制面和运维工具的默认语言。它不是本团队业务服务的默认语言。

**适合扛的负载**：

- Kubernetes 控制器：watch API、调谐循环、CRD。client-go 与 controller-runtime 是事实标准，Java Operator SDK 能写，但示例、控制器生成和招聘市场都薄一个数量级；
- 网格控制面、入口控制器、发布系统（Istio、Traefik、Argo CD、Higress 的控制面都属于这一类）；
- 要分发到大量机器上的单一静态二进制：探针、备份代理、节点工具；
- 内存预算按几十 MB 计、逻辑相对直、并发模型是「大量网络连接 + 少量业务规则」的独立进程。

**成本**：

- 泛型和错误处理对复杂领域模型不友好，交易、账务、权限这种长生命周期代码的表达力弱于 Java。
- GC 在绝大多数 RPC 里足够好，在亚毫秒尾延迟的数据面上会暴露（Discord 读状态、以及各家最终把数据面放到 Envoy/Rust 的原因）。
- 引入 Go 等于引入第二套构建、依赖、观测埋点和值班技能。只为「一个业务服务看起来更云原生」不划算。

**业界位置**：Kubernetes、containerd、etcd、Prometheus、Helm、Cilium 的控制进程、Istio、Consul、Vault、Terraform、NATS、Jaeger、OpenTelemetry Collector、Argo、Traefik、Higress 控制面、字节 Kitex/Hertz、蚂蚁 MOSN、腾讯 Polaris、Uber Cadence。

## 3.3 Rust

**定位**：要自己掌握尾延迟和内存上限的数据面。本团队默认采用别人写好的 Rust/C++ 数据面，不在业务项目里引入 Rust。

**适合扛的负载**：无 GC 的代理、嵌入式存储引擎、对 p99.9 有硬指标的转发路径。Linkerd2-proxy、Cloudflare Pingora、TiKV、Vector、AWS Firecracker 是公开案例。

**成本**：所有权模型拉长开发周期，和 Spring 生态之间没有自然的调用方式，只能走网络协议。团队规模不足以同时养熟 JVM 和 Rust 两套生产路径。

## 3.4 C 与 C++

**定位**：采用，不新写。Nginx、HAProxy、Redis/Valkey 是 C；Envoy、gRPC 核心是 C++。这些项目的正确用法是部署和配置，扩展优先用它们官方的扩展点（Envoy 的 Filter 用 C++ 或 Wasm，Nginx 用配置和受控的 Lua）。

业务团队用 C++ 写 Envoy Filter 之前，先确认规则是否能用现有过滤器和 Wasm（可以用 Go/Rust/TinyGo 编译）表达。大多数租户路由和鉴权用业务网关或 Wasm 就够。

## 3.5 Python

**定位**：模型训练、数据脚本、低 QPS 的内部工具。线上业务路径和网关不用 Python。

Spring AI、LangChain4j 解决的是「Java 服务怎么调用模型」。训练脚本、评测笔记本、一次性数据清洗留在 Python。自由线程（3.13 起实验、后续版本仍非默认）没有改变「业务服务应和现有事务栈在一起」的结论。

## 3.6 TypeScript（Node.js）

**定位**：由前端团队独立发布的面向页面 BFF，职责是接口裁剪和按屏聚合（见 4.3）。NestJS 是这一层常见的框架。

带数据库事务、权限判定、对账规则的逻辑留在 Java 服务。Node 单线程事件循环在 CPU 密集和复杂事务里没有优势，也会把领域模型拆到两个语言里。

## 本章小结

- Java 覆盖业务和全部 Spring 形态的组件。
- Go 覆盖自研的 Kubernetes 控制面和节点工具。
- Rust 和 C/C++ 覆盖数据面，方式是采用 Envoy、Nginx、Linkerd-proxy。
- Python 覆盖 AI 训练与脚本，TypeScript 覆盖前端拥有的 BFF。
- 新组件立项时，先用这张清单排除语言，再用第四章确认组件类别。

# 四、按组件的语言选型

## 4.1 总表

「开发语言」指本团队要写代码时的选择。「采用」指运行现成实现，本团队只写配置、规则和客户端。

| 组件 | 对齐的 Spring 项目或平台等价物 | 开发语言 | 采用什么，而不是重写 |
|---|---|---|---|
| 业务微服务 | Spring Boot、Spring Framework、Spring Modulith | Java | — |
| 面向页面的 BFF | 无（或一层薄的 Boot 服务） | 前端拥有则 TypeScript，否则 Java | — |
| 业务网关 | Spring Cloud Gateway | Java | 集群入口另采用 Envoy 系 |
| 边缘 / 集群入口 | Ingress、Gateway API | 不自研 | Envoy、Nginx、Higress、APISIX、Kong |
| 服务发现客户端 | Spring Cloud Kubernetes / Nacos / Eureka | Java 客户端 | 服务端用 Nacos，或云原生上用 Service |
| 配置中心 | Spring Cloud Config、Nacos、Apollo | 不自研服务端；客户端 Java | Nacos 或 Apollo |
| 业务熔断限流 | Resilience4j、Sentinel、Spring Cloud Circuit Breaker | Java | 全局限流可交给入口 Envoy |
| 声明式调用 | OpenFeign、HTTP Interface、Spring Cloud LoadBalancer | Java | — |
| RPC 框架与桩 | Spring gRPC、Dubbo | 业务侧 Java；契约 Protobuf | 不新写 RPC 框架 |
| 消息客户端 | Spring for Apache Kafka、AMQP、Pulsar、Spring Cloud Stream | Java | Broker 用 Kafka 或 RocketMQ |
| 事务与数据访问 | Spring Data、Spring 事务 | Java | 跨服务事务优先避免；确有需要再评估 Seata |
| 安全 | Spring Security、Authorization Server、Spring Session | Java | 人类用户的 OAuth/OIDC；服务间 mTLS 在云原生上交给网格 |
| 可观测埋点 | Micrometer、Micrometer Tracing | Java 埋点 | Collector 与 Prometheus 采用 Go 实现 |
| 批处理 | Spring Batch、Spring Cloud Task | Java | TB 级离线计算采用 Flink/Spark，不放大 Batch |
| 集成与遗留协议 | Spring Integration、Spring Web Services、Spring LDAP | Java | — |
| 业务 AI 编排 | Spring AI | Java 编排，Python 训练 | — |
| 缓存 | Spring Data Redis | Java 客户端 | Redis 或 Valkey |
| 注册/配置/协调的服务端 | — | 不自研 | Nacos、etcd |
| Operator、网格控制面 | — | Go | Istio、Higress、Argo 能覆盖时先采用 |
| 网格数据面 | — | 不自研 | Envoy；需要嵌入式 Sidecar 时评估 MOSN |
| 内部 CLI | Spring Shell | 要注入业务 Bean 时用 Java；分发到机器上的运维工具用 Go | — |

下面每节按「定位 → 语言 → 案例 → 自研边界」展开。总表已经够用的组件写短，网关、业务服务、中间件这三类写透。

## 4.2 业务微服务

**定位**：承载领域规则、事务、权限判定和对存储与消息的访问。对应 Spring Boot、Framework、Data、Security、Modulith。这是团队代码量的主体。

**语言**：Java，Spring Boot 4.x，JDK 21 或 25，Web 层用 Spring MVC + 虚拟线程。模块边界变复杂时用 Spring Modulith 做结构约束，而不是把模块拆成另一种语言的进程。

Kotlin 仅在团队已经把 Kotlin 定为方言时使用。响应式栈不作为业务默认：一个请求里只要有一次阻塞 JDBC，WebFlux 的收益就被驱动模型抵消，排障成本留下。

**案例**：

- Netflix 的微服务治理样本（Zuul、Eureka 以及大量业务服务）建立在 JVM 上，Spring Cloud 的早期能力就是把这套样本产品化。
- 阿里交易与中台链路以 Java 为主，Dubbo 解决的是 Java 服务之间的 RPC，而不是替换业务语言。
- 银行渠道、账务周边、政企中台的公开架构里，Spring Boot 仍是默认应用框架。换 Go 的公开案例集中在互联网新业务，不在有 Oracle 和复杂事务的存量域。

**自研边界**：业务服务本身就是该写的东西。不要在业务仓库里再写一套通用 RPC、注册或链路 SDK；这些用第四章后面的既有项目。

**什么时候允许一个业务服务用 Go**：同时满足下面三条再开评审——单副本内存预算明显低于 JVM 的空载（例如要在边缘盒子上跑几十个副本）、领域逻辑薄到接近转发、团队里已经有人值班 Go。三条里缺一条，就用 Java，把内存问题交给副本规格和堆参数。

## 4.3 面向页面的 BFF

**定位**：给某一种界面单独准备的后端（Backend for Frontend）。浏览器、App、管理端只调用自己的 BFF；BFF 按「这一屏要什么」调用领域微服务，再收成页面能直接渲染的一份数据。它是无状态进程，不保存业务数据，也不做跨服务事务。

领域服务按业务能力划分（订单、用户、商品），接口稳定、与具体页面无关。页面要的是另一份形状：一屏拼多份数据，字段少而扁，Web、App、管理端还各不相同。BFF 放在这两边中间。

**主要作用**：

1. **按页面聚合。** 订单详情一屏要订单、买家、商品、库存。浏览器只发一次请求，BFF 并行调用这几个服务，拼成一个响应。页面不必知道后面有几个服务。
2. **按界面裁剪。** 领域接口返回完整订单，列表页只要单号、状态、金额、首图。裁剪放在 BFF，领域模型不用为每个页面加字段。
3. **按体验分开演进。** Web、App、管理端各有一个 BFF 时，改 App 的聚合方式不会迫使 Web 或订单服务一起发版。
4. **处理这一屏的失败方式。** 推荐服务超时，详情页仍要打开，BFF 把推荐降级成空列表。这种「这一屏可以缺什么」是页面规则，不是订单领域的规则。

登录校验、租户、全局限流仍在网关（4.4）。订单能不能看、库存怎么扣、事务怎么提交，仍在领域服务（4.2）。

**采用之后的整体架构**：入口仍是边缘代理加业务网关，其下按界面拆出一层。领域服务对 BFF 以及其他后端提供领域 API。

```
浏览器          App / 小程序         管理后台
   │                │                  │
   └────────────────┼──────────────────┘
                    │  HTTPS，一次请求对应一屏
                    ▼
        边缘入口（Nginx / Envoy / Ingress）
                    │  TLS、连接数、全局限流
                    ▼
        业务网关（Spring Cloud Gateway）
                    │  登录态、租户、按路径转发
        ┌───────────┼───────────┐
        ▼           ▼           ▼
     Web BFF     App BFF    管理端 BFF
        │           │           │
        └───────────┼───────────┘
                    │  领域 API，与页面无关
        ┌───────────┼───────────┐
        ▼           ▼           ▼
     订单服务     用户服务     商品服务
        │           │           │
        └───────────┼───────────┘
                    ▼
           Oracle / Redis / Kafka
```

一次「订单详情」的走法：

1. 页面请求 `GET /bff/web/order-detail?id=123`。
2. 边缘入口卸掉 TLS，业务网关校验令牌、写入用户和租户，把 `/bff/web/**` 转到 Web BFF。
3. Web BFF 并行调用订单、用户、商品、库存；库存超时则该块为空，其余照常返回。
4. BFF 收成页面 DTO：状态文案、金额格式、按钮是否可点所需的标志。按钮最终能不能执行，以领域服务在提交接口上的判定为准。
5. 页面随后的「取消订单」打到订单服务的命令接口（仍经网关），不在 BFF 里做事务。

| 层 | 回答的问题 | 例子 |
|---|---|---|
| 边缘入口 | 连接和流量能不能进来 | TLS、全局限流 |
| 业务网关 | 你是谁、进哪个系统 | 令牌、租户、路由 |
| BFF | 这一屏要看什么 | 并行查询、裁字段、本屏降级 |
| 领域服务 | 业务是否成立 | 下单、扣库存、权限判定、事务 |

**什么时候加这一层**。出现「一屏跨多个领域服务」或「多种端的数据形状不同」时，按端增加 BFF，避免把页面字段做进订单服务。只有一种界面、一屏只调用一个服务时，页面经网关直接访问领域 API，不必为了分层再加一个透传进程。

**语言**：本团队维护的 BFF 用 Java，Spring Boot 4.x，MVC + 虚拟线程，部署合同与业务服务相同（有平台时进 Kubernetes，否则虚拟机上的同一个 jar）。聚合由前端团队独立发布、且其中没有事务和权限判定时，用 TypeScript（NestJS）。BFF 之间不互相调用。

**案例**：

- 这个模式由 SoundCloud 的 Phil Calçado 总结为 BFF：每种用户体验一个后端，避免一个通用 API 同时伺候 Web 和移动端。
- Netflix 按设备提供体验 API，不同设备的载荷不同，领域服务保持与屏幕无关。
- 国内互联网的端 BFF（App、小程序、管理端各一层）是同一结构：端上的聚合跟着端的版本走，交易服务的接口不跟着页面改。

**自研边界**：BFF 里写页面 DTO、并行查询和本屏降级。领域规则、事务、资源权限判定留在领域服务。登录态和全局限流留在网关。不把 BFF 做成另一个领域服务，也不在 BFF 里访问数据库里的订单表。

## 4.4 网关

网关在业界是两层，语言不同。混成「一个网关项目」是选型里最常见的错误。页面级聚合放在 BFF（4.3），不放进网关过滤器。

### 4.4.1 集群入口 / 边缘数据面

**定位**：终结 TLS、连接治理、按路由表转发、全局限流、访问日志。规则相对规整，连接数和每秒包数是指标。对应 Kubernetes Ingress、Gateway API，或虚拟机前面的四层/七层负载均衡。

**语言**：不自研。采用 Envoy（C++）、Nginx（C）或 HAProxy（C）。需要管理界面和控制面时采用现成产品：

| 产品 | 数据面 | 控制面 | 适合的用法 |
|---|---|---|---|
| Envoy + Gateway API 实现（Envoy Gateway 等） | C++ | Go | 云原生集群入口的默认选项 |
| Higress（阿里开源，Apache） | Envoy | Go | 要 WAF、插件和国内生态时的入口 |
| APISIX | OpenResty（Nginx + Lua） | etcd + 可选 Go 的 Ingress 控制器 | 路由规则动态、插件用 Lua 表达时 |
| Kong | OpenResty | Go（Ingress 控制器） | 插件市场和声明式配置 |
| Traefik | Go（自身既是数据面也是控制面） | Go | 规则简单、组件越少越好 |
| Spring Cloud Gateway | Java / Netty | 无独立控制面 | 见下一小节，不放在公网边缘当唯一入口 |

Traefik 证明数据面也可以用 Go 写，它的适用面是中等流量和简单规则。公网边缘、连接数上去之后，业界主路径仍是 Envoy 和 Nginx。Cloudflare 用 Rust 写 Pingora 替换自己的 Nginx，针对的是他们的边缘规模，不是企业集群入口的默认动作。

**虚拟机上的同一层**：继续用 Nginx、HAProxy 或 Envoy 的主机发行版，前面可以是硬件/云负载均衡。不要为了虚拟机专门用 Java 再写一个边缘代理。

### 4.4.2 业务网关

**定位**：登录态校验、租户路由、协议适配、按业务头灰度、审计日志。规则变化跟业务版本走，开发的人是业务团队。对应 Spring Cloud Gateway。一屏数据的拼装见 4.3。

**语言**：Java。Spring Cloud Gateway 基于 WebFlux 和 Netty，适合「连接多、逻辑是过滤器链、进程内几乎不访问数据库」的这一层。过滤器、谓词用 Java 写，和 Spring Security 的资源服务器模型放在一个进程里。

**案例**：

- Netflix Zuul 1（阻塞 Servlet）到 Zuul 2（Netty）都是 Java。他们的网关逻辑和业务语言相同，所以能把鉴权和路由测试放进同一个工程体系。
- 阿里在公网入口用 Higress/Envoy，在更靠近业务的地方仍大量使用 Java 网关与 Dubbo 网关。两层并存，而不是用一个进程包打天下。
- 本团队已有的结论：集群入口交给 Ingress/Gateway API，业务边界保留 Spring Cloud Gateway。语言选择把这个分层落实为「入口不写 Java，业务网关不写 C++」。

**自研边界**：在 Spring Cloud Gateway 上写过滤器和路由配置，属于正常开发。从零写一个基于 Netty 的网关，只在 Spring Cloud Gateway 的过滤器模型确实表达不了、并且流量证明需要独立进程时才考虑，语言仍然是 Java。用 Go 重写业务网关，只会把鉴权库和业务 DTO 复制一份。

**流量大到什么程度要把逻辑挪走**：业务网关的 CPU 主要耗在业务过滤器上时，先水平扩容这个 Java 进程。扩容成本高于入口代理、且规则可以下推成 Envoy 路由或 Wasm 时，把「已经稳定的那部分规则」下推到入口，把仍在变化的鉴权和租户逻辑留在 Java。下推的是规则，不是把整个网关换语言。

## 4.5 服务治理：发现、配置、限流、调用

这些在 Spring 清单里是一组库：Spring Cloud 的 Discovery、Config、LoadBalancer、OpenFeign、Circuit Breaker，加上 Alibaba 的 Nacos 与 Sentinel。它们是 **Java 库或现成服务器**，不是新语言的机会。

| 能力 | 虚拟机上怎么开发 | 云原生上怎么开发 |
|---|---|---|
| 服务发现 | 使用 Nacos 客户端（Java）。Eureka 只维护存量 | 业务不写注册代码，用 Kubernetes Service。需要标签路由时用 Spring Cloud Kubernetes 读取 Pod 标签，仍是 Java 客户端 |
| 配置 | 使用 Nacos 或 Apollo，不新写配置服务器。Spring Cloud Config 仅在已经以 Git 为配置源、且没有界面诉求时保留 | 非敏感配置可用 ConfigMap；有灰度、审计、历史版本时继续用 Nacos/Apollo |
| 客户端负载均衡 | Spring Cloud LoadBalancer，Java | 四层均衡交给 kube-proxy。业务权重、金丝雀标签仍可留在 Java 客户端，或上收到网格 |
| 熔断、舱壁、业务限流 | Resilience4j 或 Sentinel，Java，写在调用方 | 相同。全局限流、连接数保护放在入口 Envoy，避免每个服务各写一套全局限流 |
| 声明式 HTTP | Java 的 HTTP Interface（Framework 6/7）或 OpenFeign | 相同 |
| 重试与超时 | 业务幂等语义的重试写在 Java（Spring 的重试 / Resilience4j） | 网络级超时可由网格做；业务重试仍在 Java，避免两层同时重试 |

**案例**：Nacos、Sentinel、Apollo（携程）的服务端都是 Java，因为它们的第一批用户是 Java 微服务，控制台和客户端要一起交付。Consul、etcd 的服务端是 Go，因为它们出生在基础设施仓库。本团队若部署注册中心，选 Nacos 等于选一个 Java 服务端来运维，客户端和业务同语言；选 etcd 等于选一个 Go 服务端，只通过协议访问。两种都合理，都不构成「用 Go 重写一个注册中心」。

**自研边界**：写业务侧的隔离策略、线程池舱壁、幂等键，用 Java。不新写注册中心、配置服务器和限流令牌服务。

## 4.6 RPC

**定位**：服务之间的二进制调用。对应 Spring gRPC、Dubbo。

**语言**：契约用 Protobuf（与语言无关），服务端和客户端用 Java。Dubbo 适合已经在 Java 技术半径内、需要治理元数据的内部 RPC；Spring gRPC 适合要和外部非 Java 系统对齐、或希望契约文件成为唯一接口描述的场景。一个域内只留一种。

**案例**：

- gRPC 的核心是 C++，grpc-java 与 grpc-go 都是正式实现。Google 用它跨语言，每个语言只写桩，不重写核心。
- Dubbo 主体是 Java，dubbo-go 是为了接入 Go 服务。有 Go 服务要进已有 Dubbo 域时才引入 dubbo-go，不为了「未来可能有 Go」提前引入。
- 字节 Kitex 是 Go，因为他们的业务默认语言是 Go。框架语言跟着业务仓库走，这个方向和「我们用 Java 写业务，所以 RPC 桩用 Java」是同一条原则。

**自研边界**：不新写 RPC 框架、序列化协议和注册集成。

## 4.7 消息、缓存与协调：中间件本体 vs 客户端

微服务团队说的「做中间件」，多数时候是在做客户端封装、主题规范和消费语义，少数时候才是在做 Broker。两件事的语言完全不同。

### 4.7.1 客户端与业务封装

**语言**：Java。使用 Spring for Apache Kafka、Spring AMQP、Spring for Apache Pulsar、Spring Data Redis。团队要写的是：主题命名、幂等消费、重试主题、事务外盒、序列化约定。这些是库，跟着业务服务发布。

Spring Cloud Stream 的绑定器适合「渠道已经抽象、要在 Kafka 与 Rabbit 之间替换」的场景。团队若已锁定 Kafka 或 RocketMQ，直接用对应的 Spring 客户端更直观，少一层绑定器。

### 4.7.2 Broker、缓存引擎、协调服务端

**语言**：不自研。

| 需求 | 采用 | 实现语言 | 说明 |
|---|---|---|---|
| 日志型消息、可回放 | Apache Kafka | Scala / Java | 客户端用 Spring for Apache Kafka |
| 事务消息、延迟消息、和 Java 生态贴合 | Apache RocketMQ | Java | 阿里系业务的常见选择；运维一个 Java Broker 对 Java 团队更可读 |
| 多租户、队列与流合一 | Apache Pulsar | Java（Broker）+ BookKeeper（Java） | 运维复杂度高于 Kafka，有明确多租户诉求再用 |
| 传统 AMQP、复杂路由 | RabbitMQ | Erlang | 能用就用，不碰 Erlang 源码 |
| 轻量命令通道 | NATS | Go | 只在需要简单发布订阅、不想运维 Kafka 时 |
| 缓存 | Redis 或 Valkey | C | 客户端 Java |
| 注册与配置一体 | Nacos | Java | 与 Spring 客户端同语言运维 |
| 强一致键值、Kubernetes 已经依赖 | etcd | Go | 云原生上往往已经有，不必再部署一个注册中心 |
| 老的协调 | ZooKeeper | Java | 只维护存量；Kafka 已可脱离它 |

**案例**：Kafka 和 RocketMQ 选择 Java/Scala，是因为 Broker 的复杂度在副本协议、存储和消费语义，JVM 扛得住，开发效率比 C++ 划算。Redis 选择 C，是因为内存数据结构和延迟是产品本身。TiKV 选择 Rust，是因为存储引擎要可控的内存和尾延迟。这三档分别对应「我们不该重写的三样东西」。本团队的开发落在客户端那一档。

**什么时候才允许写一个独立的中间件进程**：现有 Broker 的协议表达不了业务语义，并且这个语义被多个服务重复实现。写出来的进程默认仍是 Java（例如一个批量投递调度器、一个业务事件总线），部署上按无状态或有状态分别归入第二章的矩阵。不要以「中间件」为名用 Go 新写一个消息引擎。

## 4.8 数据访问、事务与分布式事务

**定位**：对应 Spring Data、事务抽象、以及清单外的 Seata。

**语言**：Java。关系库用 Spring Data JDBC 或 JPA 的其中一种，一个服务内不要两套并存。Oracle 驱动是 Java 生态里最完整的，这是业务留在 JVM 上的硬约束之一。

跨服务的更新，优先改成单服务本地事务加消息投递（事务外盒），用 Java 在业务服务里实现。Seata（Java）只在已经存在跨库、且业务不能改成最终一致时引入。Seata 本身不作为团队要新写的框架。

**案例**：阿里用 Seata 解决的是 Java 微服务里的跨库事务，服务端和客户端都是 Java。把协调者改成 Go 不会减少业务里对事务边界的理解成本。

## 4.9 安全

**定位**：人的登录、令牌、方法级权限、会话。对应 Spring Security、Spring Authorization Server、Spring Session。服务之间的零信任是另一层。

**语言**：

- 用户认证、资源服务器、方法级鉴权：Java，写在业务服务或业务网关里。授权服务器优先采用现成的 Keycloak（Java）或 Spring Authorization Server；团队只写客户端注册和权限模型。
- 服务间 mTLS：云原生上交给网格（Istio 的数据面是 Envoy），业务不开证书轮转的代码。虚拟机上用内部 CA 和有限的证书分发，仍然不要在每个服务里手写 TLS 状态机。
- 密钥：采用 Vault（Go）或云厂商密钥服务。Spring Vault 是 Java 客户端，用来取密钥，不是用来再写一个保险库。

**案例**：Keycloak、Spring Authorization Server 是 Java，因为会话、用户目录和业务权限在应用层。HashiCorp Vault、cert-manager 是 Go，因为它们是集群里的守护进程。Ory（Hydra/Kratos）用 Go 提供另一条身份基础设施路线；已经在 Spring Security 上建了权限模型之后，不平行再引入一套。

## 4.10 可观测、批处理、集成与 AI

**可观测**

- 业务进程内的指标、追踪、日志桥：Java，Micrometer + Micrometer Tracing，导出到 OpenTelemetry。
- 采集器、Prometheus、后端存储：采用。OpenTelemetry Collector 与 Prometheus 是 Go。SkyWalking 的后端是 Java，若团队更希望观测后端和业务同语言，可以选它；新系统更常见的组合是 Micrometer → OTel Collector → Prometheus/Tempo 一类后端。
- 不自研采集器和时序库。

**批处理**

- 日终、对账、文件导入、数据量在单库可处理的范围内：Java，Spring Batch。需要调度时用 Spring Cloud Task 或外部调度触发同一个 Boot 进程。
- 数据量到分析型引擎的规模：采用 Flink（Java）或 Spark（Scala）。作业代码可以是 Java，引擎不自研。
- 批处理的部署：短作业在云原生里用 Job；跑数小时、堆很大的作业按第二章放虚拟机或独立节点池。语言不变。

**集成与遗留协议**

- SOAP、文件、LDAP、旧消息：Java，Spring Integration、Spring Web Services、Spring LDAP。这些库存在的原因就是「用业务语言接遗留系统」。用 Go 重写适配器，等于放弃这批库。

**AI**

- 训练、清洗、评测脚本：Python。
- 已有业务系统里的检索增强、工具调用、和权限数据一起编排：Java，Spring AI。模型服务本身（推理进程）采用 vLLM 等现成服务，不把推理引擎写进 Spring 进程。

**案例**：Flink 与 SkyWalking 选择 Java，是为了和作业/探针的宿主语言一致。Prometheus 与 OTel Collector 选择 Go，是因为它们是每节点一个的基础设施进程，静态二进制和内存占用优先。Spring AI 选择 Java，是为了接现有的事务和安全，而不是在 Java 里重做一套训练框架。

## 4.11 平台控制器、网格与内部工具

这一层只有云原生形态才出现，也是本团队唯一默认使用 Go 的开发面。

**Operator 与 CRD 控制器**

**语言**：Go，controller-runtime。典型职责：把「部署一个带外置配置的中间件」「按 CR 发放证书」「按状态做故障转移」收成控制循环。

Java Operator SDK（基于 Fabric8）能写简单控制器。本团队只在控制器逻辑必须复用大量现成 Java 客户端、且控制器数量只有一个时考虑它。第二个控制器开始，就统一到 Go，避免两个客户端生态。

**能采用就不写**：证书轮转用 cert-manager，Kafka 用 Strimzi（控制面是 Go，Kafka 本身仍是 JVM），工作流用 Argo Workflows 或 Argo CD。自己写 Operator 的前提是：这个资源的调谐规则是业务独有的，现成控制器没有。

**网格**

- 控制面采用 Istio（Go）或等价实现。
- 数据面采用 Envoy。蚂蚁 MOSN（Go）的价值是可嵌入、可按模块裁剪，适合要深度定制 Sidecar 的平台团队。业务团队把网格当基础设施使用，不 fork 数据面。

**CLI**

- 要连数据库、复用 Service 层：Java，Spring Shell 或 Picocli，作为同一个工程的另一个入口。
- 要拷贝到跳板机、无 JDK 环境运行的巡检工具：Go，单一二进制。

**案例**：Kubernetes 的控制器、Istio、Argo、cert-manager、Strimzi 的控制进程、Higress 的控制面都是 Go。这个一致性来自 client-go，不是来自「Go 更适合微服务」。把业务服务写成 Go，并不会自动获得这层生态。

## 本章小结

- 业务、本团队维护的 BFF、业务网关、治理 SDK、数据访问、安全、批处理、集成、AI 编排：Java。前端独立发布且无事务的 BFF 可以用 TypeScript。
- 集群入口和网格数据面：采用 C++/Rust/C 的现成代理。
- Broker、缓存、注册中心：采用，客户端用 Java。
- Operator 和节点工具：Go。
- 偏离总表需要同时给出负载证据和值班能力，不接受只引用某一家互联网公司的框架名单。

# 五、同一种组件，换部署形态时语言要不要变

## 5.1 本章定位

本章防止两种返工：迁到 Kubernetes 时顺手重写语言；留在虚拟机时拒绝使用已经是 C++/Go 的入口和采集器。

## 5.2 结论对照

| 组件 | 留在虚拟机 | 迁到云原生 | 语言是否变化 |
|---|---|---|---|
| 业务微服务 | fat jar，systemd，JVM 按机器内存设置堆 | 同一 jar 放进镜像，内存请求/限制写进 Pod，探针替换自定义心跳 | 不变，仍是 Java |
| 面向页面的 BFF | 与业务服务相同的 jar 或 Node 进程 | 同一交付物进镜像，探针与业务服务相同 | Java 或 TypeScript 都不因迁移而更换 |
| 业务网关 | 独立的 Spring Cloud Gateway 进程，前面是 Nginx/HAProxy | 同一进程作为集群内一层；TLS 和全局限流可上收到入口 | 不变 |
| 集群入口 | Nginx、HAProxy、Envoy 的主机部署 | Ingress 或 Gateway API | 本来就不是 Java，迁移动作是换控制方式 |
| 服务发现 | Nacos Java 客户端 | 删除注册逻辑，改用 Service DNS；灰度标签改读 Kubernetes 标签 | 客户端库变化，语言不变 |
| 配置 | Nacos/Apollo | 简单项可改 ConfigMap；要灰度则保留原配置中心 | 不变 |
| 消息客户端 | Java 客户端连虚拟机上的 Broker | 同一客户端连独立节点池或集群外的 Broker | 不变 |
| Broker 本体 | 虚拟机上的 Kafka/RocketMQ | 仅在磁盘和调度设计完成后迁入 Operator（如 Strimzi） | Broker 语言不变 |
| 指标 | Java 进程暴露 Prometheus 端点，或推到采集器 | 同一端点由 Prometheus 抓取；追踪走 OTel | 埋点语言不变，采集器保持 Go |
| 运维脚本 | Shell、Ansible | 其中「要持续调谐」的部分收成 Go Operator，一次性脚本保持 Shell | 只有新的控制器是 Go |

迁到云原生时，Java 服务要改的是运行参数，不是语言：容器里按 cgroup 设置内存（使用能识别容器限制的 JVM 参数）、给齐就绪/存活/启动探针、把优雅停机时间设得大于入口摘流时间、日志写到标准输出。这些在现有的容器化开发建议里已经有动作级说明。

## 5.3 云原生也不会改写的三个判断

1. **虚拟线程已经覆盖「业务并发」这个迁移动机。** 迁移动机若是「容器里线程太多、内存顶满」，先把请求模型改成虚拟线程并收紧堆，再讨论语言。改完仍然是副本太小、空载 JVM 占满限额，才回到 4.2 的 Go 例外条款。
2. **原生镜像不是默认交付物。** GraalVM 原生镜像能把冷启动降到毫秒到数百毫秒、把内存降下来，代价是构建期可达性推导、反射配置、以及部分 JDBC 与字节码增强库的限制。长驻的业务服务用 JVM。只有缩到零、且依赖能通过原生镜像测试的小型函数，才把原生镜像当作交付形态，语言仍是 Java。
3. **Sidecar 不是业务语言的替代品。** 网格把 mTLS、部分重试和指标做进 Envoy 之后，业务进程还是 Java。不要为了「少装一个 Java Agent」把服务改成 Go。Agent 或 Micrometer 导出是更小的动作。

## 5.4 虚拟机也不会改写的三个判断

1. **入口仍然采用 Nginx/Envoy。** 虚拟机上没有 Ingress 对象，不代表要用 Spring Cloud Gateway 去终结所有公网连接。公网侧的连接治理留给专门的代理进程。
2. **采集器可以用 Go 二进制。** 虚拟机上跑 Prometheus 的 node exporter、OTel Collector，不需要这些工具有 Java 版本。
3. **不要为了「机器上只有 JDK」而拒绝静态二进制工具。** 巡检、日志投递这类节点工具用 Go 更易分发。这不构成业务服务改用 Go 的理由。

## 本章小结

- 部署形态切换的检查单是：探针、内存、配置来源、发现方式、入口归属。
- 检查单里没有「更换业务语言」这一项。
- Go 在迁移中出现的位置，是新增的控制器和节点工具。
- C++/Rust 在两种形态下都只以入口代理的形式出现。

# 六、落地清单

## 6.1 默认栈

从现在开始的新组件，直接套用：

| 项 | 决定 |
|---|---|
| 业务服务、BFF（服务端拥有）、业务网关、批处理、集成适配 | Java 21+，Spring Boot 4.x，MVC + 虚拟线程 |
| 服务间契约 | 对外和对非 Java 系统用 Protobuf/gRPC；Java 域内已有 Dubbo 则沿用 Dubbo，不并行新增 |
| 消息 | 客户端 Spring Kafka 或 RocketMQ 的 Java 客户端；Broker 采用，不自研 |
| 缓存 | Redis/Valkey + Java 客户端 |
| 注册与配置 | 虚拟机与轻量 Kubernetes：Nacos。深度 Kubernetes：发现用 Service，配置按是否要灰度决定留 Nacos 还是用 ConfigMap |
| 熔断限流 | 业务语义 Resilience4j 或 Sentinel；全局限流放在入口 |
| 集群入口 | Envoy 系（Gateway API 或 Higress）。虚拟机用 Nginx 或 Envoy |
| 观测 | Micrometer 埋点，OTel Collector 采集 |
| 安全 | Spring Security；授权服务器采用 Keycloak 或 Spring Authorization Server；云原生的服务间 mTLS 交给网格 |
| 自研控制器 | Go |
| 训练脚本 | Python |

一个业务域的生产语言就是 Java。Go 仓库单独放平台组件，不和业务多模块工程混在一个构建里。

## 6.2 允许偏离的例外

偏离要在设计评审里写明「负载证据」和「谁值班」。允许的例外只有这些：

| 例外 | 条件 | 语言 |
|---|---|---|
| 边缘或节点上的独立工具 | 无 JDK、要单一文件分发、逻辑不涉及领域模型 | Go |
| Kubernetes 控制器 | 需要持续调谐 API，且现成 Operator 覆盖不了 | Go |
| 前端独立发布的 BFF | 只有聚合和裁剪，事务和权限在 Java 服务中 | TypeScript |
| 模型训练与离线评测 | 不承载在线事务 | Python |
| 极小内存或硬尾延迟的转发进程 | 有采样数据证明 JVM 达不到，且逻辑是转发不是领域 | 优先改用 Envoy/Wasm；仍不够再评估 Rust，由平台组承担 |

「团队有人学过 Go」不是例外条件。

## 6.3 停止自研的边界

下面这些直接采用，立项时不讨论实现语言：

- 边缘代理、网格数据面、CNI；
- 消息 Broker、缓存引擎、关系库；
- 注册中心与配置中心的服务端；
- 采集器、时序库、追踪后端；
- 证书控制器、通用 GitOps 引擎；
- RPC 框架和序列化协议。

团队的开发预算放在：领域服务、业务网关过滤器、消费与投递语义、权限模型、批处理作业、以及确属业务独有的控制器。

## 6.4 评审时的五个问题

1. 这个进程的热点是领域规则、包转发，还是 Kubernetes 调谐？
2. 它的调用方是不是 Spring 服务？如果是，共享代码是不是 Java 库？
3. 它跑在虚拟机还是 Kubernetes？依据是第二章矩阵的哪一行？
4. 现成的 Envoy、Nacos、Kafka、OTel Collector、Argo、Keycloak 是否已经覆盖？
5. 若语言不是 Java，值班的人在不在这个仓库的责任范围内？

五个问题都有明确答案，语言也就确定了。

## 本章小结

- 默认：业务 Java，入口采用现成数据面，平台控制器 Go，中间件本体不自研。
- 云原生和虚拟机共享同一份业务代码，差在运行合同和治理组件的归属。
- 换语言是例外流程，要有负载数据和值班人，不由部署形态自动触发。
