# 一、总览:G1 是什么,为什么是它

## 1.1 一句话定位

> **G1(Garbage-First)是一台"面向服务端、把停顿当作第一目标"的分代收集器:它把堆切成几百上千个等大的 Region,每次 GC 只挑"垃圾最多、回收性价比最高"的一小批 Region 搬移整理(这也是名字 Garbage-First 的由来),从而在几 GB 到几十 GB 的大堆上,把单次停顿控制在用户设定的目标(`-XX:MaxGCPauseMillis`,默认 200ms)附近。**

JDK 9 起它是默认收集器([JEP 248](https://openjdk.org/jeps/248)),JDK 27 起它**在所有环境**(包括 1 核小机)都是默认([JEP 523](https://openjdk.org/jeps/523))——十五年演化之后,它就是 Java 世界的"底盘 GC"。

## 1.2 G1 之前的世界:Parallel 与 CMS 的困局

理解 G1 的每个设计,都要先看它的两位前辈缺什么:

| 收集器 | 思路 | 痛点 |
|--------|------|------|
| **Serial / Parallel**(JDK 8 默认) | 分代 + 整体复制/标记-整理,吞吐优先 | 堆一大,单次 Full GC 停顿动辄数秒~数十秒;停顿与堆大小成正比,不可控 |
| **CMS**(JDK 9 弃用 / 14 移除) | 并发标记-**清除**,停顿低 | ① **标记-清除不整理 → 碎片**:老年代分配不下面朝大对象时只能提前 Full GC(Serial 整理);② **并发失败(concurrent mode failure)**:老年代涨得比标记快就退化;③ 维护两套 GC 的成本高 |

CMS 的根本矛盾:**想不清碎片,就得整体整理(停顿长);想整理,就得把堆作为一个整体来搬(Parallel 的老路)**。G1 的答案是把"堆"这个整体打碎——**碎片问题从"堆级"降维到"Region 级"**:回收永远以 Region 为单位搬移,天然就是整理,只是每次只搬一小部分。

## 1.3 设计哲学:三句话读懂 G1

1. **物理不分代,逻辑分代**:堆不再物理上划成连续的 young/old 两块,而是切成一串等大 Region(1MB~32MB,由堆大小自动算);每个 Region 动态充当 Eden、Survivor、Old 或 Humongous。分代假设照用,但"代"的边界是弹性的。
2. **回收按性价比,不按代**:每次 GC 选出一个 **CSet(Collection Set)**——young GC 时是全部 young Region;mixed GC 时在老年代里挑"垃圾最多、停顿预算装得下"的那批。**永远先收垃圾最多的 Region(Garbage-First),单位停顿换最多内存。**
3. **停顿是目标,不是结果**:用户给 `-XX:MaxGCPauseMillis=200`,G1 的自适应引擎(G1Policy/G1IHOPControl)用历史停顿数据**预测**每个 Region 的回收成本,反向控制 young 代大小、CSet 规模、并发标记启动时机。**它不是"收集完顺便报个时间",而是"按预算倒推能收多少"。**

## 1.4 【全景专题】G1 优化发展史(6u14 → 27)

G1 不是某个 JDK 版本"一次性发布"的功能,而是迭代了 **18 年**的产品。按本系列的约定,跨版本演进的特性在这里做时间线全景:

| 版本 | JEP/变更 | 变化 | 为什么要变 |
|------|----------|------|-----------|
| **JDK 6u14**(2009) | — | G1 以**实验特性**进入 HotSpot(`-XX:+UnlockExperimentalVMOptions -XX:+UseG1GC`) | Sun 需要一个"大堆 + 可控停顿"的服务端 GC 应对 CMS 的碎片化,先放进 6u 给企业试用 |
| **JDK 7u4**(2012) | — | G1 **转正**:官方支持、可用于生产 | 实验 3 年稳定性达标;Oracle 官方文档把 G1 定位为 CMS 的长期替代者 |
| **JDK 8**(2014) | — | 大量打磨:并行 RSet 更新、 refining、错误修复 | G1 在 8 上仍非默认(默认 Parallel),但"大堆选 G1"已是官方推荐 |
| **JDK 8u20**(2014) | [JEP 192](https://openjdk.org/jeps/192) | **字符串去重**(`-XX:+UseStringDeduplication`,G1 专属) | 后台线程把内容相同的 String 底层数组指向同一份,实测可省存活堆的 ~10%;只做在 G1 上(依赖其并发标记) |
| **JDK 8u60 / 9**(2015-17) | — | **Humongous 对象 eager reclaim**:引用很少的大对象在 young GC 直接回收,不等标记 | 大对象占 Region 却要等整个并发标记才能回收,太浪费 |
| **JDK 9**(2017) | [JEP 248](https://openjdk.org/jeps/248) | **G1 成为默认 GC** | 服务器默认堆变大,大堆上"可预测停顿"比纯吞吐更重要;CMS 同版弃用([JEP 291](https://openjdk.org/jeps/291)) |
| JDK 9 | [JEP 271](https://openjdk.org/jeps/271) | **统一 GC 日志**(`-Xlog:gc*` 取代 PrintGCDetails 等几十个 flag) | GC 诊断的第一入口——本文第三章的地基 |
| **JDK 10**(2018) | [JEP 307](https://openjdk.org/jeps/307) | **Full GC 并行化** | G1 最痛的一刀:退化 Full GC 此前是**单线程**,几十 GB 堆上一次十几秒;并行化后改善数倍 |
| JDK 10 | [JEP 304](https://openjdk.org/jeps/304) | 统一 GC 接口(收集器解耦出 JVM) | 架构层面的解耦,让 ZGC/Shenandoah 后续能干净地接入 |
| **JDK 12**(2019) | [JEP 344](https://openjdk.org/jeps/344) | **可中止的 mixed GC** | mixed 回收的老年代部分拆成"必收 + 可选(optional)",一旦到达停顿预算立刻收手——停顿达标优先于回收进度 |
| **JDK 14**(2020) | [JEP 345](https://openjdk.org/jeps/345) | **NUMA 感知分配**(`-XX:+UseNUMA`) | 多路服务器上,让对象优先分到"离当前 CPU 近"的内存节点;同时 **CMS 在本版移除**(JEP 363),G1 全面接棒 |
| **JDK 15**(2020) | [JEP 346](https://openjdk.org/jeps/346) | **空闲时归还内存**(`G1PeriodicGCInterval` 等) | 云环境按内存峰值付费,但 G1 此前"宁可占着也不还";低负载时主动触发并发周期并 uncommit |
| **JDK 17/18 前后** | 非 JEP | RSet 底层重写为 **card set**(稀疏集/数组/Howl 位图分桶,`g1CardSet.hpp`);标记后的 **RSet 重建搬进并发阶段**(日志中的 `Concurrent Rebuild Remembered Sets and Scrub Regions`,本机 JDK 21 实测已有) | RSet 内存开销和 refinement CPU 是 G1 被诟病多年的点;数据结构重写 + 并发化双管齐下 |
| **JDK 22**(2024) | [JEP 423](https://openjdk.org/jeps/423) | **Region Pinning(区域固定)** | JNI 临界区(`GetPrimitiveArrayCritical`)内对象不能被搬;此前 G1 只能把整个 GC 推迟或退化 Full GC——现在可以钉住少量 Region,其余照收 |
| **JDK 23**(2024) | [JEP 475](https://openjdk.org/jeps/475) | **屏障展开后移**(C2 后期宏展开) | 写屏障是 G1 的固定税;把屏障展开从 C2 前端挪到后期,能做更激进的优化消除,编译出的代码更快 |
| **JDK 26**(2026) | [JEP 522](https://openjdk.org/jeps/522) | **降低同步开销** | G1 内部锁/同步的瘦身,目标是吞吐追平 Parallel GC |
| **JDK 27**(2026) | [JEP 523](https://openjdk.org/jeps/523) | **G1 成为一切环境的默认 GC** | 1 核/小内存机器此前默认 Serial(同代码在容器和物理机行为不一致);522 + 小堆优化让 G1 在小环境也可接受,"一致性"战胜"分环境特调"。同版新增 `G1IHOP`、`G1UseReferencePrecleaning` 等参数(附录/二.10 实测) |

**把 18 年读成三个时代:**

- **可用性时代(6u14~8)**:证明"区域化回收 + 可预测停顿"这条路能走通,稳住不崩;
- **默认化时代(9~15)**:登基默认(248)、补齐最痛的并行 Full GC(307)、把停顿预算做成一等公民(344)、云原生化(345/346);CMS 从弃用到移除(291/363),选择权收归 G1;
- **打磨时代(17~27)**:RSet 重写、区域固定(423)、屏障优化(475)、同步瘦身(522),最终"全环境默认"(523)——G1 的角色从"备选"变成"底盘",极致停顿的场景让给分代 ZGC/Shenandoah([JDK版本特性变化.md](JDK版本特性变化.md) 15.5)。

## 1.5 收集器对比:G1 在坐标系里的位置

| 维度 | Parallel | CMS(已移除) | **G1** | ZGC/Shenandoah(分代) |
|------|----------|--------------|--------|----------------------|
| 算法 | 分代复制+整理 | 并发标记-清除 | **区域化复制(标记-整理)** | 并发标记-整理(染色指针/转发指针) |
| 停顿 | 大且不可控 | 小但波动(退化 Full) | **小且可控(目标驱动)** | 亚毫秒级,与堆大小基本无关 |
| 碎片 | 无(整理) | **有(不整理)** | **无(按 Region 搬移)** | 无 |
| 吞吐 | 最高 | 中 | 高(27 起逼近 Parallel) | 中(写/读屏障税) |
| 堆上限舒适区 | <8GB | 4~8GB | **4~64GB** | 16GB~TB 级 |
| 适合场景 | 离线计算 | (历史)低延迟 Web | **绝大多数在线服务** | 极致延迟(大堆实时服务) |

## 1.6 本章小结

- G1 解决的核心矛盾:**"碎片"与"停顿"不可兼得**——把堆 Region 化之后,整理不再需要全堆停顿,停顿预算反推回收量。
- 三句话:**逻辑分代的等大 Region;每次回收挑垃圾最多的 Region;停顿目标驱动自适应。**
- 发展史三个时代:**可用(6u~8)→ 默认(9~15)→ 打磨至全环境默认(17~27)**,关键 JEP:192 字符串去重 / 248 默认 / 307 并行 Full / 344 可中止 mixed / 345 NUMA / 346 归还内存 / 423 区域固定 / 475 屏障后移 / 522 同步瘦身 / 523 全环境默认。
- 选型一句话:在线服务默认就是它;只有"延迟极敏感 + 大堆"才考虑分代 ZGC/Shenandoah,"纯吞吐离线"才考虑 Parallel。

## 2.1 堆的物理结构:HeapRegion

**白话**:G1 把堆按 2 的幂切成 N 个等大 Region。Region 大小只有一个公式:**clamp(堆上限 / 2048, 1MB, 32MB)**——G1 以"约 2048 个 Region"为目标反推 Region 大小。每个 Region 同一时刻只能是**六类角色之一**:Eden / Survivor / Old / Humongous(首块) / Humongous Continuation(后续块) / Free。角色是**动态**的:一个 Region 上一轮是 Eden,这轮回收后下一轮可能直接变成 Old。

**Region 的六类角色:里面放什么对象,收集中干什么**

| 角色 | 里面放什么 | 收集过程中干什么 |
|------|-----------|------------------|
| **Eden** | "刚出生"的对象——应用线程 TLAB 里的新对象最终都落到这里(2.2) | young GC 的主要"原料":整批 Eden 的活对象被并行**复制**到新 Survivor 或晋升 Old,Eden 本体作废、**整体回收**(永远不做原地清理)。它是全堆分配速率的主要承接者,"朝生夕死"假设的兑现处。日志:`Eden regions: 85->0(82)` |
| **Survivor** | 在 young GC 中活下来、但年龄还不够晋升的对象(年龄 +1) | 下次 young GC 继续作为回收对象被复制;年龄达到动态阈值(受 `TargetSurvivorRatio=50` 影响)就晋升 Old。同时它是并发标记的**"根 Region"**——标记开始后第一个并发子阶段 `Concurrent Scan Root Regions` 扫的就是它(标记期间它要被搬走,必须趁早扫完)。角色意义:老年代的**安检缓冲带**,把短命对象挡在老年代之外 |
| **Old** | "熬出头"的长命对象(从 Survivor 晋升而来) | young GC 基本不碰它(只有晋升写入);回收靠两条路:① **mixed GC**——并发标记后存活率 < `G1MixedGCLiveThresholdPercent(85%)` 的 Region 进候选,被分批捎带回收(2.7);② 全空的 Old Region 在标记周期的 `Concurrent Cleanup for Next Mark` 阶段直接整体回收。日志:晋升让它涨(`Old regions: 124->133`),mixed 让它降 |
| **Humongous(首块)** | **超过 Region 一半**的巨型对象:不走 young 代、不走 TLAB,直接分配(对象头 + 数据起始,见 2.3) | 回收路径特殊,三条:① 引用稀少的在 young GC **直接回收**(eager reclaim);② 并发标记确认死亡后,同样在 young GC 回收;③ **mixed 不收它、Full GC 不搬它**。只要活着就钉死一串连续 Region——是 Evacuation Failure 的常见帮凶(案例 2)。日志:`Humongous regions: 55->24` |
| **Humongous Continuation** | 巨型对象的**后续数据块**(纯数据,无对象头) | 不能独立回收、不能当分配目标,生死完全跟随首块——对象死亡整串一起释放。它们挤占的是"连续空间",young GC 找 to-space 落脚点时最容易被卡住 |
| **Free** | 什么都不放——已回收干净 / 从未使用的空 Region | 全场的"角色现货池":Eden 扩容、新 Survivor 挑选、晋升目标、humongous 找连续块、GC 搬移的 to-space 落脚点,**全部现划现转**。`G1ReservePercent=10` 保的就是它的下限——**Evacuation Failure 的本质就是 Free + 预留不足以当落脚点**(2.8)。日志:`112 free (112M)`(jcmd GC.heap_info) |

【源码证据】角色在源码里就是 4 个位标记,换角色只是"改标签"(g1HeapRegionType.hpp:61-75):

```cpp
typedef enum {
  FreeTag               = 0,
  YoungMask             = 2,
  EdenTag               = YoungMask,        // Eden 与 Survivor 共享 young 位
  SurvTag               = YoungMask + 1,
  HumongousMask         = 4,
  StartsHumongousTag    = HumongousMask,    // 首块
  ContinuesHumongousTag = HumongousMask + 1,// 后续块
  OldMask               = 8,
  OldTag                = OldMask
} Tag;
```

一个能体现"改标签"之廉价的函数:`relabel_as_old()`(g1HeapRegionType.hpp:137)——Region 被搬空后**不必回 Free 池再排队**,Eden/Survivor/Free 可以就地转成 Old(晋升分配区直接用现成的空 Region),与上表"Free 是现货池、转角色只改标签"互为印证。

【源码证据】Region 大小的计算(g1HeapRegion.cpp:69):

```cpp
void G1HeapRegion::setup_heap_region_size(size_t max_heap_size) {
  size_t region_size = G1HeapRegionSize;
  // G1HeapRegionSize = 0 means decide ergonomically.
  if (region_size == 0) {
    region_size = clamp(max_heap_size / G1HeapRegionBounds::target_number(),  // 目标 2048 个
                        G1HeapRegionBounds::min_size(),                        // 下限 1MB
                        G1HeapRegionBounds::max_ergonomics_size());            // 自动上限 32MB
  }
  region_size = round_up_power_of_2(region_size);
  region_size = clamp(region_size, G1HeapRegionBounds::min_size(),
                     G1HeapRegionBounds::max_size());                          // 硬上限 512MB
```

常量在 `g1HeapRegionBounds.hpp:36-49`:`MIN_REGION_SIZE = 1MB`、`MAX_ERGONOMICS_SIZE = 32MB`、`MAX_REGION_SIZE = 512MB`、`TARGET_REGION_NUMBER = 2048`。

【实测】-Xmx64m 的小堆启动时打印 `Heap Region Size: 1M`(64MB/2048=32KB,被 1MB 下限托住);默认 8GB MaxHeapSize 下 Region 为 4MB(8GB/2048=4MB,`-XX:+PrintFlagsFinal` 实测 `G1HeapRegionSize = 4194304 {ergonomic}`)。

**日志印证**:每次 GC 汇总里的四行就是按角色盘点 Region:

```
GC(13) Eden regions: 85->0(82)        // Eden 数: 回收前 85 -> 回收后 0 (下一轮目标 82)
GC(13) Survivor regions: 10->8(12)
GC(13) Old regions: 124->133          // mixed GC 时这行下降, 见 2.7
GC(13) Humongous regions: 0->0
```

## 2.2 分配路径:TLAB → Eden → 触发 GC → Humongous

**白话**:Java 线程分配对象几乎总是四步走——① 线程私有的 TLAB 里指针碰撞(无锁,最快);② TLAB 用完申请新 TLAB(在 Eden 的分配分区里切);③ Eden 放不下 → 触发一次 young GC 再试;④ 对象大到越过 humongous 阈值 → 走完全不同的大对象通道(见 2.3)。

**先说清 TLAB 是什么**(Thread-Local Allocation Buffer,线程本地分配缓冲):

- **解决的问题**:堆是所有线程共享的,若每次 `new` 都去竞争移动 Eden 的分配指针(需要 CAS/加锁),多线程下开销很大;
- **机制——"批发转零售"**:线程一次性从 Eden **领一小块私用**(几十 KB~几百 KB),之后线程内的 `new` 在自己的 TLAB 里做**指针碰撞**(bump-the-pointer):把私有指针前移"对象大小"即可——没有锁、没有 CAS,速度接近栈分配。TLAB 用完了再申请新的一块;Eden 满了就触发 young GC;
- **所有权私有,内存仍属共享堆**:TLAB 只是 Eden 里的一小块,"使用权"私有,对象照样归 GC 管;
- **大小自适应**:默认 `UseTLAB=true`、`ResizeTLAB=true`,JVM 按各线程分配速率动态调 TLAB 大小(JDK 27 实测默认:`MinTLABSize=2KB`、`TLABRefillWasteFraction=64`),让分配大户领大块、慢线程领小块;
- **大对象不走 TLAB**:TLAB 上限卡在 humongous 阈值(`g1CollectedHeap.hpp:1209` 的注释)——这也是 2.3 里"512KB 数组恰好越界"的另一半原因;
- **亲戚 PLAB**:GC 搬移线程复制对象时,从目标 Region(to-space/Old)批量领的复制缓冲——"GC 工作线程的 TLAB",`Evacuate Collection Set` 阶段的并行搬运靠它;
- **观测**:`-Xlog:gc+tlab=debug`(注意单写 `tlab` 不匹配,实测提示需用 `tlab*` 或 `gc+tlab`)。

一句话:**TLAB 把"在共享堆上分配对象"这件共享资源操作,变成了线程私有的纯算术操作——这是 G1 敢于宣称"Eden 分配几乎零成本"的底气。**

【源码证据】分配总入口按大小分流(g1CollectedHeap.cpp:443):

```cpp
HeapWord* G1CollectedHeap::mem_allocate(size_t word_size) {
  if (is_humongous(word_size)) {
    return attempt_allocation_humongous(word_size);   // 大对象: 独立通道
  }
  return attempt_allocation(word_size, word_size, &dummy, true /* allow_gc */);  // 常规: TLAB/Eden
```

常规通道慢路径是重试循环 `attempt_allocation_slow`(:453):锁 Heap_lock 扩分配区,不行就 `do_collection_pause`(:2544)发起一次 **`VM_G1CollectForAllocation`** VM 操作,在 safepoint 里跑 young GC,回来重试——这就是 young GC 最常见的启动方式,也是日志里 `G1 Evacuation Pause` 这个 cause 的来源(分配失败引发的停顿,即"搬移停顿")。

## 2.3 Humongous 对象:G1 的"超大件行李"

**白话**:超过 **Region 一半**的对象叫 humongous(巨型对象):它们直接分配在老年代语义的连续 Region 序列上,不进 young 代、不走 TLAB,回收也特殊处理。它是 G1 上线事故的头号惯犯(第四章案例 1/2)。

【源码证据】阈值判定(g1CollectedHeap.hpp:1209):

```cpp
static bool is_humongous(size_t word_size) {
  // Note this has to be strictly greater-than as the TLABs
  // are capped at the humongous threshold and we want to ...
  return word_size > _humongous_object_threshold_in_words;
}
static size_t humongous_threshold_for(size_t region_size) {
  return (region_size / 2);
}
```

**注意"严格大于"**:1MB Region 的阈值是 512KB,那么 `new byte[512*1024]` 算不算 humongous?**算!** 数组还有对象头(压缩 oop 下 ~16B),512KB+16B > 512KB,恰好越线——这是真实的线上陷阱(本系列实验就踩到了,见第四章案例 2)。

大对象分配通道(g1CollectedHeap.cpp:684 `attempt_allocation_humongous`)有两个关键行为:

1. **每次分配前都检查是否该启动并发标记**(:708):`policy()->need_to_start_conc_mark("concurrent humongous allocation", word_size)`——大对象能快速吃掉堆,所以 humongous 分配是并发标记的"加速触发器",日志里的触发原因就是 **`G1 Humongous Allocation`**。
2. 失败则发起 young GC 后重试,还不行就 try_full_collection。

【源码证据】分配时按 Region 对齐连占:`humongous_obj_allocate_initialize_regions`(g1CollectedHeap.cpp:314)把连续 N 个 Region 的第一个标成 Humongous Start,其余 Humongous Continuation,并把这些 Region 从"可分配池"摘除——**只要对象活着,这串 Region 谁也用不了**。

**回收**:① **eager reclaim**(8u60/9 起):young GC 时,若某 humongous 对象引用数很少(无 RSet 记账,"没有别人跨 Region 引用它"),可判定死亡直接回收,不用等并发标记(判定逻辑 `is_potential_eager_reclaim_candidate`,g1CollectedHeap.cpp:2577,注释明确"引用多的对象可能还活着,不选");② 并发标记确认死亡后,同样在 young GC 清掉;③ **mixed GC 不收 humongous Region**(太贵),这也是案例 2 里"mixed 帮不了大对象"的原因。

【实测】600KB 数组在 1MB Region 下反复分配,G0 的两次 GC 之间 Humongous 从 55 个 Region 掉到 24 个(eager reclaim 直接回收了 31 个):

```
GC(0) Pause Young (Concurrent Start) (G1 Humongous Allocation) 56M->25M(128M) 1.331ms
GC(0) Humongous regions: 55->24
```

## 2.4 记忆集 RSet:跨 Region 引用的"账本"

**白话**:young GC 只回收 young Region,但老年代可能引用年轻对象(否则每次回收都得扫全堆,G1 就死了)。G1 给**每个 Region 维护一套 RSet(Remembered Set):"谁引用了我"**——其实记录的是"哪个卡页(card)里有指向我的指针"。卡页对应堆中 512B,由**卡表(card table,字节数组)**标记脏;写引用的指令后面跟着**写后屏障**:改了引用就把对应卡表字节标脏,再由**并发 refinement 线程**异步把脏卡"精化"进目标 Region 的 RSet。

**JDK 17/18 前后的重写**:旧版 RSet 是"细粒度/粗粒度/全量"三级结构,内存开销大、易 coarsen 退化;新版是 **card set**(每个 Region 一个):小集合用稀疏存储,大了用数组卡片,再大用 Howl(位图分桶),极端情况 coarsen 成 Full(`g1CardSet.hpp:187` `G1CardSet`,`g1CardSet.hpp:47` `G1CardSetConfiguration`)。**收益:RSet 内存显著下降、不再有不可逆的粗化级联。**

【源码证据】young GC 中扫描"堆根"(从老年代指向 young 的卡)在 `G1RemSet::scan_heap_roots`(g1RemSet.cpp:542);屏障侧两件套(g1BarrierSet.inline.hpp):

```cpp
// 写前屏障(SATB): 引用即将被覆盖 -> 把旧值入 SATB 队列(见 2.5)
inline void G1BarrierSet::enqueue(T* dst) { ... queue_set.enqueue_known_active(queue, ...); }   // :50

// 写后屏障(card): 引用被更新 -> 卡表字节标脏, 等 refinement 线程精化
CardValue* byte = local_card_table->byte_for(field);
if (*byte == G1CardTable::clean_card_val()) {
  *byte = G1CardTable::dirty_card_val();
}                                                                                              // :76-79
```

**成本与观测**:refinement 线程数 `-XX:G1ConcRefinementThreads`(实测默认 = ParallelGCThreads,16 核机为 13);GC 期间花在 RSet 更新上的时间占比由 `G1RSetUpdatingPauseTimePercent`(默认 10)控制——它决定"GC 时顺手精化脏卡"的力度。RSet 带来的额外内存/cpu 开销,是 G1 在小堆小核环境长期不如 Serial/Parallel 的主因,也是 JEP 522 优化的重点。另外,标记周期结束后 RSet 的重建在**并发阶段**完成——日志中的 `Concurrent Rebuild Remembered Sets and Scrub Regions`(本机 JDK 21/25/27 实测均有)。

## 2.5 并发标记:三色标记 + SATB

**白话**:并发标记要和业务线程赛跑。G1 选 **SATB(Snapshot-At-The-Beginning)**:标记开始的瞬间"拍快照",**凡快照里活着的对象,标记全程都按活处理**。实现方式是**写前屏障**:任何引用字段被覆盖前,把**旧值**压入线程私有的 SATB 缓冲队列;并发标记线程后台消费这些队列。这样"引用被改掉"这件事一定留下了旧值痕迹,不会漏标。代价是**浮动垃圾**(快照后变死的对象这轮也算活),换来的是屏障极轻。

【源码证据】周期开始时激活屏障(把所有线程的 SATB 队列置为 active),g1ConcurrentMark.cpp:937:

```cpp
SATBMarkQueueSet& satb_mq_set = G1BarrierSet::satb_mark_queue_set();
// This is the start of the marking cycle, we're expected all
// threads to have SATB queues with active set to false.
satb_mq_set.set_active_all_threads(true,  /* new active value */
                                   false /* expected_active */);
```

Remark 停顿里再关掉(g1ConcurrentMark.cpp:1335)——"开启/关闭"的边界决定了哪些对象算快照内的。缓冲区有阈值(`G1SATBBufferEnqueueingThresholdPercent`,默认 60%:入队前先过滤已标记对象),满了就进全局队列由并发线程处理。

**一个周期的完整站队**(与日志一一对应,顺序由 `g1ConcurrentMarkThread` 驱动):

| 阶段 | STW? | 干什么 |
|------|------|--------|
| `Pause Young (Concurrent Start)` | ✔ | 一次普通 young GC,顺手:激活 SATB、初始标记 roots、把 survivor 区登记为"根 Region" |
| `Concurrent Scan Root Regions` | ✗ | 扫根 Region(survivor,因为标记期间它们会被搬,必须趁早) |
| `Concurrent Mark` | ✗ | 主标记:从根可达性遍历 + 消费 SATB 队列 |
| `Concurrent Preclean` | ✗ | (可配 `G1UseReferencePrecleaning`)提前消化一部分引用/脏卡,给 Remark 减负 |
| `Pause Remark` | ✔ | 停:处理剩余 SATB 缓冲、引用处理、类卸载(可选)。**SATB 在此关闭**(:1335) |
| `Concurrent Rebuild Remembered Sets and Scrub Regions` | ✗ | 为老年代候选 Region 并发重建 RSet(为 mixed 做准备)+ 清理 |
| `Pause Cleanup` | ✔ | 收尾统计、拿候选 Region 列表 |
| `Concurrent Cleanup for Next Mark` | ✗ | 回收全空 Region、重置位图 |

**中止与重试**:周期随时可能被打断——发生 Evacuation Failure 要 Full GC、或 Full GC 抢占时,日志会出现 **`Concurrent Mark Abort`**;JDK 27 里还有一种 `Concurrent Undo Cycle`(周期刚启动即被回滚,`g1CollectedHeap.cpp:2558` 的 `start_undo_concurrent_cycle`)。【实测】第四章案例 1 的日志里两者都出现了。

**白话**:young GC = "把 Eden + Survivor 里的活对象搬到新的 Survivor(或晋升 Old),Eden 整体作废"。CSet 就是全部 young Region;搬移(评估→复制→改指针)由 `ParallelGCThreads` 个工作线程并行完成。

## 2.7 Mixed GC:"垃圾优先"真正落地的地方

**白话**:并发标记结束后,G1 手里有一批"垃圾比较多的老年代候选 Region"。接下来若干次 young GC(默认目标 8 次,`G1MixedGCCountTarget=8`)**顺路**捎上一些老年代候选一起收——这就是 mixed GC。它不是一个独立 GC 类型,而是"young GC + 老年代增量"。

**候选怎么挑、挑多少**,四个旋钮(默认值为 JDK 27 实测):

| 参数 | 默认 | 含义 |
|------|------|------|
| `G1MixedGCLiveThresholdPercent` | 85% | 存活率高于它的老年代 Region **不进候选**(收它不划算) |
| `G1MixedGCCountTarget` | 8 | 标记后最多分 8 次 mixed 收完候选 |
| `G1OldCSetRegionThresholdPercent` | 10% | 单次 mixed 最多收 老年代 Region 数的 10%(控制单次增量) |
| `G1HeapWastePercent` | 5% | 可回收垃圾低于堆的 5% 就不做了(性价比止损) |

【源码证据】mixed 的单次预算与 young 尺寸联动决策在 `G1Policy::calculate_desired_eden_length_before_mixed`(g1Policy.cpp:508):把候选 Region 组的预测回收时间(`gr->predict_group_total_time_ms()`)累加进本轮停顿预测,再反推 Eden 还能留多大;老年代候选加入 CSet 走 `G1CollectionSet::add_old_region`(g1CollectionSet.cpp:120)。

**JEP 344(可中止 mixed)在源码里的样子**:候选分"必收"与"可选(optional)"两部分——GC 进行到停顿预算用尽时,可选部分直接放弃,日志层面 mixed 的 CSet 可动态缩水;代码上体现为 `G1CollectionSet::iterate_optional`(g1CollectionSet.cpp:188)与候选分组(`g1Policy.cpp:512` 按 `from_marking_groups()` 分组遍历)。**解读日志:`Pause Young (Prepare Mixed)` 是第一轮(候选盘点),随后 `Pause Young (Mixed)` 循环;若 Mixed 次数总是远少于 8,往往是每轮可选部分被预算砍掉(好事,停顿达标了)或 `G1HeapWastePercent` 止损。**

【实测·教学点】本章实验(老年代 144MB 全是 2KB 密集小对象)出现了 18 个 Mixed 停顿,但 `Old regions` 几乎不降:

```
GC(16) Pause Young (Mixed) (G1 Evacuation Pause) 223M->148M(256M) 1.994ms
GC(16) Old regions: 140->146        // mixed 在做, 但晋升(+6)盖过了回收(-0~2)
```

原因:老年代 Region 存活率 ~100%,全部高于 `G1MixedGCLiveThresholdPercent=85%`,没有候选可收——**mixed 不是"老年代清理器",它只捡软柿子**。随后每轮随机删除部分长命对象制造老年代垃圾后,老年代 Region 数从 144 涨到 199(碎片化,Region 空洞变多),mixed 才开始有收获(第四章案例 3 完整分析)。

## 2.8 悲观失败:Evacuation Failure(to-space exhausted)

**白话**:GC 搬移需要"落脚点"——新 Survivor 或晋升的 Old Region。G1 平时**预留堆的 10%**(`G1ReservePercent=10`)作为 to-space 缓冲,并在 CSet 大小上留保守余量。但当存活对象远超预测(或被 humongous Region 挤占,连续空间不足),复制到一半**没有落脚点了**——这就是 **Evacuation Failure**(老日志叫 **to-space exhausted**)。此时:① 本次 GC 变成"白干"(搬了一半,失败区对象原地自救 self-forward);② G1 立刻考虑追加一次 **Full GC** 兜底(`[gc,ergo] Attempting full compaction`)。

【源码证据】日志后缀的出处(g1YoungCollector.cpp:81-98):

```cpp
if (_collector->evacuation_failed()) {
  os::snprintf_checked(evacuation_failed_string, ...,
                       " (Evacuation Failure: %s%s%s)",
                       _collector->evacuation_alloc_failed() ? "Allocation" : "",
                       _collector->evacuation_alloc_failed() && _collector->evacuation_pinned() ? " / " : "",
                       _collector->evacuation_pinned() ? "Pinned" : "");
```

失败 Region 记账:`_pss->record_evacuation_failed_region(r, _worker_id, true /* cause_pinned */)`(g1YoungCollector.cpp:638);JEP 423 区域固定之后,"Pinned"成为失败的第二种原因(JNI 临界区钉住的 Region 不能搬)。

**【实测】同一触发场景在三个 JDK 版本的措辞对照**(排查老日志时别迷路):

| JDK | Young GC 失败措辞 | 后续动作措辞 |
|-----|-------------------|--------------|
| 21 | `Pause Young (Normal) (G1 Evacuation Pause) (Evacuation Failure)` | `Pause Full (G1 Compaction Pause)` |
| 25 | `... (Evacuation Failure: Allocation)` | `Pause Full (G1 Compaction Pause)` |
| 27 | `... (Evacuation Failure: Allocation)`(pinned 时为 `Allocation / Pinned`) | `[gc,ergo] Attempting full compaction` → `Pause Full (G1 Compaction Pause)` |
| 8~17 前后(旧日志) | `to-space exhausted`(老资料/旧日志) | `Pause Full (G1 Compaction Pause)` |

> 排查口诀:**日志里出现 Evacuation Failure / to-space exhausted,无论哪个版本,都是"G1 撑不住了"的最高优先级信号**(案例 1)。

## 2.9 Full GC:最后的兜底

**白话**:Full GC 是**全堆、单线程→并行、彻底整理**的停顿,以秒计,是设计上要**避免**而非优化的路径。JDK 10 的 JEP 307 把它并行化(此前 G1 的 Full GC 是单线程,大堆上灾难)。触发源:Evacuation Failure 追加、`System.gc()`(可用 `-XX:+DisableExplicitGC` 或 `-XX:+ExplicitGCInvokesConcurrent` 改道)、元数据不足、`jmap -histo:live` 等。

【实测】一次 Evacuation Failure 触发的 Full GC(JDK 27,5 阶段,源码 `g1FullCollector.cpp:215` `G1FullCollector::collect()`,五个 `GCTraceTime(Info)` 在 :314/:367/:500/:508/:525):

```
[0.070s][info ][gc,ergo     ] Attempting full compaction
[0.070s][info ][gc,start    ] GC(9) Pause Full (G1 Compaction Pause)
[0.070s][info ][gc,task     ] GC(9) Using 2 workers of 13 for full compaction
[0.070s][info ][gc,phases,start] GC(9) Phase 1: Mark live objects    // 全堆标记(含引用处理/类卸载)
[0.074s][info ][gc,phases,start] GC(9) Phase 2: Prepare compaction   // 计算每个 Region 的搬移目的地
[0.072s][info ][gc,phases,start] GC(9) Phase 3: Adjust pointers      // 全部引用改到新地址
[0.072s][info ][gc,phases,start] GC(9) Phase 4: Compact heap         // 实际搬运
[0.074s][info ][gc,phases,start] GC(9) Phase 5: Reset Metadata
[0.075s][info ][gc          ] GC(9) Pause Full (G1 Compaction Pause) 62M->40M(64M) 4.950ms
```

**显式 GC 的日志名不同**:`System.gc()` 触发的 Full GC 显示 `Pause Full (System.gc())`(【实测】JDK 21/25/27 一致),排障时可据此一眼区分"人为触发"与"故障触发"。另注意 Full GC **也不搬 humongous Region**(连续 Region 难以腾挪;存活的大对象继续占着)——【实测】案例 2 变体里 `Pause Full (G1 Compaction Pause) 93M->93M(96M)` 前后不变,92 个 humongous Region 纹丝未动。

## 2.10 自适应引擎:IHOP 与停顿目标

**白话**:G1 什么时候启动并发标记?答案是**IHOP(Initiating Heap Occupancy Percent)**:老年代占用达到阈值就启动。静态阈值默认 45%,但 JDK 9+ 默认**自适应**(`G1UseAdaptiveIHOP=true`):G1 根据历史"标记周期时长、期间老年代涨速、young 代大小"动态调整阈值——目标是"标记结束时老年代恰好涨到接近满,让 mixed 接着收"。

【源码证据】阈值计算(g1IHOPControl.cpp:116):

```cpp
size_t G1IHOPControl::old_gen_threshold_for_conc_mark_start() const {
  if (!_is_adaptive || !have_enough_data_for_prediction()) {
    return (size_t)(_initial_ihop_percent * _target_occupancy / 100.0);   // 数据不足: 回退静态 45%
  }
  // 三个预测来源: 周期期间老年代直接分配速率、peak humongous 增量、维持 young 尺寸的晋升量
```

【实测】`-Xlog:gc+ihop=debug` 下每次 GC 都报当前阈值与占用:

```
[debug][gc,ihop] GC(13) Basic information (value update), old-gen threshold: 120795955B (45.00%),
                 target occupancy: 268435456B, old-gen occupancy: 138641136B (51.65%)
```

**与停顿目标的关系**:`MaxGCPauseMillis=200` 驱动 young 代尺寸在 `G1NewSizePercent=5% ~ G1MaxNewSizePercent=60%` 之间伸缩(预测的 young 回收耗时接近预算就缩 young)。**手动设置 `-XX:InitiatingHeapOccupancyPercent`(或 JDK 27 的 `G1IHOP`)会关闭自适应**,一般不建议。

## 3.3 一条停顿日志的解剖学

以汇总行为例(JDK 9+ 统一格式):

```
[2.347s][info ][gc] GC(13) Pause Young (Concurrent Start) (G1 Evacuation Pause) 217M->139M(256M) 1.723ms
   │       │       │     │        │                    │                  │                │
 uptime  level   tag  GC 编号  停顿类型             触发原因           内存变化(前->后(容量))  纯停顿
```

- **GC 编号**:JVM 生命周期内单调递增,是关联多行日志的钥匙(同一编号的 start/heap/phases/cpu 行属于同一次 GC);
- **停顿类型**四选一:`Normal`(普通 young)、`Concurrent Start`(本轮顺带启动并发标记)、`Prepare Mixed`(标记完成后的第一轮,盘点候选)、`Mixed`(捎带老年代回收);
- **触发原因**常见五种:`G1 Evacuation Pause`(分配失败,最常见)、`G1 Humongous Allocation`(大对象触发)、`G1 Preventive GC`(预防性:预测本轮 eden 填满前晋升会出问题,提前收,JDK 17+ 也有)、`G1 Compaction Pause`(Full GC 专属)、`System.gc()`(显式触发);
- **`217M->139M(256M)`**:回收掉的 78MB 是这一轮的"收益";`139M` 是存活水位——**存活水位长期逼近总容量,离 Evacuation Failure 就不远了**;
- 附属行:`gc,task`(用了几个搬运线程)、`gc,heap`(四类 Region 增减)、`gc,metaspace`、`gc,cpu`(User/Sys/Real——**Real 与 User 严重不成比例时要查 CPU 限额/NUMA**);

**并发阶段的行**不带内存变化,只有耗时:`Concurrent Mark Cycle 4.139ms` 是整个并发周期总账,中间的 `Concurrent Mark From Roots 1.560ms` 等是子阶段。

## 3.4 【实测】一次完整生命周期的逐行精读

真实日志(节选自第四章案例数据,`-Xlog:gc*,gc+ihop=debug,gc+age=trace`):

```

[2.347s] GC(14) Concurrent Mark Cycle                          ← 周期开始(并发, 不停应用)
[2.347s] GC(14) Concurrent Scan Root Regions 0.230ms           ← 扫 survivor 根区
[2.347s] GC(14) Concurrent Mark From Roots 1.560ms             ← 主标记(3 个并发线程)
[2.349s] GC(14) Concurrent Preclean 0.006ms
[2.349s] GC(14) Pause Remark 141M->141M(256M) 0.269ms          ← 唯一较大的 STW 点(处理 SATB 残留/引用)
[2.349s] GC(14) Concurrent Rebuild Remembered Sets ... 1.235ms ← 为 mixed 候选重建 RSet
[2.351s] GC(14) Pause Cleanup 141M->141M(256M) 0.108ms         ← 统计收尾
```

## 3.5 关键词速查表:看到什么,该想什么

| 日志关键词 | 含义 | 优先级 | 去哪(章节) |
|-----------|------|--------|-------------|

| `Pause Full (G1 Compaction Pause)` | 兜底 Full GC(秒级停顿) | 🔴 最高 | 案例 1/4 |

# 四、实战案例集:从日志到根因

> **一句话定位**:七个案例,每个都按"现象 → 日志证据 → 推理链 → 根因 → 处置 → 预防"展开。案例 1~5 的日志为本机可复现实验(附录 C),案例 6~7 是生产中高频出现的模式,用实测数据佐证关键结论。

## 案例 1:晚高峰定时 Full GC——Evacuation Failure 的标准姿势

**现象**:服务每晚上 8 点出现 1~2 次 200ms+ 停顿抖动,平时 P99 只有 20ms。

**日志证据**(JDK 21/25/27 各取一行,完整日志见附录 C 复现):

```
JDK 21: GC(5) Pause Young (Normal) (G1 Evacuation Pause) (Evacuation Failure) 50M->52M(64M) 1.273ms
JDK 25: GC(5) Pause Young (Normal) (G1 Evacuation Pause) (Evacuation Failure: Allocation) 58M->55M(64M)
JDK 27: GC(7) Pause Young (Normal) (G1 Evacuation Pause) (Evacuation Failure: Allocation) 58M->59M(64M) 0.534ms
JDK 27: [gc,ergo] Attempting full compaction
JDK 27: GC(9) Pause Full (G1 Compaction Pause) 62M->40M(64M) 4.950ms      ← 秒杀所有 SLO 的那一行
JDK 27: GC(9) Phase 1: Mark live objects ... Phase 4: Compact heap        ← 全堆串行→并行整理
JDK 27: GC(3) Concurrent Mark Abort                                       ← 正在跑的并发标记被牺牲掉
```

**推理链**:

1. `Evacuation Failure` + 回收后内存**不降反升**(`50M->52M`)——young GC 白干;
2. 紧跟 `Attempting full compaction` → `Pause Full`——G1 已经放弃挣扎,只能全堆整理;
3. 回看前几轮:`Old regions: 56->59->63` 持续上涨、每次 GC 存活水位 `58M/59M/61M/62M` 逼近 `(64M)` 总容量——**堆里没有落脚空间了**;
4. `Concurrent Mark Abort`:并发标记周期被 Full GC 打断,进一步加剧恶性循环。

**根因**:老年代被持续填满(本实验是常驻缓存对象;生产上常见的是晚高峰缓存加载、大促囤积对象),to-space 预留(`G1ReservePercent=10%`)被挤占,搬移失败。

**处置**(按优先级):

1. **先看是不是该扩堆**:存活水位长期 > 90% 堆容量,加参数是止痛,加内存才是治病;
2. 扩不了时:`-XX:G1ReservePercent=15`(加大预留,代价是可用堆变小)、检查是否有大对象占着连续空间(案例 2);
3. 让高峰错峰:缓存加载分批(大数组切小,见案例 2)。

**预防**:告警盯住两个指标——`Pause Full` 出现次数(0 期望)与每次 GC 后的存活水位比(`used/heap`)。

## 案例 2:"512KB 陷阱"——Humongous 风暴拖垮整个 GC 计划

**现象**:批处理服务内存 OK,但 GC 频繁、单次 young GC 慢、启动大量 `G1 Humongous Allocation` 并发标记。

**日志证据**(本机实测,1MB Region):

主实验(反复分配 600KB 数组,128MB 堆):

```
GC(0) Pause Young (Concurrent Start) (G1 Humongous Allocation) 56M->25M(128M) 1.331ms
GC(0) Humongous regions: 55->24        ← eager reclaim 帮忙收了 31 个瞬时大对象
```

变体(把 60 个 1MB 数组**常驻**在 96MB 堆里——大对象活着不走,才是真正的灾难):

```
GC(2) Pause Young (Prepare Mixed) (G1 Humongous Allocation) (Evacuation Failure: Allocation) 93M->93M(96M)
[gc,ergo] Attempting full compaction
GC(3) Pause Full (G1 Compaction Pause) 93M->93M(96M) 2.135ms   ← Full 了也没用!
GC(3) Humongous regions: 92->92                                 ← 存活大对象钉住 Region, Full 无法整理
```

**推理链**:

1. 触发原因全是 `G1 Humongous Allocation` → 分配压力来自大对象,不是普通对象洪峰;
2. 512KB 数组 + 16B 对象头 > 512KB(1MB Region 的一半)——**"看起来刚好不超标"的对象其实是 humongous**(源码:`g1CollectedHeap.hpp:1209` 严格大于);
3. 存活的 humongous 连续占用 Region(`Humongous regions: 92->92`),把堆打成"蜂窝煤",young GC 的搬移落脚点(连续 Region)不足 → Evacuation Failure → Full GC;
4. **Full GC 也不搬 humongous**(连续 Region 难腾挪),`93M->93M` 白忙一场。

**根因**:大对象分配设计与 Region 大小不匹配。

**处置**:

1. **代码层优先**:大数组/大集合切片(如 10 万条记录分批加载)、避免用 `byte[]` 做长生命周期缓存(换堆外或分页);
2. **参数层**:调大 Region 让对象不再"超大":`-XX:G1HeapRegionSize=16m` 后 8MB 以内对象都不是 humongous(代价:Region 数变少,停顿粒度变粗);
3. 验证手段:改完看启动日志 `Heap Region Size` + `Humongous regions: X->Y` 的 X 是否归零。

**预防**:压测时统计对象大小分布(jemalloc 风格的 allocation profiling 或 JFR 的对象分配事件),给"最大常驻对象"留出 2 倍 Region 余量。

## 案例 3:Mixed 收不动与老年代"虚胖"——为什么并发标记天天跑

**现象**:GC 日志显示 `Concurrent Mark Cycle` 每 2~3 秒一次(理论上应该是分钟级),CPU 里 3 个 `GC Thread#` 并发线程常驻;young GC 倒是不长。

**日志证据**(本机实测,见 2.7 与 2.10):

```
[debug][gc,ihop] GC(16) Basic information (value update), old-gen threshold: 120795955B (45.00%),
                 target occupancy: 268435456B, old-gen occupancy: 152274688B (56.73%)   ← 1.5GB/2.68GB 已过半
GC(16) Pause Young (Mixed) (G1 Evacuation Pause) 223M->148M(256M) 1.994ms
GC(16) Old regions: 140->146                          ← mixed 在做, 但老年代不降反升
```

**推理链**:

1. 标记周期高频启动 → 每次 mixed 后老年代占用很快又越过 IHOP → **说明 mixed 几乎没收回东西**;
2. `Old regions` 只涨不降:本实验老年代是 2KB 密集小对象,每个 Region 存活率 ~100%,高于 `G1MixedGCLiveThresholdPercent=85%`,**没有候选 Region**;
3. 删除部分长命对象后再看:老年代 Region 数从 144 涨到 199——删除在 Region 内留下空洞,存活率降到阈值之下,mixed 开始收(**Region 数上升但 used 下降,即"虚胖"到"瘦身"**)。

**根因**(生产对照):

- 老年代存活率高、垃圾少 → 高频标记是正常现象,但 CPU 白烧;更好的做法是**调高 IHOP**(`-XX:G1IHOP=60` 等)让标记攒够垃圾再跑(注意:手动设置会关闭自适应 IHOP,需持续观察);
- 若是"Region 数虚胖"(空洞多、used 不高):老年代碎片化,说明有大量"分配后集中死亡"的错峰对象混进老年代——治理晋升(缩短对象存活期/`TargetSurvivorRatio`)比调 GC 更有效。

**处置**:先算"标记频率 × 单次 mixed 回收量"的性价比;收不回 5%(`G1HeapWastePercent`)就让它歇着,把 CPU 留给应用。

**预防**:把 `Old regions` 与 `used` 的比值(区域利用率)纳入监控,低于 70% 时排查老年代碎片。

## 案例 4:一上线就 Full GC?抓出 System.gc() 幕后黑手

**现象**:新版本上线后每几分钟一次 200ms+ 停顿;团队排查无分配异常。

**日志证据**(本机实测,JDK 21/25/27 一致):

```
GC(1) Concurrent Mark Cycle 1.998ms                       ← 常规周期
GC(2) Pause Full (System.gc()) 49M->49M(96M) 5.738ms      ← 名字里写着原因
```

**推理链**:Full GC 的名字分两种——`(G1 Compaction Pause)` 是故障触发(Evacuation Failure 追加、元数据不足等),**`(System.gc())` 是代码里有人显式调用**。老代码(连接池、缓存库、`-XX:+ExplicitGCInvokesConcurrent` 未开时的 RMI 分布式垃圾回收)是惯犯。

**处置**:

1. `-XX:+DisableExplicitGC` 一刀切?**危险**:`System.gc()` 顺带承担 DirectByteBuffer 的堆外内存清理,禁用后堆外内存可能 OOM;
2. 推荐 `-XX:+ExplicitGCInvokesConcurrent`:显式 GC 改道为并发标记周期(停顿毫秒级,还能清堆外);
3. 找到调用方:JFR(`jdk.SystemGC` 事件)/arthas(`watch java.lang.System gc`)一抓一个准。

**预防**:代码规约禁用 `System.gc()`;上线前 grep 依赖包。

## 案例 5:Pre Evacuate 变长——百万引用的账单

**现象**:缓存型服务 young GC 从 5ms 涨到 30ms;`Evacuate Collection Set` 本体没变,增量全在 `Pre Evacuate Collection Set`。

**日志证据**(本机实测,维护 300 万个 WeakReference):

```
GC(0) Pause Young (Normal) (G1 Evacuation Pause) 88M->47M(1536M) 29.279ms
[debug][gc,ref] GC(0) ReferenceProcessor::execute queues: 13, RefProcThreadModel::Multi, marks_oops_alive: false
GC(0) Pre Evacuate Collection Set: 0.23ms   ← 16 核机器上依然只有亚毫秒(整个实验峰值 0.40ms)
```

**推理链**:

1. 引用对象(Weak/Soft/Final/Phantom)的发现与清理发生在 young GC 的前置阶段(Pre Evacuate 里),`gc+ref=debug` 能看到它跑了几条队列;
2. 引用处理是**并行**的(RefProcThreadModel::Multi),其成本 ≈ 引用数 ÷ 并行度。**16 核机器上百万级引用只要零点几毫秒;4 核容器上同样规模就是 5~10ms**——这就是为什么同样的代码在小规格容器上 GC 突然变长;
3. 常见根因:缓存框架用 WeakHashMap/WeakReference 做过期、大量 Finalizer 对象(finalize() 还会拖慢单独的 Finalizer 线程形成堆积)。

**处置**:① 减引用对象:缓存过期换显式过期(时间轮/redis TTL);② Finalizer 换 try-with-resources/`Cleaner`;③ 实在多,加大 `ParallelGCThreads`(若 CPU 有余)并升级 JDK(24/27 的并发预处理 `G1UseReferencePrecleaning` 已把一部分引用工作挪出停顿)。

**预防**:监控 `Pre Evacuate Collection Set` 与 `Evacuate Collection Set` 的比值,>30% 预警。

## 案例 6:升级 JDK 后"日志对不上"——措辞与语义的版本陷阱

**现象**:从 8/11 升到 17/21/25/27 后,老脚本/老告警规则失效;或 grep `to-space exhausted` 永远匹配不到。

**证据与要点**(全部本机实测):

| 关注点 | 旧版本(8~17 前后) | 21 | 25/27 |
|--------|-----------|-----|-------|
| 搬移失败 | `to-space exhausted` | `(Evacuation Failure)` | `(Evacuation Failure: Allocation)`(pin 时 `.../ Pinned`) |
| Full GC 追加动作 | 直接进 Full | 直接进 Full | `[gc,ergo] Attempting full compaction` 先行 |
| 引用处理位置 | 独立 `Ref Proc` 阶段 | 并入 `Pre Evacuate Collection Set` | 同左 + 可选并发预处理 |
| Full GC 阶段 | 4 阶段 | 4 阶段(实测) | 5 阶段(多 `Phase 5: Reset Metadata`,实测) |
| 堆根合并 | 旧版本(`Merge ERs`) | `Merge Heap Roots`(实测) | 同左 |

**推理链**:统一日志(JEP 271)之后,措辞仍在小版本间微调,**依赖文本匹配的告警是脆弱的**;正确姿势是解析结构化字段(GC id + 类型 + 原因)而不是 grep 原文。

**处置**:告警规则迁移到"结构化信号"(GCEasy/gctoolkit 解析,或 JFR 事件流);把版本对照表(2.8 + 本表)放进运维手册。

## 案例 7:容器里的三笔"隐形账"——内存、CPU、NUMA

**现象**:同一镜像,物理机 GC 表现良好,进容器后 OOMKilled 或 GC 频繁;或 32 核大机上 mixed 并发阶段特别长。

**证据与推理**:

1. **内存账**:容器只看 `used` 而按 `committed` 收费/设限。G1 默认"只涨不还"(增长后不主动 uncommit),`jcmd GC.heap_info` 里 `committed >> used` 时容器 OOMKilled 风险高。**处置**:JDK 15+ 开 `-XX:G1PeriodicGCInterval=300000`(5 分钟空闲触发周期 GC 归还,MANAGEABLE 可运行时调);配合 `-XX:MaxRAMPercentage=75` 而不是拍脑袋 -Xmx;
2. **CPU 账**:容器 CPU 限额(如 2C)下,JVM 若未感知(log `CPUs: 16 total, 2 available` 正常感知)会开出过多 GC 线程,GC 时把限额外可用 CPU 吃爆;反之感知正常时 `ParallelGCThreads=2`,同样的 GC 工作量停顿翻数倍——**容器小核是 young GC 变长的第一嫌疑**(结合案例 5,引用处理成本 ×(16/2))。**处置**:小核上调小堆(≤2GB)、显式 `-XX:ParallelGCThreads` 平衡、升级 JDK 26/27(JEP 522/523 后 G1 小环境表现明显改善);
3. **NUMA 账**:多路服务器上对象跨节点访问延迟差可达 1.5~2 倍,JEP 345 让 Eden 按节点就近分配(启动日志 `NUMA Support: Disabled` → 加 `-XX:+UseNUMA` 变 Enabled)。

**预防**:镜像发布清单固化三条——`-XX:MaxRAMPercentage`、`-Xlog:gc*` 滚动文件、启动日志归档(里面有 CPUs/Memory/Region Size 三个"体检值")。

## 5.1 问题 → 参数/动作映射

| 症状(日志) | 第一动作 | 第二动作 |
|-------------|----------|----------|
| Evacuation Failure / Full GC | 查存活水位,不够就扩堆 | `G1ReservePercent↑`;排查 humongous(案例 1/2) |
| 高频 `G1 Humongous Allocation` | 代码切大对象 | `G1HeapRegionSize↑`(案例 2) |
| 标记周期过于频繁 | 确认 mixed 回收量(案例 3) | `G1IHOP↑`(关自适应需观察)/治理晋升 |
| young GC 停顿超预算 | 看 `Evacuate` vs `Pre Evacuate` 占比 | CSet 大小检查(young 尺寸/晋升速度)/引用治理(案例 5) |
| `Pause Remark` 长 | 检查标记期修改量/类数量 | 升级 JDK(并发预处理)/类加载治理 |
| 容器 OOMKilled | `committed` vs `used` | `G1PeriodicGCInterval` + `MaxRAMPercentage`(案例 7) |
| mixed 阶段 CPU 高 | RSet 开销评估 | `G1ConcRefinementThreads` 与 `G1RSetUpdatingPauseTimePercent` 微调 |
| 显式 Full GC | `ExplicitGCInvokesConcurrent` | 找调用方(案例 4) |

## 5.2 监控指标清单(告警建议)

1. `Pause Full` 次数 = 0(硬指标);
2. young GC P99 / MaxGCPauseMillis 达成率;
3. 每轮 GC 后存活水位比(`used/(max)`),>85% 预警;
4. `Humongous regions` 数量及其波动;
5. 并发标记周期频率与单次时长(趋势);
6. `Pre Evacuate`/总停顿占比;
7. `committed` vs `used`(容器环境必看)。

## D. 术语表

| 术语 | 含义 |
|------|------|
| Region | G1 堆的最小管理单元(1~32MB,上限 512MB),同一时刻充当一种角色 |
| CSet | 本次 GC 要回收的 Region 集合(young GC=全部 young;mixed=young+老年代候选) |
| RSet | 每个 Region 的"谁引用了我"账本,以卡页为单位,支撑部分回收 |
| Card / Card Table | 512B 堆片段 / 记录脏片段的字节数组,写后屏障维护 |
| SATB | 标记开始拍快照,写前屏障保留旧引用,防并发漏标 |
| TAMS | Top-At-Mark-Start,标记开始时 Region 的分配水位,水位之上是新对象 |
| PLAB / TLAB | GC 搬移线程 / 应用线程的本地分配缓冲 |
| Evacuation Failure | 搬移时无落脚点(旧称 to-space exhausted),触发 Full GC 兜底 |
| IHOP | 老年代占用达到阈值即启动并发标记(默认自适应) |
| Mixed GC | 标记完成后,顺带回收老年代候选 Region 的 young GC |
| Eager Reclaim | 引用稀少的 humongous 对象在 young GC 直接回收 |
