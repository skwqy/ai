# 零、定义、实现与微服务要补的那一段

## 0.1 优雅停机的定义

**优雅停机是一次有界的、按依赖顺序完成的退出：先停止接收新工作，再把已经接手的工作做完或做到可恢复的边界，然后按“使用者先于被使用者”的顺序释放资源，最后进程自己退出。**

把它拆成四个同时成立的条件：

| 条件 | 含义 | 做不到时的表现 |
|---|---|---|
| 停收新工作 | 上游（网关、Service、注册中心、消息中间件）不再把新请求、新消息交给这个实例 | 停机过程中仍有新流量打进来，客户端看到连接失败 |
| 排空已接手的工作 | 已经在执行的 HTTP 请求、已经拉取未确认的消息、必须做完的后台任务，在宽限时间内结束 | 响应写到一半被掐断，消息未提交位点后重复消费 |
| 有界 | 每一类等待都有超时。超时之后放弃剩余工作并继续退出，而不是无限期挂住 | 一个 WebSocket 或一条慢消息把实例卡死，编排系统只能 SIGKILL |
| 顺序正确 | 还在用连接池的请求先结束，连接池后关；还在写日志的停机逻辑先打完，日志系统后停 | 请求还在跑，数据源已经关了 |

和另外两种退出的差别：

- **立即停机**（`server.shutdown=immediate`，或 SIGKILL）：进程马上断开监听、中断线程。在途请求直接失败。适合可以丢工作的本地工具，不适合在线服务。
- **无限等待**：不设超时，直到所有连接和任务自然结束。长连接和泄漏的任务会让进程永远不退出，滚动发布卡住。

所以优雅停机不是“尽量多等一会儿”，而是 **拒绝新工作 + 排空旧工作 + 超时封顶 + 资源后关**。Spring Boot 4.1.1 把后半段（进程内的拒绝、排空、超时、拆 Bean）做成了默认行为；前半段里“让上游真的停止送工作”要由部署环境和业务入口补上。这就是 0.2 和 0.3 的分界。

## 0.2 Spring Boot 如何实现

Boot 没有单独的“优雅停机框架”。它把 JVM 的退出信号接到 Spring 容器的 `close()`，再由 `SmartLifecycle` 的相位把 Web 服务器、消息监听器和线程池排成固定顺序。4.1.1 上这条链默认就是通的。

实现可以看成五步。

**第一步：登记 JVM shutdown hook，让 SIGTERM 变成 `context.close()`。**

`SpringApplication` 启动时启用 `SpringApplicationShutdownHook`。JVM 退出时这个 hook 对每个已注册的 `ApplicationContext` 调用 `close()`，并最多再等 10 分钟直到容器变为 inactive（`SpringApplicationShutdownHook` 的 `TIMEOUT` 与 `closeAndWait`）。Kubernetes、systemd、`docker stop` 发给 1 号进程的 SIGTERM 会走到这里。SIGKILL 不会。

**第二步：`close()` 一开始就把就绪状态打成拒绝流量。**

`ServletWebServerApplicationContext.doClose()` 和 Reactive 栈的同名方法，在调用父类 `doClose()` 之前发布 `ReadinessState.REFUSING_TRAFFIC`。Actuator 的 `readiness` 健康组把这个状态映射为 `OUT_OF_SERVICE`。这一步只改应用自己的就绪标志，不会等待 kubelet 或注册中心完成传播。

**第三步：父类 `doClose()` 按固定顺序拆容器。**

`AbstractApplicationContext.doClose()`（Framework 7.0.9）的顺序是：

1. 发布 `ContextClosedEvent`。`ThreadPoolTaskScheduler` 默认在这里提前 `shutdown()`，不再触发新的调度。处理请求的 `ThreadPoolTaskExecutor` 默认不在这里拒绝任务。
2. `DefaultLifecycleProcessor.onClose()`，按相位从高到低停止所有 `SmartLifecycle`。
3. `destroyBeans()`，关闭数据源和其他 `DisposableBean`。此时生命周期相位已经走完，在途请求理论上已经结束。

**第四步：用两个 `SmartLifecycle` 把“排水”和“真正停服务器”拆开。**

创建内嵌 Web 服务器时，Boot 注册：

- `webServerGracefulShutdown`，相位 `SmartLifecycle.DEFAULT_PHASE - 1024`（`Integer.MAX_VALUE - 1024`）。`stop(Runnable)` 里调用 `webServer.shutDownGracefully(...)`。
- `webServerStartStop`，相位再低 1024。`stop()` 里调用 `webServer.stop()`；若排水还没结束，这里 `abort()`。

`server.shutdown` 的默认值是 `Shutdown.GRACEFUL`（`ServerProperties`）。因此 Tomcat / Jetty / Reactor Netty 都会装上排水实现：

| 服务器 | 拒绝新请求的方式 | 怎么判断“在途工作结束了” |
|---|---|---|
| Tomcat | `Connector.pause()` + `closeServerSocketGraceful()`。新连接拒绝，已有空闲连接上的新请求也拒绝 | 每 50ms 看异步进行中计数和各 Servlet 的 `countAllocated` |
| Jetty | `Connector.shutdown()`。新连接拒绝；旧连接上仍可再处理请求，响应带 `Connection: close` | 每 100ms 看 `StatisticsHandler` 的活跃请求数 |
| Reactor Netty | `disposeNow` 一直等到连接排空；相位超时后中断排水线程 | Netty 自己的连接排空 |

每一相位的等待上限来自 `spring.lifecycle.timeout-per-shutdown-phase`，Boot 默认 30 秒（`LifecycleProperties`）。Framework 处理器自身的默认值是 10 秒，Boot 的 `LifecycleAutoConfiguration` 把它改成 30 秒。超时后处理器进入下一相位，不会无限等。

**第五步：比 Web 更高的相位先停“还会产生新工作”的入口。**

相位数字越大越早停。Boot 4.1.1 搭配的组件默认落点是：

```
Integer.MAX_VALUE              Rabbit 监听容器、Quartz、业务默认 SmartLifecycle
Integer.MAX_VALUE - 100        Kafka 监听容器
Integer.MAX_VALUE - 1024       HTTP 排水
Integer.MAX_VALUE - 2048       HTTP 服务器 stop / abort
Integer.MAX_VALUE / 2          线程池
0                              普通 Lifecycle
然后 destroyBeans              数据源
```

因此一次默认停机在进程内的顺序是：**停消息和调度 → 排空 HTTP → 停 Web 服务器 → 停线程池 → 关连接池**。这就是 Boot 已经实现的优雅停机。

官方文档 `graceful-shutdown.adoc` 与上述源码一致：三种内嵌服务器、Servlet 与 Reactive 两种栈，默认开启；要退回立即断开才配置 `server.shutdown=immediate`。

## 0.3 基于 Spring Boot 的微服务要怎么做

Boot 负责进程内那一段。微服务还有进程外的上游，Boot 不会替你等待它们。要做到 0.1 的定义，服务侧只补 Boot 没有覆盖的缺口。

**已经由 4.1.1 默认完成、不要再重做的部分**

- 不必再写 `server.shutdown=graceful`。默认就是 `GRACEFUL`。只有确定可以丢弃在途请求时才设 `immediate`。
- 不必自己 `pause` Tomcat Connector，也不必再注册一个 JVM shutdown hook。再挂一套 hook（包括 Logback 的 `<shutdownHook>`）会和 Boot 的 hook 抢顺序。
- 不必在业务里手动把就绪状态改成 `REFUSING_TRAFFIC`。`doClose()` 会发布。前提是探针读的是这次发布能影响到的那份 `ApplicationAvailability`。

**必须补上的部分**

1. **让上游先停止送新工作，再让 SIGTERM 进来。**  
   Kubernetes 上用 `preStop` 睡眠（常见 10～20 秒），睡眠期间进程仍正常服务，Service 端点在这段时间里去掉本 Pod。`preStop` 结束后 kubelet 才发 SIGTERM，Boot 才开始排水。没有 Kubernetes、只有注册中心时，在 `ContextClosedEvent` 里摘流并等待传播——这个事件发生在暂停连接器之前。不要在 `preStop` 里调用 Actuator 的 `shutdown` 端点。

2. **探针分开打。**  
   就绪探针打 `/actuator/health/readiness`（只看 `readinessState`），存活探针打 `/actuator/health/liveness`（只看 `livenessState`）。聚合 `/actuator/health` 把数据库、磁盘算进去，停机或依赖抖动时会把还在排水的 Pod 杀掉或提前摘掉。Actuator 在 classpath 上时，这两个组默认就有（`management.endpoint.health.probes.enabled` 缺省即启用）。

3. **把总宽限写成各段之和。**  
   `terminationGracePeriodSeconds`、`docker stop -t`、systemd `TimeoutStopSec` 都要满足：

   ```
   停止宽限 ≥ preStop（或注册中心等待）
            + spring.lifecycle.timeout-per-shutdown-phase × 会拖满的相位数
            + 收尾缓冲（建议 ≥ 10s）
   ```

   默认每相位 30 秒。Kafka 通常在自己的 10 秒内结束，HTTP 排水会用满 30 秒。只给 Pod 30 秒时，排水会被 SIGKILL 掐断，优雅停机等于没做。`docker stop` 的默认 10 秒同样不够。

4. **每一种入口的个人超时短于它所在的那一档。**  
   - HTTP 请求超时、网关超时 < `spring.lifecycle.timeout-per-shutdown-phase`。  
   - Kafka 处理时长 < 容器 `shutdownTimeout`（默认 10 秒）。消费要幂等，因为相位超时会在位点提交前拆掉消费者。  
   - Rabbit 同理，默认再等 5 秒。  
   - gRPC 保持或显式写下 `spring.grpc.server.shutdown.grace-period`（默认 30 秒），不要设成负数（负数表示一直等）。  
   - WebSocket、SSE、长轮询算在途请求，会占满 HTTP 那一档，然后被 abort。客户端要能重连到其他实例。

5. **后台任务单独打开等待，请求线程池保持默认。**  
   随请求提交、随响应结束的 `ThreadPoolTaskExecutor` 不要开 `strictEarlyShutdown`，否则 `ContextClosedEvent` 一到就拒绝提交，此时 HTTP 还在排水。必须做完的队列、对账任务才设置：

   ```yaml
   spring:
     task:
       execution:
         shutdown:
           await-termination: true
           await-termination-period: 20s
   ```

   Quartz 默认不等正在执行的 Job。Job 必须做完时打开 `spring.quartz.wait-for-jobs-to-complete-on-shutdown`，并让该相位的超时盖住最长 Job。

6. **数据源留到最后关。**  
   连接池走 `destroyBeans()`，在全部生命周期相位之后。不要写成高相位的 `SmartLifecycle` 去提前关池。

7. **自定义停止逻辑遵守回调契约。**  
   自己的 `SmartLifecycle.stop(Runnable)` 在 `finally` 里执行回调。不回调会占满该相位的 30 秒。`isPauseable()` 返回 `false`，避免 Framework 7 的 `pause()` 把实例摘流但进程还在。

一份同时满足定义的最小配置：

```yaml
# 应用。server.shutdown 保持默认 graceful，这里写出来便于阅读
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s
management:
  endpoint:
    health:
      probes:
        enabled: true
```

```yaml
# Pod
spec:
  terminationGracePeriodSeconds: 90
  containers:
    - name: app
      lifecycle:
        preStop:
          exec:
            command: ["sh", "-c", "sleep 15"]
      readinessProbe:
        httpGet:
          path: /actuator/health/readiness
          port: 8080
        periodSeconds: 5
        failureThreshold: 1
      livenessProbe:
        httpGet:
          path: /actuator/health/liveness
          port: 8080
```

这 90 秒覆盖：`preStop` 15 秒、Kafka 默认约 10 秒、HTTP 排水 30 秒，以及线程池和连接池的收尾。Rabbit 或 Quartz 会把最高相位用满时，再加一份最多 30 秒。

上线前用一次真实 SIGTERM（不要用 IDE 的停止按钮）核对三件事：日志里有 `Graceful shutdown complete`；就绪探针变为 `OUT_OF_SERVICE` 而存活探针在进程退出前仍是 `UP`；没有 `Shutdown phase ... still running after timeout`。三者都成立，0.1 的定义才在这个服务上落地。

# 一、总览

## 1.1 一句话定位

**Spring Boot 4.1.1 的优雅停机，是“JVM 收到 SIGTERM → 关闭 ApplicationContext → 按 SmartLifecycle 相位从高到低停止 → 每个相位最多等一段时间”这条链。** Web 容器的“拒绝新连接、等在途请求结束”只是其中的一个相位，而且这个相位默认就是打开的。微服务要做的，是把注册中心摘流、Kubernetes 端点收敛、消息消费、定时任务和线程池，排进这条链的正确位置，并让编排系统的强杀时间盖住整条链。

## 1.2 设计哲学：先记住四句话

1. **停机主权在 Spring 生命周期，不在容器自己的 JVM hook。** `SpringApplicationShutdownHook` 收到退出信号后 `close()` 容器；Tomcat / Jetty / Netty 的排水由 `SmartLifecycle` 驱动。
2. **相位数字越大，越早停止。** 同一相位里的 `SmartLifecycle.stop(Runnable)` 被依次调用，然后共用一个超时一起等回调。
3. **宽限是“每个相位一份”，不是“整个进程一份”。** Boot 把每相位超时设为 30 秒。消息、HTTP、线程池若落在不同相位，最坏情况是多份 30 秒相加。
4. **拒绝流量和排空请求是两件事。** `doClose()` 一开始就把就绪状态打成 `REFUSING_TRAFFIC`；真正暂停连接器发生在更后面的 Web 相位。Kubernetes 的端点传播必须发生在 SIGTERM 之前，Boot 不会替你插入这段等待。

## 1.3 停机分层

```
编排系统（Kubernetes / systemd / docker stop）
  preStop 或等价等待            ← 端点 / 注册中心收敛，此时进程仍在正常服务
  SIGTERM
        │
        ▼
SpringApplicationShutdownHook   ← JVM shutdown hook，最多再等容器变成 inactive（10 分钟）
        │ context.close()
        ▼
WebServerApplicationContext.doClose()
  1. 发布 ReadinessState.REFUSING_TRAFFIC
  2. super.doClose()
       2a. ContextClosedEvent     ← 调度器可能在这里提前 shutdown()
       2b. DefaultLifecycleProcessor.onClose()   ← 按相位停 SmartLifecycle
       2c. destroyBeans()         ← 连接池、未走 Lifecycle 的资源
  3. webServer.destroy()
```

相位从高到低（停止顺序）的默认骨架：

| 停止顺序 | phase | 典型成员 | 这一档在做什么 |
|---|---|---|---|
| 1 | `Integer.MAX_VALUE`（`SmartLifecycle.DEFAULT_PHASE`） | 业务自己写的默认 `SmartLifecycle`、Quartz `SchedulerFactoryBean`、Spring AMQP 监听容器 | 停掉仍会产生新工作的入口。Rabbit 容器自己的 `shutdownTimeout` 默认 5 秒 |
| 2 | `Integer.MAX_VALUE - 100` | Spring Kafka 监听容器（`AbstractMessageListenerContainer.DEFAULT_PHASE`） | 停止拉取并提交位点。容器自己的 `shutdownTimeout` 默认 10 秒 |
| 3 | `DEFAULT_PHASE - 1024` | `webServerGracefulShutdown` | 暂停连接器，等待在途 HTTP 结束 |
| 4 | `DEFAULT_PHASE - 2048` | `webServerStartStop` | `webServer.stop()`，必要时打断尚未结束的排水 |
| 5 | `Integer.MAX_VALUE / 2` | `ThreadPoolTaskExecutor` / `ThreadPoolTaskScheduler` | 等执行器里还在跑的任务 |
| 6 | `0` | 普通 `Lifecycle`（未实现 `Phased`） | 其余生命周期对象 |

`2147483647 - 1024 = 2147482623`，再减 `1024` 是 `2147481599`。执行器相位 `1073741823` 小于 Web 的 start/stop 相位，所以线程池停在 Web 容器真正 `stop()` 之后。在途请求在排水期间仍然能向 `ThreadPoolTaskExecutor` 提交任务。

## 1.4 一次停机的时间线

```
SIGTERM
  │
  ├─ 发布 REFUSING_TRAFFIC          （探针下一次抓到会变成 OUT_OF_SERVICE）
  ├─ ContextClosedEvent
  │     ThreadPoolTaskScheduler 默认在这里 initiateShutdown()
  │     ThreadPoolTaskExecutor 默认不提前拒绝任务（strictEarlyShutdown=false）
  ├─ phase MAX：Quartz、Rabbit 监听容器、自定义默认相位
  │     本相位最多 spring.lifecycle.timeout-per-shutdown-phase（默认 30s）
  ├─ phase MAX-100：Kafka 监听容器（自带 shutdownTimeout 默认 10s）
  ├─ phase MAX-1024：HTTP 优雅排水
  │     Tomcat 50ms 轮询、Jetty 100ms 轮询；超时后进入下一相位
  ├─ phase MAX-2048：webServer.stop() → gracefulShutdown.abort()
  ├─ phase MAX/2：执行器停止并等待正在执行的任务
  └─ destroyBeans：数据源、其余 DisposableBean
SIGKILL（若编排系统的宽限先耗尽，上面任何一步都会被掐断）
```

## 1.5 关键问题 → 做法

| 问题 | 做法 | 详见 |
|---|---|---|
| 优雅停机指什么，Boot 做了哪一段 | 停收、排空、有界、按顺序释放。Boot 默认完成进程内这段；上游等待由部署补上 | 第零章 |
| 还要不要写 `server.shutdown=graceful` | 4.1.1 默认已是 `GRACEFUL`。要立刻断开才写 `immediate` | 第二章 |
| 30 秒不够 / 太长 | 调 `spring.lifecycle.timeout-per-shutdown-phase`，并按相位个数做总预算 | 第三章、第六章 |
| 滚动发布仍有 502 | 在 SIGTERM 之前用 `preStop` 等端点收敛；探针打 `readiness` 组 | 第五章、第六章 |
| 停机时任务被中断 | 分清请求线程池和后台线程池；后台池打开 `await-termination` | 第七章 |
| WebSocket / SSE 把宽限吃满 | 它们算“在途请求”，超时后被 abort | 第四章 |
| 消息重复或丢失 | 消费者停在 HTTP 排水之前；提交位点要在相位超时内完成 | 第七章 |
| 有人调用 HTTP 把进程关掉 | `shutdown` 端点默认 `Access.NONE` | 第八章 |

## 1.6 版本基线

| 事实 | 证据 |
|---|---|
| Boot 4.1.1 发布 | tag `v4.1.1`，2026-08-20；发行说明含 “Upgrade to Spring Framework 7.0.9” |
| `server.shutdown` 默认 `GRACEFUL` | `ServerProperties` 字段初始值；4.0.0 的同字段已是 `Shutdown.GRACEFUL` |
| 官方参考文档与源码一致 | `documentation/.../web/graceful-shutdown.adoc`：三种内嵌服务器、两种 Web 栈，默认开启；用 `server.shutdown=immediate` 关闭 |
| 每相位超时默认 30s | `LifecycleProperties.timeoutPerShutdownPhase = Duration.ofSeconds(30)` |
| Framework 自己的默认是 10s | `DefaultLifecycleProcessor` 字段注释与初值：6.2 起默认 10000ms。Boot 的自动配置把它改成 30s |

2.3 引入这项能力时需要显式打开。写 4.1.1 的配置时，以本 tag 的默认值为准。

## 1.7 可直接落地的实践清单

1. **保持默认优雅停机。** 不要把 `server.shutdown` 设成 `immediate`，除非这个进程可以丢弃在途请求（批处理、本地工具）。
2. **给每相位一个明确超时。** 起点用默认 30s；在途请求的 P99 明显高于它时再加大。请求自身的超时要短于这个值，让请求在 abort 之前自己结束。
3. **总预算按相位相加，而不是只留一份 30s。** `terminationGracePeriodSeconds`（以及 `docker stop -t`、systemd `TimeoutStopSec`）≥ `preStop` + `timeout-per-shutdown-phase` × 会拖满的相位数 + 5～10 秒收尾。
4. **Kubernetes 用 `preStop` 消化端点传播，用 SIGTERM 触发 Boot。** `preStop` 期间进程仍在接受请求；Boot 的排水从 SIGTERM 才开始。
5. **就绪探针只打 `readiness` 组，存活探针只打 `liveness` 组。** 聚合 `/actuator/health` 把数据库、磁盘算进去，停机和抖动时会误杀。
6. **注册中心摘流放在 Web 排水之前，并且不要阻塞同一个相位里的其他 `stop()`。** 无 Kubernetes 时，在 `ContextClosedEvent` 里摘流并等待传播；有 Kubernetes 时把这段等待放在 `preStop`。
7. **请求用的 `ThreadPoolTaskExecutor` 保持默认（不要开 `strictEarlyShutdown`）。** 后台执行器才打开 `spring.task.execution.shutdown.await-termination` 和 `await-termination-period`。
8. **消息监听、gRPC、Quartz 各自的等待时间都要落在所属相位的超时之内。** Kafka 容器默认相位是 `Integer.MAX_VALUE - 100`、自身再等 10 秒；Rabbit 在默认相位、自身再等 5 秒。gRPC 默认宽限 30 秒（`spring.grpc.server.shutdown.grace-period`）。Quartz 默认不等待正在执行的 Job。
9. **自定义 `SmartLifecycle` 的 `stop(Runnable)` 结束时必须执行回调。** 不回调会占满该相位的全部超时。
10. **不要暴露 `shutdown` 端点来代替 SIGTERM。** 它默认关闭；打开后会跳过 `preStop` 那种“先收敛再排水”的窗口。
11. **不要再注册一套 Logback 的 JVM shutdown hook。** 优雅停机的日志打在 `context.close()` 过程中，另一套 hook 会抢先把日志停掉。
12. **在 IDE 里点停止，往往不是 SIGTERM。** 本地看到“立即退出”不能当作生产行为。

# 二、信号从哪进来

## 2.1 模块定位

生产环境里，Kubernetes、systemd、`docker stop` 发给 1 号进程的是 SIGTERM。Boot 在启动早期登记一个 JVM shutdown hook，退出时由它关闭容器。关闭容器才会走到后面的相位和 Web 排水。

## 2.2 Hook 先关掉容器，再跑附加动作

【源码证据】`core/spring-boot/src/main/java/org/springframework/boot/SpringApplicationShutdownHook.java`

```java
private static final int SLEEP = 50;
private static final long TIMEOUT = TimeUnit.MINUTES.toMillis(10);

public void run() {
    // ...
    Collections.reverse(handlers);
    contexts.forEach(this::closeAndWait);
    closedContexts.forEach(this::closeAndWait);
    handlers.forEach(Handler::run);
}
```

`closeAndWait`（约 143–164 行）调用 `context.close()`，然后每 50ms 看一次 `isActive()`，最多等 10 分钟。这个 10 分钟只在进程还能活这么久时生效。Kubernetes 的 `terminationGracePeriodSeconds` 先到就会 SIGKILL，hook 的 10 分钟等不到。

附加的 `SpringApplication.getShutdownHandlers().add(...)` 在所有容器 `close()` 之后才跑，适合进程级收尾，不适合“还要依赖 Bean”的摘流。

## 2.3 默认就是 GRACEFUL

【源码证据】`module/spring-boot-web-server/.../autoconfigure/ServerProperties.java` 104–107 行：

```java
/**
 * Type of shutdown that the server will support.
 */
private Shutdown shutdown = Shutdown.GRACEFUL;
```

官方文档 `graceful-shutdown.adoc` 写明：Jetty、Reactor Netty、Tomcat，以及 Servlet 与 Reactive 两种栈，默认开启。关闭方式：

```yaml
server:
  shutdown: immediate
```

Tomcat 工厂把这个值传进服务器（`TomcatServletWebServerFactory.getTomcatWebServer`，429 行）：

```java
return new TomcatWebServer(tomcat, getPort() >= 0, getShutdown());
```

`TomcatWebServer` 只在 `shutdown == GRACEFUL` 时创建 `GracefulShutdown`（109 行）。两参数构造器写死 `Shutdown.IMMEDIATE`（95 行）——自己 `new TomcatWebServer(tomcat, true)` 会绕过默认优雅停机。业务代码应走 Boot 的工厂，而不是直接 new。

Jetty 在 `getShutdown() == GRACEFUL` 时包一层 `StatisticsHandler`（`JettyServletWebServerFactory` 182–186 行）。没有这层，`JettyWebServer.createGracefulShutdown` 返回 null，`shutDownGracefully` 会立刻以 `IMMEDIATE` 结束。自定义 Jetty `Handler` 树时要保留这层统计 handler。

## 2.4 IDE 与 `shutdown` 端点

官方文档的注意点：IDE 停止按钮若不是 SIGTERM，就不会走这条 hook，表现成立即退出。

Actuator 的停机端点默认不可用：

【源码证据】`module/spring-boot-actuator/.../context/ShutdownEndpoint.java` 39–67 行：`@Endpoint(id = "shutdown", defaultAccess = Access.NONE)`。一旦被调用，先睡 500ms 再 `context.close()`。这会进入与 SIGTERM 相同的 `close()` 路径，但发生时编排系统还没做 `preStop`，上游仍可能往这个实例送流量。生产上用 SIGTERM 驱动停机；端点保持默认关闭。

## 本章小结

- 优雅停机的开关是“进程能不能收到 SIGTERM 并活过后续相位”，不是再写一行 `server.shutdown=graceful`。
- Hook 的 10 分钟上限挡不住编排系统的 SIGKILL。总时长由编排系统决定。

# 三、相位：谁先停，最多等多久

## 3.1 两个 Web 生命周期

容器在 `onRefresh()` 里创建 Web 服务器时，注册两个单例（`ServletWebServerApplicationContext.createWebServer`，193–195 行；Reactive 栈在 `ReactiveWebServerApplicationContext` 107–108 行做同样的事）：

- `webServerGracefulShutdown` → `WebServerGracefulShutdownLifecycle`
- `webServerStartStop` → `WebServerStartStopLifecycle`

相位常量在 `WebServerApplicationContext`：

```java
int GRACEFUL_SHUTDOWN_PHASE = SmartLifecycle.DEFAULT_PHASE - 1024;
int START_STOP_LIFECYCLE_PHASE = GRACEFUL_SHUTDOWN_PHASE - 1024;
```

`SmartLifecycle.DEFAULT_PHASE` 在 Framework 7.0.9 是 `Integer.MAX_VALUE`（`SmartLifecycle.java` 82 行）。因此排水相位高于 start/stop 相位，`close()` 时排水先执行。

排水生命周期只实现带回调的停止（`WebServerGracefulShutdownLifecycle` 58–76 行）：

```java
public void stop() {
    throw new UnsupportedOperationException("Stop must not be invoked directly");
}

public void stop(Runnable callback) {
    this.running = false;
    this.webServer.shutDownGracefully((result) -> callback.run());
}

public int getPhase() {
    return WebServerApplicationContext.GRACEFUL_SHUTDOWN_PHASE;
}
```

`isPauseable()` 返回 `false`（79–81 行）。Framework 7 的 `context.pause()` 走 `stopBeans(true)`，会跳过不可暂停的 Bean。**滚动发布和缩容要走 `close()` / SIGTERM。** `pause()` 不会暂停连接器。

## 3.2 每相位一份超时

【源码证据】Boot `LifecycleAutoConfiguration` 39–45 行把 Framework 的处理器换掉，并写入配置：

```java
DefaultLifecycleProcessor lifecycleProcessor = new DefaultLifecycleProcessor();
lifecycleProcessor.setTimeoutPerShutdownPhase(properties.getTimeoutPerShutdownPhase().toMillis());
```

`LifecycleProperties`（29–36 行）前缀是 `spring.lifecycle`，`timeoutPerShutdownPhase` 默认 `Duration.ofSeconds(30)`。

Framework 侧 `DefaultLifecycleProcessor` 的字段默认是 `10000`（124 行，注释写明 6.2 起 10 秒）。没被 Boot 自动配置替换时（例如在单元测试里手 new 容器）才是 10 秒。正常 Boot 应用是 30 秒。

某个相位还可以单独加长或缩短：`setTimeoutForShutdownPhase(phase, timeout)`。Boot 的配置项只有“所有相位同一个值”。某个相位特别慢时，注册一个 `DefaultLifecycleProcessor` Bean 自己设置（自动配置带 `@ConditionalOnMissingBean`，用户自定义会让位）。

停止循环（`LifecycleGroup.stop`，633–660 行）：

1. 对本相位每个 `SmartLifecycle` 调用 `stop(callback)`。回调里 `latch.countDown()`。
2. `latch.await(该相位超时)`。
3. 超时后打日志：`Shutdown phase {phase} ends with N beans still running after timeout of ...ms`，然后进入下一相位。超时不会取消已经在跑的排水线程；下一相位的 `webServer.stop()` 才会 `abort()`。

同一相位的 `stop(callback)` 若在调用回调之前同步 `sleep`，for 循环里后面的 Bean 要等它返回才收得到 `stop()`，而且这段睡眠发生在 `latch.await` 之前，会加在该相位的 30 秒之外。摘流等待放在 `ContextClosedEvent`，或单独一个没有其他 Bean 的相位。Kafka 容器的相位是 `Integer.MAX_VALUE - 100`，和默认相位不是同一档。

依赖关系会打乱相位：`doStop` 先停 `getDependentBeans`（458–465 行）。给低相位 Bean 声明 `depends-on` 一个高相位 Bean，会把前者提前拖进后者的停止过程。Web 服务器和数据源不要用 `depends-on` 绑在一起。

## 3.3 回调是契约

`SmartLifecycle.stop(Runnable)` 的约定（142–145 行）：处理器只调用这个重载；回调必须在组件真正停止之后执行。默认实现是同步 `stop()` 然后立刻回调。自己写异步停止时，漏掉 `callback.run()` 的后果是该相位干等到超时。日志里会看到自己的 Bean 名留在 “still running” 列表中。

## 3.4 建议配置

```yaml
spring:
  lifecycle:
    # 在途 HTTP 的硬上限。请求超时、网关超时都应短于它。
    timeout-per-shutdown-phase: 30s
```

观察每次发布的停机日志：

- `Commencing graceful shutdown. Waiting for active requests to complete`
- `Graceful shutdown complete` 或 `Graceful shutdown aborted with one or more requests still active`
- `Shutdown phase ... still running after timeout`

第二种和第三种说明预算不够，或有长连接 / 未回调的 `SmartLifecycle`。

## 本章小结

- HTTP 排水是独立相位，默认在消息消费那一档之后、线程池那一档之前。
- 30 秒是每一档的上限。档数上去之后，进程总时长线性增长。
- 自定义停止逻辑要么尽快回调，要么单独占一个相位，避免堵住同相位的其他人。

# 四、三种内嵌服务器怎么拒绝新请求

## 4.1 共同行为

`shutDownGracefully` 在后台线程里排水，尽快返回到生命周期处理器，处理器用相位超时等回调。结果有三种（`GracefulShutdownResult`）：

| 枚举 | 含义 |
|---|---|
| `IDLE` | 宽限内在途请求已经没有了 |
| `REQUESTS_ACTIVE` | 宽限结束时仍有在途请求，随后被 abort |
| `IMMEDIATE` | 服务器没启用优雅停机，回调立刻发生 |

## 4.2 Tomcat

【源码证据】`module/spring-boot-tomcat/.../GracefulShutdown.java`

- 新线程名 `tomcat-shutdown`（56 行）。
- 对每个 `Connector`：`pause()`，再 `closeServerSocketGraceful()`（93–96 行）。
- 每 50ms 看一次：异步进行中计数 `StandardContext.getInProgressAsyncCount()`，以及每个 `StandardWrapper.getCountAllocated()`（98–123 行）。
- `abort()` 把 `aborted` 设为 true，循环退出。

`TomcatWebServer` 的 javadoc（441–447 行）写明语义：**新连接被拒绝；已经空闲的持久连接上的新请求也被拒绝。** `stop()`（352–354 行）在拆掉 Connector 之前调用 `gracefulShutdown.abort()`。

因此：

- 普通阻塞请求、异步请求、占着 Wrapper 的 WebSocket / SSE，都会让 `isActive` 保持 true，直到结束或被 abort。
- 虚拟线程不改变这个判断，计数在 Wrapper 上，不在平台线程池上。
- 客户端会看到连接失败或中途断开，而不是一个稳定的 HTTP 状态码。网关要把这种失败当成“实例正在退出”，而不是业务 5xx 去重试到同一实例。

## 4.3 Jetty

【源码证据】`module/spring-boot-jetty/.../GracefulShutdown.java` 与 `JettyWebServer` 310–318 行。

- 对每个 `Connector` 调用 `shutdown()`。
- 用 `StatisticsHandler.getRequestsActive()` 每 100ms 轮询。
- javadoc：**新连接被拒绝；已有连接上的请求仍会接受，但响应带 `Connection: close`。**

和 Tomcat 的差别要写进网关策略：Jetty 在排水期间仍可能在旧连接上接一个新请求，处理完就关掉连接。空闲长连接不会像 Tomcat 那样被直接拒掉。

`server.setStopTimeout(0)`（`JettyServletWebServerFactory` 193 行）把 Jetty 自己的停止等待交给 Boot 的相位超时，避免两套超时各等一次。

## 4.4 Reactor Netty

【源码证据】`module/spring-boot-reactor-netty/.../GracefulShutdown.java` 49–84 行，以及 `NettyWebServer` 202–216、241–252 行。

- 排水线程里 `server.disposeNow(Duration.ofNanos(Long.MAX_VALUE))`，也就是一直等到连接排空。
- 相位超时后，`stop()` 调用 `gracefulShutdown.abort()`，对排水线程 `interrupt()`。
- javadoc：新连接被拒绝，已有空闲连接上的请求也被拒绝。
- `stop()` 里若配置了 `lifecycleTimeout`，再用这个时长 `disposeNow`。它是 stop 阶段的第二段等待，要算进总预算。

## 4.5 实践

- Servlet 服务默认 Tomcat 即可，排水语义最符合“停机后不要再接任何新请求”。
- 使用 Jetty 时，把“旧连接还能再进一个请求”写进客户端与网关的预期，并依赖 `Connection: close` 回收连接。
- WebFlux / Netty 的排水可以被中断；中断点就是相位超时，不是 `Long.MAX_VALUE` 那段名义上的无限等待。
- 长连接端点（WebSocket、SSE、长轮询、HTTP/2 上一直不结束的流）会占满 `GRACEFUL_SHUTDOWN_PHASE`。这类实例把 `timeout-per-shutdown-phase` 定成可接受的中断时间，并让客户端能重连到其他实例。
- 应用层请求超时 < 相位超时。这样大多数请求以业务超时结束（`IDLE` 或正常响应），而不是被 abort 切断。

## 本章小结

- 三种服务器都在网络层停掉新连接，差别在“已经建立的连接上还接不接请求”。
- 宽限用尽的表现是 `REQUESTS_ACTIVE` 加上连接被打断，不是再多等一轮。

# 五、先把就绪探针打成拒绝流量

## 5.1 close 的第一件事

Servlet 与 Reactive 的 `doClose()` 在调用 `super.doClose()` 之前发布就绪状态（`ServletWebServerApplicationContext` 172–176 行，Reactive 对应 154–158 行）：

```java
protected void doClose() {
    if (isActive()) {
        AvailabilityChangeEvent.publish(this, ReadinessState.REFUSING_TRAFFIC);
    }
    super.doClose();
    // ... webServer.destroy()
}
```

`ReadinessStateHealthIndicator`（34–37 行）把 `ACCEPTING_TRAFFIC` 映射为 `UP`，把 `REFUSING_TRAFFIC` 映射为 `OUT_OF_SERVICE`。

事件发布在**正在关闭的那个** `ApplicationContext` 上（`AvailabilityChangeEvent.publish` 76–78 行）。Spring 的事件默认向父容器传播，不向子容器传播。管理端口若是子容器，子容器里的监听器收不到这次事件。探针若是每次调用 `ApplicationAvailability.getReadinessState()` 来拉状态，就要保证它注入的是主容器那一份可用性 Bean。单独管理端口时，用一次真实的 SIGTERM 看 `/actuator/health/readiness` 是否变为 `OUT_OF_SERVICE`，作为上线前检查。

## 5.2 探针组默认就有

【源码证据】`AvailabilityProbesAutoConfiguration` 42 行：

```java
@ConditionalOnBooleanProperty(name = "management.endpoint.health.probes.enabled", matchIfMissing = true)
```

Actuator 在 classpath 上且未把该属性设为 `false` 时，就会注册 `livenessState` 与 `readinessState`。`AvailabilityProbesHealthEndpointGroups`（67–71 行）始终建立两个组：

| 组名 | 成员 | 附加路径（仅当打开 add-additional-paths） |
|---|---|---|
| `liveness` | `livenessState` | `/livez` |
| `readiness` | `readinessState` | `/readyz` |

附加路径默认关闭，由 `management.endpoint.health.probes.add-additional-paths=true` 打开，并且挂在主端口（`WebServerNamespace.SERVER`）。未打开时，路径是健康端点下的组：

- 存活：`/actuator/health/liveness`
- 就绪：`/actuator/health/readiness`

组里只有对应的 state 指示器，不包含数据库、磁盘、Redis。这是探针该打的地址。

## 5.3 为什么还要 preStop

`REFUSING_TRAFFIC` 和暂停连接器发生在同一次 `close()` 里，中间只隔着 `ContextClosedEvent` 和更高相位。kubelet 的下一次探针、EndpointSlice 的传播，都赶不上这几秒。SIGTERM 到来时连接器马上开始拒绝，那些还没更新端点的客户端会拿到连接错误。

Kubernetes 的顺序是：Pod 进入 Terminating → 执行 `preStop` → `preStop` 结束后发 SIGTERM → 从 deletionTimestamp 起算，超过 `terminationGracePeriodSeconds` 则 SIGKILL。`preStop` 的睡眠时间算在宽限里。

```yaml
# 应用
server:
  shutdown: graceful   # 4.1.1 的默认值，写出来只为了让配置自解释
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s
management:
  endpoint:
    health:
      probes:
        enabled: true
        add-additional-paths: true   # 主端口 /readyz /livez；不用也可以，改打 group 路径
```

```yaml
# Pod
spec:
  terminationGracePeriodSeconds: 90
  containers:
    - name: app
      lifecycle:
        preStop:
          exec:
            command: ["sh", "-c", "sleep 15"]
      startupProbe:
        httpGet:
          path: /actuator/health/liveness
          port: 8080
      livenessProbe:
        httpGet:
          path: /actuator/health/liveness
          port: 8080
      readinessProbe:
        httpGet:
          path: /actuator/health/readiness
          port: 8080
        periodSeconds: 5
        failureThreshold: 1
```

这里 90 秒的构成：`preStop` 15 秒 + Kafka 那一档按默认 10 秒计 + HTTP 排水 30 秒 + 约 15 秒给线程池和连接池，再留余量。Rabbit 若和 Quartz 把 `Integer.MAX_VALUE` 那一档用满，再加一份最多 30 秒。`readiness` 的 `failureThreshold: 1` 缩短的是探针间隔，替代不了 `preStop`：Boot 要到 SIGTERM 之后才翻转就绪状态。

`preStop` 里不要调用 `shutdown` 端点，也不要 `kill` 进程。那段时间应用应继续正常服务。

没有 Kubernetes、只有注册中心（Nacos、Eureka、Consul）时，传播等待要放在进程内、且在暂停连接器之前。`ContextClosedEvent` 的监听器位于 `lifecycleProcessor.onClose()` 之前（`AbstractApplicationContext.doClose` 1188–1204 行），此时连接器仍在服务。在监听器里摘流并睡眠，睡眠时长另加到进程管理器的停止超时上，不要假设它被算进 `timeout-per-shutdown-phase`。

## 本章小结

- 就绪状态在排水之前翻转，但翻转和暂停连接器几乎连在一起。
- 让上游停止送流量的等待，放在 SIGTERM 之前（`preStop`）或 `ContextClosedEvent` 里，不要放在 Web 排水相位里。

# 六、时间预算

把一次停机会用到的等待加起来，写进编排系统。

| 段落 | 默认量级 | 是否占用 `timeout-per-shutdown-phase` |
|---|---|---|
| `preStop` 睡眠 | 由你设定，常见 10–20s | 否，但占用 `terminationGracePeriodSeconds` |
| `ContextClosedEvent` 里的摘流等待 | 由你设定 | 否，它发生在相位循环之前 |
| `phase = MAX` Rabbit / Quartz / 业务默认 Lifecycle | 最多 30s；Rabbit 自身默认再以 5s 封顶 | 是，整相位一份 |
| `phase = MAX-100` Kafka 监听容器 | 最多 30s；容器 `shutdownTimeout` 默认 10s | 是，单独一档 |
| `phase = MAX-1024` HTTP 排水 | 最多 30s | 是 |
| `phase = MAX-2048` `webServer.stop()` + abort | 通常很快；Netty 另有 `lifecycleTimeout` | 是 |
| `phase = MAX/2` 执行器 | 最多 30s，且受 `await-termination-period` 影响 | 是 |
| `destroyBeans` 关池、刷日志 | 通常数秒 | 否 |
| Boot hook 等 inactive | 上限 10 分钟 | 否；SIGKILL 会提前到来 |

公式：

```
停止宽限 ≥ preStop + ContextClosedEvent 等待
         + timeout-per-shutdown-phase × 会拖满的相位数
         + 收尾缓冲（建议 ≥ 10s）
```

会拖满的相位以停机日志为准，不要按“理论上有五个相位”去乘。一个卡住且不回调的 Bean 会独占它所在相位的全部超时。

`docker stop` 的默认等待只有 10 秒，盖不住默认的 30 秒排水。镜像的停止超时要和上面的公式一致。

## 本章小结

- 30 秒是相位预算，不是 Pod 预算。
- 先看一次真实停机日志里有几条 “still running after timeout”，再定 `terminationGracePeriodSeconds`。

# 七、线程池、消息、调度、gRPC、数据源

HTTP 排水只覆盖“已经进了 Web 容器的请求”。微服务里的工作还有别的入口，它们走别的相位。

## 7.1 执行器：请求池和后台池分开

Framework 7.0.9 里，执行器的 `SmartLifecycle` 相位是 `Integer.MAX_VALUE / 2`（`ExecutorConfigurationSupport.DEFAULT_PHASE`，75 行），停在 Web `stop()` 之后。

`ContextClosedEvent` 的处理（504–534 行）会分叉：

- `acceptTasksAfterContextClose` 或 `waitForTasksToCompleteOnShutdown` 为 true：标记 `lateShutdown`，不在事件里提前 `shutdown()`。
- 否则：`initiateEarlyShutdown()` → `executor.shutdown()`，不再接受新任务。

`ThreadPoolTaskExecutor` 覆盖了早停（425–428 行）：只有 `strictEarlyShutdown == true` 才调用父类。默认 `false`（100 行，javadoc 222–238 行写明 6.1.4 起默认宽松）。**处理请求的池子保持这个默认。** 打开 `strictEarlyShutdown` 之后，`ContextClosedEvent` 一到就拒绝新任务，此时 HTTP 排水还没开始，在途请求里的 `@Async` / `submit` 会收到 `RejectedExecutionException`。

`ThreadPoolTaskScheduler` 没有这层放宽，默认会在 `ContextClosedEvent` 里早停。停机开始后不要再指望 `@Scheduled` 触发新的一轮。

Boot 把配置映射到这两个开关（`ThreadPoolTaskExecutorBuilder` 333–335 行）：

```java
map.from(this.acceptTasksAfterContextClose).to(taskExecutor::setAcceptTasksAfterContextClose);
map.from(this.awaitTermination).to(taskExecutor::setWaitForTasksToCompleteOnShutdown);
map.from(this.awaitTerminationPeriod).as(Duration::toMillis).to(taskExecutor::setAwaitTerminationMillis);
```

对应属性：

```yaml
spring:
  task:
    execution:
      pool:
        shutdown:
          # 默认 false。true 会跳过执行器的协调停止相位。
          accept-tasks-after-context-close: false
      shutdown:
        # true 等价于 waitForTasksToCompleteOnShutdown，销毁时不 shutdownNow。
        await-termination: true
        await-termination-period: 20s
    scheduling:
      shutdown:
        await-termination: true
        await-termination-period: 20s
```

`await-termination` 默认 `false`（`TaskExecutionProperties.Shutdown` 242 行）。默认销毁路径是 `shutdownNow()`，队列里的任务被取消，正在跑的任务被中断。

实践：

- **随请求创建、随响应结束的任务**：用默认 `ThreadPoolTaskExecutor`。排水期间池子仍接受提交，Web 停掉之后才进入执行器相位。
- **停机时必须做完的后台任务**（发对账消息、刷本地队列）：打开 `await-termination` 并给出 `await-termination-period`。这段等待发生在销毁阶段时，数据源可能已经开始关闭。任务若还要访问数据库，让执行器 Bean 依赖数据源，利用“先停依赖方”的销毁顺序；并把 `await-termination-period` 算进总预算。
- **虚拟线程模式**下，应用执行器换成 `SimpleAsyncTaskExecutor`（`TaskExecutorConfigurations` 91–94 行）。同一组 `spring.task.execution.shutdown.await-termination*` 会写成 `taskTerminationTimeout`（174–176 行），语义是取消剩余任务前的等待，不是线程池的 `awaitTermination`。切换 `spring.threads.virtual.enabled` 后要重新看一次停机日志。

## 7.2 消息消费停在 HTTP 排水之前

两套监听容器都实现 `SmartLifecycle`，相位都高于 Web 排水（`Integer.MAX_VALUE - 1024`），所以都是先停消费、再排空 HTTP。HTTP 处理函数里同步发出的消息不依赖本地消费者；本地消费者不会在排水期间继续拉取。

【源码证据】Spring Kafka 4.1.1（Boot 4.1.1 发行说明中的对应版本）`AbstractMessageListenerContainer`：

```java
public static final int DEFAULT_PHASE = Integer.MAX_VALUE - 100; // late phase
```

`ContainerProperties.DEFAULT_SHUTDOWN_TIMEOUT` 为 `10_000L` 毫秒。Boot 4.1.1 的 `KafkaProperties.Listener` 没有 shutdown 字段，未自定义容器时就是这 10 秒。它短于相位的 30 秒，正常路径下 Kafka 这一档会在 10 秒内回调，不会把 30 秒用满。

Spring AMQP 4.1.1 的 `AbstractMessageListenerContainer` 把 `phase` 设为 `Integer.MAX_VALUE`，`DEFAULT_SHUTDOWN_TIMEOUT` 为 `5000` 毫秒。它和 Quartz、业务默认 `SmartLifecycle` 停在同一档，共用一份 30 秒；容器自己通常 5 秒就返回。

相位超时若先于容器超时到来，处理器不再等回调，直接去停下一档。消费者可能在未提交位点时被拆掉，表现为重复消费。消费逻辑要幂等。

实践：

- 单条处理时长的上限短于该容器自己的 `shutdownTimeout`（Kafka 10 秒、Rabbit 5 秒），而容器超时又短于 `spring.lifecycle.timeout-per-shutdown-phase`。
- 要拉长 Kafka 的停止等待时，在容器定制器里调 `shutdownTimeout`，同时确认 `MAX - 100` 这一相位的预算盖得住。Boot 的 `KafkaProperties` 不暴露这个字段。
- 摘流睡眠放在 `ContextClosedEvent`（所有相位之前）。写进 `Integer.MAX_VALUE` 的同步 `stop()` 会挡住同相位的 Rabbit 和 Quartz，并在 30 秒相位超时之外再加一段墙钟时间。

## 7.3 gRPC

Boot 4.1 自带的服务器属性前缀是 `spring.grpc.server`（`GrpcServerProperties` 39 行）。停机宽限（116–122 行）：

```java
/**
 * Maximum time to wait for the server to gracefully shutdown. When the value is
 * negative, the server waits forever. When the value is 0, the server will force
 * shutdown immediately.
 */
private Duration gracePeriod = Duration.ofSeconds(30);
```

```yaml
spring:
  grpc:
    server:
      shutdown:
        grace-period: 30s
```

负值会无限等待，直到编排系统 SIGKILL。生产上用正数，并且 ≤ 该服务器生命周期所在相位的超时。同时提供 HTTP 与 gRPC 时，两套宽限都要出现在总预算里；若它们落在不同相位，就是两段时间。

## 7.4 Quartz

`QuartzProperties.waitForJobsToCompleteOnShutdown` 默认 `false`（59–62 行），属性名 `spring.quartz.wait-for-jobs-to-complete-on-shutdown`。默认停机不等正在执行的 Job。Job 必须做完时打开它，并确认 Scheduler 所在相位的超时盖住最长的 Job。打不开这个开关又不能接受中断时，Job 本身要可续跑。

`spring.task.scheduling` 管的是 Boot 的 `ThreadPoolTaskScheduler`，不管 Quartz。两套调度都在用时，两个开关都要设。

## 7.5 数据源

Hikari 等连接池通过 `DisposableBean` 在 `destroyBeans()` 里关闭，位于全部 `SmartLifecycle` 相位之后（`AbstractApplicationContext.doClose` 1196–1207 行：先 `onClose()`，再 `destroyBeans()`）。在途请求和执行器相位里的任务，默认还能拿到连接。

不要把“关闭数据源”写成一个高相位 `SmartLifecycle`，否则 HTTP 排水期间连接已经没了。

## 本章小结

- Web 排水不包含消息拉取、定时触发和线程池队列。这三样有自己的相位和默认“不等待”。
- 请求线程池保持宽松早停；后台工作显式打开等待，并把等待算进预算。

# 八、自定义扩展时的约束

业务侧若要插入摘流、刷盘、通知网关，遵守下面的形状即可，不必再包一层线程或再注册一个 JVM hook。

```java
public final class DeregisterLifecycle implements SmartLifecycle, Ordered {

    // 使用默认相位：停在 HTTP 排水之前。
    // 真正的“等注册中心传播”放在 ContextClosedEvent，避免堵住本相位的 for 循环。

    @Override
    public void stop(Runnable callback) {
        try {
            registry.deregister();
        }
        finally {
            callback.run();
        }
    }

    @Override
    public int getPhase() {
        return SmartLifecycle.DEFAULT_PHASE;
    }

    @Override
    public boolean isPauseable() {
        return false;
    }
}
```

```java
@Component
class DeregisterOnClose implements ApplicationListener<ContextClosedEvent> {

    @Override
    public void onApplicationEvent(ContextClosedEvent event) {
        registry.deregister();
        // 仅用于没有 preStop 的部署。时长加到进程停止超时里。
        Thread.sleep(Duration.ofSeconds(10));
    }
}
```

约束：

- `callback.run()` 放在 `finally`。
- `isPauseable()` 返回 `false`，避免 `pause()` 把实例从注册中心摘掉但进程还在。
- 不在这个 Bean 上声明会把 Web 服务器或数据源提前停掉的 `depends-on`。
- 不额外 `Runtime.addShutdownHook`。Boot 已有 hook；多个 hook 的顺序不确定。
- Logback 配置里不写 `<shutdownHook>`。停机日志需要在 `close()` 期间还能输出。

## 本章小结

- 扩展点用 `ContextClosedEvent` 和 `SmartLifecycle` 就够了。
- 回调、相位、暂停标志决定它会不会把整次停机拖死。

# 九、上线前核对

用一次真实 SIGTERM 核对，而不是 IDE 的停止按钮。

1. 停机日志里出现 `Commencing graceful shutdown`，随后是 `Graceful shutdown complete`。若是 `aborted` 或 `REQUESTS_ACTIVE`，加长相位超时或缩短请求 / 长连接的寿命。
2. 没有意外的 `Shutdown phase ... still running`。有的话，日志里的 Bean 名就是没按时回调的组件。
3. SIGTERM 之后、进程退出之前，`/actuator/health/readiness` 变为 `OUT_OF_SERVICE`，`/actuator/health/liveness` 在进程还活着时保持 `UP`。存活探针若打到聚合健康，依赖失败会在排水期间把 Pod 杀掉。
4. Kubernetes 事件里 `preStop` 先于容器退出；`terminationGracePeriodSeconds` 大于第六章的公式。Pod 被 `OOMKilled` 或 `Error` 且 reason 含 `DeadlineExceeded` 时，就是宽限不够。
5. 消息：停机窗口内的重复消费可以被业务幂等吃掉；没有“停机后仍在拉取”的日志。
6. 后台任务：打开 `await-termination` 的池子打出正常终止，而不是 `Timed out while waiting for executor`。
7. `management.endpoint.shutdown.access` 保持默认关闭。

# 十、贯通：一份默认配置在停机时实际发生的事

以“Tomcat + Actuator + 一个默认相位的 Kafka 监听容器 + 默认的 `ThreadPoolTaskExecutor` + Kubernetes”为例，4.1.1 不改 `server.shutdown` 时：

1. kubelet 执行 `preStop`（若配置了 `sleep`）。这段时间连接器、消费者、线程池都还在工作，Service 端点开始去掉这个 Pod。
2. SIGTERM 进入 `SpringApplicationShutdownHook`，调用 `context.close()`。
3. `doClose()` 发布 `REFUSING_TRAFFIC`。下一次就绪探针变为 `OUT_OF_SERVICE`。
4. `ContextClosedEvent`：`ThreadPoolTaskScheduler` 若存在，会提前不再接新的调度；`ThreadPoolTaskExecutor` 默认仍接受任务。
5. 相位 `Integer.MAX_VALUE`：Rabbit 监听容器（自身最多等 5 秒）与 Quartz 在这一档停止。没有这两样时，这一档很快过去。
6. 相位 `MAX - 100`：Kafka 监听容器停止，默认最多 10 秒提交位点。
7. 相位 `MAX - 1024`：Tomcat `pause` + `closeServerSocketGraceful`，每 50ms 查看在途请求，最多 30 秒。
8. 相位 `MAX - 2048`：若上一步还没结束，`abort()` 打断它，然后停止 Connector。
9. 相位 `MAX / 2`：执行器停止。默认不等待队列，销毁时 `shutdownNow()`。
10. `destroyBeans()`：关闭数据源。hook 看到容器 inactive 后返回。若前面的墙钟时间超过 `terminationGracePeriodSeconds`，进程在中途收到 SIGKILL，HTTP 排水那一步没有意义。

优秀实践就是把第 1 步的传播等待、第 5–8 步的相位超时、第 9 步的收尾，加总后写进编排系统，并让每一种工作入口（HTTP、消息、调度、gRPC、后台池）的个人超时短于它所在的那一档。
