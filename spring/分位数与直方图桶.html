Micrometer / Prometheus 指标模型

分位数与直方图桶

它们不是两个并列的指标，而是同一件事的两种表示：桶是原料，分位数是用原料加工出来的成品。理解这一层，才能看懂为什么"服务端 P99"只能建在桶上。

三句话结论

桶是一组固定边界上的累计计数，可相加、可合并，是唯一能跨实例算全局分位数的原料。
分位数是排序后第 N% 位置上的值，抗长尾、可读性强，但不可平均、不可相加。
配置上：服务端多实例只开直方图；客户端分位数只用于单实例诊断。

01一图看清两者的关系

下面是一个真实形状的耗时分布（1000 次调用）。柱子是"落在每个耗时区间的次数"，折线是"累计占比"，橙点是"在累计曲线上读出分位数"的位置。

读法：从左边 50% 的高度水平向右，撞到累计折线，再垂直落下来读横轴，得到 P50 ≈ 36ms。这就是分位数的全部含义。

同一次观测的三个数讲三个故事：平均耗时约 81ms、P50 ≈ 36ms、P99 ≈ 750ms。用户"典型体验"是 36ms，报表会写 81ms，而最慢那 1% 的人在等 0.75 秒。三个数都对，但只有 P99 描述了那 10 个人的绝望。

02直方图桶：把分布切成格子

2.1 定义

桶（bucket）是一组预先固定的边界，每个桶记一个数：耗时小于等于该边界的调用次数。在 Prometheus 文本格式里，它长这样：

order_create_seconds_bucket{le="0.05"}  680
order_create_seconds_bucket{le="0.1"}   830
order_create_seconds_bucket{le="0.25"}  920
order_create_seconds_bucket{le="+Inf"}  1000

2.2 四条不可动摇的规则

规则含义为什么必须这样
边界固定一旦定下，每次抓取都报同一组 le 值后端要能逐次对齐、桶间相减；边界漂移 = 序列不可比
累计语义le="0.1" 的值包含所有更小桶的次数单调不减才能被 histogram_quantile 使用，也自带"≤"的语义
自检点le="+Inf" 必须等于 _count不等就说明有样本被丢弃（超时、溢出、负值）
精度上限落在同一桶里的值无法再区分P99 的最大误差等于它所在桶的宽度

最后一条是桶的根本代价：桶是有损压缩。图 1 里 P99 落在 [500, 1000] 这一档，跨度 500ms，所以 750ms 只是插值出来的猜测——真实值可能是 520，也可能是 980。想看清尾部，只能把桶在尾部加密。

2.3 累计桶与增量桶：同一个分布，两种写法

同一组数据，Prometheus 报"累计"，OTLP 报"增量"。形状完全相反，但信息等价（前提是桶边界一致）。

累计桶（Prometheus）增量桶（OTLP / Datadog）
语义迄今 ≤ 该边界的总次数，永远递增本步（默认 60s）内落在该档的次数
相邻两档相减得到该档的增量为负 → 无意义得到累计量 → 无意义
计算分位数后端直接 histogram_quantile先还原成累计，或按后端规则
进程重启归零，rate() 出现断点不影响（每步独立）
丢失一次抓取无影响（下次仍是全量）永久丢失该步数据

2.4 精度就是桶边界的密度

假设 SLO 是 300ms，但桶边界只有 250 和 500。那么无论真实情况如何，你只能报出："P99 在 250ms 到 500ms 之间"。这不是估算误差，是信息已经丢了。

所以设桶的原则只有一条：把桶密集地放在你关心的区间。做法有两个：

  • 设 serviceLevelObjectives（SLO 边界），只在你真正要考核的档位加密，成本最低；
  • 收窄 minimumExpectedValue / maximumExpectedValue，让自动生成的桶落在有效区间内（见 2.5）。

2.5 Micrometer 的桶是从哪来的

Micrometer 不动态学习分布，而是用一张预生成的固定桶表，按配置的 [min, max] 切片：

  • 桶表的生成规则：以 4 的幂为骨架，中间按"上一次幂的 1/3"等距插值，再补上 +Inf。所以真实的桶是 1, 2, 3, 4, 5, ... 14, 16, 21, 26, ... 这种形状，不是整齐的 1/2/5 序列。
  • 切片区间由 minimumExpectedValue 和 maximumExpectedValue 决定：区间越宽，桶越多。
最常踩的坑

DistributionStatisticConfig 的 maximumExpectedValue 默认是 +Infinity。这意味着切片几乎等于整张桶表，单个 publishPercentileHistogram() 就能让一条 Timer 膨胀出上百个桶——序列数直接涨一个数量级。正确做法是同时显式设定 min 和 max（例如 1ms ~ 5s），让切片落在几十个桶。

2.6 桶的成本可以算出来

一条 Timer 在 Prometheus 里占用的序列数：

序列数 = 标签组合数 × (桶数 + 3)      // +3 是 _count / _sum / _max

举例：http.server.requests 有 20 个 uri × 5 个 method × 6 个 status = 600 个标签组合，桶数 73，则

600 × (73 + 3) = 45 600 条序列

这就是为什么"随手开个直方图"在小集群上没感觉，在大集群上能压垮 Prometheus。桶是用存储换分辨率，本质上是笔预算。

03分位数：在曲线上读一个位置

3.1 定义

P99 的严格定义是：把样本按大小排序后，第 99% 个位置上的那个值。它回答的是"最慢的那 1% 从哪里开始"，而不是"平均有多慢"。

几个常用档位各自回答不同的问题：

档位回答的问题典型用途
P50一半请求快于多少典型用户体验；与 P99 对照判断"整体变慢"还是"局部受害"
P90开始进入慢区间的门槛前端渲染、首屏体验基线
P95尾部从哪里开始常规 SLI、日常告警
P99长尾有多长SLO 考核、容量规划、下游依赖评估
P999极端尾部GC 停顿、锁竞争、网络抖动定位
MAX历史上发生过的最坏一次故障复盘；不适合告警（单点极值，抖动大）

3.2 为什么不用平均值

1000 次调用，其中 980 次 10ms、20 次 5s（比如每 50 次有一次缓存击穿）：

指标值它让你以为什么
平均值(980×10 + 20×5000) / 1000 = 110ms"还行，稍微慢一点"
P5010ms"绝大多数请求非常快"
P995s"每 50 个用户就有一个在等 5 秒"

平均值被头部拉低、又被尾部拉高，两头抵消成一个"看起来无害"的数字。平均值是唯一一个既不代表典型用户、也不代表最差用户的指标。

3.3 三个必须纠正的误读

误读一

"P99 = 99% 的请求快于这个值"。严格说是"第 99 百分位上的观测值"。用桶计算时还会在桶内做线性插值，所以它天然带误差，且误差上限就是桶宽。

误读二

"把多个实例的 P99 平均就是全局 P99"。这是本文最需要记住的一条，见 3.5。

误读三

"只看 P99 就够了"。P50 与 P99 同时抬升 = 整体变慢（资源不足、全量慢查询）；只有 P99 抬升而 P50 平稳 = 部分请求受害（下游抖动、GC、连接池争抢）。两者的组合才是诊断信息。

3.4 两条实现路线

客户端分位数聚合直方图
Micrometer 开关publishPercentiles(0.5, 0.99)publishPercentileHistogram() 或设 SLO
存储的是什么每实例一个 HdrHistogram，采集时算成几个数固定边界上的桶计数
产出形态..._seconds{quantile="0.99"}..._seconds_bucket{le="0.5"}
精度高（受 percentilePrecision 影响）受桶边界限制
内存每实例一份直方图，较重固定（桶数 × 计数器）
跨实例聚合不能能（桶可相加）
适用单实例诊断、离线分析服务端 SLO、多实例面板、告警

3.5 分位数为什么不可平均

三个实例等流量，各 1000 次请求，实例 C 有 1% 的请求慢到 1 秒：

实例 A · P99 = 100ms 实例 B · P99 = 100ms 实例 C · P99 = 1000ms
把 P99 直接平均
400ms

(100 + 100 + 1000) / 3。但合并后 3000 次请求里只有 10 次落在 1 秒，第 2970 位仍落在 100ms 那档——真实全局 P99 是 100ms，误差 4 倍。

把桶相加再重算
≈ 100ms

3000 次请求的桶逐档相加，重新找第 2970 位。这是唯一正确的"全局 P99"，也是它必须建在桶上的原因。

为什么：分位数只记录"某个位置的值"，丢掉了"这个位置前后各有多少样本"。合并两个分布时，你需要的是每个区间的数量，而不是两个孤立的位置坐标。这就是分位数不可加、不可平均、不可跨时间求和的数学根源。

推论：以下操作全部是错的，而且错得静默——不会报错，只会给你一个看起来很合理的数字。

  • 多实例 P99 取平均（或取最大）
  • 按分钟算 P99，再对 24 小时取平均求"日 P99"
  • 按机房算 P99，再线性组合成"全国 P99"

04在 Micrometer 里怎么配

4.1 三个开关，三种产出

配置产出能跨实例聚合用途
publishPercentiles(0.5, 0.95, 0.99){quantile="0.99"}不能单机诊断
publishPercentileHistogram()_bucket{le="..."}能服务端首选
serviceLevelObjectives(...)少量指定 _bucket能SLO 达标率，成本最低
都不开（默认）仅 _count / _sum / _max—只能算平均和 QPS

4.2 三种注解写法

@Timed(value = "order.create", histogram = true)                        // → _bucket，生产首选
@Timed(value = "order.create", percentiles = {0.5, 0.99})               // → quantile 序列，单机诊断
@Timed(value = "order.create", serviceLevelObjectives = {0.1, 0.3, 1})  // → 只在 100ms / 300ms / 1s 三档有桶

4.3 生产推荐配置

给 HTTP 指标配一组"边界密在有效区间"的桶，同时把所有 Timer 的默认上界收窄——这一步能直接省掉一半序列数：

@Bean
MeterFilter httpDistribution() {
    return MeterFilter.configure(
        "http.server.requests",
        DistributionStatisticConfig.builder()
            .minimumExpectedValue(Duration.ofMillis(1))
            .maximumExpectedValue(Duration.ofSeconds(5))
            .serviceLevelObjectives(
                Duration.ofMillis(100),
                Duration.ofMillis(300),
                Duration.ofSeconds(1))
            .build());
}

@Bean
MeterFilter shrinkDefaultHistogram() {
    return MeterFilter.configure(
        DistributionStatisticConfig.builder()
            .maximumExpectedValue(Duration.ofSeconds(10))
            .build());
}
为什么这样配

serviceLevelObjectives 会在最终桶集合里额外注入这三个边界，所以即使自动生成的桶不密，SLO 那三档永远精确——"P99 是否超过 300ms"这个问题能被明确回答，而不是"在 250 到 500 之间"。

4.4 查询对照

想看什么PromQL
QPSsum(rate(http_server_requests_seconds_count[1m]))
平均耗时sum(rate(..._sum[5m])) / sum(rate(..._count[5m]))
全局 P99histogram_quantile(0.99, sum by (le) (rate(..._bucket[5m])))
SLO 达标率sum(rate(..._bucket{le="0.3"}[5m])) / sum(rate(..._count[5m]))
单实例 P99（不聚合）...{quantile="0.99"}，只能按 instance 分别看

注意 P99 那条必须带 sum by (le)：先把所有实例、所有 uri、所有 status 的桶加起来，再算分位。少写一个 by (le)，Prometheus 会逐序列算分位，得到的是一堆单实例 P99，不是全局值。

05五个高频误用

  1. 把 P99 做平均。多实例、多机房、按时间的 P99 一律不可平均（3.5 已证）。要全局 P99 只能存桶。
  2. 以为 P99 是"99% 的请求快于此值"。严格说是"第 99 百分位的观测值"；用桶算时还会在桶内线性插值，天然带误差。
  3. 桶边界定得太糙。SLO 是 300ms，桶边界却只有 250 和 500，那你永远只能报一个区间。桶边界就是观测分辨率。
  4. percentiles 与 histogram 同时开。前者每实例一份 HdrHistogram（重），后者每序列几十上百条时间序列（贵）。Prometheus 场景只开 histogram。
  5. 只看 _max 当尾部。_max 是窗口内的单点极值，会被单个异常样本污染；P99 才是稳定的尾部指标。

上线前检查清单

  • 所有告警与 SLO 都建在 _bucket 上，没有一条建在 quantile 上
  • 桶的 maximumExpectedValue 已显式设置（不是默认的 +Infinity）
  • SLO 边界确实出现在 _bucket{le=...} 里（抓一次 /actuator/prometheus 确认）
  • P99 查询带 sum by (le)，且分母用 rate(_count)
  • 算过序列数预算：标签组合数 × (桶数 + 3)

计算分位数的三步（这正是 histogram_quantile 做的事）：

  1. 目标排位 = 分位点 × 总数：P99 → 0.99 × 1000 = 990。
  2. 定位桶：在累计列里找到第一个 ≥ 990 的值，得到桶 (500, 1000]。
  3. 桶内线性插值：500 + (990 − 980) / (1000 − 980) × (1000 − 500) = 750ms。

同理：

  • P50：排位 500，落在 (25, 50]，桶内比例 (500−360)/320 = 0.4375，得 25 + 0.4375×25 ≈ 35.9ms。
  • P95：排位 950，落在 (250, 500]，比例 (950−920)/60 = 0.5，得 250 + 0.5×250 = 375ms。
  • 平均：用各档中点估算 ≈ 81ms；精确值需 _sum / _count。
一个静默的边界情况

如果分位数落在 le="+Inf" 那一档（即最高边界仍然不够高），Prometheus 的 histogram_quantile 会返回 +Inf 或 NaN，面板上表现为一根断线或一个空点。这几乎总是意味着 maximumExpectedValue 设小了——不要以为是查询写错了。
