## 0. 一页结论

先给六条判断，后文逐条给证据。

| # | 结论 | 置信度 |
|---|---|---|
| 1 | 这是一套「**探针主导 + 日志旁路**」的拼装式体系，不是某个统一框架，三条链在存储层互不相连 | 高 |
| 2 | **指标传输**的 owner 是 OTel（OTLP），但**指标语义**的 owner 是 Micrometer——这是两个不同的问题，初稿曾把它们混为一谈 | 高 |
| 3 | 指标源头是 **Micrometer**（`http_server_requests_seconds_count` 的复数 `requests` 是铁证），说明 micrometer 桥或 `OtlpMeterRegistry` 已启用 | 高（据实测反馈） |
| 4 | 一旦代码里出现 `MeterRegistry` / `@Timed` 却没有开桥，这些数据**默认出不去**，这是本体系最大的隐性地雷 | 高 |
| 5 | Trace 是纯 OTel 一套：W3C `traceparent` 传播 + `parentbased_always_on` 采样 + OTLP/gRPC 导出 | 高 |
| 6 | 三条链唯一的接缝是 **MDC 里的 `trace_id` / `span_id` 两个字符串**，且这个接缝是「静默失效」型 | 高 |

**2026-11-01 修订**：初稿据「指标走 gRPC」推断指标的语义也归 OTel semconv（`http.server.request.duration`）。后续确认真实指标名为 `http_server_requests_seconds_count`——复数 `requests` 是 Micrometer 的指纹，说明桥接已启用。3.1 节据此改写，反例分析见 3.1.1。

一句话概括形态：

> **一个 JVM 里跑着两条互不知情的遥测管道。** 一条由 agent 承载——链路是 agent 自己产生的，指标是 Micrometer 埋的、由 agent 的 SDK 送出去的；另一条是应用私有的（日志，落盘后由 filebeat 拖走进 Kafka）。它们唯一的交集，是 agent 往 MDC 里写了两个键、Logback 把它打进文件。

如果上述任何一条与你的实际配置不符，请直接跳到 [第 8 节核对清单](#8-核对清单可执行)，那里给的是可执行命令，不用猜。

## 1. 形态判定

### 1.1 三条管道的责任边界

| 维度 | 指标 | 链路 | 日志 |
|---|---|---|---|
| 埋点入口 | 字节码注入（无代码） | 字节码注入（无代码） | SLF4J API（业务代码里手写） |
| 运行时实现 | OTel SDK `SdkMeterProvider` | OTel SDK `SdkTracerProvider` | Logback `LoggerContext` |
| 谁在进程内持有状态 | agent 内的 SDK | agent 内的 SDK | Logback（MDC 是 ThreadLocal） |
| 出口协议 | OTLP/**gRPC** :4317 | OTLP/**gRPC** :4317 | **文件** → filebeat → Kafka |
| 是否经过 OTel Collector | 是 | 是 | **否** |
| 最终后端 | Prometheus / Mimir / VictoriaMetrics | Tempo / Jaeger | 消费端自行落库（ES / Loki / ClickHouse） |
| 与另两条链的关系 | 无 | 无 | **只通过 MDC 关联** |

这张表是全篇的骨架：**只有前两列共用一个 exporter 通道，第三列从采集到存储都是另一条路。**

### 1.2 与「OTel 全家桶」的差别

同样的技术栈可以有三条不同的落地方式，差别不在组件，在**信号走哪条路**：

```
方式 1（全家桶）：metrics + traces + logs ──OTLP/gRPC──▶ Collector ──▶ 三个后端
方式 2（本方案）：metrics + traces ─────────OTLP/gRPC──▶ Collector ──▶ 两个后端
                  logs ──文件──▶ filebeat ──▶ Kafka ──▶ 消费端 ──▶ 日志后端
方式 3（自建）：  metrics ──Micrometer──▶ Prometheus 拉取
                  traces  ──OTel SDK──▶ 后端      logs ──filebeat──▶ Kafka
```

你的是**方式 2**。它与方式 1 的唯一实质差异是：**日志没有 `Resource`、没有 OTLP 的批次语义、也没有 Collector 侧的统一处理**（脱敏、采样、enrichment 全缺失），换来的是 Kafka 的解耦与削峰。

### 1.3 这套形态的强项与代价

强项：

- **基础设施零侵入**：加 `-javaagent` 就有链路、JVM 指标、HTTP/JDBC 指标，不改业务代码。但**业务语义指标仍需手工埋点**；且你的项目走的是 Micrometer 桥（见 3.1.1），并非完全零代码。
- **升级即能力**：换 agent 版本就获得新插桩，不需要改 pom。
- **日志链路与业务解耦**：Kafka 挡在前面，日志后端挂了不影响业务，还能被多个下游（审计、风控、离线）复用同一份数据。

代价（后面第 7 节展开）：

- **三条链的时钟、采样、生命周期都不一致**，联合分析要靠人拼。
- **指标的可编程性几乎为零**：agent 只埋它认识的框架，业务语义指标（比如「支付成功率」）没人埋。
- **日志的关联是字符串级的**，不是结构化的，一次 join 就是一次全文检索。

图里有两个容易被忽略的细节，值得单独指出：

1. **agent 既生产 telemetry，又反过来改应用的日志框架**。图中那条从右向左的箭头（写 `trace_id` 进 MDC）是整套体系的**唯一缝合线**。它由 agent 的 `logback-appender` 类插桩完成，不经过你的代码。

## 3. 指标链：owner 到底是谁

这是你问题里最关键的一处，因为**答案不在代码里，在协议里**。

### 3.1 决定性证据：gRPC 只能锁定传输层，锁不住语义

先说一个硬事实：

> **Micrometer 生态里，没有任何一条指标路径可以走 gRPC。**

依据（在 `Micrometer&OpenTelemetry.md` 4.2 节已给过源码级确认）：

- Spring Boot 的 `management.otlp.metrics.export.*` 装配的是 `OtlpMeterRegistry`。
- `OtlpMeterRegistry` 内部用的是 `OtlpHttpMetricsSender`，而它包着 `HttpUrlConnectionSender`——**只支持 HTTP + protobuf（4318），没有 gRPC 实现**。
- 22 个 registry 里，除此之外没有任何一个说 OTLP 协议的。

再看 OTLP 的端口约定：

| 端口 | 协议 | 谁在用 |
|---|---|---|
| 4317 | gRPC | **OTel SDK 的 `OtlpGrpc*Exporter`**（agent 内置、或应用自建 SDK） |
| 4318 | HTTP/protobuf | Micrometer 的 `OtlpMeterRegistry`、`OtlpTracingRegistry` 之类 |

所以推理链是闭合的：

```
指标走 4317/gRPC
  ⇒ 发送方必须是 OtlpGrpcMetricExporter
  ⇒ 上游必须是 OTel SDK 的 SdkMeterProvider
  ⇒ Micrometer 的 OtlpMeterRegistry 不可能是这条链的发送端
  ⇒ 发送端只能是 javaagent 内置的 SDK（或应用内自建 SDK）
```

**这个推理锁定的是「传输」，锁不住「语义」。** 指标的**名字、单位、标签**从哪来，取决于 `SdkMeterProvider` 的上游挂的是谁：是 agent 自己的 instrumentation，还是 `micrometer-1.5` 桥。初稿在这里跳了一步——由「发送端是 OTel SDK」直接推出「指标名是 semconv」，这是错的。反例见下。

#### 3.1.1 反例：`http_server_requests_seconds_count` 说明了什么

##### 两个指纹

| 特征 | `http_server_requests_seconds_count` | `http_server_request_duration_seconds_count` |
|---|---|---|
| 名词 | **复数** `requests` | 单数 `request` |
| 表意 | 只有单位 `_seconds`，无 `duration` | 名字里带 `duration` |
| 归属 | Micrometer：`http.server.requests` | semconv：`http.server.request.duration` |

**单复数是最快的判别器。** Micrometer 的命名规则是 `{domain}.{plural}`（`http.server.requests`、`jvm.memory.used` 用复数例外见下），OTel semconv 是 `{namespace}.{object}.{metric}`，对象名用单数。

所以：**你看到复数，就说明埋点入口是 Micrometer。**

##### 但这个名字不能告诉你数据怎么走的

有两条完全不同的路径，最终在 Prometheus 里产出**一模一样**的名字：

```
路径 A：应用直出
  Meter.Id  http.server.requests   (Timer, baseUnit=seconds)
     │  PrometheusMeterRegistry 在「注册时」转换：
     │    . → _   ，Timer 类型补 _seconds，即 http_server_requests_seconds
     │  序列化 Histogram 时补类型后缀 _count / _sum / _bucket / _max
     ▼
  GET /actuator/prometheus  →  http_server_requests_seconds_count

路径 B：经 OTLP
  Meter.Id  http.server.requests   (Timer, baseUnit=seconds)
     │  OtlpMeterRegistry 用 NamingConvention.dot（identity），名字原样保留，
     │  单位单独放 unit 字段：name="http.server.requests", unit="s"
     │  → OtlpGrpcMetricExporter 或 OtlpHttpMetricsSender → Collector
     │  Collector 的 prometheus exporter 再做一次：
     │    . → _ ，unit 存在则补 _seconds，Histogram 补 _count / _sum / _bucket
     ▼
  Collector 的 /metrics  →  http_server_requests_seconds_count
```

两条路径的产物名字相同，是因为**两次变形恰好等价**：Micrometer 的 `PrometheusNamingConvention` 与 OTel 的 prometheus exporter 用的是同一套规则（点转下划线、单位后缀、类型后缀）。这跟 `Micrometer&OpenTelemetry.md` 5.2 节讲的「第 ③ 步只做字符替换，不改语义」是同一件事。

##### 三个判别器

| 判别点 | 路径 A：应用直出 | 路径 B：经 OTLP → Collector |
|---|---|---|
| 你在哪看到这个名字 | 应用自己的 `/actuator/prometheus` | Collector 的 prometheus exporter 端口（常见 `:8889`） |
| `_max` 序列 | 通常有 `..._seconds_max`（Micrometer 的 `publishMaxGaugeForHistograms` 默认 true） | 通常没有（Prometheus histogram 无 max 语义，导出时被丢） |
| `service_name` 标签 | 没有，只有 `application` 之类 common tag | 有（需 Collector 开 `resource_to_telemetry_conversion.enabled=true`） |
| `otel_scope_name` 之类 | 无 | 可能带（取决于 exporter 版本与 `send_metadata` 配置） |
| 抓取对象 | Prometheus 直抓应用实例 | Prometheus 抓 Collector |

**终极判别法**：看 Collector 收到的原始数据（临时挂一个 `debug` exporter）。那里能看到未经末端转换的真名——

- 若是 `http.server.requests`（点分），源头是 Micrometer，走的是桥（路径 B）；
- 若是 `http.server.request.duration`（点分、单数、带 duration），源头是 agent 的 instrumentation（纯自动埋点）。

##### 对本文其余部分的影响

这个修正会连带影响四处，读后文时请按修正后的口径理解：

1. **3.2 层 3 从「默认不通」改为「已通」**——你的项目显然开了桥，或用了 `OtlpMeterRegistry`。
2. **3.3 的注解表**：`@Timed` / `@Counted` / `@Observed` 在你的项目里是**有效**的埋点方式，不再是「空转」。
3. **3.4 的指标清单**：实际看到的名字是 Micrometer 词表（`jvm.memory.used`、`http.server.requests`、`hikaricp.connections.active`），不是 semconv 词表（`jvm.memory.used` 恰好同名，但 HTTP 与 DB 类差别很大）。
4. **5.3.1 的 Resource 讨论仍然成立**——不管名字来自谁，`service.name` 这类身份仍由 OTel 的 `Resource` 承载，桥接层不会替代它。

### 3.2 埋点 API 的三层答案

「埋点 API 是什么」这个问题，取决于你问的是哪一层。按概率从高到低排：

**层 1：实际在用——没有 API（全自动）**

如果业务代码里搜不到任何 `Meter` 相关引用，那么指标 100% 来自 agent 的 instrumentation，业务侧**零埋点代码**：

```bash
# 一行命令判定你到底在哪一层
grep -rn "MeterRegistry\|getMeter(\|@Timed\|@Counted\|@Observed\|@WithSpan" src/main/java | wc -l
```

返回 0 → 层 1；只出现 `@WithSpan` → 层 2；出现 `MeterRegistry`/`@Timed` → 层 3（且很可能有这个坑，见 3.4）。

**层 2：如果手动埋——OTel Metrics API**

```java
Meter meter = GlobalOpenTelemetry.getMeter("com.example.order");

LongCounter orders = meter.counterBuilder("order.created")
        .setDescription("下单成功数")
        .setUnit("{order}")          // UCUM 注释单位，不带花括号会被当无量纲
        .build();

orders.add(1, Attributes.of(
        AttributeKey.stringKey("order.channel"), "app",
        AttributeKey.stringKey("order.status"), "success"));
```

要点：

- `GlobalOpenTelemetry` 是**全局单例**，agent 启动时已经把它指向自己构建的 SDK。你不需要（也不应该）再 `OpenTelemetrySdk.builder()` 一次——那样会拿到第二个 SDK，数据要么双发，要么被 agent 覆盖后静默丢失。
- 只依赖 `opentelemetry-api`（compile scope），实现由 agent 提供。**这是 javaagent 模式最大的好处**：API 与实现解耦，换后端不动代码。

**层 3：团队习惯 Micrometer——`MeterRegistry`（你的项目在这一层）**

```java
// 你面板上看到的指标就来自这里：名字是 http.server.requests，不是 semconv
registry.timer("order.process", "channel", "app").record(Duration.ofMillis(120));

// HTTP 那一条甚至不用写：Spring Boot 的 Observation 自动注册 http.server.requests
```

判定你在这一层的依据是 3.1.1：`http_server_requests_seconds_count` 里的复数 `requests` 只可能来自 Micrometer。说明下面两条至少成立一条：

- agent 的 `micrometer-1.5` 插桩被显式打开（`-Dotel.instrumentation.micrometer.enabled=true`）——它在该版本里是 `disabled_by_default: true`，必须显式开；
- 或应用用了 `OtlpMeterRegistry`（`management.otlp.metrics.export.*`），走 4318/HTTP 而非 gRPC。

**没开桥会怎样**（验证时仍有用）：`MeterRegistry` 保持 `SimpleMeterRegistry`，数据只活在堆里，`/actuator/metrics` 看得到、后端一条没有。

接通之后发生的事：

- 埋点 API 仍然是 Micrometer 的（`MeterRegistry`、`@Timed`、`@Observed`）；
- **名字不做转换**：`OtlpMeterRegistry` 用 `NamingConvention.dot`，注册名保持 `http.server.requests`，单位单独放在 metric 的 `unit` 字段——到 Collector 的 prometheus exporter 才变成 `http_server_requests_seconds`；
- 数据落到 OTel SDK，走 OTLP 出去；
- **单向**：Micrometer → OTel 可以，反向读回来不行；
- **有损**：Micrometer 的 tag 只有字符串，OTel 的数值型属性（如 `http.response.status_code` 是 int）在桥上只能以字符串落地。

#### 3.2.1 怎么判断是「agent 桥」还是「OtlpMeterRegistry」

两者都能让 `http.server.requests` 出现在 OTLP 里，但机制、协议、配置完全不同。四层判别，从最省事的开始。

**第 1 层：看依赖**

```bash
mvn -q dependency:tree -Dincludes='io.micrometer:micrometer-registry-otlp'
unzip -l target/app.jar | grep -i "micrometer-registry-otlp"
```

Spring Boot 默认**不带** `micrometer-registry-otlp`。没有它就不可能有 `OtlpMeterRegistry`，只剩 agent 桥一种可能。

**第 2 层：看开关**

| 开关 | 属于 | 默认 |
|---|---|---|
| `-Dotel.instrumentation.micrometer.enabled=true` | agent 桥 | false（`disabled_by_default: true`） |
| `management.otlp.metrics.export.enabled` | `OtlpMeterRegistry` | 类路径有 otlp registry 时默认 true |
| `management.otlp.metrics.export.url` | `OtlpMeterRegistry` | 默认 `http://localhost:4318/v1/metrics` |

第三个值得盯住：`OtlpMeterRegistry` 的默认地址就落在 **4318**，这个默认值本身就是最硬的指纹。

**第 3 层：看运行时 Bean 类型（最直接）**

```java
@Bean
ApplicationRunner showRegistry(MeterRegistry registry) {
    return args -> log.info("MeterRegistry => {}", registry.getClass().getName());
}
```

| 类名 | 结论 |
|---|---|
| `io.opentelemetry.instrumentation.micrometer.v1_5.OpenTelemetryMeterRegistry` | agent 桥 |
| `io.micrometer.registry.otlp.OtlpMeterRegistry` | Boot 自带 |
| `io.micrometer.prometheusmetrics.PrometheusMeterRegistry` | 应用直出 Prometheus，与 OTLP 无关 |

也可以走 `/actuator/beans`，但输出很大，grep `MeterRegistry` 更快。

**第 4 层：看网络（终极）**

```bash
ss -tnp | grep -E ':(4317|4318)'                       # 应用侧
curl -s localhost:8888/metrics | grep otelcol_receiver_accepted_metric_points   # Collector 侧
```

判读：

- 4318 有 ESTABLISHED 且 `metric_points > 0` → `OtlpMeterRegistry`；
- 只有 4317 有连接且 `metric_points > 0` → agent 桥。

必须结合 `metric_points` 判，因为 trace 也在 4317 上，只看端口会误判成「指标走 gRPC」——这正是初稿翻车的同一个坑。

**两个辅助信号**

1. **`/actuator/prometheus` 还能不能用**：agent 桥若接管了全局 registry，这个端点通常失效或返回空（它绑的是 `PrometheusMeterRegistry` 类型）。
2. **导出节奏**：`OtlpMeterRegistry` 是 `StepMeterRegistry`，step 整分对齐（00:00、00:01）；agent 的 `PeriodicMetricReader` 从启动时刻起算，不对齐。看数据点时间戳是否卡在整分。

**并存会怎样**

两者同时生效时，同一指标会被两条链各发一份（4317 + 4318），Collector 侧看到重复；或者 `MeterRegistry` 被桥替换后，`OtlpMeterRegistry` 变成孤儿 bean，白占内存不发数据。所以「两套都配」不是保险，是隐患。

### 3.3 注解全景

Java 世界里「观测注解」有四套，分属两个体系，**能不能被 agent 认，完全取决于归属**：

| 注解 | 所属体系 | 需要什么 | agent 是否认 | 产物 |
|---|---|---|---|---|
| `@WithSpan` | OTel | `opentelemetry-instrumentation-annotations`（compileOnly 即可）+ agent 的 `annotations` 插桩 | **认（默认开）** | Span |
| `@SpanAttribute` | OTel | 同上 | 认 | Span 属性 |
| `@Timed` | Micrometer | `micrometer-core` + `TimedAspect` bean | 认（3.2 层 3 的开关已开） | Timer（Micrometer） |
| `@Counted` | Micrometer | `micrometer-core` + `CountedAspect` bean | 同上 | Counter（Micrometer） |
| `@Observed` | Micrometer Observation | `micrometer-observation` + `ObservedAspect` bean | 同上 | Observation（可派生 span + timer） |

三件事必须说清楚：

1. **`@Timed` 靠 AOP，需要显式声明 `TimedAspect` bean**（Spring Boot 不自动注册）。没开桥时它只在 `SimpleMeterRegistry` 里记账、`/actuator/metrics` 看得到而后端起不到；桥一旦打开（你的情况），这条路径就通了。
2. **`@Observed` 是 Micrometer 系里最"现代"的一个**，它同时能产出 span 和 timer（通过 `ObservationRegistry` 的 handler）。但它的 span 走的是 Micrometer Tracing 的桥，与 agent 的 span 是**两套**，混用会出现同一方法两个 span 甚至两条 trace。
3. **agent 自身不提供任何注解**。`@WithSpan` 的类在 `opentelemetry-instrumentation-annotations` 里，agent 只是"认得"它。

### 3.4 默认能拿到哪些指标（两套词表对照）

agent 的指标覆盖是「框架认识什么就有什么」。但**你看到的名字取决于桥有没有开**，所以给两列对照——左列是你在 Prometheus 面板上实际会看到的名字（Micrometer 词表），右列是同一件事在 semconv 里的写法：

| 类别 | 你在面板上看到的（Micrometer → Prometheus） | semconv 对应 | 说明 |
|---|---|---|---|
| HTTP 服务端 | `http_server_requests_seconds_count` | `http.server.request.duration` | 差别最大的一类：复数 `requests`、无 `duration` |
| HTTP 客户端 | `http_client_requests_seconds_count` | `http.client.request.duration` | RestClient / Feign 自动产生 |
| JVM 内存 | `jvm_memory_used_bytes` | `jvm.memory.used` | 语义同名，但 Prometheus 里多了 `_bytes` |
| JVM GC | `jvm_gc_pause_seconds_count` | `jvm.gc.duration` | |
| JVM 线程 | `jvm_threads_live_threads` | `jvm.thread.count` | 单位 `threads` 被写进名字 |
| 进程 | `process_cpu_usage` / `system_cpu_usage` | `process.cpu.utilization` | |
| 连接池 | `hikaricp_connections_active` | `db.client.connection.count`（按状态分） | 需注册 Hikari 的 binder 才有 |
| 执行器 | `executor_active` / `executor_queued` | 无直接对应 | Micrometer 独有 |

三条判断：

1. **JVM 类两边长得像**（`jvm.memory.used` 恰好同名），最容易让人误判「我们用的就是 semconv」；**HTTP 与 DB 类差别最大**，一眼能分。
2. **凡是 Timer 类型，Prometheus 名里必有 `_seconds`**；凡是 Size 类型，必有 `_bytes`。这是 `PrometheusNamingConvention` 的补齐规则，不是 semconv 的 `_duration` 表意惯例。
3. 如果面板上**同时**出现 `http_server_requests_seconds_count` 与 `http_server_request_duration_seconds_count`，说明两套埋点并存（Micrometer 一套 + agent 的 servlet instrumentation 一套），QPS 会翻倍。这是必须排查的重复采集——桥开了不等于 agent 的 instrumentation 关了。

**关键判断**：这些指标的共同点是「**基础设施指标**」。它们能回答「服务是不是慢了」，回答不了「支付成功率是多少」「哪个渠道的下单量掉了」。后者必须手工埋点——而按 3.2 的分析，你现在的埋点通道是**不通的**（层 3 未开）。这是这套体系最实际的能力缺口。

### 3.5 指标链上的六个断点

按出现频率排序：

1. **服务名没配** → 所有服务在 Prometheus 里都叫 `unknown_service:java`，`service.name` 维度完全失效。`otel.service.name` 没配时，agent 回退到 `unknown_service:java`。
2. **`@Timed` / `MeterRegistry` 空转**（仅在未开桥时）→ 本地有数、后端无影；桥开了就不会出现，判别方法见 3.1.1。
3. **两套埋点并存、QPS 翻倍** → 桥开了但 agent 的 servlet instrumentation 也开着，`http_server_requests_*` 与 `http_server_request_duration_*` 各记一份。见 3.4 第 3 条。
4. **端口/协议错配** → `otel.exporter.otlp.endpoint` 写成 `:4318` 但 `protocol` 仍是默认的 `grpc`（或反之），表现为启动不报错、指标全丢、日志里反复 connection reset。
5. **`Resource` 与 tag 混用** → 把 `service.name` 当 commonTag/tag 打进每条序列，基数暴涨、且与 OTLP 的 Resource 语义冲突。
6. **导出间隔与抓取间隔不同步** → agent 默认 60s 推一次（`otel.metric.export.interval`），Prometheus 若 15s 抓一次，会看到 4 个重复点后跳一下，`rate()` 出现锯齿。

## 4. Trace 链：纯 OTel 一套

### 4.1 谁产生 span

**全部由 agent 的 Instrumentation 在字节码层产生**，业务代码里看不到任何 `Tracer`：

| 位置 | 插桩 | span 类型 | 关键属性 |
|---|---|---|---|
| Tomcat 收到请求 | `tomcat` / `servlet` | SERVER | `http.request.method`、`url.path`、`http.response.status_code` |
| RestClient / Feign 发出请求 | `http-client` / `spring-web` | CLIENT | `server.address`、`url.full` |
| JdbcTemplate 执行 | `jdbc` | CLIENT | `db.system`、`db.statement`（默认可能被截断/关闭） |
| Kafka 生产/消费 | `kafka-clients` | PRODUCER / CONSUMER | `messaging.*` |

**为什么业务代码不需要 `@WithSpan`**：agent 已经在框架边界打了 span，业务方法内部的 span 对「定位哪个下游慢」帮助有限。真正需要 `@WithSpan` 的场景是：一个方法内部有多个可独立计时的阶段（比如「校验→扣减→落单」），且你想在 trace 上看到它们的分段耗时。

### 4.2 传播：W3C，不是 B3

默认 `otel.propagators=tracecontext,baggage`，即 `traceparent` / `tracestate` 两个头。

```
traceparent: 00-6acba46119d0c678b5d37f4cf4f3d35f-b5d37f4cf4f3d35f-01
             │  │                                │                │
             │  │                                │                └─ flags：01 = sampled
             │  │                                └─ parent-id（16 hex）
             │  └─ trace-id（32 hex）
             └─ version
```

三个必须知道的点：

1. **跨进程只有 trace-id 一致，span-id 各进程不同**。so 你在两个服务的日志里看到同一个 `trace_id`、两个不同 `span_id`，这是**正常**的，不是 bug。
2. **改传播格式会断链**。如果上游是 Brave（B3）或 Dubbo（自定义 attachment），必须显式配 `otel.propagators=tracecontext,b3` 之类的组合，否则下游收到的是新 trace（`trace_id` 变了，链路断成两截）。这是异构系统接入时第一号事故。
3. **异步边界会丢上下文**。Kafka 生产消费靠 `kafka-clients` 插桩自动带上 `traceparent` 到消息头；但**自建线程池、`CompletableFuture`、虚拟线程**不会自动继承——agent 的 `executor` 插桩能覆盖一部分（`ThreadPoolExecutor` 的 `execute`/`submit`），虚拟线程的 `Thread.ofVirtual().start()` 覆盖不全。丢上下文的症状是：日志里 `span_id` 为空、下游服务开了新的 trace。

### 4.3 采样：`parentbased_always_on`

agent 默认 `otel.traces.sampler=parentbased_always_on`：

- 根 span：总是采样（100%）。
- 子 span：跟随父决定（父采样则子采样）。

含义：**默认状态下你不丢任何 trace**。这在低流量时没问题，高流量时会先打爆 Collector 再打爆存储，而且 `parentbased_always_on` 的「一致性」保证了链路完整（不会出现半条链）。

如果要降采样，正确的做法是 **Collector 侧 tail sampling**（按 `http.status_code=5xx` 或 `duration > 1s` 保样本），而不是客户端 head sampling——因为 head sampling 在请求开始时就要决定，那时你还不知道它会不会报错。客户端只在极端流量下用 `parentbased_traceidratio` 兜底。

### 4.4 `Resource`：最容易漏、最贵的一行配置

Trace 和后端所有查询都靠 `Resource` 区分来源。最少要有四项：

```bash
OTEL_SERVICE_NAME=order-svc
OTEL_RESOURCE_ATTRIBUTES=service.version=1.4.2,deployment.environment=prod,\
service.namespace=commerce,k8s.pod.name=$(POD_NAME)
```

漏了 `OTEL_SERVICE_NAME` 的后果不是报错，是**所有服务在 Tempo 里叫 `unknown_service:java`**，然后你要靠 `service.instance.id`（随机 UUID）去猜哪个是哪个。

### 4.5 不能与 Micrometer Tracing 并存

如果项目里同时有 `micrometer-tracing-bridge-otel` + `OtlpSpanExporter`（也就是「既加了 agent，又留着 starter」），会发生：

- 两套代码都想设置全局 `OpenTelemetry` 实例；
- agent 先启动、先占位，应用侧的自建 SDK 要么拿到 agent 的实例（这时 exporter 配置被忽略），要么产生第二个实例（这时 span 双发，后端看到重复 trace）；
- 表现是「一条请求两条 trace」或「应用配置的 endpoint 完全无效」。

判定方法：看启动日志里有没有 `GlobalOpenTelemetry` 相关的 warning，或数一下后端同一条请求的 trace 数量。**agent 在场时，应用侧所有 tracing 的 starter 与 exporter 配置都应该移除。**

## 5. 日志链：SLF4J / Logback + filebeat → Kafka

### 5.1 SLF4J 的角色：只有一个门面

SLF4J 在观测体系里不产生任何 telemetry，它只做一件事：把 `log.info()` 转成对底层实现（Logback）的调用。**它不参与 trace，也不参与指标**。

真正的价值在于：因为门面存在，你才能在不改代码的情况下换实现（Logback ↔ Log4j2），而 agent 的日志插桩对两者都有对应模块（`logback-appender` / `log4j-appender`）。**这也是为什么 `Self4j.md` 那类文档值得单独看——门面选错，后面所有插桩都要换。**

### 5.2 Logback 三件套在观测中的真实分工

你提到的三个组件，在观测体系里扮演的是**三种完全不同的角色**，很多人把它们混为一谈：

| 组件 | 执行时机 | 真实职责 | 是否参与「关联」 |
|---|---|---|---|
| **MDC** | 由 agent 写入，随线程传播 | **承载 trace 上下文**（`trace_id`/`span_id`），是唯一的关联载体 | **是，唯一** |
| **Marker** | 由业务代码附加在单条日志上 | 语义分类（`SECURITY`/`AUDIT`/`CONFIDENTIAL`），驱动**路由**与**阻断** | 否 |
| **TurboFilter** | 在 logger 级别判断**之前**，每条日志都过 | 全局门禁：按 Marker/MDC/线程/频率做 ACCEPT/DENY/NEUTRAL | 否，但能保护 MDC 不被污染 |

三者串起来是一条固定的流水线：

```
log.info(marker, "msg")
   │
   ├─▶ TurboFilter 链（MarkerFilter → DynamicThresholdFilter → 自定义限流）
   │      任一个返回 DENY 就终止，事件根本不会被创建
   │
   ├─▶ Logger 级别判断（root/logger 的 effective level）
   │
   ├─▶ 创建 LoggingEvent —— 此刻快照 MDC（trace_id/span_id 被固化进事件）
   │
   └─▶ Appender（Console / RollingFile / 带 EvaluatorFilter 的审计文件）
           EvaluatorFilter + OnMarkerEvaluator 按 Marker 决定 ACCEPT/DENY
```

两个由这个顺序导出的结论：

1. **TurboFilter 里读得到 MDC**（它是 ThreadLocal，调用线程上还在），所以 `DynamicThresholdFilter` 能按 `MDC{debugOn}` 动态调级——这是「线上临时开 DEBUG」的标准做法，比改配置重启安全。
2. **MDC 在事件创建时就被快照进 `LoggingEvent`**，所以 `AsyncAppender` 里的 `%X{}` 仍然能取到值。真正丢 MDC 的是**自己 new Thread / 线程池 / 虚拟线程**——那里没有 ThreadLocal 继承，除非手动 `MDC.getCopyOfContextMap()` + `setContextMap()`。

### 5.3 MDC：唯一的接缝，也是静默失效点

agent 通过日志框架插桩往 MDC 写 trace 上下文。**这里有个非常具体的坑：键名。**

| 来源 | MDC 键名 |
|---|---|
| OTel javaagent（`logback-appender` 插桩） | `trace_id`、`span_id`、`trace_flags` |
| Micrometer Tracing（Brave / OTel bridge） | `traceId`、`spanId` |
| 自研 filter 手工塞 | 随心 |

**两套命名不通用**。如果你的 `logback-spring.xml` 里写的是 `%X{traceId}`，而实际是 agent 注入，那这一格永远是空的——而且**不报错、不告警、日志照常输出**。这就是「静默失效」：体系看起来在跑，关联能力是 0。

同理，如果业务代码里 `MDC.put("traceId", ...)` 手工设置，而 agent 写的是 `trace_id`，会出现**两个键并存、一个空一个满**的奇观。

核对方法见 8 节，一行 `grep` 就能确认。

### 5.3.1 Resource：唯一能回答「我是谁」的模型

后面 5.4 节会说到「日志没有 Resource」，但这句话在没解释 Resource 之前是空的。先把模型立起来。

#### 三层骨架，三种信号共用

OpenTelemetry 对 metrics / traces / logs 用**同一套**数据分层：

```
Resource                    谁产生的？进程级、不可变
  └ InstrumentationScope    用哪个库产生的？包名 + 版本
      └ 记录                 这次发生了什么？
         ├─ Span            （traces）
         ├─ DataPoint       （metrics）
         └─ LogRecord       （logs）
```

这不是三个独立设计的巧合，而是 OTel 的核心抽象：**先声明生产者身份，再挂载测量结果**。所以三种信号在后端可以用同一套维度过滤与跳转——前提是三者都带 Resource。

#### Resource 与 attribute 的分工

一句话：

> **Resource 描述「谁在测」，attribute 描述「这次测到了什么」。**

| | Resource | attribute（span / metric point / log record 上的） |
|---|---|---|
| 回答 | 哪个服务、哪个版本、哪个环境、哪台机器 | 这次请求的方法、状态码、订单号 |
| 生命周期 | 进程级，启动时固定 | 逐条记录不同 |
| 数量级 | 十几个键 | 每条几个到几十个 |
| 传输位置 | 批次外层，只出现一次 | 每条记录内部 |
| 基数风险 | 低（受部署单元数量约束） | 高（受业务维度约束） |

判断一个键该放哪：**换个请求它不变，就是 Resource；逐请求变化，就是 attribute。**

放错的两种代价：`service.name` 放错到 attribute，每条序列多一个常量标签，存储放大且无查询价值；`order.id` 放错到 Resource，Resource 无限膨胀，Collector 会把每一条都当成新 Resource 建流。

#### 标准键表

| 键 | 例子 | 缺失后果 |
|---|---|---|
| `service.name` | `order-svc` | 后端全部落到 `unknown_service:java`，第一检索维度失效 |
| `service.namespace` | `commerce` | 多团队同名服务无法区分 |
| `service.version` | `1.4.2` | 无法回答「是不是只有新版本有问题」 |
| `deployment.environment` | `prod` / `gray` | 环境混在一张图上 |
| `service.instance.id` | uuid | 无法区分同服务多实例 |
| `host.name` | `node-3` | 无法定位单机故障 |
| `k8s.pod.name` / `k8s.namespace.name` | `order-svc-7d9f-abc` | 容器重建后无法追溯 |
| `telemetry.sdk.*` | `java / opentelemetry / 2.33.0` | 排查 SDK 自身问题 |

最少配四项：`service.name`、`service.version`、`deployment.environment`、`service.namespace`。

#### Resource 在三个后端里变成什么

Resource 是传输层概念，到存储层会被「投影」成各后端自己的维度，这一步有点号被替换的坑：

| 后端 | 投影方式 | 注意 |
|---|---|---|
| Prometheus / Mimir | 需 Collector 开 `resource_to_telemetry_conversion.enabled=true` 才会展开成序列标签，不开则只留 `job` / `instance` | label 名不允许点，`service.name` → `service_name` |
| Tempo | `service.name`（+ `service.namespace`）是 trace 的必填检索维度，也是 service graph 的节点名 | 缺了就没有服务视图 |
| Loki | 默认映射成 stream label，同样下划线化 | stream label 基数要克制，别把 `host.name` 全放进去 |
| Jaeger | `service.name` 直接作为服务下拉框 | 同上 |

**「点号被替换」和 `Micrometer&OpenTelemetry.md` 5.2 节讲的「名字三次变形」是同一条规律**：OTLP 里保留点分，进了 Prometheus 系就变下划线。所以 Grafana 查询里看到的是 `service_name`，不是 `service.name`。

#### 「日志没有 Resource」到底缺了什么

不是缺服务名（你肯定写了），缺的是三件事。

**（1）词表分裂**

`logback-spring.xml` 里大概是 `service` 或 `app`，而 trace/metric 里是 `service.name`。同一条链在 Tempo 里按 `service.name=order-svc` 检索，在 ES/Loki 里按 `service:"order-svc"` 检索。代价不是多敲几个字符，而是**无法自动化跳转**：Grafana 的 trace→logs 联动要求两边 label 名一致，名字对不上就只能人工复制 trace_id 去搜。

**（2）身份靠人工维护**

`service=order-svc` 是写死在 `customFields` 里的常量。镜像被复制成第二个部署（灰度、多活、改名）时，日志里的名字还是旧的。OTel 的 Resource 是运行时注入的（`OTEL_SERVICE_NAME` / `OTEL_RESOURCE_ATTRIBUTES` / Downward API），换部署只改环境变量。filebeat 侧要追平，得靠 `add_kubernetes_metadata` + `add_fields` 在采集端重贴——**贴上去的还是另一套键名**，问题绕回（1）。

**（3）存储放大**

日志本体约 120 字节，`service/env/host/pod` 约 80 字节：

- 单行 200 字节，其中约 40% 是重复身份；
- 10 万条/秒 → 一天约 86 亿条 → 重复部分约 **690 GB/天**（未压缩，按上述字节数估算）；
- 更贵的隐性成本在写入路径：ES 每行做一次字段提取与索引，Loki 每行算一次 stream hash；OTLP 那侧 Collector 解析一次 `resource` 就定了整批的流。

#### 示例对照

OTLP（JSON 形态便于阅读，实际为 protobuf）：

```json
{"resourceLogs":[{
  "resource":{"attributes":[
    {"key":"service.name","value":{"stringValue":"order-svc"}},
    {"key":"service.version","value":{"stringValue":"1.4.2"}},
    {"key":"deployment.environment","value":{"stringValue":"prod"}}]},
  "scopeLogs":[{"scope":{"name":"com.example.order","version":"1.0"},
    "logRecords":[
      {"timeUnixNano":"1761958800123000000","severityNumber":9,"severityText":"INFO",
       "body":{"stringValue":"下单成功"},
       "attributes":[{"key":"trace_id","value":{"stringValue":"abc..."}}]},
      {"...":"还有 511 条，均不重复 resource"}]}]}]}
```

Kafka 里的一条：

```json
{"@timestamp":"2026-11-01T09:00:00.123Z","level":"INFO","message":"下单成功",
 "service":"order-svc","env":"prod","host":"node-3","pod":"order-svc-7d9f-abc",
 "trace_id":"abc...","span_id":"111..."}
```

信息量相同，**结构层级不同**：左边身份在外层一次，右边身份在每行一次。

#### 为什么它是「关联的第一步」

`trace_id` 只能回答「哪一次请求」，回答不了「哪个服务、哪个版本、哪个环境」。而排障时最常问的恰恰是后者：

> 「这个 500 只在 v1.4.2 的 prod 出现」——这是 Resource 的维度。
> 「这一单为什么慢」——这是 trace_id 的维度。

两者缺一不可：**Resource 定位实体，trace_id 定位实例。**

### 5.4 filebeat → Kafka：旁路的五个代价

日志不走 OTLP 而走文件 + filebeat + Kafka，换来解耦，代价是五件事必须自己补：

**代价 1：必须落盘。** filebeat 读文件，所以 `RollingFileAppender` 是硬前提。只配 `ConsoleAppender` 就采不到（容器里走 stdout 的场景另说，那是 Docker/K8s 的日志文件）。

**代价 2：多行日志会被拆碎。** Java 堆栈天然多行。filebeat 必须配：

```yaml
filebeat.inputs:
  - type: filestream
    paths: [/var/log/app/*.log]
    parsers:
      - multiline:
          type: pattern
          pattern: '^\d{4}-\d{2}-\d{2}'
          negate: true
          match: after
          max_lines: 500
```

不配的后果：一条 200 行的异常被切成 200 条 Kafka 消息，消费端再想按 `trace_id` 聚合成一个异常，只能靠时间窗口猜。

**代价 3：事件时间 ≠ 采集时间。** filebeat 有 `scan_frequency`（默认 10s）与 `close_inactive`（默认 5m），日志从产生到进 Kafka 有秒级到分钟级抖动。filebeat 会带 `@timestamp`（事件时间）和 `event.ingested`（采集时间），**消费端必须用前者排序**，否则跨服务的日志顺序会乱。

**代价 4：没有结构化。** 纯文本 pattern 进 Kafka，消费端每读一次就要正则解析一次。正确做法是 Logback 直接输出 JSON（`logstash-logback-encoder` 或 Logback 1.5 内置 encoder），把 `trace_id`、`span_id`、`service`、`level` 提为顶层字段：

```xml
<encoder class="net.logstash.logback.encoder.LogstashEncoder">
  <includeMdcKeyName>trace_id</includeMdcKeyName>
  <includeMdcKeyName>span_id</includeMdcKeyName>
  <customFields>{"service":"order-svc","env":"prod"}</customFields>
</encoder>
```

**代价 5：分区与顺序。** Kafka 的 key 决定分区。日志 topic 若用随机 key，同一条 trace 的日志会散落到不同分区，消费端无法保证顺序。**用 `trace_id` 做 key**，可以让同一条链路的日志落同一分区，天然有序。

### 5.4.1 OTLP 的批次语义

5.4 的五个代价讲的是**工程层面**要自己补的东西（落盘、多行、时间、结构化、分区）。还有两个**模型层面**的缺失不在那五条里：缺 Resource（见 5.3.1）与缺批次语义（本节）。

#### 三层嵌套

OTLP 的 RPC 不是一条数据一个请求，而是：

```
ExportLogsServiceRequest          （或 ExportTraceServiceRequest / ExportMetricsServiceRequest）
└─ resource_logs[]                每个元素 = 一个 Resource + 它底下的一批记录
   └─ scope_logs[]                按产生它的库分组（InstrumentationScope）
      └─ log_records[]            真正的数据
```

三种信号共用这个形状（`resource_spans` / `resource_metrics` / `resource_logs`），只是叶子节点类型不同。

因为进程内只有一个 SDK（一个 Resource），所以一个进程导出的一批数据天然只有一个 `resource_logs` 元素——**「一批 = 一个服务」是结构决定的**。

#### 五条语义

| # | 语义 | OTLP 的具体行为 | filebeat → Kafka 的对应物 |
|---|---|---|---|
| 1 | 共享外层 | Resource 每批一次；接收端解析一次即可给整批打标签 | 无；每行自带全部身份字段 |
| 2 | 缓冲与节奏 | `BatchLogRecordProcessor` 默认 512 条 / 5s / 队列 2048，攒够或超时才发 | Kafka producer 的 `linger.ms` / `batch.size` 是**传输层批**，消费端仍逐条可见 |
| 3 | 失败语义 | gRPC 可重试状态码 + 指数退避；队列满直接丢弃；丢弃数可上报 | 至少一次投递，重试整批，重复靠消费端去重或 `enable.idempotence` |
| 4 | 部分成功 | 响应里 `partial_success.rejected_log_records` 允许只拒一部分 | ack=all 全有或全无 |
| 5 | 编码 | protobuf + gzip，整批压缩，字段名不进 wire | `compression.type`（lz4/zstd），压缩整批字节但保留 JSON 键名 |

第 3 条的默认值决定了「进程被 kill 会丢多少」，值得记牢：

| 参数 | 默认 | 含义 |
|---|---|---|
| `otel.bsp.max.queue.size` | 2048 | 队列满则丢弃，不阻塞业务线程 |
| `otel.bsp.max.export.batch.size` | 512 | 单次请求最多带多少 |
| `otel.bsp.schedule.delay` | 5000ms | 最长等多久 |
| `otel.blrp.*`（日志同款） | 同上 | BatchLogRecordProcessor 的对应参数 |

**这就是「OTLP 的批次是内存缓冲」的含义**：进程被 `kill -9`，队列里最多 2048 条记录连同那 5 秒窗口一起丢掉。要抗这一点，得在 Collector 侧开 `file_storage` 做持久化队列，或者接受「可观测数据允许丢一点」。

#### 公允比较：两种「批」不是一回事

不要因为 OTLP 有批次就认为它全面占优：

| 维度 | OTLP 批次 | Kafka 批次 |
|---|---|---|
| 缓冲位置 | 进程内存 | broker 磁盘 |
| 进程崩溃 | 丢失未发送部分 | 已 ack 的不丢 |
| 可回放 | 不支持（Collector 侧 `file_storage` 可补） | 天然支持，改 offset 即可 |
| 多下游复用 | 一份数据一个用途 | 同一 topic 可被多个消费组消费 |
| 身份语义 | Resource 规范化、批次级 | 无，靠约定 |
| 结构化程度 | `body` / `attributes` 强制分离，属性有类型 | 自由 JSON，键名与类型全凭约定 |
| 机器可比较字段 | `severityNumber` 是枚举（1–24） | `"INFO"` 是字符串，排序过滤要自己映射 |
| 时间精度 | 纳秒（`timeUnixNano`），SDK 打点 | 毫秒/微秒，beat 打点，有采集偏差 |

结论：**Kafka 赢在「不丢、可回放、可复用」，OTLP 赢在「语义规范、跨信号同源」。** 两者不是替代关系。

#### 一个常被误解的点：批次边界 ≠ trace 边界

`BatchSpanProcessor` 按「攒够 512 条或 5 秒」切批，**不按 trace 分组**。所以：

- 一批 span 里通常混着成百上千条不同的 trace；
- 一条 trace 的 span 可能被拆到相邻两批里。

这对 Collector 侧做 tail sampling 有直接影响：`tail_sampling` 要看到一条 trace 的全部 span 才能判断，若同一 trace 的 span 被负载均衡到不同 Collector 实例，就会各自判断、得出矛盾结论。解法是在 Collector 前面加 `loadbalancing` exporter 并设 `routing_key: traceID`，保证同一 trace 落到同一实例。

#### 想补的话，两条路

**路线 A（治本）：日志双发。** Logback 同时挂 OTel appender 与文件 appender：

```xml
<appender name="OTEL" class="io.opentelemetry.instrumentation.logback.appender.v1_0.OpenTelemetryAppender"/>
<appender name="FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
  <!-- 留给 filebeat，供审计/合规/离线 -->
</appender>

<root level="INFO">
  <appender-ref ref="OTEL"/>
  <appender-ref ref="FILE"/>
</root>
```

OTel appender 里的 `LoggerProvider` 与 tracer/meter 共享同一个 Resource 实例，所以三信号在后端天然同源，trace→logs 一跳直达；审计日志继续走 Kafka。这就是第 9 节建议 9 的落地形态。

**路线 B（治标）：采集端模拟 Resource。**

```yaml
processors:
  - add_kubernetes_metadata: ~
  - add_fields:
      target: resource
      fields:
        service.name: order-svc
        deployment.environment: prod
```

能解决词表分裂，解决不了每行重复、缺 severity 枚举、缺 `body` / `attributes` 分离。

### 5.5 还有一个隐藏问题：日志可能被采集了两次

`logback-appender` 插桩除了写 MDC，还有一个能力：**把日志事件转成 OTel LogRecord 导出**。是否发生取决于 `otel.logs.exporter`（agent 的默认值通常不是 `none`）。

如果它确实开着，而你的 Collector 只配了 traces + metrics 两个 pipeline，那么：

- Collector 收到一类没有 pipeline 的信号 → 丢弃 / 报错；
- 或者你以为日志只走 filebeat，实际 OTLP 里也有一份（重复存储、重复计费）。

**这一条必须核对**：要么显式 `-Dotel.logs.exporter=none`，要么在 Collector 里补一条 logs pipeline 把它接住。见 8 节。

## 6. 一条请求在三处的样子

以 `order-svc` → `stock-svc` 一次调用为例，三个信号的落点完全不同：

| 环节 | 指标（gRPC:4317） | 链路（gRPC:4317） | 日志（文件→Kafka） |
|---|---|---|---|
| order 收到请求 | `http_server_request_duration` 计数 +1，tags: method/route/status | 根 span（SERVER）开始 | `[trace_id=abc span_id=111] 收到下单请求` |
| order 调 stock | `http_client_request_duration` +1 | CLIENT span（父=111） | `[abc/222] 调用库存服务` |
| stock 收到请求 | 自己的 `http_server_...` +1 | 新 SERVER span（同一 trace，span_id=333） | `[abc/333] 查询库存` |
| 返回 | — | span 结束，入 BatchSpanProcessor（5s 一批） | 落盘 → filebeat 10s 内拖走 |

三个信号的关键差异：

| 维度 | 指标 | 链路 | 日志 |
|---|---|---|---|
| 时间粒度 | 60s 聚合一次 | 5s 一批 | 实时（但有采集延迟） |
| 是否逐请求保留 | **否**（聚合后无个体） | 是（若采样命中） | 是（全量） |
| 能否回答「这一单为什么慢」 | 不能 | 能（看 span 分解） | 能（看异常与入参） |
| 基数风险 | 高（tag 组合爆炸） | 中（span 数） | 低（但存储贵） |

**这就是必须三者都有、且必须能互跳的原因**：指标告诉你「有事」，链路告诉你「在哪」，日志告诉你「为什么」。而你这套体系里，第三跳只能靠 `trace_id` 字符串人工搜。

## 7. 故障模式清单

按「症状 → 根因 → 判定」组织，前 12 条是这套形态的高发病。

| # | 症状 | 根因 | 快速判定 |
|---|---|---|---|
| 1 | 业务指标在 Grafana 里查不到 | `MeterRegistry`/`@Timed` 埋的点没进 OTel（`micrometer-1.5` 插桩默认关） | 代码里有 `MeterRegistry` 但 4317 出口没有对应 metric 名 |
| 2 | 所有服务名都是 `unknown_service:java` | 没配 `OTEL_SERVICE_NAME` | 看任一 metric 的 `job`/`service_name` 标签 |
| 3 | 日志里 trace 位永远为空 | MDC 键名不匹配（`traceId` vs `trace_id`） | `grep -n "%X{" logback-spring.xml` 对照 agent 注入键 |
| 4 | 一条请求两条 trace | agent + 应用内 tracing starter 并存 | 后端按时间查同一 URL，出现两个 trace_id |
| 5 | 异步/虚拟线程里 span 断开 | 上下文不继承 | 日志里子线程的 `span_id` 为空 |
| 6 | 指标全丢、无报错 | endpoint 端口与 protocol 错配（4317↔gRPC / 4318↔HTTP） | `curl -v telnet` 到 4317 看是否通；看 agent 是否有重连日志 |
| 7 | Kafka 里异常日志被切成 N 条 | filebeat 没配 multiline | 按 `trace_id` 查，异常行数是 1 还是 200 |
| 8 | 日志顺序错乱 | 消费端用了采集时间而非事件时间 | 比对 `@timestamp` 与 `event.ingested` |
| 9 | 同一条日志出现两份 | agent 的 logs exporter 也在发 | Collector 的 logs pipeline 是否收到数据 |
| 10 | 启动日志有 `Failed to inject` / muzzle 警告 | agent 版本与某个库不兼容 | `-Dotel.javaagent.debug=true` 看具体 module |
| 11 | 跨语言/跨框架链路断成两截 | 传播格式不一致（W3C vs B3） | 下游首个 span 的 trace_id 是否与上游一致 |
| 12 | trace 数量与日志数量对不上 | 采样策略不对称（trace 被丢、日志全留） | 对比同一时间窗的 span 数与日志条数 |

## 8. 核对清单（可执行）

不要靠读代码猜，按顺序跑这 8 条，5 分钟能把体系摸清。

**1）确认 agent 与启动参数**

```bash
ps -ef | grep -o '\-javaagent:[^ ]*'
# 同时看环境变量（agent 的绝大多数配置走 OTEL_*）
env | grep -E '^OTEL_|^JAVA_TOOL_OPTIONS'
```

重点看三样：agent 路径与版本、`OTEL_SERVICE_NAME`、`OTEL_EXPORTER_OTLP_PROTOCOL` 与 `ENDPOINT` 的端口是否配对。

**2）确认指标真正的产出者**

```bash
# 业务代码里到底有没有 Micrometer / OTel 埋点
grep -rn "MeterRegistry\|getMeter(\|@Timed\|@Counted\|@Observed" src/main/java | head
# 有没有 tracing 的 starter（有就是双份风险的来源）
grep -rn "micrometer-tracing\|opentelemetry-spring-boot-starter" pom.xml */pom.xml
```

**3）确认 agent 实际产出了什么**

最可靠的方式是让 Collector 把收到的原始数据打出来（临时加一个 `debug` exporter，或在 Collector 的 metrics 自监控里看 `otelcol_receiver_accepted_metric_points`）。看三个东西：metric 名字、`resource.attributes`、以及**有没有 logs 信号**（对应 5.5）。

**4）确认 MDC 键名（最容易错的一步）**

```bash
grep -n "%X{" src/main/resources/logback-spring.xml
# 对照：agent 注入的是 trace_id/span_id，Micrometer Tracing 注入的是 traceId/spanId
```

再补一刀：日志里随便挑一行，看 trace 那一位是不是 `-`（空值），空的就说明键名对不上。

**5）确认插桩开关**

```bash
# 启动加这个参数，会把每个 module 的启用状态与匹配结果打到 stdout
-Dotel.javaagent.debug=true
```

搜 `micrometer` 看是否 enabled；搜 `logback-appender` 看日志插桩状态。

**6）确认日志是否被双采**

```bash
grep -rn "otel.logs.exporter" .    # 没配就是默认值，需要显式确认
# Collector 侧：看 logs pipeline 是否存在、是否收到数据
```

**7）确认 filebeat 的多行与字段**

```bash
filebeat test config -c /etc/filebeat/filebeat.yml
# 检查 multiline、paths、以及是否 output.kafka 的 key 用了 trace_id
```

**8）确认采样**

```bash
env | grep OTEL_TRACES_SAMPLER     # 空 = parentbased_always_on
```

## 9. 改进建议

### P0：让现有两条链真正可用（不改架构）

1. **补齐 `Resource` 四项**：`service.name`、`service.version`、`deployment.environment`、`service.namespace`。这是投入产出比最高的一行配置。
2. **明确指标的 owner，二选一，不要摇摆**：
   - 全 OTel：业务指标用 `GlobalOpenTelemetry.getMeter()`，删掉所有 `MeterRegistry` 用法；
   - 保留 Micrometer：显式 `-Dotel.instrumentation.micrometer.enabled=true`，并接受「tag 只有字符串」的语义损失。
   现在这种「写着 Micrometer、跑着 OTel」的状态，是最坏的组合。
3. **统一 MDC 键名**，并在 CI 里加一条断言（日志里必须有非空的 `trace_id`），把静默失效变成显式失败。
4. **Collector 加 `memory_limiter` + `batch`**，并显式声明只接哪几种信号，避免 5.5 的意外。

### P1：让三条链能互跳

5. **日志改结构化 JSON**，`trace_id`/`span_id` 提为顶层字段，filebeat 不再需要正则。
6. **Kafka 分区键改用 `trace_id`**，同链日志同分区，消费端可有序聚合。
7. **filebeat 配 multiline**，堆栈不再被拆碎。
8. **加 tail sampling**（Collector 侧）：`status_code=5xx` 或 `duration>1s` 全留，其余按 10% 留。这样既能降存储，又不会丢掉真正要看的那批——head sampling 做不到这一点。

### P2：把缺口补上

9. **日志双通道分流**（这是本方案最值得做的一步）：
   - **排障日志**：走 OTLP logs 进 Collector，与 trace 同源、共享 `Resource`，后端可直接按 trace_id 互跳；
   - **审计日志**：保留 filebeat → Kafka，因为审计要求的是不可篡改、长期留存、多下游复用。
   现在把两类日志塞进同一条 Kafka 管道，等于用审计的管道做排障，两边都不满意。
10. **用 Collector 的 `spanmetrics` / `servicegraph` connector** 从 trace 派生 RED 指标。这一步的妙处是：**它绕开了 3.2 的埋点难题**——不需要改代码，只要 trace 有，指标就有，而且天生与 trace 的语义（route、status）一致。
11. **业务语义指标**（支付成功率、渠道转化率）只能手工埋，放到 OTel Metrics API，别绕 Micrometer。
