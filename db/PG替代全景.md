| 级别 | 含义 |
|------|------|
| **默认留在 PG** | 专业组件相对 PG 扩展没有另一套更合适的数据模型。空间数据属于这一档 |

| **从第一天分开** | 数据模型和故障域都不同。缓存和分布式锁属于这一档 |

# 一、总览

## 1.1 一句话定位

**PostgreSQL 是一个带可装载类型、索引访问方法和后台进程的关系型数据库。** 卡片里的十行，多数不是「PG 内核新长出来的中间件」，而是：有人把队列、检索、向量、时序、图、地理这些数据结构做成了扩展，或者做成了贴着 PG 协议的独立进程。它们和业务行共享事务、共享一份备份，这是收益；它们也共享 WAL、共享缓冲、共享检查点和同一个故障域，这是天花板。

所以「一个 PG」在工程上指的是 **一个引擎、一种运维习惯**，不是 **一个集群扛下所有流量**。

## 1.2 设计哲学：扩展为什么进得去，以及为什么进不去

四条就够解释整张卡片。

1. **服务器进程里留了口子。** 自定义类型、操作符类、索引访问方法、后台 worker、逻辑解码输出插件、外部数据包装器，都是 PG 公开的扩展面。PostGIS、pgvector、TimescaleDB、pg_cron、pgmq、ParadeDB 的 `pg_search`、Apache AGE 全部站在这些口子上。没有这个扩展面，卡片无法成立。
2. **事务同库是唯一硬收益。** 下单和入队、正文和向量、资产和几何，放在同一个 `COMMIT` 里，就没有双写和回放延迟。专业组件更强的地方，几乎都是另一套存储和另一套扩缩，不是更完整的 ACID。
3. **存储引擎仍是带 MVCC 的行存堆表，前面有一条 WAL。** 更新是新元组，删除是死元组，靠 VACUUM 回收；提交要等 WAL。高频改大字段、队列空转、缓存刷新、海量扫描、深图遍历，全部撞在这套机制上。细节见 [PostgreSQL原理分析.md](PostgreSQL原理分析.md) 第 4、5、6 节。
4. **扩展跑在 postmaster 的进程里。** 索引构建、压缩、Cypher 执行和普通查询抢同一块 `shared_buffers`、同一条 WAL、同一组 autovacuum。扩展缺陷可以把整个实例打下来。隔离流量的办法是另一个集群或一个库外进程，不是再 `CREATE EXTENSION`。

## 1.3 能力分层：卡片把四层叠成了一列

卡片的「PG 方案」一列把内核特性、扩展和独立进程写在一起。落地时这四层的安装方式和故障域完全不同。

```
┌────────────────────────── 库外进程（不在 postmaster 里）──────────────────────────┐
│  PostgREST          应用侧工人（消费队列、跑编排、调外部 API）                      │
│  连接池 PgBouncer   逻辑复制的下游（另一套 ParadeDB / 分析实例）                    │
├────────────────────────── 第三方扩展（自建或特定平台才有）─────────────────────────┤
│  pgmq               pg_search（ParadeDB，AGPL）    Apache AGE                      │
│  TimescaleDB        pgvectorscale（把向量索引放到磁盘上的可选路径）                 │
├────────────────────────── 托管云里常见、仍要显式打开 ──────────────────────────────┤
│  pgvector           pg_cron            PostGIS（空间这一行的本体）                  │
│  pg_trgm            pg_stat_statements postgres_fdw                                │
├────────────────────────── 内核（任何 PG 18 都有）──────────────────────────────────┤
│  JSONB / SQL/JSON   UNLOGGED           内置全文检索（tsvector / GIN）              │
│  声明式分区         SKIP LOCKED        咨询锁（advisory lock）                     │
│  LISTEN / NOTIFY    生成列             逻辑复制                                    │
│  RLS                递归 CTE           GiST / GIN / SP-GiST                        │
└───────────────────────────────────────────────────────────────────────────────────┘
```

托管服务的扩展白名单不等于社区扩展目录。Amazon RDS、Aurora、Cloud SQL、Azure Database for PostgreSQL 普遍提供 PostGIS、pgvector、pg_cron、pg_trgm。`pg_search` 在作者文档里写明：托管服务没有显式支持之前不能安装。TimescaleDB、AGE、pgmq 同样要逐个平台核对。**图上的一行字，可能对应「改一条 SQL」或「换一种 Postgres 发行版」。**

              │ 或更大的向量库    │

物理流复制复制的是 WAL。UNLOGGED 表的内容不进 WAL，备库上是空的。ParadeDB 社区版还有一层更窄的限制：堆表可以走 PG 自己的复制，**BM25 索引在社区版不随物理复制到备库**，高可用和只读副本上的搜索索引属于企业版能力。逻辑复制复制的是行变更，下游要自己建索引，因此搜索读和下单写可以拆开，代价是搜索变为最终一致。

## 1.5 关键问题 → 方案映射（判决表）

这张表是全文的结论。后面十章是它的论证。

| 卡片上的原组件 | 卡片给的方案 | 本文级别 | 真正留在 PG 的部分 | 拆出去的信号 |
|---|---|---|---|---|
| RabbitMQ / Redis Streams | pgmq | 默认同库，越过信号再拆 | 和业务写入同一事务的任务、发件箱 | 持续高投递、复杂路由、跨机房扇出、要独立扩消费者 |
| Elasticsearch | pg_search · 全文检索 | 默认同库，越过信号再拆 | 千万级以内的关键词、前缀、和行过滤绑在一起的检索 | 独立扩搜索集群、重聚合分面、分析器是产品本身、单机数 TB 以上 |
| MongoDB | JSONB | 默认同库，越过信号再拆 | 关系行上的半结构化属性 | 文档是聚合根且被高频整篇重写，或要按文档分片 |
| Pinecone / Milvus | pgvector | 默认同库，越过信号再拆 | 和业务行一起过滤的向量召回 | 亿级全精度、毫秒级高 QPS、索引内存放不下 |
| Redis | UNLOGGED 表 | 从第一天分开（缓存和锁） | 可整表丢弃的临时数据、导入暂存 | 卡片自己已写明：缓存和锁留在 Redis。UNLOGGED 并不接这个需求 |
| Celery | pg_cron + pgmq | 只留简单子集 | 库内定时 SQL、用队列表投递载荷 | 工人池、重试退避、chord / group、限流、任务代码不在库里 |
| ClickHouse | TimescaleDB | 时序运营分析可同库；海量扫描另说 | 要和业务表 JOIN、要事务修正的时序 | 百亿行以上的 ad-hoc 列扫描、高基数聚合、扫描吞吐是目标 |
| Neo4j | Apache AGE | 只留简单子集 | 浅层邻接，且要和关系数据同事务 | 深遍历、大图上的最短路、PageRank / 社区发现这一类算法 |
| CRUD 后台服务 | PostgREST | 只留简单子集 | 权限模型能落进 RLS 的稳定资源 API、内部工具 | 多步业务、外部调用、要独立演进的对外 API |
| 专用 GIS 数据库 | PostGIS | 默认留在 PG | 矢量地理、空间关系、和业务表同事务 | 超大栅格分析、城际路网的专用路由引擎可以再外挂；事务型 GIS 不必换库 |

## 1.6 对卡片十行脚注的校正

完整原表在文首「卡片原文」。脚注方向大多是对的，粒度不够，有两行把不同的东西写成了一个名字。

| 卡片原文 | 校正 |
|---|---|
| pgmq，超高吞吐用专用 MQ | pgmq 的模型接近 SQS：读出后在可见性超时内隐藏，超时未删除则再次可见。这是「超时窗口内不重复投递」，超时之后仍是至少一次。它不是 AMQP 的 exchange，也不是 Redis Streams 的消费者组。RabbitMQ 和 Redis Streams 不该占同一格 |
| pg_search · 全文检索，超大规模独立部署 | 内核全文检索（`tsvector` + GIN）和 ParadeDB `pg_search`（Tantivy 上的 BM25）是两套实现。前者随 PG 发行，排序不是 BM25。后者是 AGPL 扩展，托管云通常要等服务商支持；社区版的搜索索引不在物理备库上 |
| JSONB，高频改大字段慎用 | 这句话成立，而且原因具体：改 JSONB 的一个键会写一条新堆元组，大文档还会重写 TOAST。它替代不了「以文档为分片单位的数据库」 |
| pgvector，亿级向量用专库 | 当作容量信号成立，不是一条硬悬崖。账首先是内存：1 亿条 1536 维 float32 裸向量约 614GB，HNSW 图还在这之上。千万级、过滤条件能写进 SQL 时，pgvector 往往是更省事的选择 |
| UNLOGGED 表，缓存与锁留 Redis | 后半句成立。前半句不是 Redis 的替代物。UNLOGGED 跳过 WAL，崩溃恢复后表被清空，正常关闭再启动则数据还在；它仍然是堆表，没有 TTL、哈希、有序集合和亚毫秒内存结构 |
| pg_cron + pgmq，编排放应用层 | 成立。pg_cron 执行的是 SQL，元数据只装在集群内的一个库里；同一任务不会并发跑第二份。Celery 的 canvas、重试和工人进程不在这两个扩展里 |
| TimescaleDB，海量 OLAP 用列存 | 方向对，主语要换。Timescale 的列存是分块上的压缩，执行器仍是 PostgreSQL。和 ClickHouse 的向量化列存不是同一量级。没装 Timescale 时，原生声明式分区已经能做保留和分区裁剪 |
| Apache AGE，重图算法用图库 | 成立。AGE 把 Cypher 交给 SQL 执行，图存在表里，没有 Neo4j 那套图算法库。openCypher 覆盖不完整 |
| PostgREST，复杂业务要后端 | 成立，但「复杂」要换成可操作的标准：一步写完、不变量能写成约束和 RLS、不调用外部系统。PostgREST 是独立进程，数据库才是它的后端 |
| PostGIS，行业标准 | 成立。这一行和前面九行不同：PostGIS 就是那个专业 GIS 组件，只是以扩展的形式住在 PG 里 |
| 这就是一个 PG 能给你的 | 引擎可以是一个。集群从第一天就至少要再加 Redis（如果有缓存或锁）。搜索、分析和大规模向量用逻辑复制或专用库拆读路径，而不是等主库先过载 |

## 1.7 版本演进：这张卡片不是某一个大版本发布的

内核能力是十几年加上去的，卡片里的「AI 浪潮」只解释了向量那一行的流行，解释不了其余九行。

| 时间 | 和本文有关的能力 |
|------|------------------|
| 9.1 | UNLOGGED 表 |
| 9.4 | JSONB |
| 9.5 | `SELECT … FOR UPDATE SKIP LOCKED`，后来所有「用 PG 做队列」的底层原语 |
| 9.6 起 | 并行查询，分析型语句才开始能用多核。执行器仍是行存 |
| 10 | 声明式分区、逻辑复制。逻辑复制是以后把搜索或分析拆出去的通道 |
| 11 | 存储过程、分区能力补齐 |
| 12 | 存储生成列、SQL/JSON path。生成列用来把 JSONB 里的热字段变成真列 |
| 14 | JSONB 下标赋值 |
| 15 | `MERGE`；视图增加 `security_invoker`，和 PostgREST 的权限模型直接相关 |
| 16 | SQL/JSON 构造函数、从备库做逻辑解码 |
| 17 | 分区和 VACUUM 继续改进；`JSON_TABLE` 一类的 SQL/JSON 更完整 |
| 18（本文基线，2025-09） | 异步 I/O、虚拟生成列（现为默认；列本身不能建索引，逻辑复制也不带走）、B-tree skip scan。没有改变「行存 + WAL + MVCC」这条天花板 |

扩展是另一条时间线：PostGIS 从 2000 年代就是地理信息的默认选择；pg_cron、pgvector、pgmq、ParadeDB、AGE 都是内核之外的项目。pgvector 被广泛使用是 2023 年之后的事，因为检索增强生成要把「向量近邻」和「业务过滤」写在同一条 SQL 里。这解释了卡片标题里的「AI 时代」，也说明其余几行（GIS、JSONB、队列、时序）并不是被 AI 带出来的。

MySQL 有 JSON、有全文索引、也有空间类型。卡片把「为什么不是 MySQL」放在标题里，原因不在语法，而在扩展面：PG 允许一个外部项目注册类型、索引访问方法和后台进程，PostGIS 和 pgvector 都是这个接口的用户。MySQL 侧没有积累出同等位置的地理与向量扩展生态。需要对照存储引擎本身时，看 [MySQL原理分析.md](MySQL原理分析.md)，本文不展开。

## 本章小结

卡片把「扩展进得了 PG」说成了「一个集群可以当这些专业组件用」。前半句来自 PG 的扩展接口，后半句被 WAL、MVCC 和进程内故障域否定。十行里只有 PostGIS 是默认替代；缓存和锁从第一天留在 Redis；队列、检索、JSONB、向量、时序是默认同库、按信号拆；Celery、Neo4j、通用后端只把简单子集放进 PG。

# 二、共同天花板：十行边界为什么长得像

## 2.1 这一章在替代什么

这一章不对应卡片上的某一行。它把第三到十二章会反复出现的限制收成一张决策卡。后面每章只写该组件多出来的语义，不再重讲 MVCC。

## 2.2 收益只有一种：和业务行同一个提交

引入专业组件的成本不是许可证，而是一条同步链路：

1. 业务事务在 PG 提交。
2. 另一套系统经 CDC、消息或定时任务看到这次变更。
3. 链路延迟、重复、丢消息、回放顺序都要应用自己处理。
4. 备份、权限、故障切换变成两套。

队列、搜索、向量、时序、图、地理只要和业务行放进同一个 `COMMIT`，这条链路就消失。这是 pgmq、JSONB、pgvector、PostGIS 值得先考虑的全部理由。它们在吞吐量、召回设施或算法库上并不胜过专用系统。

反过来，Redis 缓存和锁的价值就是「可以丢、必须快、不能跟事务提交绑在一起」。把它们拉进 PG 的提交路径，收益不存在，WAL 成本还在。

## 2.3 三条所有行都要付的成本

**死元组。** 更新和删除不改原元组，只追加新版本。队列的「读出再删除」、缓存行的刷新、JSONB 大字段的局部修改、向量的重嵌入，都是高周转工作负载。autovacuum 跟不上时表膨胀，索引膨胀，计划变差。队列场景还要更激进的 autovacuum 参数，否则吞吐先掉在 VACUUM 上，而不是掉在 SQL 上。

**一条 WAL、一个主写入点。** 提交的持久化顺序由 WAL 决定。搜索索引维护、向量图的更新、时序写入和业务 OLTP 写的是同一条日志。物理备库只能放大读，不能放大写。UNLOGGED 是主动退出这条日志：快，并且崩溃后清空，备库不可用。

**一个连接一个后端进程。** 消费者、PostgREST 工作连接、pg_cron 任务、交互式会话共享 `max_connections`。Celery 那种「开很多工人」的做法直接打满 PG。前面要有连接池。长事务占着快照，VACUUM 就不能回收这个快照之后的死元组，队列和缓存表会先膨胀。

这三条的内部结构分别在 [PostgreSQL原理分析.md](PostgreSQL原理分析.md) 的第 5 节（MVCC 与 VACUUM）、第 6 节（WAL）和第 4 节（进程）。

## 2.4 扩展把故障域收成整个实例

PostGIS、pgvector、Timescale、AGE、pg_cron、pgmq、pg_search 的代码跑在数据库进程里。它们的内存、文件描述符和崩溃与 `postmaster` 在一起。一个索引访问方法的缺陷会重启整个实例，业务 OLTP 跟着停。

库外进程没有这个耦合：PostgREST、Redis、RabbitMQ、Elasticsearch、ClickHouse、Milvus、Neo4j 挂了，PG 里的事务还在。这也是「复杂业务要后端」「超大规模独立部署」的故障域版本，不只是性能版本。

同一个集群里的多个 database **不提供** 这种隔离。它们共享同一条 WAL、同一块共享内存、同一次检查点、同一组后台进程。把队列「放到另一个库」只能隔离目录和连接串，不能隔离写入放大。要隔离就换一个集群。

## 2.5 决策卡：四个问题

每引入卡片上的一行，按顺序问：

1. **这次写入要不要和业务行原子提交？** 要，就优先留在 PG 或留在 PG 的发件箱里。不要，就没有必要挤进 WAL。
2. **工作负载是追加，还是对同一行反复改？** 追加（日志、事件、时序点、只插不改的向量）对 MVCC 友好。反复改大字段、反复删消息，先算死元组。
3. **读是取出几行，还是扫描、召回、扇出、深遍历？** 按主键和少量 JOIN 是 PG 的主场。全表扫描型聚合、上亿向量的近邻、六跳以上的图、每秒几十万条的扇出，是专用引擎的主场。
4. **这个功能挂了，主库能不能跟着不可用？流量要不要单独扩？** 不能接受，就放库外，哪怕数据模型用 SQL 也能表达。

四条都偏向 PG，才适合「默认同库」。任何一条指向专用系统，就采用卡片那一行的脚注，而不是标题。

## 本章小结

十行脚注其实是同一句话：PG 出卖的是事务同库，专用系统出卖的是独立的存储、独立的扩缩和独立的故障域。高周转工作负载还要额外支付死元组。判断时先用四个问题，再进入具体组件。

# 三、消息：RabbitMQ / Redis Streams 与 pgmq

## 3.1 这一行在替代什么

业务系统里的「消息」通常是三种需求被叫了同一个名字：

| 需求 | 真正要的语义 | 典型组件 |
|------|----------------|----------|
| 事务发件箱 | 业务提交成功时，任务一定在；处理端至少一次，靠幂等去重 | 数据库表、pgmq、SQS |
| 路由与扇出 | 一条消息按主题交给很多互不知道的消费者，要死信、优先级、跨机房 | RabbitMQ |
| 可截断的高速日志 | 按偏移量追加，消费者组各自推进，允许近似裁剪 | Redis Streams、Kafka、RabbitMQ Streams |

卡片把前两种和第三种的 Redis 实现放进了同一格，方案只写了 pgmq。pgmq 覆盖的是第一格，并带了一点主题通配；它不覆盖后两格。

## 3.2 PG 侧怎么做

**不装扩展也能做队列。** `SKIP LOCKED`（9.5 起）让多个消费者各锁到不同的行：

```sql
BEGIN;
SELECT id, payload
FROM jobs
WHERE visible_at <= now()
ORDER BY id
FOR UPDATE SKIP LOCKED
LIMIT 10;
-- 处理成功后删除或把 visible_at 推后；处理失败就回滚，锁释放，行重新可见
COMMIT;
```

这个模式的代价要算清楚。`FOR UPDATE` 把锁留到事务结束，所以事务必须盖住整个处理过程：处理越慢，连接占得越久，和第二章的连接模型直接冲突。可见性超时的做法是把「隐藏到什么时候」写成列，读的时候用短事务更新这列，处理在事务外进行。pgmq 把这套做法收成了函数。

**pgmq** 是一组 SQL 对象，没有自己的常驻 worker。官方描述的模型是：

- `send` 把一条 JSON 消息放进队列表，返回消息 id。
- `read(queue, vt, qty)` 读出最多 `qty` 条，并在 `vt` 秒内对其他消费者隐藏。
- 处理完调用 `delete` 清除，或 `archive` 挪到归档表。
- 超时未删除，消息重新可见。作者把它称为可见性超时内的「恰好一次」。超时之后就是至少一次。
- 新版本增加了按 message group 的 FIFO，以及带通配符的主题路由。支持的 PG 版本覆盖 14 到 18。被 Supabase 等平台集成。

「恰好一次」只存在于「消费者在超时前成功 delete」这个窗口里。消费者已经产生了副作用（发了短信、扣了第三方的款）然后崩溃、超时后消息又被另一个工人读到，仍然会执行第二次。端到端的恰好一次靠业务幂等键，不靠队列口号。RabbitMQ 的手动 ack 和 Redis Streams 的 PEL 也是同一类契约。

和业务写在一起时，用法是：

```sql
BEGIN;
INSERT INTO orders (id, status) VALUES (1001, 'created');
SELECT pgmq.send('order_events', '{"order_id": 1001}');
COMMIT;
```

两个写入要么都在，要么都不在。这是相对 RabbitMQ 的实际优势：不用再维护「数据库提交了、消息没发出去」的发件箱轮询，因为发件箱就是这个队列。

## 3.3 专业组件多出来的部分

**RabbitMQ** 是交换机模型。direct、fanout、topic、headers 四种 exchange，加上绑定、死信、优先级、TTL、发布确认、仲裁队列。一个队列副本的热路径受单核限制，所以「一个队列打满全部吞吐」本身就是反模式；扩展靠多个队列，以及在更高吞吐时改用 RabbitMQ Streams。协议侧还有 AMQP、MQTT、STOMP 和一整套联邦、铲运插件。这些是集成总线，不是任务表。

**Redis Streams** 是内存里的追加日志：`XADD`、消费者组、待处理列表、`XACK`、按长度近似裁剪。吞吐来自内存和单线程命令执行，持久化是 RDB/AOF 的另一套取舍。它适合已经有 Redis、事件可以重建或可以容忍较短持久化窗口的场景。用 Streams 的人通常是在买吞吐和偏移量，不是在买和订单同一事务。

pgmq 近年补上的主题通配，仍然是「表上的路由」，没有独立的交换机进程，没有跨集群联邦，也没有面向百万闲置队列的设计。

## 3.4 对照

| 维度 | SKIP LOCKED 自建表 | pgmq | RabbitMQ | Redis Streams |
|------|--------------------|------|----------|----------------|
| 和业务事务原子 | 是 | 是 | 否，要发件箱 | 否 |
| 投递契约 | 自己写 | 可见性超时，至少一次 | ack，至少一次 | 消费者组 ack，至少一次 |
| 路由 | 自己写 WHERE | 队列，外加主题通配和分组 FIFO | exchange 全套 | 按流和组 |
| 扇出给互不相干的系统 | 差 | 弱 | 这是主场 | 多个组读同一条流 |
| 吞吐瓶颈 | 死元组、WAL、连接 | 同样，外加 autovacuum | 队列与集群设计 | 内存和单线程命令 |
| 消息堆积 | 表变大，VACUUM 压力 | 同左；可归档 | 磁盘队列 / 流 | 受内存和 MAXLEN 约束 |
| 运维面 | 无新组件 | 一个扩展 | 独立集群 | 已有 Redis 上的一种结构 |

吞吐不在这里给一个假的每秒条数。公开的 PG 队列测试反复强调的是同一组条件：消息体小、批量读、VACUUM 跟上、高吞吐时把队列计算和 OLTP 隔离开。越过这个区间，专用 MQ 的脚注就生效。

## 3.5 边界，以及以后怎么迁

适合 pgmq 或自建队列表的，是订单、邮件、缩略图、内部工作流这一类：每秒百到几千条、必须和业务提交绑定、消费者是自己的工人、路由只有「这个队列」。

下面任一信号出现，就引入 RabbitMQ 或 Kafka，PG 退回发件箱：

- 多个独立团队要各自订阅同一事件，订阅关系经常变。
- 需要死信、延迟重试阶梯、优先级，并且不想自己用表来模拟。
- 投递速率持续高到影响主库 WAL 和 autovacuum，业务查询的延迟跟着抖。
- 消费者数量大，连接数压过连接池。
- 跨机房复制消息。

迁移时不要把业务事务改成双写。保留「提交时插入发件箱」这个动作，另起一个中继把发件箱推到 broker，推送位点记在 PG 里。pgmq 因此是一条退路清晰的起点，不是一条死路。Redis Streams 不作为这条退路的默认下一站：它和业务事务仍然是两个系统，持久化语义还更弱；已经把 Redis 当日志用、并且接受那组取舍时再留在 Streams。

## 本章小结

pgmq 替代的是事务性任务队列，机制是可见性超时，语义是至少一次。RabbitMQ 的路由和 Redis Streams 的高速日志是另外两个组件。卡片把两者写进同一格，是这一行最需要拆开的地方。超高吞吐用专用 MQ，这句脚注成立。

# 四、检索：Elasticsearch、内核全文与 pg_search

## 4.1 这一行在替代什么

「搜索」在卡片里写成 `pg_search · 全文检索`，好像是同一个功能的两个名字。实际是三层：

| 层 | 是什么 | 排序 | 哪里能用 |
|----|--------|------|----------|
| 内核全文检索 | `tsvector` / `tsquery`，GIN 索引 | `ts_rank` / `ts_rank_cd`，看词频和权重位，没有全库 IDF 意义上的 BM25 | 任何 PG |
| `pg_trgm` | 三元组，服务模糊匹配和 `LIKE '%x%'` | 相似度，不是全文相关性 | contrib，托管云普遍有 |
| ParadeDB `pg_search` | 把 Tantivy 嵌进 PG 的 BM25 索引 | BM25，另有短语、模糊、高亮、分面，并可在同一索引里做向量混合 | 自建或 ParadeDB 自己的云；AGPL-3.0 |

Elasticsearch / OpenSearch 是第四件东西：独立的分布式倒排集群。

## 4.2 内核全文检索的机制和上限

```sql
ALTER TABLE articles
  ADD COLUMN tsv tsvector
  GENERATED ALWAYS AS (
    to_tsvector('simple', coalesce(title, '') || ' ' || coalesce(body, ''))
  ) STORED;

CREATE INDEX articles_tsv_gin ON articles USING GIN (tsv);

SELECT id, ts_rank_cd(tsv, q) AS rank
FROM articles, to_tsquery('simple', 'postgres & index') q
WHERE tsv @@ q
ORDER BY rank DESC
LIMIT 20;
```

机制上要记住的限制：

- 解析器按配置分词。默认解析器不按中文词切分：一段没有标点的中文会被当成一个大词元，`to_tsvector` 找不到里面的词。中文检索要另加 zhparser、pg_jieba 一类扩展，或者退回 `pg_trgm` 做子串。卡片如果面向中文内容，这一条比「要不要 BM25」更先碰到。
- `tsvector` 有约 1MB 的上限，词位计数在实现里被夹断。超长文档不是把它当搜索引擎文档库来存。
- GIN 的 `fastupdate` 会把新词先放进待定列表，待定列表刷新时延迟会抖一下。
- 排序函数在取出命中后再算。命中几十万行再排序取前 20，成本随命中数走，没有块最大 WAND 那种「跳过不可能进前 K 的文档」的倒排执行。
- 相关性是局部统计。要 BM25 那种语料级的逆文档频率，内核这套不够。

千万行以内、查询还要 JOIN 业务表、排序用「新近 + 简单词频」就够的后台搜索，内核全文检索够用，而且没有新的许可证和复制问题。

`pg_trgm` 解决的是另一个查询：`ILIKE '%关键字%'`、拼音或拼写近似。它不是 Elasticsearch 的替代，却经常是用户说的「搜索」的真正 SQL。GIN 或 GiST 三元组索引在托管云上就能建。

## 4.3 pg_search 多出来的，以及它新引入的边界

`pg_search` 在堆表旁边建一个覆盖型的分段倒排索引：分词、BM25、Top-K 迭代、高亮、数值和日期过滤可以走同一条索引扫描，不需要先 GIN 再回表排序。写入走 MVCC，索引和堆表在同一事务里一致。这是相对 Elasticsearch 刷新间隔的实质差别：搜索结果和已提交的行是同一个快照，而不是「刷新之后才看得见」。

ParadeDB 自己写明的约束，比卡片上的「超大规模」更具体：

- 单机垂直扩展，厂商把生产部署的舒适区描述在数 TB 量级，并指出再大要靠分区或分片的 PG；分布式查询在路线图上。这是厂商口径，不是独立基准测试的上限。
- 索引列在创建时定死，加减列要 `REINDEX`。每行写入都要更新这整份覆盖索引，写放大比「只加一个 GIN」更高。
- 社区版（AGPL-3.0）是单机。物理复制下，社区版的 ParadeDB 索引只在主库上可用；备库上的 BM25 搜索、故障转移后的搜索连续性，属于企业版。堆表和其他普通索引仍走 PG 自己的复制。
- 托管 PG 不提供这个扩展时，官方建议的接法是：业务继续写 RDS / Aurora / Cloud SQL，用逻辑复制把行同步到一套 ParadeDB，由 ParadeDB 提供搜索。这条链路是最终一致，事务同库的好处被主动放弃，用来换「索引不堵在 OLTP 的写路径上」。

AGPL 对只调用 SQL 的应用通常不等于把应用传染成 AGPL，但是公司的开源合规清单经常把 AGPL 单列。这一行在评审时要让法务看许可证，不能只看功能表。

## 4.4 Elasticsearch 仍然独立部署的部分

Elasticsearch 是分片倒排集群：分析器链、聚合、高亮、补全、percolator、索引生命周期、摄取管道，以及按查询量单独扩数据节点。它不是可靠的主数据存储。实践里 PG 是事实来源，ES 是派生索引，中间有一条必须看护的同步。同步延迟、映射变更和回放失败是这套架构的日常成本，也是 ParadeDB 想从架构里删掉的东西。

ES 继续保留的信号：

- 搜索集群的 CPU 和磁盘要单独扩，不能跟 OLTP 主库绑在一起。
- 产品就是搜索：自定义分析器、同义词热更新、复杂聚合分面、跨索引联邦。
- 数据量或查询形态超出单机倒排的舒适区。
- 组织不能接受 AGPL，也不能买企业版，同时又需要 BM25。此时内核全文检索是留在 PG 里的那一档，ES 是库外的那一档。

中文分词在 ES 里是分析器配置；在 PG 内核里是额外扩展。若内容以中文为主，先验证分词，再谈 BM25 和规模。

## 4.5 对照

| 维度 | 内核全文 + pg_trgm | pg_search | Elasticsearch |
|------|--------------------|-----------|----------------|
| 和已提交行同一快照 | 是 | 是（扩展装在这个库上时） | 否，刷新间隔 |
| 相关性 | 词频 / 权重位 | BM25 | BM25 |
| 中文 | 需额外分词扩展或三元组 | 分词器可选，部署前验证 | 分析器 |
| 和业务表 JOIN | 普通 SQL | SQL，且索引侧做了加速 | 应用侧或宽表冗余 |
| 聚合分面 | 自己写 SQL，大命中集贵 | 有 | 这是主场之一 |
| 复制 | 跟 WAL 走 | 社区版搜索索引不在物理备库 | 集群自己的副本 |
| 许可证 | PG 许可证 / contrib | AGPL，企业功能另售 | 看 Elastic 或 OpenSearch 的发行版 |
| 规模形态 | 单机，大命中集先累 | 单机数 TB 量级的厂商口径 | 分片，独立扩 |

## 本章小结

中小规模、要和业务行一致的关键词检索，先用内核全文检索；模糊匹配加 `pg_trgm`。需要 BM25、高亮、分面，并且能接受 AGPL 和「搜索索引的高可用是另一份许可证」时，用 `pg_search`。搜索要独立扩缩、或者规模超出单机倒排时，独立部署 Elasticsearch，PG 保留主数据。卡片的脚注成立，但前提是先分清两套 PG 检索，并把许可证和备库写进同一条决策。

# 五、文档：MongoDB 与 JSONB

## 5.1 这一行在替代什么

MongoDB 卖的是文档数据模型：集合、嵌套文档、按文档演进的形状、聚合管道、变更流、按片键分片。JSONB 卖的是关系行里的一个二进制 JSON 列：模式不必先于数据穷尽，热字段仍可以是真正的列，约束和事务仍是 PG 的。

两者重叠的部分是「形状不齐的属性」。不重叠的部分是「文档是不是聚合根，更新是不是按文档分片」。

## 5.2 JSONB 的机制

`jsonb` 把 JSON 解析成二进制，去掉空白、不保留键顺序、重复键只留一个。需要原文的场景用 `json` 类型，它不适合建操作符索引。

索引有两条常见路：

- 表达式索引或生成列，把 `doc->>'tenant_id'` 这类热键变成 B-tree。这是默认首选。PostgreSQL 18 起，不写 `STORED` 的生成列默认是虚拟列，读时才计算，不能在列上直接建索引，逻辑复制也不包含它。要索引这个键，用下面这样的 `STORED`，或给同一个表达式单独建索引。
- GIN。`jsonb_ops` 支持的操作符更多，索引更大；`jsonb_path_ops` 更小，主要服务包含查询 `@>`。

```sql
ALTER TABLE assets
  ADD COLUMN tenant_id text
  GENERATED ALWAYS AS (doc->>'tenant_id') STORED;

CREATE INDEX ON assets (tenant_id);
CREATE INDEX ON assets USING GIN (doc jsonb_path_ops);
```

存储代价是这一行脚注的全部内容：

- 堆元组更新产生新版本。`jsonb_set` 改一个键，写的仍是整份新文档，不是原地改那个键。
- 超过约 2KB 的值进入 TOAST，可能压缩并放到线外。改一个键经常连 TOAST 值一起重写，WAL 里记下的是大对象的变更。
- 行要留在原页且被索引的列都没变，才能走 HOT 更新、少维护索引。GIN 索引的是文档里的键值，改文档通常意味着 GIN 也要更新，HOT 用不上。
- 于是「每秒对同一批大文档改一个计数器」会变成：大元组追加、TOAST 抖动、GIN 待定列表刷新、autovacuum 追死元组。这就是「高频改大字段慎用」。

可用的形状是：稳定和会过滤的字段做成列（或生成列），JSONB 只放长尾属性；把高频变动的计数器拆到旁边的窄表。需要对照的是 MongoDB 的原地更新风格和 WiredTiger 的文档存储，而不是 JSON 语法。

SQL/JSON 从 12 的路径表达式、14 的下标赋值，到 16、17 的构造和 `JSON_TABLE`，让「把 JSON 拆开再 JOIN」可以写在 SQL 里。这加强了 JSONB 作为列的地位，没有把它变成文档数据库。

## 5.3 MongoDB 仍要单独存在的部分

- 聚合根就是文档，事务边界也是文档，周围没有关系型不变量。
- 文档很大，并且更新频繁。PG 的元组版本在这里最贵。
- 数据量需要按片键水平切分写入。PG 的单主写入要靠 Citus 一类分片，分片之后 JSONB 索引、外键和跨片事务都要重新设计。
- 团队要的是变更流驱动的下游，而不是关系约束。变更流可以对位 PG 的逻辑复制，但消费模型和运维面不同。

MongoDB 从 4.0 起有多文档事务，边界和持续时间都比 PG 的普通事务窄。选 MongoDB 的理由应当是数据模型和分片，不是「它没有事务所以更轻」——这个理由已经过时，也不够用。

## 5.4 对照

| 维度 | JSONB 列 | MongoDB 集合 |
|------|----------|----------------|
| 主模型 | 关系行，JSON 是其中一列 | 文档是聚合根 |
| 局部更新的物理代价 | 新元组，大值重写 TOAST | 文档存储引擎自己的页更新 |
| 约束 | 列类型、外键、检查、事务 | 文档校验规则，跨文档要另设计 |
| 索引 | B-tree 生成列、GIN | 二级索引、多键索引 |
| 水平写扩展 | 单主；分片是另一个产品 | 按片键分片是产品的一部分 |
| 和 SQL 生态 | 直接 JOIN | 聚合管道，或同步到别处 |

## 本章小结

JSONB 替代的是「关系模型里形状不齐的那一列」，不是 MongoDB 这个数据库。热字段提成列、大文档避免高频整篇改，脚注就成立。文档本身是业务聚合根、又要按文档分片或高频改大文档时，继续用文档数据库。

# 六、向量：Pinecone / Milvus 与 pgvector

## 6.1 这一行在替代什么

向量库解决的是近似最近邻：给定一个向量，在一大批向量里找出近的那些，并允许用元数据过滤。Pinecone 是托管服务，Milvus 是可以独立扩展查询节点和数据节点的分布式系统。pgvector 是 PG 的一个类型加两类索引，查询写在 SQL 里，和业务行同一个快照。

AI 应用把这一行推到台前，是因为检索增强生成的过滤条件（租户、权限、时间、文档是否删除）本来就在 PG 里。向量若在另一个库，每次召回都是一次跨系统拼接，还有删除不同步的问题。

## 6.2 pgvector 的机制

常见类型是 `vector`（float32）、`halfvec`（float16）、`bit`（二值），以及稀疏向量。距离操作符要和索引的操作符类成对：

| 操作符 | 距离 | HNSW / IVFFlat 的操作符类 |
|--------|------|---------------------------|
| `<->` | 欧氏 | `vector_l2_ops` |
| `<=>` | 余弦 | `vector_cosine_ops` |
| `<#>` | 内积的负值（方便 ASC 排序） | `vector_ip_ops` |

```sql
CREATE INDEX ON docs USING hnsw (embedding vector_cosine_ops);

SELECT id
FROM docs
WHERE tenant_id = $1
ORDER BY embedding <=> $2
LIMIT 20;
```

IVFFlat 构建快、召回和列表数 `lists`、探测数 `probes` 绑在一起，数据分布变了要重建。HNSW 召回更稳，构建更慢，图要放在内存里才有预期的延迟。

两个容易误判的点：

- **过滤和 LIMIT 的顺序。** 早期执行先按索引取近邻再过滤，`WHERE` 很严时，LIMIT 20 可能滤成空。pgvector 0.8 起有迭代索引扫描，缓解这个问题。计划是否真的走了迭代，要看 `EXPLAIN`，不能假设版本号就保证了过滤召回。
- **维度上限来自页。** 索引项要放进页结构。常见版本里 `vector` 上的 HNSW / IVFFlat 大约到 2000 维，`halfvec` 大约到 4000 维。这个数字变过，以所装版本的说明为准。更高维用降维、半精度或二值，或者换能把图放在磁盘上的索引。

## 6.3 亿级是一张内存账

float32 每个维度 4 字节。裸向量的下限是：

| 规模 | 维度 | 裸向量 | 加上 HNSW 图之后 |
|------|------|--------|------------------|
| 100 万 | 1536 | 约 6GB | 通常还要同量级的图内存 |
| 1000 万 | 1536 | 约 61GB | 单机仍可规划 |
| 1 亿 | 768 | 约 307GB | 图和 `shared_buffers`、业务数据抢内存 |
| 1 亿 | 1536 | 约 614GB | 全精度 HNSW 驻内存不现实 |

`halfvec` 把裸向量大约减半，召回会掉一点。二值量化再小一个数量级，用来做粗召回，再回表取全精度重排，是千万到亿级仍想留在 PG 时的常用折中。

索引构建期间 I/O 和 CPU 都很高，和 OLTP 同实例时业务延迟会抖。构建要放在低峰，或者放在从主库逻辑复制出去的专用实例上。

pgvectorscale 一类扩展用磁盘上的图（StreamingDiskANN）把「内存放不下」往后推。它仍是 PG 进程里的索引，故障域和 WAL 上的取舍要单独评估，不等于已经换成了 Milvus。

## 6.4 专用向量库多出来的部分

Milvus 这一类系统把查询节点和数据节点分开扩，索引种类包括可落盘的 DiskANN 和 GPU 索引，过滤和向量在一个专门的执行路径里，一致性级别可以按查询选。集群要运维 etcd、对象存储和流式层。Pinecone 把这些收成服务，按命名空间和规格付费，换来的是向量数据离开了业务事务。

它们值得单独引入的信号：

- 全精度向量到亿级，且延迟目标是毫秒、QPS 高。
- 召回是产品主路径，要独立扩查询，不能跟订单库绑在一个故障域里。
- 需要专用索引或 GPU，而不是 HNSW 一种图。

没到这些信号时，单独养一个向量库的同步成本高于 pgvector 的内存成本。业务主键留在 PG，向量库只存 id 和向量，是规模越过信号之后的拆法；过滤条件能下推到向量库的元数据里，避免「召回一万个 id 再回 PG 滤成二十个」。

## 6.5 对照

| 维度 | pgvector | Pinecone / Milvus |
|------|----------|-------------------|
| 和业务行同一事务 | 是 | 否，要同步 |
| 过滤 | SQL，注意计划和迭代扫描 | 元数据过滤是产品功能 |
| 索引 | IVFFlat、HNSW；磁盘图要另装扩展 | 多种，含落盘和 GPU |
| 规模舒适区 | 百万很宽裕，千万要算内存，亿级是脚注的信号 | 为十亿级设计 |
| 扩缩 | 读副本放大只读；写和建索引在主库 | 查询与数据分开扩 |
| 运维 | 一个扩展 | 一套集群或一份云账单 |

## 本章小结

向量和业务过滤在同一个事务里，规模在千万级、内存算得过来，就用 pgvector。亿级全精度加上毫秒级高 QPS，是专用向量库的区间。卡片的脚注当作容量信号成立；把它理解成「到了 1 亿条的当天必须迁」不成立，内存账和延迟目标才是判据。

# 七、缓存与锁：Redis 与 UNLOGGED 表

## 7.1 这一行在替代什么

卡片写的是「UNLOGGED 表」，脚注是「缓存与锁留 Redis」。脚注是对的，方案和脚注不是同一件事。Redis 在这张卡片里至少承担三类工作，UNLOGGED 一张表都替代不了：

| Redis 里的东西 | 买的是什么 |
|----------------|------------|
| 字符串、哈希、列表、集合、有序集合、带 TTL 的缓存 | 内存数据结构，亚毫秒，可丢失 |
| `SET key value NX PX`、Redlock 一类协议 | 跨进程互斥，带过期，避免死锁残留 |
| Pub/Sub、Streams | 扇出或日志。Streams 已在第三章讨论 |

## 7.2 UNLOGGED 实际是什么

```sql
CREATE UNLOGGED TABLE import_staging (
  id bigint PRIMARY KEY,
  payload jsonb NOT NULL
);
```

- 变更不写 WAL，所以写得比普通表快，检查点和归档也碰不到这些变更。
- **崩溃或非干净关机后的恢复会把表截空。** 正常关闭再启动，数据还在，因为关闭时的检查点已经把缓冲写出去了。
- 物理备库上这张表是空的。故障切换之后，应用若连到新主，临时数据不在。
- 它仍是 8KB 页的堆表：有 MVCC、有索引、有 autovacuum、走 SQL。没有键过期，没有原子自增到「带 TTL 的计数器」那种原语，也没有有序集合。
- 表上的序列默认仍是记日志的。用自增主键灌 UNLOGGED 表时，序列会成为意外的 WAL 来源。

因此 UNLOGGED 适合：可以整表重建的导入暂存、会话草稿、一次性的中间结果。重建流程必须写在应用里，因为切换和崩溃都会把表清空。把它当缓存用，等于用一份「可能突然全空的磁盘表」去接本来为内存命中设计的读路径，延迟和失效语义都不对。

临时表是会话级的 UNLOGGED，连接一断就没了，更不适合当共享缓存。

## 7.3 咨询锁也不是 Redis 锁

PG 有咨询锁：`pg_advisory_lock` / `pg_try_advisory_lock`，以及事务结束就释放的 `pg_advisory_xact_lock`。它们是共享内存里的 64 位键，不锁行，所以不阻挡无关表的 VACUUM。适合「这个主库上只有一个工人跑这份定时作业」。

和 Redis 锁的差别：

- 咨询锁住在当前主库的内存里，不复制，切换后全部消失。
- 会话级锁跟着连接走。连接池复用后端时，上一任客户端的会话锁可能还在，必须用事务级咨询锁或在归还连接前解锁。
- 没有 PX 那种「持有者死了 N 毫秒后键自己消失」的协议。进程死了，锁随连接消失，这点是好的；但你无法用一个和数据库无关的 TTL 在两个系统之间做租约。
- 两个客户端若在故障切换的重叠期分别连到旧主和新主，咨询锁不会帮你发现。Redis 锁也要额外的 fencing token 才说得清这件事。咨询锁没有把问题变简单。

缓存一致性若靠「更新数据库后删除 Redis 键」，删键失败要有回填或短 TTL。这是应用问题。把缓存搬进 UNLOGGED 不会取消失效逻辑，只会把失效变成「表被截空」。

## 7.4 LISTEN / NOTIFY 顺手划清

`NOTIFY` 的载荷上限约 8000 字节。没有监听者时消息直接丢掉，不落盘，不排队。监听只在同一个 database 的已连接会话之间。它可以用来叫醒一个正在 `pgmq.read` 的工人，减少空转轮询。它不是 Redis Pub/Sub 的持久替代，更不是队列。

## 7.5 对照

| 需求 | 放哪里 | 原因 |
|------|--------|------|
| 页面缓存、会话热点、排行榜、限流计数 | Redis | 内存结构、TTL、与事务解耦 |
| 跨服务互斥、带过期的锁 | Redis | 租约语义在库外 |
| 可全量重做的导入中间表 | UNLOGGED | 少写 WAL，接受崩溃即空 |
| 单主库上的作业互斥 | 事务级咨询锁 | 不引入锁服务，切换后要能重入 |
| 叫醒工人 | NOTIFY，或短轮询 | 载荷小、允许丢 |

## 本章小结

缓存和锁留在 Redis，这句脚注应当当成硬约束。UNLOGGED 是「放弃 WAL 的堆表」，服务可重建的临时数据。咨询锁只解决单主库内的互斥。这一行的方案和脚注指向两种不同的工具，按脚注执行。

# 八、定时与任务：Celery 与 pg_cron + pgmq

## 8.1 这一行在替代什么

Celery 是分布式任务系统：broker（通常是 Redis 或 RabbitMQ）、工人进程池、结果后端、重试、倒计时、速率限制，以及 chord、group、chain 这些组合。任务代码跑在应用进程里，可以访问文件系统、HTTP 和 GPU。

卡片用 `pg_cron + pgmq` 去对这个名字，脚注写「编排放应用层」。拆开看：

- pg_cron 替代的是「到点在数据库里执行一句 SQL」，对位的是 Celery Beat 加上一个只跑 SQL 的任务。
- pgmq 替代的是任务载荷的排队，已在第三章说明。
- 编排、重试策略、工人扩缩、任何数据库之外的副作用，仍在应用或专门的工作流引擎里。

## 8.2 pg_cron 的机制

pg_cron 是一个后台 worker，元数据在 `cron.job`。它必须放进 `shared_preload_libraries`，并且 **一个集群只在 `cron.database_name` 指定的那一个库里安装**。其他库的作业通过 `cron.schedule_in_database` 指定目标库，而不是把这个参数写成逗号分隔的列表。

```sql
SELECT cron.schedule(
  'purge-staging',
  '*/10 * * * *',
  $$DELETE FROM import_staging WHERE created_at < now() - interval '1 day'$$
);
```

行为上的边界：

- 执行的是 SQL，不是 Python 或任意容器。要发邮件、调 HTTP、转码，就在 SQL 里 `send` 一条 pgmq 消息，让库外工人去做。不要在库里用扩展去跑外部命令。
- 同一个任务不会并行跑两份。上一次没结束，下一次排队等它。这避免了重入，也意味着一个卡住的任务会把该任务的后续时刻全部顶住。
- 并发任务数受 `cron.max_running_jobs` 限制；若改成用后台 worker 执行，还受 `max_worker_processes` 限制。连接方式执行时，任务就是一个普通后端，占连接、占快照。
- 热备上的 pg_cron 不跑任务，提升为新主后才跑。切换窗口内的「准点」会缺一次，任务本身要能补跑。
- 时区、超级用户是否允许建任务、是否记录 `cron.job_run_details`，都是配置项。长 SQL 要自己设 `statement_timeout`，否则会被实例的默认超时取消，或者反过来把一个失控 SQL 留到占满 I/O。
- 它没有 Celery 的重试退避、死信和结果后端。失败记在运行明细里，下一步做什么由人写进 SQL 或由应用查询这张明细。

## 8.3 应用层编排具体指什么

「编排」不是一句空的脚注。下面这些留在应用或工作流引擎（继续用 Celery，或换成以持久化流程为模型的引擎）：

- 任务 A 成功后再跑 B，A 失败走另一支，并且分支要可视化、可重放。
- 扇出一百个子任务，全部完成后再汇总。Celery 的 chord 就是这个。pg_cron 没有对应物。
- 重试带抖动，且要区分「对方 429」和「数据违反约束」。
- 工人按 CPU 或队列长度扩缩，任务代码随应用发布，而不是随数据库迁移发布。
- 一个任务要占住 GPU 或长时间的外部连接。这种工作放进 pg_cron 会占着数据库后端直到结束。

pg_cron 适合的是数据库自己的保养：分区维护、聚合刷新、过期数据删除、`VACUUM` 的补充调度、到点把一批 id 送进 pgmq。这些 SQL 短、可重入、和模式放在一起版本管理。

## 8.4 对照

| 维度 | pg_cron | pgmq | Celery |
|------|---------|------|--------|
| 触发 | cron 表达式 | 另有人 send | Beat 或应用调用 |
| 执行地点 | 数据库后端 | 不执行，只存消息 | 工人进程 |
| 代码 | SQL | JSON 载荷 | 应用代码 |
| 重试 / 组合 | 没有 | 可见性超时造成再投递 | 重试、chord、group、chain |
| 扩缩 | 受 worker 和连接限制 | 受主库写入限制 | 加工人 |
| 切换 | 仅主库执行 | 队列表跟 WAL 走 | broker 自己的高可用 |

## 本章小结

pg_cron 是库内的 SQL 日程表，pgmq 是载荷队列。两者相加得到「到点把工作放进队列」。Celery 的工人、重试和编排留在应用层，卡片这句脚注成立。不要把外部副作用写进 cron 任务的 SQL 里。

# 九、时序与分析：ClickHouse、TimescaleDB 与原生分区

## 9.1 这一行在替代什么

ClickHouse 是列存的 OLAP 引擎：MergeTree、按列压缩、向量化执行、分布式表。它擅长对很大的历史数据做扫描和聚合。更新是突变，不是 PG 那种随手 `UPDATE` 就进事务的模型。

TimescaleDB 是 PG 扩展（现由 Tiger Data 维护）。它把时间序列自动化成 hypertable：按时间切成 chunk、对较老的 chunk 做列式压缩、用连续聚合增量维护滚表、用策略丢掉过期 chunk。热数据仍然可以是行存，可以和业务表 JOIN，可以事务更新。

没装 Timescale 时，PG 自己的声明式分区已经能表达「按月一个分区、过期整个 `DROP`」。卡片把 TimescaleDB 写成 ClickHouse 的对应物，中间其实还有原生分区这一档。

## 9.2 三层分别做到哪

**原生声明式分区**（10 起，之后每版补齐裁剪和运维）：

- `PARTITION BY RANGE (ts)`，计划器按约束裁剪用不到的分区。
- 保留策略就是分离或丢掉分区，比 `DELETE` 几亿行便宜一个数量级，而且不制造几亿个死元组。
- 没有自动建下一分区（可用 pg_partman 补）、没有列压缩、没有连续聚合。执行仍是一行一行的执行器，并行查询能用多核，但不是列存向量化。
- 许可证和安装面就是 PG 本身。时序量还没大到要压缩时，先停在这一档。

**TimescaleDB**：

- hypertable 把「建分区、把元组路由到 chunk」收成自动行为，连续聚合类似增量物化视图，刷新在后台跑。
- 压缩列存把较冷的 chunk 按列编码，存储可以降一个数量级，聚合不必先把整个行解出来。这是相对原生 PG 的分析能力来源。
- 新数据的修正仍是 SQL 的 `UPDATE` / `INSERT … ON CONFLICT`。和 ClickHouse 里用突变或 ReplacingMergeTree 处理晚到数据，运维体验不同。
- 许可证分成 Apache-2.0 的核心和 Timescale License 下的社区功能。压缩和连续聚合属于要核对许可证的那一组。不能按「和 PostGIS 一样装上就用」来假设，托管云也往往没有它，Tiger 自己的云在支持列表里。

**ClickHouse**：

- 扫描吞吐和压缩是设计目标。高基数 `GROUP BY`、宽表、百亿行以上的即席查询，是它的区间。
- 没有 PG 的外键和多行事务。把它当业务库，应用会被迫在缺少约束的地方重做完整性。
- 适合作为派生分析存储：PG 或消息是来源，ClickHouse 吃批量或流式导入。晚到和修正要按它的表引擎设计，而不是按 `UPDATE` 设计。

## 9.3 对照

| 维度 | 原生分区 | TimescaleDB | ClickHouse |
|------|----------|-------------|------------|
| 模型 | 行存，分区裁剪 | 热块行存，冷块可列压缩 | 列存 |
| 和业务表 JOIN、事务修正 | 是 | 是 | 不作为主路径 |
| 保留 | DROP 分区 | 保留策略丢 chunk | TTL |
| 预聚合 | 自己建物化视图 | 连续聚合 | 增量物化视图 |
| 扫描量级 | 分区之后的行存扫描 | 压缩后明显好于行存，仍是 PG 执行器 | 这是主场 |
| 安装 | 内核 | 扩展 + 许可证分层 + 平台白名单 | 独立集群 |

「海量 OLAP 用列存」这句脚注，如果「列存」指 ClickHouse，成立；如果指 Timescale 已经等于 ClickHouse，不成立。Timescale 的列存是为了让时序留在 PG 里更久。

## 9.4 怎么选

设备指标、应用埋点、和工单或资产同库查询、数据要能按主键修正：原生分区或 Timescale，优先和业务同库，避免一条同步管道。

报表是对历史的大规模扫描、可以接受分钟级可见性、查询形态是宽表聚合：导入 ClickHouse 或数仓。OLTP 主库上直接对百亿行做即席分析，会把共享缓冲和 I/O 从业务查询手里夺走，这是第十四章的资源争用，不是 SQL 写得够不够好。

## 本章小结

时序先用原生分区；需要自动分块、压缩和连续聚合，并且许可证与平台都允许，再用 TimescaleDB。ClickHouse 保留给扫描本身就是产品目标的海量分析。卡片把 Timescale 和 ClickHouse 写成一对替代，中间少了原生分区，也少了「列压缩的 PG」和「列存执行器」的差别。

# 十、图：Neo4j、Apache AGE 与递归 CTE

## 10.1 这一行在替代什么

图数据库解决的是「沿关系走多跳」和「在整张图上跑算法」。Neo4j 用原生图存储（邻接不经过关系连接）、Cypher，以及图数据科学库里的中心性、社区发现、路径算法。

PG 里有两档，卡片只写了后一档：

- 递归 CTE：关系表就是图，适合树和有限深度的邻接，没有任何扩展。
- Apache AGE：在 PG 里建图，用 openCypher 的一个子集，查询函数把 Cypher 交给 SQL 执行。

## 10.2 递归 CTE 往往先于 AGE

组织、类目、引用、权限继承这一类「有向、深度有限、要和业务表 JOIN」的结构，关系表加递归就够：

```sql
WITH RECURSIVE walk AS (
  SELECT id, parent_id, ARRAY[id] AS path
  FROM nodes
  WHERE id = $1
  UNION ALL
  SELECT n.id, n.parent_id, w.path || n.id
  FROM nodes n
  JOIN walk w ON n.parent_id = w.id
  WHERE n.id <> ALL (w.path)   -- 截断环
    AND cardinality(w.path) < 8
)
SELECT * FROM walk;
```

必须有深度上限和环检测。没有这两样，一个环会把查询跑到 `statement_timeout`。这种图的边如果本来就是外键，拆到 Neo4j 里反而要同步。

## 10.3 AGE 的机制和缺口

AGE 把顶点、边存在自己的表里，`cypher()` 返回集合，再和普通 SQL JOIN。收益是：图和关系数据同库，短查询能走 SQL 的计划器和索引，备份只有一份。

边界来自实现形态：

- 变长路径会被展开成多层连接。跳数上去之后，原生图的邻接遍历不会以同样的方式膨胀。公开的小图对比里，一跳附近两者接近，跳数增加后 Neo4j 拉开。那类对比的图很小，不能当成容量测试，只说明展开成连接这条路径的形状。
- openCypher 不是完整实现。已有问题记录包括 `MERGE … ON CREATE SET` / `ON MATCH SET`、部分时间函数、否定模式谓词等缺失。从 Neo4j 迁查询不能假设原文能跑。
- 没有 Neo4j GDS 那种在图上跑 PageRank、Louvain、全图最短路的算法库。算法要自己导出子图到专用进程里算，再把结果写回。
- Cypher 属性过滤是否下推到 PG 索引，取决于执行器路径，不能假设写成了 `{name: 'Alice'}` 就会走 B-tree。大图上的点查要看 `EXPLAIN`。
- 托管云很少预装 AGE。它是自建扩展，升级要跟 PG 大版本一起验证。

## 10.4 对照

| 维度 | 递归 CTE | Apache AGE | Neo4j |
|------|----------|------------|-------|
| 存储 | 业务表 | 扩展管理的关系表 | 原生图 |
| 查询 | SQL | openCypher 子集，再嵌入 SQL | Cypher，生态完整 |
| 深度 | 人为限深的树和浅图 | 浅层可以，深层变成大连接 | 这是主场 |
| 图算法 | 无 | 无内置库 | GDS 一类库 |
| 和业务事务 | 是 | 是 | 否，要同步 |
| 安装 | 内核 | 自建扩展 | 独立库 |

## 本章小结

边就是外键、深度有限，用递归 CTE，不必为了卡片去装 AGE。需要 Cypher、图和关系同事务、遍历不深，AGE 是可选项，同时接受方言缺口。重图算法和深遍历用 Neo4j 或其他图引擎，子图导出计算、结果写回。卡片的脚注成立。

# 十一、HTTP：CRUD 后台与 PostgREST

## 11.1 这一行在替代什么

PostgREST 是一个独立的 Haskell 进程。它读系统目录，把表、视图和函数暴露成 REST，用 JWT 里的角色声明做 `SET ROLE`，权限交给 PG 的角色和 RLS。它不是扩展，挂了不会拖垮 postmaster；数据库不可用时它也没有数据。

卡片说它替代 CRUD 后台，复杂业务要后端。更可操作的分界是：

**留在 PostgREST：** 一个请求对应一次读或一次写入，不变量能写成约束、触发器或一个 SQL 函数，调用者权限能写成 RLS，没有邮件、支付、对象存储这类外部副作用。内部工具、管理后台、形状稳定的资源 API 属于这里。

**留在应用后端：** 一次用户动作要跨多步并且中间要调外部系统；API 要独立于表结构演进；返回形状是多个聚合的拼装；错误码和幂等要按对外合同来，而不是按 SQLSTATE。

「CRUD」这个词不够用。一个带状态机的单表更新可能很复杂，仍可以由一个 `SECURITY INVOKER` 函数完成。一个只是把三张表拼成页面的 BFF，却应该留在应用里。

## 11.2 权限模型是这一行的真正边界

PostgREST 的安全不在 HTTP 层重做一套，而在数据库里。最低姿势：

- 连接角色只负责登录和 `SET ROLE`，不拥有表。
- 表的所有者不是 API 角色。**表所有者默认绕过 RLS**，除非 `FORCE ROW LEVEL SECURITY`。
- 策略写在表上，按租户或所有者限制行。
- 视图默认以**视图所有者**的权限执行，会绕开调用者身上的 RLS。对外的视图使用 PostgreSQL 15 的 `security_invoker`，让调用者权限生效。
- 写入优先走参数化的函数，而不是把基表的 `INSERT` 直接暴露出去。函数默认是 `SECURITY INVOKER`。一旦改成 `SECURITY DEFINER`，函数所有者的权限会被调用者借用，定义时就要把 `search_path` 钉死。

做不到这些，PostgREST 就是一个带 HTTP 的超级用户客户端。这比「复杂业务要不要后端」更早成为否决项。

模式变更后要让 PostgREST 重新加载模式缓存。把它放在发布流程里，而不是等第一个 404。

## 11.3 不适合塞进数据库的逻辑

触发器和函数可以吸收校验和简单状态迁移，但它们会变成第二套应用代码：迁移才能发布、单测要起数据库、观察性依赖 SQL 日志。下面这些保持在应用进程里：

- 调用支付、邮件、webhook，并在失败时补偿。
- 上传文件、生成带签名的 URL。
- 面向公网的 API 版本化，合同生命周期和表结构不一致。
- 跨多个聚合的长对话，中间状态不该只存在于一张表的若干列里。

PostgREST 可以和后端并存：稳定的内部资源走它，对外的用例走应用。卡片容易读成二选一。

## 11.4 对照

| 维度 | PostgREST | 应用后端 |
|------|-----------|----------|
| 进程 | 库外、无状态，可水平复制 | 库外，有自己的发布 |
| 数据形状 | 由模式、视图、函数决定 | 由代码决定，可聚合多处 |
| 权限 | 角色 + RLS + 安全调用者 | 代码里的策略，最终仍要落到库的权限 |
| 外部副作用 | 不承担 | 这是主场 |
| 故障域 | 不拖垮数据库；没有库就没有接口 | 同左 |

## 本章小结

PostgREST 适合权限能全部落进 RLS 的稳定资源。复杂与否，看有没有外部副作用、API 要不要独立演进，而不是看是不是 CRUD。视图的所有者和 RLS 的绕过，是这一行最常见的真实事故来源。

# 十二、空间：专用 GIS 数据库与 PostGIS

## 12.1 这一行为什么是例外

前面九行都是「PG 里有一个近似物，专用系统在规模或语义上更完整」。空间这一行反过来：PostGIS 就是开源地理信息的行业标准实现，QGIS、GeoServer、GDAL 都以它为参照。所谓专用 GIS 数据库，很多本身也是关系库上的空间扩展（Oracle Spatial 一类），或者是坐在数据库之上的桌面与服务器产品。

卡片给它的脚注是「行业标准」，没有写「到了多大规模请换库」。这个不对称是对的。

## 12.2 机制

PostGIS 注册 `geometry` 和 `geography` 类型、GiST 与 SP-GiST 索引，以及一套 `ST_*` 函数：相交、包含、距离、缓冲、投影变换、聚合。`geography` 按椭球计算，距离单位是米；`geometry` 在投影坐标系里算平面距离，通常更快。索引列和查询列必须是同一类型，在 `geometry` 列上把参数转换成 `geography` 再过滤，索引用不上。

```sql
CREATE INDEX ON places USING GIST (geog);

SELECT id
FROM places
WHERE ST_DWithin(
  geog,
  ST_SetSRID(ST_MakePoint(121.47, 31.23), 4326)::geography,
  500
);
```

矢量数据、空间连接、和订单或资产同事务，是它的主场。栅格、拓扑、三维是同一扩展里的进一步能力。路网转向和大规模路径规划由 pgRouting 等扩展承担；城际规模的专用路由引擎仍可能独立部署，那是路由问题，不是「要不要把点面数据搬出 PostGIS」。

许可证是 GPL v2 及以上，和 PostgreSQL 许可证不同。应用通过 SQL 使用 PostGIS 是业界常态；若要把 PostGIS 的代码链进私有进程，才需要单独做法务评审。

## 12.3 对照

| 维度 | PostGIS | 另建一套空间库 |
|------|---------|----------------|
| 矢量事务查询 | 这是默认选择 | 多一份同步 |
| 和业务表 JOIN | 同库 | 应用拼接 |
| 工具生态 | QGIS、GeoServer、GDAL 直接连 | 看该产品的连接器 |
| 大规模栅格分析、专用路网 | 能做一部分 | 计算密集时可以外挂引擎，结果写回 |

## 本章小结

事务型的矢量 GIS 默认就是 PostGIS，不必为了「专业」再引入一个空间数据库。这一行是十行里唯一的「默认留在 PG」。外挂只发生在栅格分析或路网计算已经大到要独立扩缩的时候，空间事实数据仍以 PostGIS 为来源。

# 十三、卡片没画、但拆分时一定会碰到的能力

这些都是内核或 contrib，不需要卡片上的扩展。前面几章的「先留在 PG」经常其实用的是它们。

| 能力 | 做什么 | 和卡片的关系 |
|------|--------|----------------|
| 逻辑复制 | 按表把行变更送到另一个 PG 或逻辑下游 | 搜索、分析、向量拆读路径时的通道。复制的是行，不是索引；下游自己建 BM25 或列存 |
| 声明式分区 | 按时间或列表切表，裁剪、整块丢弃 | Timescale 之前的那一档，见第九章 |
| 生成列 | 把 JSONB 热键、全文向量写成真正的列 | 第五、四章的索引落点。18 起默认是虚拟列：不保存计算值，不能直接建索引，也不进逻辑复制。要索引或要复制，写 `STORED` |
| RLS | 行级策略 | PostgREST 的安全前提，也是多租户应用的库侧底线 |
| `postgres_fdw` | 在一个会话里查另一个 PG | 已经拆成两个集群之后，偶尔的跨库读。它不是分布式事务的替代 |
| 递归 CTE | 有限深度的树和图 | AGE 之前的那一档，见第十章 |
| `pg_trgm` | 模糊和子串 | 中文和 `LIKE '%x%'` 的第一选择，见第四章 |
| 物化视图 | 把贵的读预计算下来 | 连续聚合之前的那一档。刷新期间的锁和新鲜度要设计 |
| 咨询锁、NOTIFY | 单库互斥、叫醒会话 | 第七章。不是 Redis |

**Citus 一类分片不是这张卡片的免费续集。** 它让写可以水平拆开，同时让「一个事务随便 JOIN 全库」不再成立。pgvector、PostGIS、pgmq、AGE 在分片集群上哪些能用，要按扩展逐个核对。单主写不动时，先确认是不是索引、VACUUM 或连接池的问题；分片是数据模型改造，不是一条配置。

# 十四、同一个集群的容量、故障域和拆分顺序

## 14.1 装得上，和跑在一起，是两件事

一个主库同时承担这些工作时，争用是具体的：

| 负载 | 抢什么 |
|------|--------|
| OLTP 事务 | WAL 写入带宽、延迟敏感的缓冲页 |
| pgmq 高周转 | autovacuum、死元组、连接 |
| pg_search 或 GIN 的写入 | 索引维护放大 WAL |
| HNSW 构建 | CPU、I/O、内存，持续时间长 |
| 时序压缩或大范围聚合 | 缓冲池被扫描页冲掉，业务页被迫回磁盘 |
| pg_cron 的长 SQL | 一个后端、一份快照，挡住 VACUUM 回收 |
| PostgREST 的突发读 | 连接数 |

这些不是配置调优能同时最优的。`shared_buffers` 只有一份，检查点只有一套。症状是业务 SQL 的 p99 跟着一次索引构建或一次分析查询一起抖。监控上先看 WAL 速率、复制延迟、死元组、缓冲命中率和连接等待，而不是先换组件。

## 14.2 故障与升级

扩展越多，一次大版本升级要验证的组合越多：PostGIS、pgvector、Timescale、AGE、pg_cron、pgmq、pg_search 并不随 PG 内核一起发布。备库切换时还要记得：UNLOGGED 是空的，pg_cron 在新主上才恢复调度，ParadeDB 社区版的搜索索引可能只在原来的主库上。

备份仍是一份物理备份加 WAL 归档，这是同库的好处。恢复演练要包含「扩展能否在恢复后的版本上 `CREATE EXTENSION`」，不能只验证表数据。

## 14.3 建议的拆分顺序

按「哪一项并不因为同库而获益」来排，而不是按卡片从上到下：

1. **Redis 从第一天就在外面**，只放缓存和锁。应用接受丢缓存和锁过期。
2. **主库留下事务数据：** 业务表、JSONB 长尾、PostGIS、需要原子提交的 pgmq 或发件箱、规模还在内存账以内的 pgvector、短小的 pg_cron 保养任务。
3. **工人在库外**，消费队列，执行 Celery 或工作流。数据库不跑外部副作用。
4. **PostgREST 只挂稳定资源**，和主应用并存，权限按第十一章收紧。
5. **搜索先同库。** 写放大或查询把 OLTP 顶上去之后，用逻辑复制拆出 ParadeDB 或 Elasticsearch。接受搜索的最终一致。
6. **时序先分区。** 压缩和连续聚合有收益再上 Timescale。扫描变成主负载，再导入 ClickHouse。
7. **向量以内存账和 p99 为准**，而不是以条数的整数关口为准。越过就拆到专用实例或专用向量库，id 仍回 PG。
8. **图算法导出子图去算**，关系事实留在 PG。

每一步拆的是读路径或计算，事实来源仍是 PG 里的那次提交。这比「一个集群替换所有中间件」和「第一天就摆上八个数据库」都稳。

## 14.4 一张可以评审的目标形态

```
Redis                缓存、锁、（可选）Streams
应用 + 工人          编排、外部副作用、对外 API
PostgREST            内部稳定资源，RLS

PostgreSQL 主库      业务行、JSONB、PostGIS、发件箱/pgmq、
                     中小规模 pgvector、pg_cron 保养、内核全文

逻辑复制下游         当信号出现时才加：
                     ParadeDB 或 Elasticsearch
                     ClickHouse
                     更大的向量实例
                     Neo4j（算法，不是事实来源）
```

没有信号，就不要预建下游。有信号再拆，发件箱和逻辑复制是事先留好的接缝。

## 本章小结

一个引擎可以覆盖卡片上的大部分「默认同库」区间。一个集群覆盖不了，因为 WAL、缓冲、检查点和崩溃是共享的。Redis 始终在外；搜索、海量分析和大规模向量按信号拆读路径；编排和复杂 API 留在应用。PostGIS 留在主库。
