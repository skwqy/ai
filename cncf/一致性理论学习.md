# 一、总览：三个理论各回答什么问题

## 1.1 一句话定位

一致性理论回答的都是同一个母题——**"多份数据 / 多个操作步骤之间，什么状态才算'对'，以及为了'对'愿意付出什么代价"**，但三个理论的回答范围不同：

| 理论 | 一句话定位 | 回答的尺度 | 诞生的直接动因 |
|------|-----------|-----------|---------------|
| **ACID**（1983） | 单机上，一组操作的**正确性契约** | 一次事务内部（多个操作 × 单份数据） | 数据库崩溃恢复与并发访问的正确性 |
| **CAP**（2000） | 分布式环境下，网络分区发生时**一致性与可用性不可兼得** | 多节点 × 多副本 | 分布式系统设计者需要一条取舍准则 |
| **BASE**（2008） | 放弃强一致后，**工程上可行的折中方法论** | 多节点 × 长时间窗口 | 互联网海量请求下 CP 系统代价过高 |

三者不是并列竞争关系，而是一条演进链：**ACID 保证单机正确 → 数据要复制和分片，撞上网络分区，CAP 指出必须取舍 → 选了 A（可用性）之后，需要一套替代强一致的工程方法论，这就是 BASE → 业务最终仍然需要"既分布式又强一致"，于是 NewSQL 把 ACID 搬回分布式**。

## 1.2 设计哲学：读后面章节前先记住五句话

1. **ACID 里 A、I、D 是手段，C 是目的**。原子性、隔离性、持久性是数据库提供的机制，"一致性"（业务不变量，如转账前后总金额守恒）才是这些东西最终要伺候的对象。
2. **CAP 里的 C ≠ ACID 里的 C**。CAP 的 C 是"线性一致"（读副本时像只有一份数据），ACID 的 C 是"事务前后业务不变量成立"。同名不同义，这是最常见的混淆点（见 3.3 节）。
3. **CAP 不是"三选二"的静态标签，而是分区发生瞬间的局部决策**。同一个系统可以一部分数据偏 C、另一部分偏 A；分区结束后系统可以慢慢收敛（这恰好是 BASE 的舞台）。
4. **BASE 不是不要一致，而是把"一致"从一个瞬时约束放宽为时间窗口内的收敛承诺**——代价是窗口期内的中间状态会暴露给业务。
5. **所有弱一致方案的地基是幂等与对账**。只要消息可能重复投递、补偿可能重复执行，幂等就是绕不开的隐形地基；只要收敛不可控，对账就是最后一道安全网。
6. **BASE 之后的理论在回答三个新问题**：一致能精确刻画到什么程度（一致性谱系）、弱一致能往上修到多强（CRDT/RTC）、免协调的边界在哪（CALM/I-Confluence）——详见第五章。

# 二、ACID：单机事务的正确性契约

## 2.1 从"事务"说起

【场景】银行转账：A 账户扣 100 元，B 账户加 100 元。这是两条 UPDATE。在它们之间，进程可能崩溃、其他会话可能读到半成品数据、断电可能只落了一半磁盘。**事务（Transaction）就是把多条操作捆成一个"要么全发生、要么全不发生"的逻辑单元**。

Jim Gray 在 1981 年《The Transaction Concept》中定义了事务四性质；1983 年 Härder 与 Reuter 在《Principles of Transaction-Oriented Database Recovery》中首次用 "ACID" 概括：

| 性质 | 白话定义 | 保证的是什么 |
|------|---------|-------------|
| **A**tomicity 原子性 | 全做或全不做，没有中间态被外界看到 | "这组操作"作为一个整体生效 |
| **C**onsistency 一致性 | 事务把数据库从一个合法状态带到另一个合法状态（不变量成立） | 数据的"业务正确性" |
| **I**solation 隔离性 | 并发事务互不干扰，仿佛串行执行 | 并发正确性 |
| **D**urability 持久性 | 一旦提交，断电也不丢 | 已承诺结果不反悔 |

**记住这个不等式：A、I、D 是数据库提供的机制（手段），C 是业务声明的不变量（目的）。** 数据库能自动保证的 C 只有它"知道"的不变量——主键、唯一约束、CHECK；"转账总金额守恒"这类业务不变量数据库并不天然知道，靠的是应用层把两条 UPDATE 放进同一个事务里，再借助 A 和 I 保证它们"看起来是原子且互不干扰的"，不变量才不会被并发和崩溃打断。

## 2.2 A —— 原子性：怎么做到"全不做"

【解决什么问题】事务执行到一半崩溃（进程被 kill、断电、死锁回滚），已执行的部分必须被撤销。

【怎么解决】主流方案是 **undo log（回滚日志）**：

- InnoDB 给每条修改记录反向操作日志：INSERT 记反向 DELETE、UPDATE 记旧值，回滚时**反向执行**。
- undo log 同时是 MVCC 的地基：旧版本链条（roll_pointer 串联的版本链）让其他事务能读到"这行改之前的样子"，读回滚前的数据就是多版本快照（见 2.4）。
- 崩溃恢复遵循 ARIES 思想的三步：**分析（确定哪些事务未提交）→ 重做（redo 前滚到崩溃点）→ 撤销（undo 回滚未提交事务）**。

另一个流派是 **shadow paging**：修改写到新页，提交时原子地切换页指针，天然免回滚（SQLite 旧版、System R 用过），但因为破坏写入局部性，主流 OLTP 数据库都选择了 undo log 路线。

一个容易忽略的细节：MySQL 在 **redo log 与 binlog 之间的"内部两阶段提交"**（redo prepare → 写 binlog → redo commit），保证两份日志一致。崩溃恢复时若发现 redo 处于 prepare 而 binlog 完整，则补提交——否则主库与从库会出现分叉。这是"原子提交"思想在单机内部的体现，也是理解 2.6.2 分布式 2PC 的良好热身。

【解决不了什么 / 约束】

- **长事务的 undo 膨胀**：未提交事务的 undo 不能清理，回滚段被撑爆、回滚耗时可能接近正放时间（大事务回滚 1 小时的经典事故）。
- **原子性只覆盖"数据库内的操作"**：事务里调了一个外部 RPC（比如发出短信），数据库回滚了，短信发不回——外部副作用无法被 undo。这正是分布式事务（2.6.2）存在的根本原因。
- DDL 的隐式提交、`autocommit` 模式下每条语句自成一个事务——这些是使用者容易踩的语义边界。

## 2.3 C —— 一致性：目的而非机制

【解决什么问题】并发和崩溃之外，数据本身要满足业务规则：账户余额不能为负、订单总额等于明细之和、外键引用必须存在。

【怎么解决】分层保证：

1. **数据库强制层**：主键、唯一约束、NOT NULL、CHECK、外键、触发器——声明了就一定成立。
2. **事务机制层**：靠 A（不被崩溃打断）+ I（不被并发打断）让"多条语句共同维护的不变量"不被撕裂。转账总金额守恒就是靠"两条 UPDATE 在同一事务"。
3. **应用层**：数据库不知道的不变量（"同一用户不能同时有三个进行中的优惠"）由业务代码与设计保证。

【解决不了什么 / 约束】

- 数据库只保证"你声明过的"不变量，**写错 SQL、约束缺失、应用 bug 导致的不一致它无能为力**。
- 外键在互联网高并发场景因锁传播和运维代价（无法分库分表、级联锁）常被禁用，C 的一部分责任转移回应用层——这是"分布式化让正确性成本上升"的第一个信号。
- **ACID 的 C 与 CAP 的 C 完全不同**（后者是副本间线性一致，见 3.3），阅读任何组件文档时先分辨是哪个 C。

## 2.4 I —— 隔离性：并发正确性与性能的拔河

【解决什么问题】多个事务并发读写同一行/同一批数据时的相互干扰。

并发会产生的经典异常：

| 异常 | 定义 | 一句话例子 |
|------|------|-----------|
| 脏读 | 读到别人未提交的数据 | 读到回滚前的"扣款 100" |
| 不可重复读 | 同一事务内两次读同一行值不同 | 第一次余额 100，第二次被别人改成 80 |
| 幻读 | 同一事务内两次范围查询行数不同 | 第一次 10 条订单，第二次 11 条 |
| 丢失更新 | 两个事务读-改-写互相覆盖 | 两人同时点赞，计数只加了一次 |
| 脏写 | 覆盖了别人未提交的数据 | 回滚时把别人的合法修改一并抹掉 |
| 写偏斜（write skew） | 两个事务读同一批数据、各自写不同行，合起来破坏不变量 | 两位值班医生同时下线，值班表空了 |

【怎么解决】SQL 标准用四个隔离级别递进消除异常（详见 `D:\ai\db\DB事务隔离级别.md`）：

```
读未提交 RU ── 读已提交 RC ── 可重复读 RR ── 可串行化 SER
  防脏写        +防脏读        +防不可重复读     +防幻读/写偏斜
```

实现上有两大流派：

1. **悲观：两阶段锁（2PL）**。读加共享锁、写加排他锁，事务结束才放锁。可串行化成立，但死锁、锁等待、吞吐下降。
2. **乐观：MVCC（多版本并发控制）**。写不阻塞读（读旧版本快照），代价是维护版本链。**InnoDB、PostgreSQL、Oracle 全是 MVCC**。

InnoDB 的实现要点：

- 每行隐藏字段 `trx_id`（最后修改者）+ `roll_pointer`（指向 undo 中的旧版本），形成版本链。
- 读时生成 **ReadView**（活跃事务列表 + 高低水位），沿版本链找第一个"对自己可见"的版本。RC 级别每条语句新建 ReadView；RR 级别事务首次查询创建并复用到结束——这就是 RR 能"可重复读"的原因。
- MySQL 的 RR 用 **next-key lock（记录锁 + 间隙锁）**阻止别人在范围内插入，防止**当前读**（`select ... for update`、UPDATE）下的幻读；快照读则由固定快照天然免疫。但快照读与当前读混用时仍可能出现"读到自己快照里没有的行"，这是"MySQL RR 没完全防住幻读"争论的技术根源。
- PostgreSQL 的 RR 实际是 **快照隔离 SI**：能防幻读（快照固定），但**防不住写偏斜**；其可串行化用 **SSI**（9.1+，基于"危险结构"的读写依赖环检测，代价是冲突时 abort 率上升）。

【解决不了什么 / 约束】

- **隔离级别与性能是直接的交换关系**：Serializable 在高并发下吞吐可能跌一个数量级；全链路 RC 甚至 RU 是互联网大厂常见选择（用业务幂等与唯一约束兜底）。
- **MVCC 只解决读-写冲突，写-写冲突仍靠锁**。热点行（秒杀扣库存）依然要排队。
- **单机隔离性在分库分表后失效**：跨库的两条 UPDATE 没有共同的锁管理器和 MVCC 时钟，"同一个事务"不存在了——这直接引出 2.6.2。
- 隔离性极弱的事务方案（SAGA 缺隔离、Seata AT 默认读未提交）需要业务通过"资源正交设计 + 状态机"补偿，见 2.6.2。

## 2.5 D —— 持久性：提交之后断电也不丢

【解决什么问题】事务已对客户端返回"提交成功"，随后进程崩溃/断电，内存中的脏页丢失——承诺过的数据必须还在。

【怎么解决】**WAL（Write-Ahead Logging，先写日志后写数据）**：

1. 修改先追加写入 **redo log**（物理页级日志，顺序写），fsync 落盘，然后才允许把脏页异步刷到数据文件（随机写）。
2. 崩溃恢复时重放 redo 即可重建所有已提交修改——用"顺序写小日志"换取"随机写大页"的性能与顺序性保证。
3. **doublewrite buffer** 防止"部分页写入"：数据页 16KB 大于磁盘原子写单位（常为 4KB），断电可能写坏半页，而 redo 重放依赖页完整。先写 doublewrite 副本再写正式页，恢复时用副本还原。
4. **组提交（group commit）**把并发事务的 fsync 合并，摊薄每次刷盘的固定成本。

MySQL 两份日志的持久化旋钮（所谓"双 1 配置"）：

| 参数 | 取值 | 语义 |
|------|------|------|
| `innodb_flush_log_at_trx_commit` | 1（默认） | 每次提交 fsync redo；**0** 每秒刷（崩进程丢 1 秒）；**2** 提交时只写 OS 缓存（崩进程不丢、断电丢 1 秒） |
| `sync_binlog` | 1 | 每次提交 fsync binlog；**0** 由 OS 决定；**N** 攒 N 个事务刷一次 |

双 1 保证单机 RPO=0（不丢已提交事务），代价是写入吞吐受磁盘 fsync 能力封顶；设为 0/2 换吞吐，接受崩溃窗口丢数据——**这是 D 上的 C/A 取舍，本质上是 CAP 思想在单机持久性上的预演**。

【解决不了什么 / 约束】

- **单机 D ≠ 分布式 D**。主从异步复制下，主库提交（fsync 完成）后还没来得及传给从库就宕机，提升从库为主库，已确认的事务丢失。要 RPO=0 需要半同步复制（lossless semi-sync）或共识协议（MGR、TiDB 的 Raft）——"持久"的边界从磁盘扩展到了多数派副本。
- **持久化与审计不是一回事**：fsync 保证"数据在"，不保证"没被后续合法写覆盖"。
- fsync 是吞吐天花板：大量小事务场景，NVDMe SSD 也扛不住每事务一次 fsync 的放大，组提交与批量是唯一解药。

## 2.6 ACID 的产品版图

### 2.6.1 单机关系型数据库

**MySQL / InnoDB**

- 【解决什么问题】通用 OLTP：高并发读写、崩溃恢复、主从复制生态。
- 【怎么解决】undo（A）+ MVCC/next-key lock（I）+ redo/WAL/doublewrite（D）+ 约束（C），如上四节所述。
- 【解决不了什么 / 约束】单机容量与写吞吐上限（一般几 TB、万级 TPS 量级就要规划分库分表）；主从延迟期间读写不一致；跨库无事务；DDL 变更代价。

**PostgreSQL**

- 【解决什么问题】同上，另加更丰富的类型系统与扩展生态。
- 【怎么解决】xmin/xmax 多版本 + WAL；SSI 提供真可串行化。
- 【解决不了什么 / 约束】**版本垃圾回收（vacuum）是终身运维课题**：长事务会阻碍死元组回收，表膨胀、事务 ID 回卷（wraparound）是经典事故；单机边界同 MySQL。

**Oracle**

- 【解决什么问题】金融级 OLTP + 极端可用性（RAC 共享磁盘多活）。
- 【怎么解决】undo/redo 体系同源（InnoDB 的设计大量参考 Oracle）；RAC 多节点共享存储 + 分布式锁管理器。
- 【解决不了什么 / 约束】商业许可成本；RAC 扩展上限受共享存储与锁管理器制约，Write 扩展性不如 share-nothing 架构。

### 2.6.2 分布式事务全家桶：把"原子性"跨进程搬

【场景】微服务化后，"下单"要写订单库 + 调库存服务 + 调优惠券服务；分库分表后，一次事务的写落在不同 MySQL 实例。**单机的 undo log 管不到别的进程**，需要分布式事务协议。

#### （1）2PC / XA —— 两阶段提交

```
协调者(TC)                    参与者A(RM)         参与者B(RM)
    │── 阶段1: prepare ──────→│ 写redo/undo,锁住资源│
    │                         │ 但不提交,回复OK      │
    │── 阶段1: prepare ───────────────────────────→│ 同上
    │◄──── 都OK ──────────────┼────────────────────┤
    │  决议: commit (写入日志)  │
    │── 阶段2: commit ───────→│ 提交,释放锁          │
    │── 阶段2: commit ────────────────────────────→│ 提交
```

- 【解决什么问题】**跨多个资源（数据库/消息代理）的原子提交**：要么所有参与者提交，要么全部回滚。XA 是 2PC 的工业标准接口（`XA_START/PREPARE/COMMIT`）。
- 【怎么解决】两轮握手：先投票（参与者把修改持久化为"可提交可回滚"的悬置态并锁资源）、再决议（协调者写日志后统一提交/回滚）。协调者写决议日志这一步是关键——它宕机恢复后仍能凭日志继续驱动第二阶段。
- 【解决不了什么 / 约束】三大经典缺陷：
  1. **同步阻塞**：prepare 之后到 commit 之前，参与者的行锁一直持有，其他事务排队，吞吐急剧下降，还放大死锁概率。
  2. **协调者单点**：协调者在阶段 2 前宕机，参与者全部悬置（MySQL XA 里是"悬挂事务"，需要 `XA RECOVER` 人工处理）。
  3. **第二阶段部分失败 → 数据不一致**：commit 消息只送达部分参与者（网络分区），一部分提交了一部分没提交，且没有内建的修复机制，需要人工对账。
  - 结论：**XA 适合并发低、一致性要求极高、能接受慢的场景**（跨行转账网关、传统 ERP）；互联网高并发路径上通常绕开它。

#### （2）3PC —— 三阶段提交（理论与教训）

- 【解决什么问题】2PC 的阻塞问题：参与者悬置等不到协调者。
- 【怎么解决】拆成 CanCommit / PreCommit / DoCommit，并给参与者加**超时**：PreCommit 后超时未收到 DoCommit，参与者自行提交（因为 PreCommit 意味着多数已同意）。
- 【解决不了什么 / 约束】**网络分区下仍可能不一致**（一部分收到 PreCommit 超时自行提交，另一部分中止），且多一轮往返延迟更高。**实践中几乎没有生产级 3PC 实现**，它的价值是教学：说明"靠超时猜决议"在分区下不可靠，最终都要靠共识协议（Paxos/Raft）来选举协调者。

#### （3）TCC —— 业务层的两阶段

```
Try（资源预留）              Confirm（确认扣减）        Cancel（释放预留）
冻结账户100元          →     扣减冻结的100元       →    解冻100元
库存预扣到"锁定"             扣减锁定库存              释放锁定库存
```

- 【解决什么问题】不想用数据库 XA（性能差），又需要"跨服务的原子性"。把每个参与方的接口拆成 Try/Confirm/Cancel 三个业务方法，由事务管理器（如 Seata TC）统一调度：全部 Try 成功 → 逐个 Confirm；任一失败 → 逐个 Cancel。
- 【怎么解决】**用业务语义实现"预留-确认"**，第一阶段的锁变成了业务上的"冻结额度/锁定库存"，不长时间占用数据库锁。
- 【解决不了什么 / 约束】
  1. **业务侵入极大**：每个参与方要实现三个接口，且 Confirm/Cancel 必须幂等（重试）。
  2. **三大经典坑**：**空回滚**（Try 没到达，Cancel 先到，必须识别并直接返回成功）；**防悬挂**（Cancel 先执行完，迟到的 Try 才到，会凭空预留资源——Try 要检查"是否已被回滚"）；**幂等**（Confirm/Cancel 都可能被重试多次）。
  3. 隔离性弱：Try 与 Confirm 之间，预留资源对其他事务"部分可见"，需要业务设计规避。
  - 代表实现：Seata TCC、ByteTCC、Hmily。适合资金核心链路（性能 + 强一致语义可控），不适合长流程。

#### （4）SAGA —— 长事务拆分 + 补偿

- 【解决什么问题】跨很多服务、耗时长的事务（旅行预订：机票 + 酒店 + 租车），2PC 锁资源数小时不可接受。
- 【怎么解决】Garcia-Molina & Salem 1987：把长事务拆成一串**本地事务** T1→T2→…→Tn，每个 Ti 配一个**补偿事务** Ci（语义上的撤销：订了机票再退票）。正向全部成功则完成；中途失败则反向执行补偿 Cn→…→C1。
- 【解决不了什么 / 约束】**SAGA 没有隔离性**：
  - 别的事务能看到中间态（机票订了酒店还没订），可能基于中间态做错误决策（语义锁、版本号可缓解）；
  - 补偿失败（退款时账户被冻结）没有自动解法，只能重试 + 人工差错池；
  - 补偿是"语义撤销"而非物理回滚——退了票，座位号可能已不是原来的。
  - 编排式（Seata SAGA 状态机、Temporal/Cadence 工作流引擎）与协同式（服务间事件互订阅）两种驱动方式，前者可控性好、后者耦合低但逻辑分散。

#### （5）本地消息表与事务消息 —— 用消息达成最终一致

- 【解决什么问题】"本地数据库事务"与"发消息"这两步无法原子完成：先提交再发消息，发消息失败则两边不一致；先发消息再提交，提交失败则消息多了。
- 【怎么解决】
  - **本地消息表（eBay 模式）**：业务数据与"待发消息"在**同一个本地事务**里落库；后台任务/Canal 扫描消息表外发，发送成功标记完成。靠"同库同事务"拿到原子性。
  - **RocketMQ 事务消息**：先发**半消息**（对消费者不可见）→ 执行本地事务 → 提交/回滚半消息；Broker 长时间收不到确认则**回查**生产者。等价于把"消息表"托管给 Broker。
- 【解决不了什么 / 约束】只保证"**本地事务 + 消息可靠发出**"，**不保证下游消费成功**——消费失败要靠 MQ 重试、死信队列、告警与对账兜底；消费端必须幂等（重复投递是常态而非异常）。

#### （6）Seata AT 模式 —— 面向 Spring 用户的"自动补偿"

- 【解决什么问题】开发者想要 `@Transactional` 般的心智模型，又跨微服务/跨库。
- 【怎么解决】一阶段：业务 SQL 执行时，框架自动解析 SQL 生成**前后镜像（before/after image）存入 undo_log 表**并与业务数据同库提交（本地事务即刻提交，不长时间持锁）；二阶段：全局提交则异步删 undo_log，全局回滚则按 after 镜像校验后用 before 镜像生成反向 SQL 补偿。TC（事务协调器）维护**全局行锁**防止两个全局事务写同一行造成"回滚覆盖"（脏写）。
- 【解决不了什么 / 约束】
  - **默认全局隔离级别是读未提交**（一阶段已提交，别的全局事务能读到中间态）；要读已提交需 `@GlobalLock` + `select for update`，有代价。
  - 反向 SQL 依赖镜像校验，若期间数据被绕过 Seata 的方式修改，回滚失败转人工。
  - 全局锁引入跨服务热点串行化，高并发热点行场景退化明显。
  - 与 TCC/SAGA 的取舍：AT 省事但约束多、TCC 侵入但语义强、SAGA 适合长流程。

#### 分布式事务方案横向对比

| 方案 | 一致性 | 隔离性 | 业务侵入 | 性能 | 适用场景 |
|------|--------|--------|---------|------|---------|
| XA/2PC | 强一致 | 高（锁） | 低（驱动层） | 很差（同步阻塞） | 低并发、极高一致性要求 |
| TCC | 最终一致（可控到很强） | 中（资源预留） | **极高**（3 接口 + 3 大坑） | 好 | 资金核心链路 |
| SAGA | 最终一致 | **无**（需语义锁） | 中（写补偿） | 好 | 长流程、跨多服务 |
| 本地消息表/事务消息 | 最终一致 | 无 | 低-中（+消费幂等） | 很好 | 异步解耦型业务（通知、积分、发货） |
| Seata AT | 最终一致 | 弱（默认 RU） | **极低** | 中（全局锁） | Spring 技术栈、中低并发 |

### 2.6.3 NewSQL —— 把 ACID 搬回分布式

【场景】分库分表中间件（ShardingSphere 等）解决了容量，但**跨分片事务、跨分片 join、全局二级索引、在线扩容再平衡**四大问题都无法优雅解决。NewSQL 的主张：**不牺牲 ACID 与 SQL，用新架构获得水平扩展**。

**TiDB**

- 【怎么解决】三层拆分：TiKV（存储，按 Region 约 96MB 切片，**每个 Region 一个 Raft 组**，默认 3 副本，写要过半确认）+ PD（全局时钟 TSO + 调度）+ TiDB（无状态 SQL 层）。事务采用 **Percolator 衍生的两阶段提交**：Prewrite 打主锁/从锁（基于 TSO 时间戳排序），Commit 二次提交；冲突处理有乐观（重试）与悲观（行锁，3.0+ 默认）两种模式；隔离级别为快照隔离（对外呈现可重复读语义）。
- 【解决不了什么 / 约束】**跨节点事务的延迟与吞吐代价**：一次跨 Region 事务 = 2PC × Raft 过半确认 × TSO 取时钟，写入吞吐显著低于单机 MySQL（没有热点时）；小表高频事务场景 NewSQL 是杀鸡用牛刀；运维复杂度（PD/TiKV/TiDB 至少 3 类组件）远高于单库。

**Google Spanner**

- 【怎么解决】数据按 tablet 分片进 Paxos 组；跨组事务用 2PC；**TrueTime API**（GPS + 原子钟混合授时，误差 ε 通常 <10ms）提交后**等待 ε**（commit-wait），换来**外部一致性**（严格可串行化 + 线性一致）——用硬件把"时钟不确定"这个分布式根本难题物理消除了。
- 【解决不了什么 / 约束】依赖专用硬件（GPS 接收器 + 原子钟），一般公司无法复制；commit-wait 增加写延迟。开源界的替代思路：CockroachDB 用混合逻辑时钟 HLC（软件方案，牺牲严格外部一致），OceanBase 用中心化全局时间戳服务（GTS，思路接近 PD/TSO）。

**CockroachDB / OceanBase**

- 同属"分片 + 共识复制 + 分布式 2PC + 时间戳排序"路线，差异在时钟来源与工程取舍：CockroachDB 默认可串行化（2.0+），跨地域部署延迟敏感；OceanBase 主打金融强一致 + 同城多活（Paxos 多副本）。

## 2.7 ACID 解决不了什么（总述）

1. **单机容量与吞吐天花板**：数据量、TPS、连接数增长到一定规模，垂直扩容失效 → 分库分表 / NewSQL。
2. **跨进程的原子性**：事务内一旦有外部副作用（RPC、发消息、发短信），数据库回滚管不到 → 分布式事务全家桶（且没有一个方案同时拿到"强一致 + 高性能 + 零侵入"）。
3. **可用性与延迟代价**：强一致机制（锁、2PC、多数派确认、commit-wait）都会降低吞吐、提高延迟、缩小可用窗口。互联网海量请求下，全链路强一致在工程上不可行 → CAP/BASE 登场。
4. **单机 D 在复制环境下的边界模糊**：异步复制的主库宕机可能丢已提交事务，"持久"要重新定义（RPO 目标 + 半同步/共识）。

## 2.8 本章小结

- ACID 是**单机事务的正确性契约**：A 靠 undo log 反向补偿，I 靠锁 + MVCC 分级提供，D 靠 WAL + fsync（+doublewrite），C 是 AID 共同伺候的业务不变量。
- 每个性质的实现都有性能旋钮（隔离级别、双 1 配置、undo/vacuum），**正确性与性能是显式交换的**。
- 分布式事务的本质难题：**没有跨进程的共享 undo log 与锁管理器**。2PC 用协议换原子性（阻塞 + 单点 + 不一致窗口），TCC 用业务预留换性能（侵入），SAGA 用补偿换长事务（丢隔离），消息用最终一致换吞吐（需幂等）。
- NewSQL 用"分片 + Raft + 分布式 2PC + 统一时钟"把 ACID 搬回分布式，代价是硬件/运维复杂度与跨节点事务延迟。

# 三、CAP：分区发生时的取舍定理

## 3.1 从一个场景引入

主从异步复制的 MySQL：客户端向主库写入 `x=1` 并确认，此刻主从之间网络断了。此时一个客户端连到**从库**读 `x`：

- 若从库返回旧值 `0` → 系统仍然可用，但读到了旧数据（牺牲 C）。
- 若从库拒绝回答"我可能与主库不一致，无法响应" → 一致保住了，但系统部分不可用（牺牲 A）。

**在分区存在的前提下，这个读请求只有这两种结局，没有第三种。** 这就是 CAP 要形式化的东西。

## 3.2 形式定义（Gilbert & Lynch, 2002）

| 字母 | 定义 | 关键限定词 |
|------|------|-----------|
| **C**onsistency | 一致性：对所有节点，一次读要么读到**最近一次完成写入的值**，要么读到更新的值（即**线性一致**，等价于"只有一份数据"的假象） | 是**副本间**的一致，与 ACID 的 C 无关 |
| **A**vailability | 可用性：每个**非故障节点**收到的请求，都必须在**有限时间内**收到**非错误的响应** | 响应允许包含旧数据；"有限时间"不允许无限等待 |
| **P**artition Tolerance | 分区容忍：网络可能任意丢包/延迟/分区（节点间消息不可达），系统仍要继续运行 | 不是"容忍并恢复"，而是"分区发生时系统照常对外工作" |

**证明思路（反例构造）**：设系统由 G1、G2 两节点组成，网络分区使二者不可达。客户端在 G1 上写 `x=1` 并确认；随后客户端向 G2 发起读请求。若要求 C，G2 必须返回 `1`，但它与 G1 通信中断、拿不到新值，只能返回旧值 `0` 或报错——前者违反 C，后者违反 A。**P 在分布式系统中不可选（网络故障必然发生），所以分区瞬间 C 与 A 必舍其一。** 注意定理的严谨性：Gilbert & Lynch 在同步、部分同步、异步三种时间模型下分别证明了该结论，2002 年论文是 CAP 从"经验法则"变成"定理"的关键。

## 3.3 三大常见误解澄清（本节是全章最重要的一节）

**误解一：CAP 是"三选二"，所以存在 CA 系统。**
P 不是选项——分布式系统中网络故障是必然事件，"不容忍分区"等价于"分区时系统整体崩溃"。所以分布式系统只剩 CP 或 AP。**确实存在 CA 系统：单机系统**（单实例 MySQL、单机文件系统）——没有副本间网络，自然无分区。但这不是"选了 CA"，而是"根本没有 P 这个维度"。

**误解二：系统要么 CP 要么 AP，贴上标签一劳永逸。**
Brewer 本人在 2012 年《CAP Twelve Years Later》中修正（详见 5.1.2）：**取舍发生在"分区发生的那一瞬间"，且可以按数据、按请求粒度决策**。同一系统内：库存数据偏 CP，评论数据偏 AP；分区恢复后，系统应当收敛副本并补偿这段时间的损失——CP/AP 不是静态标签，而是策略组合。另外 A 也允许"部分可用"：拒绝 1% 写入保住 99% 读取，也算一种 AP 策略。

**误解三：CAP 的 C 是 ACID 的 C、A 是"100% 可用"。**
- CAP 的 C = 线性一致（单对象、副本间），与事务不变量无关；一个线性一致的集群照样可以存入业务错误的数据。
- CAP 的 A 只约束"非故障节点必须响应"，不承诺响应时间上限的体验标准，更不是 SLA 里的 99.99%。

**补充工具：PACELC（Abadi, 2012）**——CAP 只谈了分区时（if Partition），没谈平时（理论定位与四象限分类详见 5.1.4）：

```
if Partition  →  选 A（可用）还是 C（一致）
else（平时）   →  选 L（低延迟）还是 C（一致）
```

平时为了"所有读都线性一致"，读请求也要走主/多数派，延迟必然高于读本地副本。**Dynamo/Cassandra 属于 PA/EL（分区偏可用、平时偏低延迟）；ZooKeeper/etcd 属于 PC/EC（两者都偏一致）**。PACELC 解释了"为什么没有分区时也不能随便把一致开到最高"——延迟是平时的代价。

## 3.4 CP 站位的组件逐一分析

### ZooKeeper（ZAB 协议）

- 【解决什么问题】分布式协调原语：配置管理、分布式锁、选主、命名。这些场景**宁可不可用也不能读到错乱数据**（两个客户端同时认为自己持有锁是灾难）。
- 【怎么解决】自研 **ZAB（ZooKeeper Atomic Broadcast）**协议：崩溃恢复模式（选主 + 数据同步，zxid = epoch+计数器 保证新主不丢已提交提案、不复活旧主）+ 消息广播模式（类 2PC 但只需**过半 ACK** 即提交，非全量确认）。写请求全部转发给 Leader，过半确认后生效。
- 【读语义的微妙之处】读请求由**各节点本地内存数据**直接应答（不走过半），保证**同一客户端的顺序一致（FIFO）**，但**可能读到落后于最新的值**——所以严格说 ZooKeeper 写线性一致、读顺序一致；客户端可用 `sync()` 强制一次线性一致读。
- 【解决不了什么 / 约束】
  1. **写吞吐受单 Leader + 过半确认封顶**（万级 ops 量级），不适合高频写场景；
  2. **数据规模小**：全量树在内存，单 znode 默认上限 1MB，集群元数据量级；
  3. 分区时**少数派侧完全不可服务**（选举态），牺牲可用性；
  4. Leader 选举/GC 停顿引发**抖动风暴**；watch 是一次性触发（3.6+ 才有 persistent watch），客户端要自己重注册；
  5. 只提供原始原语（znode + watch），业务语义要自己搭。
  - 用途定位：**元数据协调**，不是数据存储，更不是消息队列（老话说"用 ZK 当队列是错误用法"）。

### etcd（Raft 协议）

- 【解决什么问题】与 ZooKeeper 同域（协调、配置、选主），Kubernetes 的事实大脑。
- 【怎么解决】**Raft**（Leader 选举 + 日志复制 + 成员变更，以"可理解性"为设计目标），配合 **MVCC 多版本**（全局 revision 单调递增）与 **watch**（从任意历史 revision 回放）。读默认**线性一致**（ReadIndex 机制：向 Leader 确认最新提交位点并等待本地应用追平，无需写日志），可选 serializable 模式换低延迟。Lease（租约）+ KeepAlive 实现服务健康检查。
- 【解决不了什么 / 约束】数据规模与写吞吐同样有硬顶：默认存储配额 2GB（建议 ≤8GB）、单 value 默认 1.5MB、写性能万级 ops 量级；**当数据库用是错误姿势**；大规模 watch 事件会放大内存压力（K8s 社区的经典调优课题）。

### Consul（Raft + Gossip）

- 【解决什么问题】服务发现 + KV + 健康检查一体化，多数据中心原生。
- 【怎么解决】Server 节点跑 Raft 保 KV 一致；Client Agent 走 **LAN/WAN Gossip 池**传播成员与健康状态（这部分是 AP 的、最终一致的）。KV 读默认有 **leader lease 保护**（Server 若在租约内未与多数派联系则拒绝服务，防止"失联 Leader 读"），也提供显式 stale 模式换可用性/性能。
- 【解决不了什么 / 约束】强一致的 KV 吞吐同样受限；服务健康状态本身是 AP 数据（gossip 传播有延迟），消费方要容忍短暂脏列表；多数据中心一致性只能最终一致（WAN 分区不阻塞）。

### HBase

- 【解决什么问题】海量稀疏表的强一致行级读写（Bigtable 开源实现）。
- 【怎么解决】行只归属唯一 Region（单 RegionServer），**单行读写天然线性一致**；RegionServer 故障后该 Region 上所有请求不可用，直到 WAL 切分重放、Region 迁移完成（分钟级）；ZooKeeper 负责元数据定位与故障感知。
- 【解决不了什么 / 约束】**只有单行原子性，无跨行/跨表 ACID**（Phoenix 的 Tephra 补齐但代价大）；宕机恢复分钟级可用性损失（典型 CP 行为）；热点问题（单调 rowkey 打到同一 Region）；Compaction 抖动。

### MongoDB（majority 模式）

- 【解决什么问题】文档型 OLTP，希望"默认好用"又能在需要时拿到强一致。
- 【怎么解决】副本集选举（类 Raft）。**一致性由 readConcern/writeConcern 显式声明**：`w:1`（主确认即返回）偏 AP、可能回滚；`w:majority` + `readConcern:majority` 提供多数派已提交语义（5.0+ 默认 w:majority）；`readConcern:linearizable` 对单文档读提供线性一致（代价是必须配 w:majority 且延迟上升）。因果一致会话（causal consistency）提供"读己之写"等保证。
- 【解决不了什么 / 约束】`w:1` 写入在故障切换时可能**回滚**（已确认数据消失，旧版本还因此出过著名事故）；linearizable 读延迟高；跨文档无原生 ACID（4.0+ 多文档事务补齐但性能代价显著）。

### Kafka（配置相关的微妙站位）

- 【解决什么问题】高吞吐分布式日志，日志不允许"悄悄分叉"（同一 offset 读到不同内容是致命的）。
- 【怎么解决】分区多副本，Leader 维护 **ISR（与 Leader 保持同步的副本集合）**；生产端 `acks=all` + Broker 端 `min.insync.replicas≥2` + `unclean.leader.election.enable=false`（0.11+ 默认）三件套：**ISR 缩水到阈值以下时，写入直接失败（NotEnoughReplicas）——用可用性换一致性**；消费只暴露高水位（HW）之前的数据；Leader Epoch 机制防止日志截断错乱；0.11+ 幂等生产者 + 事务实现流处理 exactly-once。
- 【解决不了什么 / 约束】这套配置下是"分区级 CP"，但**不是线性一致读**（消费者读到的 HW 有滞后）；`acks=1` 时立刻退化成 AP（Leader 确认即返回，宕机丢数据）；跨分区的全局顺序不存在（只有分区内有序）。**"Kafka 是 CP 还是 AP"的正确答案：取决于配置，且任何配置下都不是线性一致系统**（详见 7.5）。

### TiDB / Spanner / OceanBase（NewSQL，CP 的完整形态）

- 见 2.6.3。它们是"分区时选 C"并且用共识协议把"分区恢复后的收敛"也做强的系统：Raft/Paxos 多数派写入保证已提交数据不丢，2PC 保证跨分片原子性。代价：跨节点事务延迟、部署运维复杂度。

### CP 组件速查表

| 组件 | 共识协议 | 写语义 | 读语义 | 数据规模定位 |
|------|---------|--------|--------|-------------|
| ZooKeeper | ZAB | 线性一致（过半） | 顺序一致（sync() 可线性） | 元数据（内存级） |
| etcd | Raft | 线性一致 | 默认线性（ReadIndex），可选 serializable | 元数据（≤8GB） |
| Consul | Raft + Gossip | 线性一致（KV） | 默认带 lease 保护，可选 stale | 服务目录 + 小 KV |
| HBase | 依赖 ZK + HDFS | 单行线性一致 | 单行线性一致 | PB 级大表 |
| MongoDB | 类 Raft | w:majority 多数派 | 可配置到 linearizable | 通用文档存储 |
| TiDB | Raft（per Region）+ 2PC | 快照隔离/可串行化 | 快照读 + 可强一致读 | PB 级 OLTP |
| Spanner | Paxos + 2PC + TrueTime | 外部一致 | 线性一致 | 全球级 |

## 3.5 AP 站位的组件逐一分析

### Eureka

- 【解决什么问题】AWS 云环境的服务注册中心。Netflix 的痛点：**机房网络抖动是常态，注册中心一旦因分区拒绝服务，全部服务发现瘫痪——可用性比实时准确更重要**。
- 【怎么解决】**对等（peer-to-peer）复制**：每个节点都是平等的，注册信息异步复制到所有节点，任何节点都可受理注册/查询；**自我保护机制**：一分钟内心跳续约数低于阈值（默认期望值的 85%）时，判定"可能是网络分区而非大规模实例下线"，**停止剔除过期实例**——宁可保留可能已死的注册信息，也不清空服务列表。
- 【解决不了什么 / 约束】注册列表是**最终一致的脏数据**：刚下线的实例还挂着（调它要靠客户端重试/熔断兜底）、刚上线的实例要等复制传播；30 秒定时拉取（无推送）感知慢；无跨机房强一致语义；Eureka 2.x 已停止开发，社区基本停更（新项目多选 Nacos）。

### Cassandra / Dynamo（可调一致 + 反熵体系）

- 【解决什么问题】海量写入、多机房部署、**任何单点/单机房故障都不能停止服务**（Amazon 购物车场景：购物车丢了比暂时读到旧购物车严重得多）。
- 【怎么解决】Dynamo 论文（SOSP 2007）的完整工具箱，Cassandra 取其存储路线（Dynamo 复制 + Bigtable LSM 存储）：
  1. **一致性哈希 + 虚拟节点**：数据与负载均匀分布，节点增减只影响相邻区段；
  2. **可调一致性**：每读写声明级别（ONE/QUORUM/LOCAL_QUORUM/ALL），**R + W > N 时读写副本集合必然相交，实现"仲裁读"的强一致语义**；N=3、W=1、R=1 是典型 AP 配置（单副本确认即返回，靠异步修复收敛）；
  3. **hinted handoff**：目标节点宕机时，写请求暂存在别的节点，恢复后补投；
  4. **读修复（read repair）**：读时发现副本不一致，顺手修复；
  5. **反熵修复（anti-entropy repair）**：定期用 **Merkle 树**快速找出区间差异并修复（nodetool repair）；
  6. **向量时钟/时间戳**做并发写冲突仲裁（Dynamo 用向量时钟交业务裁决；Cassandra 用时间戳 LWW）。
- 【解决不了什么 / 约束】
  1. **没有跨节点事务**：只有单分区原子性；需要 CAS 时用基于 Paxos 的 LWT（轻量级事务），要 4 轮往返，代价巨大，不能滥用；
  2. **LWW 静默丢更新**：时钟偏差下"后写"可能覆盖"先写"的语义不一致；
  3. 二级索引弱、不支持任意关联查询——**数据模型必须按查询模式反范式设计**（query-first）；
  4. Compaction 写放大与抖动；repair 是必须排期的运维任务（不做 repair 的 Cassandra 集群迟早出数据不一致事故）。

### Redis（主从 + 哨兵/集群）

- 【解决什么问题】内存级低延迟读写（缓存、计数器、分布式锁载体）。
- 【怎么解决】主从**异步复制**（repl-backlog 增量同步）；Sentinel 过半投票做客观下线与故障转移；Cluster 分 16384 slot 分片。**异步复制意味着：主库确认的写入尚未传给从库时宕机，提升从库后这部分写入丢失**——Redis 是"最终一致、可丢最近写入"的典型 AP 系统。
- 【解决不了什么 / 约束】
  1. **默认不保证 D 与 C**：持久化（RDB 快照/AOF fsync 策略）与复制都是异步窗口；
  2. 缓解手段：`min-replicas-to-write` + `min-replicas-max-lag`（从库不够或延迟超限就拒绝写，向 CP 移动）——但本质仍是异步，只能缩小窗口不能归零；
  3. Cluster 模式多 key 操作限于同一 slot（hash tag 解决但引入倾斜）；分布式锁在故障切换时有过期锁复活风险（ fencing token 才是正解）；
  4. **把 Redis 当唯一存储用是危险设计**，核心数据必须有可靠的持久化/复制策略或以 DB 为准。

### Nacos（AP/CP 可切换的教科书案例）

- 【解决什么问题】注册中心 + 配置中心二合一，不同数据诉求不同：**临时服务实例**要高可用（实例闪断不该被立刻摘除），**配置/持久实例**要强一致。
- 【怎么解决】**临时实例走 Distro 协议（AP）**：内存存储、异步对等复制、不持久化，分区时各自可用；**持久实例与配置走 JRaft（CP）**：过半确认。同一个产品里按数据类型分别落位 CP/AP——正是"CAP 取舍按数据粒度决策"（3.3 误解二）的工业实证。
- 【解决不了什么 / 约束】两套协议并存增加理解成本；AP 侧注册数据同样要客户端容错兜底；配置的监听延迟与版本一致性要额外校验。

### AP 组件速查表

| 组件 | 复制方式 | 分区时行为 | 一致性保证 | 典型用途 |
|------|---------|-----------|-----------|---------|
| Eureka | 对等异步复制 + 自我保护 | 继续提供（脏）列表 | 最终一致 | 服务注册中心 |
| Cassandra | 一致性哈希多副本 + 反熵 | 多数副本活着即可服务 | 可调（R+W>N 可强，默认弱） | 海量写入、多机房 |
| Redis | 主从异步复制 | 从库继续读（可能旧）， failover 可能丢写 | 最终一致（可丢最近写） | 缓存/低延迟存储 |
| Nacos 临时实例 | Distro 异步复制 | 继续服务 | 最终一致 | 注册中心 |
| Kafka（acks=1） | 异步（Leader 确认） | 继续服务，可能丢消息 | 最终一致 | 非关键日志流 |

## 3.6 CAP 解决不了什么（总述）

1. **只管"分区瞬间"的一个决策**，不管分区恢复后副本如何收敛——反熵、读修复、补偿这些工程活是 BASE/实现层的事。
2. **不管延迟**——PACELC 补充了"平时一致性 vs 延迟"的取舍，而这在无故障的 99.9% 时间里才是主要矛盾。
3. **只覆盖网络分区这一种故障**。节点宕机、磁盘损坏、时钟漂移、GC 停顿（进程内暂停造成"事实分区"）都可能触发同样的 C/A 困境，但不在 CAP 的 P 范围内。实践选型时问"Jepsen 测试发现了什么"比问"它自称 CP 还是 AP"更有信息量。
4. **不管业务正确性**。线性一致的集群照样能存入业务错误的数据；ACID 的 C（不变量）在分布式下如何维护，CAP 不回答。
5. **不适用于无副本场景**（单机、无复制代理），它们天然无分区问题。
6. **粒度太粗的"CP/AP 标签"会误导**：按数据/请求粒度的策略组合才是真实系统的样子（Nacos 双协议、ZooKeeper 读顺序一致、Kafka 配置相关）。

## 3.7 本章小结

- CAP 的形式内核：**分区发生时，线性一致与完全可用互斥**（Gilbert & Lynch 2002）；分布式系统中 P 不可选，故只有 CP/AP。
- 三个澄清：C 指线性一致（≠ACID 的 C）；取舍是分区瞬间的、可按数据粒度的局部决策（≠静态三选二标签）；平时还有延迟与一致的取舍（PACELC）。
- CP 组件（ZK/etcd/Consul/HBase/majority-MongoDB/TiDB）用**共识协议 + 多数派**换不丢不乱，代价是吞吐、数据规模、分区时的可用性；AP 组件（Eureka/Cassandra/Redis/Nacos-临时）用**异步复制 + 最终收敛**换可用与低延迟，代价是脏读、丢写窗口与收敛运维。
- 给组件贴 CP/AP 标签时，永远追问三件事：**写确认要几个副本？读走谁？分区时哪一侧还能服务？**

# 四、BASE：AP 路线的工程方法论

## 4.1 从 CAP 到 BASE

CAP 证明了分区时 C/A 二选一。选 CP（ZooKeeper、NewSQL）适合协调与关键数据；但互联网业务的大部分场景（商品浏览、评论、购物车、积分、通知）**不能接受"为了强一致而大面积不可用/高延迟"**。选了 A 之后，系统是什么样、怎么开发、怎么保证最终正确？——这就是 BASE 回答的问题。

BASE 一词由 eBay 工程师 Dan Pritchett 在 2008 年 ACM Queue《BASE: An ACID Alternative》中系统阐述（思想上溯到 Brewer），是 **ACID 的反义词式命名**：

| ACID | BASE |
|------|------|
| Atomicity（原子性） | **Basically Available**（基本可用） |
| Consistency（强一致） | **Soft state**（软状态） |
| Isolation（隔离性） | **Eventually consistent**（最终一致） |
| Durability（持久性） | |

它不是一个协议，而是**一组工程模式的集合**：允许可用性优先、允许中间态存在、承诺最终收敛，然后把"窗口期不一致"的业务影响用模式消化掉。

## 4.2 三要素详解

**基本可用（Basically Available）**

系统在故障或过载时"打折服务"而不是"停止服务"：

- **响应时间变长**：搜索平时 0.5s，大促时 2s——仍然算可用；
- **功能降级**：推荐算法服务挂了就退化为"热门榜单"；评论发不出就提示"稍后重试"，但下单必须照常；
- **限流与排队**：超出容量时拒绝部分请求（限流）、排队能进（12306 候补）；
- **过载保护**：快速失败 + 自动恢复，防雪崩。

关键认知：**"基本可用"的"基本"是业务定义的**——哪些功能不可降级（下单、支付），哪些可以（推荐、评价），要在架构上预先声明。

**软状态（Soft State）**

数据允许存在**中间态**，且这个中间态是被系统设计预期、而非异常：

- 副本间主从延迟（从库数据落后主库）；
- 在途消息（消息已发出、下游还没消费）；
- 业务中间态（订单"支付中"、库存"预扣锁定量"、转账"处理中"）。

关键认知：**软状态要求所有读方（包括业务代码与 UI）显式处理中间态**——订单页面要有"支付处理中"而不是把"处理中"当异常报错。

**最终一致（Eventually Consistent）**

停止新写入后，经过一段**不确定时长**，所有副本收敛到相同状态。Vogels 在《Eventually Consistent》里进一步指出：纯"最终一致"对用户不够，还需要一系列**增强变体**（见 4.3）。

## 4.3 最终一致的"家族"：纯收敛为什么不够

纯最终一致只有一个承诺"总有一天会一样"，但用户与业务需要更强的相对保证：

| 变体 | 定义 | 反例（没有它时） | 常见实现 |
|------|------|----------------|---------|
| 读己之写（RYW） | 用户总能看到自己刚写的内容 | 自己刚发的评论刷新后消失，再刷又出现 | 会话粘滞路由：写后 N 秒/本会话的读走主库 |
| 单调读 | 一旦读到新值，不会再读到旧值 | 第一次看到余额 80，再刷新变回 100 | 按用户哈希固定读同一副本 |
| 单调写 | 同一用户的写按发起顺序生效 | 回帖顺序错乱 | 同一实体路由到同一分区 |
| 因果一致 | 有因果关系的读写全序一致 | 回复先于被回复的帖子可见 | 因果跟踪（版本向量） |
| 会话一致 | 以上保证在"会话"范围内生效 | —— | 会话级粘滞 + 版本号 |

工程上最常用的是**"读己之写 + 会话粘滞"**：MySQL 读写分离场景，写操作后的一小段时间内（或携带写事务 ID 的请求）强制路由主库；网关层记录"该用户最近写入的主库位点"，从库位点追上才放行读从库。**这是把"纯最终一致"修补成"用户可接受的最终一致"的标准手法。**

这个家族的理论出处比 BASE 早得多：1994 年 Bayou 系统的会话保证（Terry et al.），其形式化与现代应用见 5.2.2、5.3。

## 4.4 实现最终一致的工具箱（每项含机制 / 使用者 / 局限）

**（1）异步复制 + 复制延迟监控**

- 机制：主库提交后异步传播（binlog 复制、Redis repl-backlog、Cassandra gossip）。
- 使用者：MySQL/PG 主从、Redis、几乎所有 AP 系统。
- 局限：收敛窗口不可控（秒级到分钟级），failover 有丢数据窗口；必须配延迟监控与告警（Seconds_Behind_Master 等），否则"最终"永远不来时无人知晓。

**（2）反熵协议（anti-entropy）：Gossip + Merkle 树 + hinted handoff**

- 机制：节点间周期性交换摘要，用 Merkle 树比对区间哈希快速定位差异修复；写目标不可达时暂存 hint 补投。
- 使用者：Cassandra（nodetool repair）、Dynamo、Serf/Consul 成员管理。
- 局限：收敛无上界；repair 有 IO 开销，冷数据没人读不触发读修复，必须周期性全量 repair 兜底；hint 队列本身可能积压。

**（3）读修复（read repair）**

- 机制：读请求命中多副本时发现不一致，顺手把旧副本更新。
- 局限：依赖读流量——**不读的坏数据永远不被修复**，只能作为辅助。

**（4）版本管理与冲突解决：向量时钟 / LWW / CRDT**

- 机制：
  - **向量时钟**：检测"并发写"（无因果关系的两个写），把冲突上交业务裁决（Dynamo 购物车合并）；
  - **Last-Write-Wins**：按时间戳取最新，简单但**静默丢更新**，时钟偏差下语义危险（Cassandra 默认）;
  - **CRDT（无冲突复制数据类型）**：数据结构本身保证合并必然收敛且不丢——G-Counter/PN-Counter（计数）、OR-Set（集合）、LWW-Register 等。Riak KV 数据类型、Redis Enterprise CRDB（多活）、协同编辑（Yjs/Automerge）在用（CRDT 的完整理论、类型谱系与局限见 5.4）。
- 局限：向量时钟元数据随节点数膨胀；LWW 会丢数据；CRDT 只覆盖特定数据形态，复杂业务语义（"余额不能为负"）表达不了。

**（5）消息驱动的最终一致：本地消息表 / 事务消息 / 最大努力通知**

- 机制：见 2.6.2（5）。本地事务 + 可靠消息把"操作事件"可靠传播出去，下游各自消费收敛。
- 关键配套：**消费必须幂等**（重复投递是常态）；**死信队列 + 告警 + 人工干预**兜底；**最大努力通知**（支付结果通知商户）用"递增间隔重试 N 次 + 提供查询对账接口"收尾。
- 局限：只解决"传播"，不解决"业务原子性"（扣库存失败时订单已成立，要靠下游回滚/取消消息）；链路越长，监控与对账成本越高。

**（6）补偿与对账：BASE 的安全网**

- 机制：
  - **补偿事务**（SAGA 语义撤销，见 2.6.2）；
  - **T+1 对账**：每日按业务流水号两边轧差，差异进差错池（自动冲正或人工处理）——支付/清结算行业的标配；
  - **定时巡检**：扫描状态机卡单（"支付中"超过 30 分钟的单子），主动查询第三方真实状态并修正本地状态。
- 关键认知：**所有最终一致系统的正确性兜底，最终都落在对账/巡检上**。"最终一致"不是一个被动等待的过程，而是"重试 + 修复 + 对账"主动收敛的过程。

**（7）幂等基础设施：BASE 的隐形地基**

- 机制：唯一业务单号 + 去重表（消费前检查）；状态机约束（订单只允许"待支付→已支付→已发货"单向流转，重复消息非法状态直接拒绝）；乐观锁（version 字段 / `where stock >= n` 条件更新）。
- 关键认知：**只要消息/重试可能重复（至少一次投递），幂等就不是可选项**。BASE 体系的每一个环节（消息消费、补偿执行、通知重发）都依赖它。

## 4.5 典型落地场景

**场景一：订单-库存跨服务下单（消息驱动最终一致 + 单点原子防超卖）**

```
订单服务                          库存服务
   │ 1.本地事务: 插入订单(状态=待扣减) │
   │   + 写本地消息表                 │
   │ 2.投递消息 ──────────────────→  3.消费: where stock>=n
   │                                原子扣减(单库乐观锁,防超卖)
   │          4.成功 → 回发"扣减完成"消息 → 订单状态推进
   │          5.失败 → 重试N次 → 死信 → 告警 → 差错池/自动取消订单
```

要点：**防超卖的原子的扣减判断必须收敛在单库单行（强一致点），BASE 只负责跨服务的结果传播**；订单状态机保证幂等；对账任务定期核对"已支付订单 vs 已扣库存"。

**场景二：缓存与数据库双写（承认不一致窗口的收敛设计）**

- 读：Cache Aside（先读缓存，未命中读库回填）；
- 写：**先更新数据库，再删缓存**（而非更新缓存）；
- 兜底：**延迟双删**（写后删一次，延迟几百毫秒再删一次，清掉并发旧值回填）、**binlog 订阅（Canal）异步删除**——把"缓存与 DB 短暂不一致"作为接受的软状态，用异步链路保证最终一致。
- 反面教材：先删缓存再更新库（并发读回填旧值）、更新缓存（并发写覆盖）——都是没想清楚窗口的经典错误。

**场景三：注册中心选 AP（Eureka/Nacos 临时实例）**

- 分区时宁可给"可能过期的实例列表"，由调用方用重试/熔断/超时消化脏数据；因为"完全拿不到列表"（CP 拒绝服务）对调用链的打击是全局性的，而"拿到过期列表"只影响个别实例。

**场景四：支付与清结算（最终一致 + 对账兜底）**

- 支付发起 → 异步通知（重试 + 最大努力通知）→ 商户侧查询接口兜底 → **T+1 银企对账**轧差，差错池处理长款/短款。**金融互联网业务的一致性 = 实时链路（消息最终一致）+ 离线链路（对账强制收敛）双层结构**。

## 4.6 BASE 解决不了什么 / 约束（总述）

1. **强一致刚需场景**：跨服务资金划转要求"任何时刻账实相符"、秒杀库存"不多卖一单"——补偿与收敛窗口都是业务不可接受的，必须用强一致（同库事务/原子操作/NewSQL/2PC/TCC）。**BASE 不是万能替代品，先分清哪些数据"弱得起"。**
2. **窗口期中间态的业务复杂度**：所有读写路径都要处理"未收敛"（UI 的处理中状态、接口的重试语义、读旧值的容忍），代码与测试复杂度显著上升；并发窗口下的 bug 难复现（不确定性），需要混沌工程验证。
3. **"最终"不可承诺**：收敛时间没有 SLA——网络持续分区时可以一直不一致；只能靠监控（延迟指标、差异率）+ 对账兜底，无法用技术手段给出上界承诺。
4. **冲突解决语义要业务定义**：LWW 丢数据、向量时钟要业务写合并逻辑、CRDT 表达不了复杂约束——弱一致把一部分"正确性"责任从数据库转嫁给了业务代码。
5. **运维面扩大**：消息表/死信/差错池/对账平台/幂等组件都是要持续运维的常设系统；链路越长，排障越难（一个订单状态错误要跨 5 个服务追链路）。
6. **测试与可观测性要求更高**：需要全链路追踪、状态机可视化、差异率大盘，否则"最终一致"会退化成"偶尔不一致且不知道"。

## 4.7 本章小结

- BASE = **基本可用（可降级）+ 软状态（中间态合法）+ 最终一致（收敛承诺）**，是 CAP 中选 A 之后的方法论，不是一个协议。
- 三层结构缺一不可：**传播层**（异步复制/消息）负责把变化可靠送达；**收敛层**（重试/反熵/读修复/补偿）负责修复分叉；**兜底层**（幂等/状态机/对账）负责最终正确性。
- 最重要的一条工程判断：**强一致点收敛到最小（单库单行的原子操作），弱一致用消息与对账铺开**——"小处强一致、大处最终一致"是互联网架构的主流姿势。

# 五、BASE 之后：一致性理论的精细化演进（2010~2026）

## 5.0 一句话定位与全景

**CAP/BASE 是"取舍的宪法"，本章的理论是"取舍的实施细则"**——它们不再回答"选哪边"（那是 CAP 的事），而是回答三个新问题：

1. **"一致"能精确刻画到什么程度？**（Harvest/Yield、一致性谱系学、五级一致性：5.1~5.3）
2. **弱一致能往上修到多强？**（CRDT/SEC、实时因果一致 RTC：5.4、5.6）
3. **"免协调"（不写共识、不做 2PC）的边界在哪？**（CALM、I-Confluence、RedBlue、Calvin：5.5）

为什么 BASE（2008）之后再没有出现"一统天下"的口号？三个原因：**口号期的使命完成了**（ACID/CAP/BASE 用九个字母唤醒了问题意识，之后需要的是可计算、可验证的精确理论）；**问题从单点决策变成连续谱**（真实系统需要按数据、按操作、按会话分别定价一致性，二选一的框架装不下了）；**验证工具成熟**（TLA+/Jepsen 让理论承诺可以被机器验收，理论被迫精确）。

```
口号期（1970~2008）          精确期（2010~2017）              工程期（2017~2026）
────────────────────       ─────────────────────          ─────────────────────
ACID      单机契约          RTC：分区期间的最强一致          Cosmos DB 五级一致性
2PC/SAGA  原子提交          CRDT/SEC：收敛的代数化           Jepsen 一致性谱系图
CAP       分区取舍          CALM：免协调的边界               TLA+ 工业化验证
BASE      最终一致方法论     I-Confluence：不变量免协调        线性一致性检查自动化
PACELC    延迟维度           RedBlue / Calvin / TARDiS        确定性仿真测试
                             TrueTime / HLC：全序时钟
```

## 5.1 对 CAP 的修正与再表述

### 5.1.1 Harvest-Yield（Fox & Brewer，1999）——"部分可用"的两种度量

比 CAP 猜想还早一年的工作，把"可用性"这个模糊词拆成两个正交指标：

| 指标 | 定义 | 下降方式 |
|------|------|---------|
| **Yield**（产出率） | 完成的请求占总请求的比例 | 限流、拒绝、超时 |
| **Harvest**（收成率） | 响应中包含的数据完整度 | 返回部分数据、旧数据 |

**二者可以互相交换**：大促时搜索只返回前 100 条（harvest 降、yield 保）；分布式缓存只返回本地机房的数据（harvest 降、延迟与 yield 保）。这是"基本可用"里"降级"一词最早的理论化——**CAP 的 A 从此有了连续刻度**，"可用"不再是布尔值。

### 5.1.2 Brewer《CAP Twelve Years Later》（2012）——提出者的自我修订

三点修正（3.3 节的"误解澄清"即来源于此）：

1. 取舍发生在**分区瞬间的局部决策**，不是系统全局的静态标签；
2. A 允许**部分可用**（Harvest-Yield），C/A 可以按数据粒度混合——"现代 CAP 的目标是最大化分区容忍网络下 C 与 A 的可行组合"；
3. **分区恢复后系统必须主动补偿收敛**——这段"恢复期理论"正是后来反熵、CRDT、对账体系的用武之地。

### 5.1.3 Coda Hale《You Can't Sacrifice Partition Tolerance》（2010）

工程界对"我要 CA"论调的系统回击：网络分区不是"要不要容忍"的选项，而是"必然发生的事实"；宣称 CA 的分布式系统，实际是在分区时**静默地选择了丢数据或假可用**。这篇文章与后来的 Jepsen 一起，终结了产品营销里的 "CA 系统" 话术。

### 5.1.4 PACELC（Abadi，2012）——补上"平时"这一半

完整表述见 3.4。此处强调它的理论定位：**CAP 是故障理论，PACELC 是常态理论**——没有分区时，一致性与延迟的取舍才是 99.9% 时间里的主要矛盾。据此可把系统放进四个象限：

| 象限 | 含义 | 代表 |
|------|------|------|
| PC/EC | 分区偏一致、平时偏一致 | ZooKeeper、etcd、Spanner |
| PC/EL | 分区偏一致、平时偏低延迟 | 半同步复制的数据库（超时降级异步） |
| PA/EC | 分区偏可用、平时偏一致 | Dynamo/Cassandra 的 QUORUM 配置 |
| PA/EL | 分区偏可用、平时偏低延迟 | Cassandra 默认、Redis 异步复制、Dynamo 论文配置 |

## 5.2 一致性模型的谱系学：把"一致"变成可枚举的谱

### 5.2.1 两大坐标系

| 坐标系 | 视角 | 代表模型（强→弱） |
|--------|------|------------------|
| **以数据为中心**（data-centric） | 副本之间、全局顺序 | 线性一致 > 顺序一致 > 因果一致 > FIFO/PRAM > 最终一致 |
| **以客户端为中心**（client-centric） | 单个用户的可感知保证 | 读己之写、单调读、单调写、写后读 |

数据中心的谱保证"所有副本怎么收敛"，客户端中心的谱保证"每个用户看到什么"——**后者便宜得多且往往够用**：一个用户不关心别人 10 秒前的数据，但极在意自己的数据消失。

### 5.2.2 会话保证的鼻祖：Bayou（Terry et al.，1994）

比 BASE 早 14 年，Terry 等人在 Bayou 系统中定义了四大**会话保证**（4.3 节那个家族的理论出处）：

| 保证 | 定义 |
|------|------|
| Read Your Writes | 会话内的读能看到自己此前的写 |
| Monotonic Reads | 会话内读到的版本只前进不倒退 |
| Monotonic Writes | 会话内的写按发起顺序被所有副本采纳 |
| Writes Follow Reads | 会话内"读了 x 之后的写"必须发生在它读到的 x 版本之后 |

实现机制（会话 ID + 版本向量粘滞路由）是今天 MySQL 读写分离"写后读主库"、Cosmos DB 会话一致性的直接祖先。

### 5.2.3 隔离级别的一般理论：Adya（1999）

Adya 的博士论文《Weak Consistency: A Generalized Theory and Optimistic Implementations for Distributed Transactions》把 SQL-92 那套依赖"异常枚举"的隔离级别重写成**基于事务依赖图（serialization graph）的形式理论**（PL-1 / PL-2 / PL-3，以及中间档 PL-2+）。价值有三：隔离级别从此可以在任意实现（锁/MVCC）上统一定义；允许定义"比 RR 弱、比 RC 强"的中间档；与副本一致性模型（线性一致/因果一致）正式接轨。今天所有讨论写偏斜、快照隔离的论文都站在它肩上。

### 5.2.4 严格可串行化（Strict Serializability）：两根轴的顶点

**严格可串行化 = 可串行化（事务轴）+ 线性一致（副本轴）**：不仅事务可以串行排列，串行顺序还必须尊重真实时间先后。单机可串行化数据库天然拥有它；分布式系统里只有 Spanner（TrueTime + commit-wait）等少数系统能给出（"外部一致"即此语义）。它与 6.1 节的谱系图互相印证：**最强的承诺，也是最贵的承诺**。

### 5.2.5 Jepsen 与一致性谱系图（Kingsbury，2017~）

Kyle Kingsbury（Aphyr）把学术界散落的一致性模型整理成一张层级图（https://jepsen.io/consistency），并用 Jepsen 混沌测试逐个"实测"：**"宣称什么"与"实现什么"从此分开**。代表性战果（均已修复）：Redis 哨兵切换丢写、MongoDB w:1 的脏读与回滚、Elasticsearch 丢文档、旧版 Kafka unclean leader 丢数据、TiDB 早期版本的隔离缺陷。配套的**线性一致性检查算法**（Wing & Gong 1993 奠基、Lowe 2017 改进）让"验证一个并发历史是否线性一致"成为自动化步骤。

## 5.3 可调一致性：把"最终"写进 SLA

**Azure Cosmos DB（2017）五级一致性**是"理论参数化"的标志事件：

```
强 Strong ── 有界旧值 Bounded Staleness ── 会话 Session ── 一致前缀 Prefix ── 最终 Eventual
   │                  │                       │                  │                │
 线性一致        落后 ≤K 个版本或 ≤T 时间      单会话内四大保证      只要不乱序          纯收敛
（多数派）       （全球唯一可量化的中间档）     （默认级别，最常用）                      （最便宜）
```

两个理论要点：

1. **Bounded Staleness 把"多旧算旧"变成 SLO 参数**（K/T），且全部五级经过 TLA+ 形式化验证（微软 2023 年公开）——BASE 的"最终不可承诺"第一次有了工业解法：**承诺一个界，而不是承诺一个时刻**。
2. **会话一致成为云产品默认**：因为四大保证（5.2.2）覆盖了 90% 的用户可感知异常，成本又远低于强一致——"以客户端为中心的一致性"打赢了性价比之战。

## 5.4 CRDT：把最终一致变成定理（强最终一致 SEC）

### 5.4.1 理论内核

Shapiro、Preguiça、Baquero、Zawirski（2011）定义 **CRDT（无冲突复制数据类型）**：把"合并"设计进数据类型本身，使其满足**交换律、幂等性、单调性**，则任意乱序、重复的消息投递下，所有副本**必然收敛到同一状态**——这叫**强最终一致（SEC）**：收敛不靠运气、不靠对账，靠代数。

| 实现族 | 原理 | 网络要求 | 代表 |
|--------|------|---------|------|
| **State-based（CvRDT）** | 副本交换完整状态，merge 是半格上的 join | 消息可乱序可重复（幂等） | G-Counter、OR-Set |
| **Op-based（CmRDT）** | 只广播操作，要求并发操作可交换 | 需要可靠的因果广播 | 协同编辑类 |
| **Delta-state（2016 优化）** | 只传状态增量 | 同 CvRDT | 现代实现主流 |

### 5.4.2 常见类型与语义

| 类型 | 数据语义 | 注意点 |
|------|---------|--------|
| G-Counter / PN-Counter | 只增计数器 / 可增减计数器 | 每副本一个分量，合并取 max（求和） |
| G-Set / 2P-Set / OR-Set | 集合与"可撤销集合" | 删除用墓碑（tombstone），有空间代价 |
| LWW-Register / MV-Register | 单值寄存器（时间戳/多版本裁决） | LWW 会静默丢更新（同 Cassandra 的老毛病） |
| 序列 CRDT（RGA/Logoot/WOOT） | 文本协同编辑的字符序列 | Yjs/Automerge 的底层 |

### 5.4.3 落地与案例

- **Riak KV 数据类型**、**Redis Enterprise 多活（CRDB）**（跨地域双活写）、Cassandra 的 counter 列（受限的 PN-Counter：只允许自增/自减，靠专用协调路径保证交换性）；
- **SoundCloud** 用 CRDT 替代共识协议做在线状态同步（Peter Bourgon《Consistency without Consensus》演讲，注意这是工程演讲不是论文）；
- **协同编辑**：Yjs/Automerge 把 CRDT 带进前端。与 OT（Operation Transform，Google Docs 路线，需中心服务器变换矩阵）相比，CRDT 免中心节点、天然离线合并，代价是元数据膨胀——这正是 **Local-first Software**（Kleppmann 等，2019）论证的方向：**让软件的可用性、隐私、离线能力不依赖云端**，CRDT 是它的理论引擎。

### 5.4.4 CRDT 解决不了什么

1. **SEC ≠ 强一致**：CRDT 只承诺收敛，不承诺"读到的就是最新的"，更不是线性一致；
2. **语义受限**：能表达计数/集合/寄存器/序列，表达不了跨对象的业务不变量（"余额≥0"）——那是 5.5（I-Confluence）的领地；
3. **元数据与墓碑回收**是持续课题：版本向量随副本数增长，删除标记需要全局 GC 时机（Yjs 的状态压缩、Automerge 3 的重构都是为此）；
4. **"不冲突"≠"语义正确"**：并发转账在 CRDT 里数学上干净，业务上可能仍是错的。

## 5.5 免协调的边界：CALM、I-Confluence、RedBlue、TARDiS、Calvin

BASE 的逆问题：**"不写共识、不做 2PC"到底能走到哪？** 这是 2010 年代理论含量最高的部分。

### 5.5.1 CALM 定理（Hellerstein & Alvaro）

**内容**：一个分布式程序存在一致的、免协调的实现，**当且仅当**程序逻辑是**单调的**——追加输入只会让输出集合增大，永不推翻已有结论。

- **推论**：取反（NOT）、聚合（COUNT/SUM）、删除、唯一性检查都是非单调点，每个都需要一个"协调点"；而 feed 流追加、日志记录、计数累加天然单调，可以完全无协调地最终一致。
- **工程意义**：把"哪里必须付协调成本"从架构经验变成了**可判定的问题**（Bloom/Bloom^L 语言尝试把 CALM 直接做进编程模型）。
- 出处：《Keep CALM and Delay On》（CIDR 2011）提出；《Keeping CALM: When Distributed Consistency Is Easy》（CACM 2020）系统化。有人说它比 CAP 更根本——**CAP 说协调不可避免，CALM 说哪部分其实免费**。

### 5.5.2 Coordination Avoidance 与 I-Confluence（Bailis et al.，VLDB 2015）

CALM 看"程序"，I-Confluence 看"**不变量**"：给定业务不变量（余额≥0、库存≥0），形式化判定**哪些事务并发组合可以在不做 2PC 的情况下执行而不破坏不变量**。

- 血统：O'Neil 的 **Escrow Transactions**（1986，按不变量预扣额度）——"冻结 100 元"就是 escrow；
- 直觉结论：可交换且离不变量远的操作（各账户独立充值）免协调；不可交换或贴近不变量边界的操作（余额清零线上的扣款）必须协调；
- 落地：Draco（Bailis 等的原型）、**Anna**（伯克利，基于格 lattice 的免协调 KV，ICDE 2019）。

### 5.5.3 RedBlue Consistency（Li et al.，OSDI 2012）

把操作**染色**：蓝 = 可乱序、免协调执行（最终一致），红 = 必须串行协调（线性一致）。应用开发者声明每个操作的颜色，系统在分区时提供**介于最终一致与线性一致之间的可控中间档**。后续 **TARDiS**（Crooks et al.，SIGMOD 2016）更进一步：分支-合并模型——分区时各分支独立写，恢复后用应用定义的 merge 函数合并，把"补偿"从兜底机制升级为一等公民。

### 5.5.4 Calvin：用"确定性"换掉 2PC（SIGMOD 2012）

另一条免 2PC 的路：**如果事务的读写集事先确定、执行过程确定，那么所有副本按相同顺序重放日志就能得到相同结果**——不需要分布式提交协议的"投票-决议"，只需要一个全局序。Calvin 用"预声明读写集 + 全局日志序"实现分布式事务，代价是灵活性（读写集不能运行时确定、长事务/慢节点拖慢全局流水线）。**Fauna** 是它的生产化尝试。

### 5.5.5 本节小结表

| 方案 | 核心思想 | 免掉了什么 | 付出的代价 |
|------|---------|-----------|-----------|
| CALM/Bloom | 单调性 ⇔ 免协调 | 单调程序的全部协调 | 语言/模型迁移成本 |
| I-Confluence/Anna | 不变量可免协调并发 | 2PC（对远离边界的操作） | 分析复杂度；边界处仍要协调 |
| RedBlue | 操作按需染色 | 蓝操作的全部协调 | 应用要标注；红操作仍全局串行 |
| TARDiS | 分支-合并 | 分区期间的协调 | 业务要写 merge 函数 |
| Calvin | 确定性重放 | 2PC 阻塞与投票 | 读写集预声明；straggler 拖全局 |

## 5.6 因果一致的天花板：RTC、COPS、Eiger、GentleRain

**Mahajan/Alvisi/Dahlin（2010）证明：实时因果一致（RTC）是网络分区期间、保持可用的前提下可实现的最高一致性**——比它更强的（线性一致、严格可串行化）都要求跨分区通信，而因果一致只需要"每个副本知道因果依赖是否已可见"。

实现这一上限的系统谱系：

| 系统 | 年份/会议 | 关键技术 |
|------|----------|---------|
| COPS | SOSP 2011 | 显式依赖检查（读时等待依赖可见）；《Don't Settle for Eventual》 |
| Eiger | NSDI 2013 | COPS 的列存储版，把因果一致扩到事务性读写集 |
| Bolt-on | SIGMOD 2013 | 在黑盒 KV（如 Cassandra）之上叠加因果层 |
| GentleRain | SoCC 2014 | 用"稳定时间戳"替代显式依赖列表，o(1) 元数据，工程可扩展 |
| CausalSpartan | VLDB 2021 | 依赖追踪的进一步优化 |

**定位**：这一支是 AP 路线的"理论天花板"——它告诉 Eureka/Cassandra 类系统的设计者：最终一致往上还有一整层"因果 +"的空间，且已被证明可以实现。实践中多数注册中心停在会话/最终一致（够用），因果层主要在多活存储与协作类产品中落地。

## 5.7 顺序与时钟：Lamport → 向量时钟 → TrueTime → HLC

分布式一致性的底层是"给事件排全序"的能力，四代时钟构成一条清晰的技术线：

| 代际 | 时钟 | 机制 | 代价 | 代表 |
|------|------|------|------|------|
| 1 | Lamport 逻辑时钟（1978） | 计数器，保证因果偏序 | 只有偏序，无法判定"并发" | 理论基座 |
| 2 | 向量时钟（1988，Mattern/Fidge） | 每副本一个分量，可精确判定并发 | 元数据 O(节点数) | Dynamo、Riak |
| 3 | TrueTime（2012） | GPS+原子钟，有界不确定度 ε，commit-wait ε | 专用硬件 | Spanner |
| 4 | HLC 混合逻辑时钟（2014） | 物理时钟为主 + 逻辑修正 | 纯软件，常数元数据 | CockroachDB、YugabyteDB |

**NewSQL 的"强"从来不是共识协议单方面给的，而是"共识（日志顺序）+ 全序时钟（外部时间基准）"的组合**：Raft 只保证日志一致，TrueTime/HLC 才把"外部世界的先后"编码进来，从而拿到严格可串行化。

## 5.8 验证工程：理论承诺的"机器验收"

2017 年之后，一致性理论的最终形态是**可验证性**：

1. **TLA+**（Lamport 的形式规约语言）工业化：AWS 自 DynamoDB 时代起在核心协议设计与改造中广泛使用 TLA+（Newcombe 等《How Amazon Web Services Uses Formal Methods》，CACM 2015）；Azure Cosmos DB 五级一致性全部 TLA+ 验证后上线。**协议设计从"写完上线看事故"变成"先数学证明再上线"**。
2. **Jepsen 黑盒实测**：对声称的保证做故障注入（分区/时钟漂移/GC 停顿），用线性一致性检查器判定并发历史。它最大的贡献是把"一致性"从营销词变成**可复现的实验结论**。
3. **确定性仿真测试**（FoundationDB 开创，内部使用多年后 SIGMOD 2021 公开）：把整个集群跑在确定性的单进程仿真器里，同一随机种子下 bug 必然复现——TigerBeetle/Antithesis 把它做成了商业化测试基础设施。

**规律**：口号期理论靠"说服"，精确期理论靠"证明"，工程期理论靠"验收"。

## 5.9 架构层的方法论：日志成为一致性的中心

### Lambda → Kappa

- **Lambda 架构**（Marz，2011）：批处理层 + 速度层双路径，用两层互补逼近"正确且新鲜"，代价是**同一业务逻辑写两遍**（批与流的代码一致性难题）。
- **Kappa 架构**（Kreps，《Questioning the Lambda Architecture》，2014）：**只有一条路径**——日志（Kafka）是唯一事实源，一切视图都是日志重放的投影，要改逻辑就"从头重放"。**这是把"最终一致"从"副本收敛"重新定义为"投影收敛"**——一致性问题的重心从多副本同步转移到日志与视图的秩序。

### Event Sourcing / CQRS

Greg Young（2010 前后）普及：**状态 = 事件的折叠**。写模型只追加事件（单调的，恰好落在 CALM 的免费区），读模型（投影）各自异步收敛——BASE 的"软状态"在这里变成了"投影延迟"；CQRS 的读写分离天然给出"读己之写"的实现点（读自己的投影走最新位点）。

### 流处理的 exactly-once：1985 年的理论 2015 年落地

- **Chandy-Lamport 分布式快照**（1985）：不停流地拍下全局一致状态——Flink 的 checkpoint barrier 就是它的工业实现；
- **Kafka 事务**（KIP-98，2017）：生产端幂等 + 跨分区事务，配合消费端 offset 提交进同一事务，实现 source→state→sink 的端到端 exactly-once（本质是流式 2PC）；
- **Temporal/Cadence（durable execution）**：工作流状态本身事件溯源化，重试/补偿由运行时保证——**SAGA 从"模式"变成了"运行时能力"**。

**一句话**：2010 年代架构理论的大方向，是把"一致性"从**副本间的实时同步**迁移到**日志的重放秩序**——写路径只保证追加的单调性（免协调），正确性由重放与投影的确定性保证，再加上对账兜底。

| 理论/概念 | 年份 | 回答的问题 | 代表系统/落地 |
|-----------|------|-----------|--------------|
| 会话保证 | 1994 | 用户可感知的最小一致 | Bayou → 读写分离粘滞路由/Cosmos 会话级 |
| Harvest/Yield | 1999 | 部分可用怎么度量 | 一切降级/限流体系 |
| Adya PL 级别 | 1999 | 隔离级别的一般形式理论 | 现代隔离级别讨论的公理 |
| RTC | 2010 | 分区期间最强一致 | COPS/Eiger/GentleRain |
| CRDT/SEC | 2011 | 收敛如何成为定理 | Riak/Redis CRDB/Yjs/Automerge |
| CALM | 2011 | 何时可以免协调 | Bloom；架构级"协调点"分析 |
| CAP 修订 | 2012 | CAP 到底怎么用 | 3.3 节的正确打开方式 |
| RedBlue/TARDiS | 2012/2016 | 中间档一致与分支合并 | 多活业务系统 |
| Calvin | 2012 | 不用 2PC 的分布式事务 | Fauna |
| TrueTime/HLC | 2012/2014 | 分布式全序时钟 | Spanner/CockroachDB |
| PACELC | 2012 | 平时延迟 vs 一致 | 四象限分类（3.4） |
| I-Confluence | 2015 | 不变量下的免协调事务 | Anna/Draco；escrow 复兴 |
| 五级一致性 | 2017 | 一致性 SLO 参数化 | Cosmos DB（TLA+ 验证） |
| Kappa/ES/CQRS | 2011~2014 | 日志作为一致性中心 | Kafka 生态/Flink/Temporal |
| TLA+/Jepsen/确定性仿真 | 2013~ | 承诺如何机器验收 | AWS/Azure/FDB |

**三阶段规律**：

1. **口号期（1970~2008）**：ACID/CAP/BASE——用最少的字符唤醒最大的问题意识；
2. **精确期（2010~2017）**：RTC/CRDT/CALM/I-Confluence/PACELC——把取舍的边界一个一个算清楚；
3. **工程期（2017~2026）**：五级一致性/TLA+/Jepsen/确定性仿真——把理论变成可配置、可验证、可写进 SLA 的工程参数。

**趋势判断**：一致性粒度会继续从"系统级标签"细化到"**每个操作的 SLO**"（Cosmos DB 已经做到）；协调的定价会继续从"架构师经验"下沉到"**编译器/运行时可判定**"（CALM 路线）；而对绝大多数业务系统，5.9 节的日志中心路线——**写路径单调追加 + 读路径投影收敛 + 对账兜底**——仍是性价比最高的答案。

## 5.11 本章小结

- BASE 之后没有新口号，但有一整层精确理论：**修正层**（Harvest-Yield、CAP 修订、PACELC）修复了 CAP 的刻板印象；**上限层**（RTC、严格可串行化）标定了弱一致与强一致的天花板；**免费层**（CRDT、CALM、I-Confluence）划出了免协调的疆域；**工程层**（五级一致性、TLA+、Jepsen）把承诺变成参数与验收。
- 三个最好记的"心智钩子"：**CAP 说协调不可避免，CALM 说哪部分其实免费，CRDT 说收敛可以不靠协调，五级一致性说"最终"可以折算成 K 和 T。**
- 对实践者：把这些理论当**坐标系**而非**结论**——遇到具体问题先定位"它在哪个轴上、离天花板多远、协调点在哪"，而不是问"该选 CP 还是 AP"。

# 六、横向对比与选型决策

## 6.1 一致性模型谱系（强 → 弱）

```
线性一致 ─ 顺序一致 ─ 因果一致 ─ 会话一致 ─ 最终一致
(最像单副本)  (分区内有序)  (有因果全序)  (RYW/单调…)   (只承诺收敛)
   │            │            │            │            │
 Spanner      Kafka        动态追踪      读写分离      Cassandra
 单机串行     单分区日志    (COPS类)      粘性读主      Redis从库
 etcd线性读                              +位点校验     Eureka列表
```

与隔离级别的关系（另一根轴，事务内部的顺序保证）：

```
RU ─ RC ─ RR ─ 快照隔离SI ─ 可串行化SER ─ 严格可串行化(=SER+线性一致)
                                    │              │
                              传统单机SER      Spanner外部一致
                              (PG SSI)         (承诺跨事务的真实顺序)
```

两个轴正交：**隔离级别管"并发事务怎么交织"，一致性模型管"多副本/多节点怎么同步"**。单机可串行化系统只占满第一根轴；Spanner/严格可串行化的 NewSQL 两根轴都占满——这就是"最强语义"，也对应最高延迟。

## 6.2 三个"C"的对比

| 维度 | ACID 的 C | CAP 的 C | BASE 的 C（最终一致） |
|------|-----------|----------|---------------------|
| 对象 | 事务前后的业务不变量 | 多副本间线性一致 | 多副本间收敛 |
| 时间性 | 事务提交瞬间成立 | 每次读都成立 | 窗口之后成立，窗口长度无界 |
| 保证者 | 数据库约束 + 事务机制 | 共识协议/仲裁读写 | 复制 + 修复 + 对账 |
| 失败的样子 | 约束被破坏（脏数据） | 读到旧值 | 短暂读到旧值 + 永不收敛的风险 |

## 6.4 场景 → 方案选型决策表

| 场景 | 一致性要求 | 推荐方案 | 理由 |
|------|-----------|---------|------|
| 单库内的资金扣减、状态变更 | 强一致 | 本地事务 + 行锁/乐观锁 | 最简单可靠，ACID 全覆盖 |

| 微服务间资金操作（高并发） | 强语义最终一致 | TCC（或预扣+确认的变体） | 资源预留不长期持锁 |
| 长流程编排（跨 5+ 服务、分钟级） | 最终一致 | SAGA / Temporal 工作流 | 补偿链可控、可观测 |

| 配置中心、分布式锁、选主 | 一致优先 | etcd / ZooKeeper / Consul | 错乱数据不可接受 |
| 缓存层 | 最终一致 | Cache Aside + binlog 订阅失效 + 延迟双删 | 承认窗口，异步收敛 |
| 秒杀防超卖 | 强一致（临界点） | Redis Lua 原子预扣（可接受少量超卖+回补）或 DB 条件更新；BASE 传播结果 | 原子判断必须单点收敛 |
| 跨行转账、银行核心 | 强一致 + 审计 | 强一致协议 + T+1 对账兜底 | 合规与资金安全 |

## 6.5 贯穿案例：一张订单的完整旅程（三个理论如何协同）

下单链路：**下单 → 扣库存 → 支付 → 扣款 → 发货**。

1. **订单创建 + 库存预扣（强一致点）**：订单记录与"预扣库存"在一个本地事务（或库存服务内单行原子扣减）。这里用 ACID——因为它是最小强一致点，其他方案都撑不住"不超卖"。
2. **支付（最终一致 + 强语义）**：订单服务发"待支付"消息（本地消息表）；支付网关回调驱动状态机流转，状态机保证幂等与顺序。支付中状态是合法软状态。
3. **扣款（TCC）**：账户服务 Try 冻结额度 → 支付成功 Confirm 扣减 → 超时 Cancel 解冻。资金路径不容窗口期错误，用 TCC 拿强语义；三大坑（幂等/空回滚/防悬挂）在账户服务内统一处理。
4. **发货与物流（BASE）**：消息驱动，最终一致即可；物流单号回填允许分钟级延迟。
5. **底座**：注册中心 Nacos AP（临时实例）+ 配置中心 CP（JRaft）；分布式锁用 etcd；全链路幂等（唯一单号）+ 差错池 + **T+1 对账**做最终兜底。
6. **分区演练**：库存服务与订单服务之间网络分区——订单仍可创建（进入"待扣减"软状态），消息积压；分区恢复后消息消费、库存补扣或订单自动取消（补偿），对账核对差异率。**这就是 CAP 的 A 侧选择 + BASE 的收敛闭环。**

# 七、FAQ：高频争议问题速答

**Q1：CAP 的 C 和 ACID 的 C 有什么区别？**
对象不同：ACID 的 C 是"事务前后业务不变量成立"（如金额守恒）；CAP 的 C 是"多副本读起来像只有一份数据"（线性一致）。一个管事务语义，一个管副本同步。Spanner 之类系统两者都占，才容易混淆。

**Q2：到底有没有 CA 系统？**
有——单机系统（单实例 MySQL、无复制的任何存储）。分布式系统里网络分区必然发生，P 不是可选项；宣称"CA"的分布式产品要么在撒谎，要么指"分区时会整体不可用"（这其实就是 CP 的极端形态）。

**Q3：ZooKeeper 读可能读到旧值，还算 CP 吗？**
算。CP 判断看**分区时的行为**：少数派侧完全停止服务（宁可不可用），这是 CP 的本质。读旧值是"平时用顺序一致读换低延迟"（PACELC 的 EC 侧取舍），与 CP 定位不矛盾；要强一致读就 `sync()` 一下。

**Q4：Redis 到底是 AP 还是 CP？能信吗？**
Redis（默认异步复制）是 AP 倾向：故障转移可能丢最近写入，复制延迟窗口读到旧值。`min-replicas-to-write` 等配置只能缩小窗口不能归零。**把 Redis 当唯一数据源是危险设计**；当缓存或可容忍丢失的数据存储用，并明确"以 DB 为准"。

**Q5：Kafka 是 CP 还是 AP？**
配置决定，且都不是线性一致系统：`acks=all + min.insync.replicas≥2 + unclean.leader.election.enable=false` 时，ISR 不足就拒绝写入——分区级 CP 行为；`acks=1` 是 AP。但消费者读的是高水位之前的数据，存在滞后，所以任何配置下都达不到线性一致读。跨分区全局无序。

**Q6：有了最终一致，为什么还要对账？**
"最终"没有时间上界，且任何环节（消息丢失、补偿失败、bug）都可能让收敛永远不发生。对账是把"被动等待收敛"升级为"主动强制收敛"的审计机制，是最终一致体系的正确性终点。金融系统尤其如此。

**Q7：Raft/Paxos 和 2PC 是什么关系？会互相替代吗？**
不替代、可叠加：共识协议（Raft/Paxos）解决"一组副本对日志顺序达成一致"（复制层）；2PC 解决"多个独立参与者对提交/回滚达成一致"（事务层）。TiDB = 每个分片 Raft 复制 + 跨分片 2PC；2PC 的协调者自身也需要容错，实践中协调者状态就放在共识组里（如 Seata TC 集群 + 注册中心）。

**Q8：FLP 不可能性定理说共识不可能，那 Raft 为什么能用？**
FLP 的前提是**纯异步**（无超时可用）+ 确定性 + 哪怕一个节点故障。实践系统都假设"部分同步"（最终消息会到达，可用超时）——Raft 的选举超时、ZAB 的心跳超时就是在"用超时打破 FLP 僵局"。理论上不完美，工程上够用。

**Q9：最终一致的"最终"大概是多久？能承诺吗？**
不能承诺。健康系统内通常毫秒到秒级（主从延迟、消费延迟），但网络分区、消费积压、修复任务停摆时可以是分钟到小时甚至无限期。正确的姿势是：监控收敛指标（复制延迟、消费 lag、对账差异率）并设告警，而不是对外承诺上界。

**Q10：新业务要用分布式事务，第一反应该是什么？**
先问三个问题：① 能不能把强一致点塞进**一个本地事务**（重新划服务边界/数据归属，往往能）？② 真的需要跨服务实时原子吗（资金类→TCC/2PC/NewSQL；一般业务→消息最终一致）？③ 补偿失败、消息丢失时**谁兜底**（对账/差错池有没有）？顺序对了，方案自然收敛；直接跳到"选哪个框架"通常说明前两问没想清。

**Q11：CAP/BASE 之后的新理论（CRDT/CALM/RTC/五级一致性）会取代它们吗？**
不会取代，而是细化与工具化。CAP/BASE 仍是战略层的第一因——分区时必须取舍、选了 A 就要有收敛方法论；之后的理论各管一段：CRDT 回答"AP 路线的收敛怎么做成定理"，CALM/I-Confluence 回答"哪里其实可以免协调"，RTC 标定 AP 路线的理论天花板，五级一致性把"最终"折算成可写进 SLA 的参数。实践者的正确姿势：**用 ACID/CAP/BASE 定方向，用新理论定参数**（详见第五章）。

# 八、附录

## 8.1 术语表

| 术语 | 含义 |
|------|------|
| 线性一致（Linearizability） | 每次读都读到最近一次完成的写；多副本表现得像单副本 |
| 顺序一致（Sequential Consistency） | 所有节点看到的操作顺序一致（但不要求按真实时间序） |
| 因果一致（Causal Consistency） | 有因果关系的操作全序一致，无因果的可各自为政 |
| 最终一致（Eventual Consistency） | 停止写入后，副本在一段时间内收敛 |
| RYW（Read Your Writes） | 用户总能读到自己的写 |
| MVCC | 多版本并发控制：写不阻塞读，读旧版本快照 |
| WAL | Write-Ahead Logging：先写日志再写数据页 |
| 2PL | 两阶段锁：加锁阶段与释放阶段严格分离 |
| Write Skew | 两事务读同一批数据、各写不同行、合起来破坏不变量 |
| ISR | Kafka 中与 Leader 保持同步的副本集合 |
| RPO / RTO | 灾难恢复目标：可容忍丢多少数据 / 多久恢复服务 |
| 反熵（Anti-Entropy） | 副本间主动比对并修复差异的协议 |
| Hinted Handoff | 目标节点故障时由他人暂存写请求、恢复后补投 |
| CRDT | 无冲突复制数据类型：结构上保证合并收敛 |
| LWT | 轻量级事务（Cassandra 基于 Paxos 的 CAS） |
| 幂等 | 同一操作执行多次与执行一次效果相同 |
| 对账 | 按业务单号双向核对流水、差异进差错池的收敛机制 |
| Jepsen | 分布式系统一致性验证工程（Kyle Kingsbury），以"打脸"著称 |
| 强最终一致（SEC） | CRDT 的保证：更新最终送达 + 已送达相同更新集的副本状态等价——收敛不靠运气靠代数 |
| CALM 定理 | 程序存在一致的免协调实现 ⇔ 程序逻辑单调（Hellerstein & Alvaro） |
| I-Confluence | 给定业务不变量，判定事务能否免 2PC 并发执行而不破坏不变量 |
| RTC（实时因果一致） | 网络分区期间（保持可用前提下）可实现的最高一致性（Mahajan 等，2010） |
| HLC（混合逻辑时钟） | 物理时钟为主、逻辑修正兜底的分布式时钟，CockroachDB/YugabyteDB 的全序方案 |
| Bounded Staleness | 有界旧值：读最多落后最新写 K 个版本或 T 时间，可写进 SLA（Cosmos DB） |
| 严格可串行化 | 可串行化 + 线性一致，分布式事务语义的天花板（Spanner 外部一致） |
| Harvest/Yield | 收成率（数据完整度）与产出率（请求完成率）——"部分可用"的两种度量 |
| 确定性仿真测试 | 整个集群跑在确定性仿真器里，同一随机种子下 bug 必然复现（FoundationDB 首创） |
